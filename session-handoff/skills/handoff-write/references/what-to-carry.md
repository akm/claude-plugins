# 何を書き、何を書かないか

引き継ぎ文の読み手は、**旧セッションの会話を読めない新しいセッション**。モデルが違うことも多い。雛形 ([template.md](template.md)) の各節を、この読み手が引き継ぎ文だけで作業を始められるように埋める。

## 各節の埋め方

| 節 | 書くこと | 書かないと何が起きるか |
| --- | --- | --- |
| 目的 | 作業全体で何を達成したいか。関連する Issue / PR の URL | 「次にやること」だけでは、迷ったときの判断の基準が伝わらない |
| 次にやること | 最初の 1 手を、対象のファイルと操作まで具体的に書く。その後の見通しは箇条書き | 新しいセッションが、リポジトリの探索から始め直す |
| 決めたことと理由 | 採った方針と、その理由 | 理由が無いと、状況が変わったときに方針を見直してよいかが分からない |
| 却下した案 | 検討して採らなかった案と、採らなかった理由 | 新しいセッションが、同じ案をもう一度検討する |
| 確かめた事実 | 調査で分かったこと。ファイルはリポジトリのルートからの相対パスと行、コマンドは実行した形と結果の要点 | 同じ調査を繰り返す |
| 未確認のこと | 推測のままのこと、試していないこと | 推測が、事実として引き継がれる |
| 現在の状態 | 未コミットの変更の一覧と、それぞれが何のための変更か。未 push のコミット。走らせたままの処理。作った一時ファイルの場所 | 新しいセッションが、途中の変更を意図の分からないものとして扱う |
| 人間からの指示 | この作業に限って受けた指示や好み (「テストは後回しでよい」など) | 会話にしか残っていない制約が失われる |

**該当する内容が無い節は、節を消さずに「なし」と書く。** 節が無いと、読み手は「書き忘れた」のか「無かった」のかを区別できない。

**「確かめた事実」と「未確認のこと」を混ぜない。** 自分で実行して結果を見たものだけを事実に入れる。コードを読んで「こう動くはず」と考えたものは未確認に入れる。

## 書かないもの

- **会話の経過** (誰が何を言ったか、どの順で試したか)。結論と理由だけを書く。ただし、試して失敗したことは「却下した案」か「確かめた事実」に入れる
- **リポジトリを読めば分かること** (コードの構造、git の履歴、コミット済みの変更の中身)
- **ファイル `CLAUDE.md` やメモリに既にあること**。新しいセッションにも読み込まれる
- **機密の値** ([sensitive-data.md](sensitive-data.md))

## 読み手の立場での検査

書き終えたら、会話を知らない人として読み直し、次が無いことを確かめる。

- **会話への参照**: 「さっきの件」「上で述べた方法」「例のファイル」
- **説明の無い造語や略語**: 会話の中で生まれた呼び名 (「案 B」「新方式」など) は、中身を書くか、初出で説明を添える
- **種類を添えていない識別子**: 「`sites`」ではなく「テーブル `sites`」、「`site.go`」ではなく「ファイル `internal/store/site.go`」
- **埋め残した `{{…}}`**

## 長さ

GitHub のコメントの上限は 65,536 文字。**その半分 (約 30,000 文字) を超えたら、書きすぎを疑う。** 多くの場合、会話の経過か、リポジトリを読めば分かることが入っている。長いコマンドの出力が要るなら、出力そのものではなく、再実行するコマンドを書く。
