# handoff-write: 引き継ぎ文を書いて保存する

いまのセッションの作業を、**このセッションの会話を読めない新しいセッション**が再開できるように、引き継ぎ文を書いて保存する。読む側はスキル [handoff-resume](../handoff-resume/SKILL.md)。

**このスキルは明示的に依頼されたときだけ使う。**

## 前提知識

- **compact (会話の自動要約) との違いは、書く側が「次に何をするか」を知っていること。** 会話全体を均等に縮めるのではなく、次の作業に要ることを選んで書く。何を選ぶかの正本は [references/what-to-carry.md](references/what-to-carry.md)。
- **節の構成の正本は雛形 [references/template.md](references/template.md)。** 節を足したり消したりしない — 読む側は節の名前を手がかりに読む。
- **雛形の 1 行目の `<!-- session-handoff v1 -->` は、読む側とフックが引き継ぎ文を見分ける目印。** 必ず本文の 1 行目に置き、前に何も書かない。

## 引数

| 引数 | 意味 | 省略時 |
| --- | --- | --- |
| 番号、または `--local` | 保存先 | 手順 1 の順で決める |
| `--model <名前>` | 受け手に想定するモデル | 「指定なし」と書く |
| `--effort <値>` | 受け手に想定する effort | 「指定なし」と書く |
| `--next <文>` | 次のセッションで最初にやること | 会話から決める。決まらなければ人間に尋ねる |

## 手順

1. **保存先を決める。** 引数があればそれに従う。無ければ次の順で決める。

   1. **PR**: 現在のブランチに PR があり (`gh pr view --json number,url,state`)、**引き継ぐ作業がその PR の作業である**
   2. **Issue**: 作業の対象の Issue が決まっている (会話で番号が挙がっている、ブランチ名に番号が入っている、など)
   3. **ローカルファイル**: 上のどちらでもない

   **ブランチに PR があるだけでは PR を選ばない。** PR のブランチにいるまま別件の調査をしていた場合、その引き継ぎ文を PR に投稿すると、無関係な文書が PR に残る。会話の作業が PR のものかどうかを判断し、**根拠を手順 5 の確認で示す**。

   引数で番号を受けた場合は、Issue か PR かを判別する。

   ```bash
   gh api repos/<owner/repo>/issues/<番号> --jq '.pull_request != null'
   ```

   `true` なら PR、`false` なら Issue。**終了コードで判別しない** — `gh issue view <番号> --json ...` は PR の番号でも終了コード 0 を返す。

2. **リポジトリの状態を採る。**

   ```bash
   git rev-parse --show-toplevel
   git branch --show-current
   git rev-parse --short HEAD
   git status --porcelain
   git log --oneline @{upstream}..HEAD   # 上流が無ければ「上流なし」と書く
   ```

   **未コミットの変更があっても止めない。** 作業の途中で引き継ぐことが、このスキルの目的の 1 つ。一覧を「現在の状態」に書き、それぞれが何のための変更かを添える。

3. **雛形を埋める。** 各節の埋め方は [references/what-to-carry.md](references/what-to-carry.md)、機密の扱いは [references/sensitive-data.md](references/sensitive-data.md) に従う。本文はスクラッチ用のディレクトリのファイルに書く (保存先がローカルなら、手順 5 の置き場に直接書いてよい)。

   - `writer_model` は、このセッションのモデル名。分からなければ「不明」と書き、推測しない
   - `reader_model_and_effort` は、`--model` / `--effort` の値。無ければ「指定なし」

4. **読み手の立場で検査する。** [references/what-to-carry.md](references/what-to-carry.md) の「読み手の立場での検査」の各項目を確かめ、見つけたものを直す。埋め残した `{{…}}` が無いことも確かめる。

5. **保存する。**

   **GitHub の場合**: **投稿の前に人間に確認する** (示す内容は [references/sensitive-data.md](references/sensitive-data.md) の「投稿前の確認」)。承認を得たら投稿する。

   ```bash
   # PR
   gh pr comment <番号> --repo <owner/repo> --body-file <本文のパス>
   # Issue
   gh issue comment <番号> --repo <owner/repo> --body-file <本文のパス>
   ```

   **本文は必ず `--body-file` で渡す。** `--body` に長文を直接渡すと、シェルの引用で壊れる。コマンドが返すコメントの URL (`…#issuecomment-<ID>`) を控える。

   **同じ PR / Issue に過去の引き継ぎ文があっても、新しいコメントを足す。** 過去のコメントは編集も削除もしない。

   **ローカルの場合**: コミット対象にならない置き場を、次の順で選ぶ。

   1. `git check-ignore -q tmp` が成功すれば (ディレクトリ `tmp/` が git に無視されていれば) `tmp/`
   2. そうでなければ `$(git rev-parse --git-dir)/session-handoff/`。ディレクトリ `.git/` の中は git が追跡しないので、`.gitignore` の設定に関わらずコミット対象にならない
   3. git のリポジトリの外なら、スクラッチ用のディレクトリ

   ファイル名は `handoff-<YYYYMMDD>-<hhmm>-<ブランチ名>.md`。ブランチ名の `/` と、ファイル名に使えない文字は `-` に置き換える。detached HEAD なら `detached-<短縮 SHA>`。**同名のファイルが既にあれば上書きせず、末尾に `-2`、`-3` … を足す。** `handoff-` で始まり `.md` で終わる形は、フックがこのファイルを見分けるのに使うので変えない。

6. **報告する。** 保存先と、**新しいセッションに貼る 1 行**を、コピーできるようにコードブロックで出す。

   ````markdown
   引き継ぎ文を投稿しました: <コメントの URL>

   新しいセッションに、次の 1 行を貼ってください。

   ```
   /handoff-resume <コメントの URL>
   ```

   想定する受け手: モデル <名前> / effort <値> (新しいセッションで選んでから貼ってください)
   ````

   - **GitHub の場合は、番号ではなくコメントの URL を渡す。** 番号だと、読む側が「最新の引き継ぎ文を探す」ことになり、後から別の引き継ぎ文が足されたときに意図と違うものを読む
   - **ローカルの場合は絶対パスを渡す。** 新しいセッションが別の作業ツリー (worktree) で開かれても届くようにするため
   - 「想定する受け手」の行は、`--model` か `--effort` を受けたときだけ出す

## 原則

- **引き継ぎ文をコミットしない。** GitHub のコメントか、コミット対象にならない置き場に置く。
- **新しいセッションを起動しない。** どのモデルで、いつ始めるかは人間が決める。
- **会話の全文を保存しない。** 全文が要るなら、このセッションを残しておけば足りる。
