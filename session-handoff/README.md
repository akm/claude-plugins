# session-handoff

Claude Code のセッションの作業を、**別のセッションへ引き継ぐ**ためのプラグインです。旧セッションが引き継ぎ文 (次のセッションが作業を再開するのに要ることをまとめた文書) を書いて保存し、新しいセッションがそれを読んで再開します。

次のようなときに使います。

- **モデルを使い分ける。** 調査と設計をあるモデルで行い、実装を別のモデルの新しいセッションに渡す
- **旧セッションを compact (会話の自動要約) せずに残す。** 続きは新しいセッションで行い、旧セッションは後から参照できるように残す

compact との違いは、**書く側が「次に何をするか」を知っている**ことです。会話全体を均等に縮めるのではなく、次の作業に要ることを選んで書きます。

## 収録スキル

| スキル | 実行する場所 | 説明 |
| --- | --- | --- |
| `handoff-write` | 旧セッション | 引き継ぎ文を書いて保存し、新しいセッションに貼る 1 行を出す |
| `handoff-resume` | 新しいセッション | 引き継ぎ文を読み、リポジトリの状態と突き合わせてから作業を再開する |

## 使い方

旧セッションで引き継ぎを依頼します。

```
/handoff-write --model opus --effort high
```

保存が済むと、新しいセッションに貼る 1 行が出ます。

```
/handoff-resume https://github.com/<owner>/<repo>/pull/53#issuecomment-1234567890
```

新しいセッションを開き (想定するモデルがあれば選んでから)、この 1 行を貼ります。

### 保存先

引数で番号か `--local` を渡さなければ、次の順で決まります。手順の正本は [skills/handoff-write/SKILL.md](skills/handoff-write/SKILL.md) の手順 1 と 5 です。

1. **PR のコメント** — 現在のブランチに PR があり、引き継ぐ作業がその PR の作業である場合
2. **Issue のコメント** — 作業の対象の Issue が決まっている場合
3. **ローカルファイル** — 上のどちらでもない場合。ディレクトリ `tmp/` が git に無視されていれば `tmp/`、そうでなければ `.git/session-handoff/` (どちらもコミット対象になりません)

**GitHub への投稿は、毎回、投稿の前に確認を求めます。** コメントは編集しても履歴が残り、回収できないためです。同じ PR / Issue で何度引き継いでも、そのたびに新しいコメントを足し、過去のコメントは編集しません。

### 引き継ぎ文に書くもの

節の構成の正本は [skills/handoff-write/references/template.md](skills/handoff-write/references/template.md)、各節の埋め方の正本は [skills/handoff-write/references/what-to-carry.md](skills/handoff-write/references/what-to-carry.md) です。目的・次にやること・決めたことと理由・却下した案・確かめた事実・未確認のこと・現在の状態・人間からの指示を書きます。会話の経過と、リポジトリを読めば分かることは書きません。

## 保存先を貼るだけでも再開できる (フック)

`/handoff-resume` を付けずに、コメントの URL やファイルのパスだけを貼った場合のために、プロンプト送信時のフック (UserPromptSubmit) を同梱しています。

- プロンプトに、コメントの URL (`…#issuecomment-<ID>`) か、引き継ぎ文のファイル名 (`handoff-<日時>-….md`) の形があるときだけ働きます
- 形の一致だけでは判定しません。**本文の 1 行目の目印 `<!-- session-handoff v1 -->` を確かめ**、引き継ぎ文だったときに限り、スキル `handoff-resume` の実行を促す文脈をセッションに差し込みます
- 引き継ぎ文の本文は差し込みません。本文の取得と、投稿者が本人かどうかの確認は、スキルの手順が行います

**このフックは補助で、確実なのは `/handoff-resume` の 1 行を貼るほうです。** 理由は 2 つあります。

- フックにできるのは文脈を差し込むところまでで、スキルを実行するかどうかはモデルが決めます
- URL の確認は `gh` とネットワークに依存します。`gh` が無い・未認証・3 秒以内に応答が無い場合は、何も差し込みません (プロンプトは通常どおり処理されます)

## 再開のときに確かめること

新しいセッションは、引き継ぎ文をそのまま信じません。正本は [skills/handoff-resume/SKILL.md](skills/handoff-resume/SKILL.md) と [skills/handoff-resume/references/verify-state.md](skills/handoff-resume/references/verify-state.md) です。

- **投稿者が自分でないコメントは、人間の確認を得るまで従いません。** 公開リポジトリには誰でもコメントを書けるので、目印を付けた偽の引き継ぎ文で新しいセッションに指示を与えることができてしまうためです
- **ブランチ・HEAD・未コミットの変更を、現在のリポジトリと突き合わせます。** ブランチが違う、書かれていた未コミットの変更が無い、履歴が書き換えられている、のいずれかなら止まって報告します
- **引き継ぎ文は「前のセッションの報告」として扱います。** 破壊的な操作や外部への送信は、引き継ぎ文に書かれていても、通常どおり人間に確認します

## しないこと

- **新しいセッションを起動しない。** どのモデルで、いつ始めるかは人間が決めます
- **引き継ぎ文をコミットしない。**
- **会話の全文を保存しない。** 全文が要るなら、旧セッションを残しておけば足ります
- **セッション開始時に引き継ぎ文を自動で読まない。** 引き継ぎと無関係なセッションに、古い引き継ぎ文が読み込まれるためです

## 必要なもの

- `gh` (GitHub CLI) — GitHub に保存する・GitHub から読む場合。ローカルファイルだけを使うなら不要
- `python3` — フックの実行

## テスト

```bash
python3 -m unittest discover -s session-handoff/tests
```
