# doc-structured: 文書の構成の決定の一覧

2026-11-03 から 2026-11-05 までの相談で決めたことを、最後の状態でまとめた一覧。2026-11-06〜07 のレビュー (5 つの sub-agent の指摘を、利用者と 1 つずつ確認した) で変えた決定と足した決定も、この一覧に反映している。問 15 (文書の一部のコピー) は 2026-11-07 に足した。途中で変えた決定は、変えた後の内容だけを各問に書き、何を変えたかは末尾の「後の問とレビューで変えた決定」にまとめた。

親の Issue は [#192](https://github.com/akm/claude-plugins/issues/192)。

- 目的: Claude Code で作るアプリケーションの文書を、長く保守できる構成にする。
- 作るもの: この構成の規則・生成と検査のツール・スキル・hook を持つプラグイン `doc-structured`。
- 親の Issue と sub-issues (このリポジトリの Issue) は、決定を繰り返して書かず、このファイルを参照する。決定を変えたときは、このファイルを直し、末尾の「後の問とレビューで変えた決定」に行を足す。

## 全体の原則

1. 用語は、それを導入する文書で定義する。用語集は定義を持たず、定義への索引にする。
2. 列挙できる事実 (モデル・属性・値・操作・テーブル・画面など) は YAML に書く。説明と判断は手書きの Markdown に書く。人が読む一覧の Markdown は YAML から生成する。
3. 決めたことは YAML が SSOT で、作ったもの (文言・エラーメッセージ・実際のスキーマ・ルート) はコードが SSOT。
4. 現在の仕様 (いつも今の状態に直し、検査する) と、記録 (書いた時点の内容のまま残し、検査しない) を分ける。
5. ディレクトリ `docs/` の直下のディレクトリは、読者ごとの 1 つの文書にする。
6. 親のディレクトリの文書が子を参照し、子は親を参照しない。
7. 規則の SSOT はプラグインの文書。プロジェクトには、生成したコピーとプロジェクト固有の規則だけを持つ。

## 親の Issue の範囲と、移行の方針 (レビューで決めた)

- **親の Issue の範囲から外したもの**: マニュアル (問 11 の `docs/manual/`。この構成でマニュアルを書くプロジェクトが決まったときに、別の Issue でそのプロジェクトの文書に当てて形式を決める。それまでプラグインにマニュアルの機能は無い)。コードへの ID の定数の生成 (問 8。必要になったときの別の Issue)。決定そのものは、この一覧に残す。
- **一部だけの移行は、プラグインの動作確認のためのもの**で、実際のプロジェクトの main ブランチにはマージしない。実際の移行は、全体を移せるようになってから、実際のプロジェクトの Issue で行う。そのため、古い構成と新しい構成が並ぶ期間の規則 (まだ移していない文書の一覧・古い文書へのリンク・検査 j の対象外の一覧) は作らない。検査 b・i・c-2 の対象は、新しい構成が定めるパスだけ。
- **形式 (YAML の形式・ID の形・名前の形) を変えたときにプロジェクトが追従する手段**は、実際のプロジェクトの全体の移行を main ブランチにマージする時から用意する。それまでは形式を自由に変え、動作確認のブランチは作り直す。マージの後に形式を変えるときは、その変更と一緒に手段を用意し、どんな手段にするかは最初に必要が出たときに決める。
- **検査が増えたときの既存の違反**: 違反を許容する一覧 (ベースライン) は持たない。バージョンを上げる PR で、失敗した箇所をすべて直す (上げる時期はプロジェクトが決められる)。
- **要件の識別子** (`FR-MENU-001` のような形) を持つプロジェクトの、以前の識別子と新しい ID の対応と、コードとテストの参照の書き換えは、各プロジェクトの移行の計画で扱う。プラグインの決定 (問 3「要件を別の項目として持たない」) は変えない。

## 検査が保証すること・保証しないこと (指針。レビューで足した)

この節は、Claude が希望して足した指針である。これを根拠に規則やほかの指針を決めるときは、必ず利用者の許可を得る。「定義は 1 か所だけ」は指針であって、絶対の原則ではない。

**検査が保証しないこと** (親の Issue に書く):

- 定義が 1 か所だけにあること (同じ内容が 2 か所に書かれていないこと)。内容の重複を調べる機能は doc-structured に作らず、必要なときに既存のプラグイン doc-dag を使う。同じ節の近い位置で似た説明が繰り返されることを調べる仕組みが無いことは、このリポジトリの Issue として別に記録する (未作成)。
- ロールと操作の表 (`docs/system/permissions.md`) が、実装の認可と同じであること。
- 外部の URL に到達できること。
- 2 回目以降のラベルそのものが古い語のまま残っていないこと (`refs` で探して人が直す)。
- Issue と PR の本文がスキル `links-fix` に渡されたこと (CI は本文を検査しない)。

**書き方の指針** (規則の文書に指針として書く。検査しない):

- YAML の定義の項目には、その名前が何を指すかを 1〜2 文で書く。規則・理由・手順は `concept.md` に書く。
- 手書きの節 1 つには、1 つのこと (1 つの規則・1 つの判断・1 つの概念) だけを書く。
- 1 つの節の中で、同じ内容を 2 度書かない。要約と詳細の両方を書かない。表に書いた内容を、文で繰り返さない。マークで囲んだコピー (問 15) は例外。

**手書きの Markdown の大きさ** (検査 k。レビューで足した):

- ファイルの行数の指針は 50 行。デフォルトで許容する上限は 100 行。100 行を超える場合は、合理的な理由をファイルの冒頭か末尾に、決まった書き出しのコメント (例 `<!-- 行数が上限を超える理由: … -->`) で書く。
- 検査 k は、100 行を超えていて理由のコメントが無いファイルをエラーにする (50 行を超えただけでは報告しない)。理由の中身は検査せず、レビューで人が見る。
- 対象は手書きの Markdown。生成するファイル・記録・YAML は対象外。末尾の定義の行は数えない。節の大きさは測らない。
- 100 行を超えたファイルを分ける先の形と、50・100 という値が実際の文書に合うかは、最初に手書きのファイルを扱う sub-issue (4a) で決める。sub-issue 4a ([#196](https://github.com/akm/claude-plugins/issues/196)) で決めた内容 (値は 50・100 のまま、理由のコメントは `#` の見出しの次の行だけ、分ける先は子のファイル `<種類>/<名前>.md`) は、規則の文書 [doc-structured-docs.md](../rules/doc-structured-docs.md) の節「手書きの Markdown の大きさ」と [doc-structured-domains.md](../rules/doc-structured-domains.md) の節「手書きの Markdown」にある。

## 問 1: 生成の元と用語の索引

- 生成の元は、ドメインごとのファイル `docs/domains/NN-<name>/domain.yaml`。書くのは列挙できる事実 (モデル・属性・値・状態・遷移・操作・ロール・未分類のアプリケーション用語・名前と 1〜2 文の定義) だけで、説明は Markdown に書く。
- プロジェクトは、`domain.yaml` の内容をいくつかの YAML に分けて、ドメインのディレクトリのサブディレクトリに置ける。ツールはドメインのディレクトリの下のすべての YAML を読む。ID は名前から作るので、ファイルの配置に依存しない。分けるときは参照の向きの規則に従い、検査 i が向きを確認する。どのように分けられるか (種類ごとか任意か) は sub-issue 2 で決める (決めた形は [rules/doc-structured-domains.md](../rules/doc-structured-domains.md) の「YAML を分ける」)。
- **未分類のアプリケーション用語** (略称「未分類の用語」。記号 `ut`): このアプリケーションのために定義した言葉のうち、モデル・属性・値・操作などの、ほかのどの種類にも当たらないもの。ほかの種類に当たらないままでよく、モデルや属性として扱うことになったときに、その種類へ移す。`domain.yaml` に英語名・日本語名・1〜2 文の定義を書く。定義は生成するファイルに ID のアンカー付きで出し、用語の索引からリンクする。規則・理由・背景は `concept.md` に書いて ID を参照する。YAML の項目の名前と、定義を出す生成ファイルの名前は sub-issue 2 で決める (索引 `terms.md` とは別のファイル。決めた名前は [rules/doc-structured-domains.md](../rules/doc-structured-domains.md) の「YAML の形式」)。
- 生成したファイルはコミットする。先頭に生成元とコマンドを書く。先頭の記述は、frontmatter のある Markdown でも、YAML のコメントでも書ける形にし、バージョンをまたいで変えない。
- ドメインごとの用語の索引 `terms.md` と、全体の用語の索引 `docs/glossary.md` は生成する。意味は書かず、定義へのリンクを持つ。

## 問 2: ID

- ID は、アンカーの名前であり、リンクのフラグメントでもある。
- 形は、種類の記号と名前 (snake_case) をハイフンで交互につなぐ。親から子の順に並べる。
- 種類の記号: `d` ドメイン、`m` モデル、`a` 属性、`v` 値、`ut` 未分類のアプリケーション用語、`op` 操作、`ev` イベント、`pre` 操作の前提、`r` ロール、`sg` 画面グループ、`s` 画面、`t` テーブル、`c` カラム、`sc` 受け入れシナリオ、`sn` シーン、`ts` ドメインのテストシナリオ、`sys` ディレクトリ `docs/system/` のファイル、`h` 手書きの節。マニュアル (範囲外) の記号 `mu`・`mf`・`mr`・`oc` は、使うときのために残す。
- ファイルの種類を表す記号 (`concept`・`design`・`requirements`・`models`・`functions`・`schema`・`test_scenarios` など) は名前を取らない。ファイルの ID は、親の ID に記号を足したもの (`d-orders-concept`)。節は `-h-<名前>` を足す (`d-orders-concept-h-immutable_after_confirm`)。
- 例: `d-menu_items-m-menu_item-a-serving_status-v-sold_out`、`d-menu_items-t-menu_items-c-sold_out`、`d-orders-ut-business_day`、`sg-staff-s-menu_items`、`sc-dine_in-sn-order_dishes`、`sys-security-h-session_timeout`。
- Markdown では `<a name="ID"></a>` と見出しを書く。検査は明示のアンカーだけを受け付け、見出しから自動で作られるフラグメントは受け付けない。アンカーと見出しの間に空行があってもよい (整形ツールが入れる)。アンカーは、参照する節にだけ付ける。
- 属性やカラムの「型」は ID を持たない値で、改名の対象ではない。

## 問 3: 事実の種類と配置先

| 書くこと | 配置先 |
|---|---|
| 問題 | `concept.md` の節 (長ければ `problem.md`) |
| 概念・境界・不変条件・方針・理由 | `concept.md` |
| モデル・属性・値・状態・未分類のアプリケーション用語 | `domain.yaml` → 生成 `models.md` と用語の定義のファイル |
| 操作 | `domain.yaml` → 生成 `functions.md` |
| 設計の判断と短い理由 | `design.md` |

- 状態の遷移は 1 つの YAML の形式で書く。2〜3 個の状態で条件が無ければ属性の下に書き、複雑ならファイル `state-machines-<属性>.yaml` に書く (`domain.yaml` と同じディレクトリ。サブディレクトリ `state-machines/` にはしない。遷移は操作などから参照されうるので、サブディレクトリに置くと参照の向きの規則に反しやすいため)。遷移表 (Markdown) と図 (mermaid の stateDiagram-v2) を生成する。
- 要件を別の項目として持たない。定義が要件になる。

## 問 4: スキーマ

- ファイル `schema.yaml` に、テーブル・カラム・主キー・外部キー・インデックス・属性との対応を書く。CHECK 制約と部分インデックスの条件 (WHERE) は書かない (実際の制約と条件は `schema-actual.md` に出し、条件の意味は `design.md` に書く)。
- ドメインごとに、対応表と ER 図を `schema.md` として生成する。ほかのドメインのテーブルは、参照するカラムだけを書いてリンクにする。
- 全体のスキーマと ER 図 (`docs/system/schema.md`) と、実際のスキーマの ER 図 (`docs/system/schema-actual.md`) も生成する。`schema-actual.md` をコミットするかどうかは、プロジェクトごとに決める。
- 設計と実装の違いは、検査 j で確認する (問 12)。

## 問 5: ドメインの番号と名前

- ドメインの番号は作った順で、後から変えない。ディレクトリ名 `NN-<name>` が番号の SSOT。
- 改名はサブコマンドとスキル `rename` で行う (問 12)。ドメインの改名では、ディレクトリ名も変え、以前の名前を `former_names` に残す。
- 読む順は依存から求めて、生成する索引 `docs/domains/README.md` に書く。依存の表と図は `docs/domains/dependencies.md` に生成する。
- **ドメインの依存に数える参照**: あるドメインの YAML (`domain.yaml`・`state-machines-<属性>.yaml`・`schema.yaml`) がほかのドメインの ID を参照していれば、参照の種類を問わず (モデルの参照・操作・操作の前提・状態の定義と遷移・テーブルの外部キー)、そのドメインへの依存に数える。手書きの Markdown のリンクは対象外 (検査 c-2 が扱う)。検査 c-1 と読む順は、この依存から求める。適用 A3 で循環が出たら、その例を元に解消の方法 (定義を別のドメインへ移す・循環を許可する関係を決めるなど) を利用者と決める。

## 問 6: README と画面

- ファイル `README.md` は索引だけにして、生成する。内容は、内容を表す名前のファイルに書く。
- **画面グループ** (記号 `sg`): 画面をまとめる単位で、ロールや利用者と関係を持たない。SvelteKit のルートのグループと同じ性質で、共通の設計と画面遷移の図を共有する。開発レベルの種類として英語名で書き、日本語名は持たない (画面グループ `staff` の画面「メニュー管理」)。入れ子にするかどうか (1 階層の案) は sub-issue 12 で決める。
- 画面は、ディレクトリ `docs/screens/<画面グループ>/<画面>/` に、`screen.yaml`・`requirements.md`・`design.md` (レイアウトは節) を置き、`operations.md`・`attributes.md`・`transitions.md` を生成する。画面を使えるロールは `screen.yaml` に書く。
- ロールは権限だけの単位。ロールの階層は扱わず、行えるロールを 1 つずつ並べる。
- 共通の設計は `docs/screens/design.md` と `docs/screens/<画面グループ>/design.md` に書く。URL の一覧 `docs/screens/paths.md` と、画面グループごとの画面遷移 `<画面グループ>/transitions.md` を生成する。
- 画面に番号は付けない。

## 問 7: テスト

- 受け入れシナリオ 1 つを 1 つの Markdown (`docs/tests/acceptance/<名前>.md`) に書く。シーンは節とアンカーで、順序はファイル `scenarios.yaml` に書く。シナリオの一覧 `docs/tests/acceptance/README.md` を、この順序で生成する (`docs/README.md` はそこへリンクする)。
- シーンには、前提・操作・期待と、ID のリンクを書く。frontmatter は持たない。
- テストは ID を名前に書く。検査は、シーンからテスト、テストからシーンの両方を確認する。
- Gherkin を使うかどうかは、プロジェクトごとに決める。
- ドメインの `test_scenarios.md` は、複数の操作の流れと、境界の条件に限る。節の ID の形 (記号 `ts`) と、検査 e の対象にするかどうかは sub-issue 13 で決める。

## 問 8: 横断の要件と設計

- ディレクトリ `docs/system/` に、`requirements.md` (非機能)・`architecture.md`・`security.md`・`testing.md` を置く。プロジェクトごとにファイルを足してよい。
- ロールと操作の表 `permissions.md` を生成する。検査 d は、画面が使う操作のそれぞれについて、その画面を使えるロールの中に、その操作を行えるロールが 1 つ以上あることを確認する。この表と実装の認可が同じかどうかは検査しない (「検査が保証しないこと」)。
- コードへの ID の定数の生成 (`src/lib/generated/<ドメイン>.ts`) は、親の Issue の範囲から外した (必要になったときの別の Issue)。
- コードとテストに書いた ID があることを検査し (検査 l)、サブコマンド `refs <ID>` の対象にもコードとテストを含める。設定にコードとテストのパスを書いたプロジェクトだけ。どの文字列を ID として扱うかは sub-issue 17 で決める。
- 画面の表記 (文言) は `domain.yaml` に書かない。コードが SSOT。
- 文言のキーに文書の ID を使うことは試みで、うまくいかなければ方針を変える。

## 問 9: CONCEPT.md

- ファイル `docs/CONCEPT.md` は手書きで、製品レベルの問題・解決・ドメインの分け方の理由を書く。
- モデルと画面の節は、生成した一覧へのリンクだけにする。
- issues の節は置かない。設計中のメモは、メモと書いて、書いた人が消す。

## 問 10: 計画と ADR

- 計画 (`docs/plans/YYYY-MM-DD-topic.md`。コミットする) と ADR (`docs/decisions/NNNN-topic.md`) は記録。
- それに基づく作業の間は更新してよい。完了した後は書き換えない (最後に「実装は PR #N で完了」と書くことはできる)。
- doc-structured は検査の対象にしない (表現の検査は wording-guard が行う)。中のリンクが古くなってもよい。
- 先頭に「これは計画 (または判断の記録) で、現在の仕様は docs/ の各文書を参照」と書く。
- `design.md` には今の判断と短い理由を書き、ADR は経緯や代替案が要るときだけ書く。
- 判断を置き換えるときは新しい ADR を書き、古い ADR には何も足さない。

## 問 11: 入口の文書とマニュアル

- ルートの `README.md` は手書き (製品の段落・動かし方・`docs/CONCEPT.md` と `docs/README.md` へのリンク)。`docs/README.md` は生成する索引。
- `CLAUDE.md` には、プラグインの規則へのリンクと、プロジェクト固有のことだけを書く。
- 運用の手順書 (runbook) は置かず、ディレクトリ `docs/manual/` を作る。**この項目は親の Issue の範囲外** (別の Issue で、この構成でマニュアルを書くプロジェクトの文書に当てて形式を決める)。
  - `units/<ロール>/<slug>.md`: 1 ユニットが 1 つのゴール。frontmatter に、必要とする成果と提供する成果などを書く。本文は、概要・前提条件・手順・事後条件・うまくいかないときは。
  - `flows/<slug>.md`: ユニットの順序と引き継ぎ。
  - `flows/conditions.yaml`: フローの分岐の条件の定義。
  - `reference/`: 参照資料。
  - `units/dependencies.yaml` と README (「やりたいことから探す」表) は生成する。
- 運用者などの製品の外のロールは、`architecture.md` の節「担当」で定義する。
- 開発の手引きは、まず README の節に書き、後で開発者のロールのユニットにする。

## 問 12: 生成物・検査・分担・配り方

### (1) 生成物

- 生成するファイルは「ディレクトリの全体像」のとおり。すべてコミットする (`schema-actual.md` だけプロジェクトごと)。スクリプト `bin/doc-structured` も生成したファイル (`setup` が最初に作り、`generate` が生成し直し、hook が直接の編集を拒否する)。
- 生成の出力は、同じ入力からいつも同じにする。プロジェクトの整形ツール (prettier など) には合わせず、**生成したファイルは整形ツールの対象から外す** (`setup` が設定する。問 12 (4))。
- 生成したファイルの競合の規則は「ツールで生成したファイルの競合を手動で解決せず生成し直す」の 1 文だけ (規則に手順を含めない)。生成したファイルには、git の組み込みの merge driver `binary` を設定する (利用者ごとの git の設定は要らない。競合したときに残る内容は、規則の文書 [rules/doc-structured-docs.md](../rules/doc-structured-docs.md) の「生成したファイル」)。設定は `generate` がファイル `docs/.gitattributes` に生成する (sub-issue 3 で決めた。経緯は [#195](https://github.com/akm/claude-plugins/issues/195))。`docs/.gitattributes` が設定するのはディレクトリ `docs/` の下の生成したファイルだけで、`docs/` の外の生成したファイル (`bin/doc-structured`・`.claude/rules/doc-structured*.md` など) には、それを生成する sub-issue で、同じ形のファイル `.gitattributes` をそのディレクトリに足す。それ以外のファイルの競合を、競合のマークが入ったまま一度コミットし、解決するコミットを別に足し、その後 `generate` してコミットする流れも使える (規則・hook・CI はこれを妨げない。競合のマークが入った YAML で `generate` がエラーになるのは意図どおり)。
- 被参照の一覧のファイル `backlinks.md` は作らない。ある ID を参照しているファイルと節は、サブコマンド `refs <ID>` がその場で出力する。
- 参照される定義に「これを参照するもの」の一覧を生成するのは 1 か所だけ: `models.md` の各モデルの「このモデルを参照するモデルとテーブル」。

### 参照の書き方

- 文書の参照は、すべて Markdown の reference-style のリンクで書く (生成するファイルも、外部の URL も同じ)。
- 本文は `[ラベル]` の 1 回の記述を標準にする。`[文][ラベル]` は、別の表示の文が要るときだけ使う。`[文](URL)` の形は使わない。
- 定義の行 `[ラベル]: 相対パス#ID "完全な名前"` は、ファイルの末尾に書く。ラベルは文中で読める語にする。1 つのファイルで、1 つのラベルは 1 つの参照先だけを指す。title の引用符は `"` と `'` のどちらも受け付ける (整形ツールが書き換えるため。規則の文書の例は `"`)。

### 参照の向き

- Markdown のリンクも、YAML の名前の参照も、祖先のディレクトリのファイルを指さない。同じディレクトリ・子孫・別のサブツリーは指してよい。判定は参照先の場所で行う。生成したファイルを指す Markdown のリンクは対象にしない (sub-issue 4c で決めた。生成したファイルの場所はツールが決め、参照される定義を移して直せないため。経緯は [#198](https://github.com/akm/claude-plugins/issues/198)。規則は [rules/doc-structured-docs.md](../rules/doc-structured-docs.md) の「参照の向き」)。
- 複数のサブディレクトリから参照される定義は、親に置かない。この規則の読み方として、規則の文書に「依存関係を整理するときに重要なのは、参照される定義をサブディレクトリに移すことであって、参照しているファイルを移すことではない」と説明する (新しい規則ではない。文面はそのときに確認する)。
- 記録は対象にしない。コードとテストの ID は、向きの対象にしない (存在だけを検査 l で確認する)。

### (2) 検査

| 検査 | 確認すること |
|---|---|
| a | 生成し直して差分が無い (手書きのファイルの中のコピーのブロックを含む。問 15) |
| b | リンク: ID がある・明示のアンカーを指す・ID の形式・定義の無いラベルが無い・使われていない定義が無い・`[文](URL)` の形が無い・定義の行の title が完全な名前と同じ・各ファイルで参照先を最初に指す箇所の書き方 (問 14)。コードブロック・インラインコード・mermaid の図の中の `[` と `]` はラベルとして扱わない |
| c-1 | YAML の依存に循環が無い: ドメイン間 (問 5 の数え方)・同じドメインのモデル間・テーブルの外部キー。モデル間とテーブル間の自己参照だけ例外 |
| c-2 | 手書きの Markdown の参照に、節 (ID) の単位で循環が無い (生成するファイル・記録・画面から画面へのリンクは除く) |
| d | 画面が使う操作のそれぞれについて、その画面を使えるロールの中に、その操作を行えるロールが 1 つ以上ある |
| e | 受け入れシーンとテストが、両方から対応している |
| h | YAML の形式と、参照する名前がある |
| i | 参照の向き (Markdown と YAML) |
| j | 設計と実装の差分 |
| k | 手書きの Markdown の行数 (100 行を超えていて理由のコメントが無いファイル) |
| l | コードとテストに書いた ID がある (設定にパスを書いたプロジェクトだけ) |

- 検査 f (マニュアル) は親の Issue の範囲外。検査 g (表現。wording-guard) は doc-structured の検査から外した (wording-guard の hook とスキルが行い、CI で実行する方法は wording-guard の #165 で扱う)。
- 循環してよい関係 (あることだけ確認する): 画面の遷移・状態の遷移。
- 同じドメインのモデルの親子は、外部キーを持つモデルから 1 方向だけ `domain.yaml` に書く。
- 外部の URL に到達できるかどうかは検査しない。

### 検査 j: 設計と実装の差分

- `schema.yaml` と実際のスキーマ、`screen.yaml` の URL パスとルートのファイルを比べる。
- テーブル・カラム・インデックス・画面に、フラグ `planned: true` を付けられる。

| YAML | 実装 | planned | 結果 |
|---|---|---|---|
| ある | ある | なし | 成功 |
| ある | ある | あり | エラー「実装されたので planned を外す」 |
| ある | ない | あり | 成功 |
| ある | ない | なし | エラー「planned を付けるか YAML から消す」 |
| ない | ある | - | エラー「YAML に足す (または実装を戻す)」 |
| 比べる項目が違う | | | エラー |

- 比べる項目: テーブルの有無、カラムの名前・型・NULL を許可するか・デフォルト値、主キー、外部キー、一意の制約、インデックスのカラムの組。型は正規化してから比べる。
- 比べない項目: カラムの並び順、制約とインデックスの名前、コメント、所有者と権限、CHECK 制約、部分インデックスの条件 (WHERE)。
- 差分は、正規化した形どうしの unified diff と、指示の行で示す。
- 一時的なデータベースにマイグレーションを適用して読む。手元にデータベースが無ければ、スキルは実行できないと伝えて終了する。

### (3) 分担

**CI**

- プラグインが決めるのは、保証 (マージの時点で、ready な PR の最新のコミットに対して検査が成功している)・検査の群・参考のワークフローだけ。いつ実行するかはプロジェクトが決める。
- 群は 2 つ。軽い群 (文書と YAML だけで実行できる検査) と、重い群 (検査 j・`schema-actual.md` の生成し直し・テストの一覧をランナーから取る場合の検査 e)。軽い群はランナー `ubuntu-slim` で実行する。
- 生成は手元で行い、CI は確認するだけ。CI は自動で直さず、コミットもしない。
- ドラフトの間は、スキルが手元で検査する。

**hook**

- PreToolUse (Edit・Write・NotebookEdit) で、生成したファイルの直接の編集を拒否するだけ。生成したファイルかどうかは、ファイル自身の先頭の記述で判定する。Bash での編集と人のエディタでの編集は hook では防げず、検査 a が検出する。
- 拒否するときに、直す元のファイルと生成のコマンドを伝える。
- 検査は実行しない。プロジェクトごとの設定は持たない。

**スキルとサブコマンド** (名前は同じ。プラグイン名もコマンド名も `doc-structured`)

| 名前 | すること |
|---|---|
| `generate` | YAML と frontmatter から生成物を作り直す (`.claude/rules/` の規則のコピー・`bin/doc-structured`・手書きのファイルの中のコピーのブロックを含む) |
| `check [--light\|--heavy]` | 検査を実行する。指定が無ければ `--light`。サブコマンドには `--all` と `--only <検査>` もある |
| `links-fix` | 定義の無いラベルに定義の行を足す。古い title を書き換える (既存の引用符は書き換えない)。各ファイルで参照先を最初に指す箇所の `[ラベル]` を長い形 (種類 + 名前) に、2 回目以降の ID と書ける形を名前が見える形に書き換える。`--stdin` で Issue と PR の本文を受け取る (問 13)。最初の箇所の `[文][ラベル]` の文は書き換えない |
| `refs <ID>` | ある ID を参照しているファイルと節を出力する (設定にパスがあれば、コードとテストも) |
| `impl-diff` | 検査 j だけを実行し、差分を示す。何も変えない |
| `impl-diff-resolve` | 差分を 1 件ずつ解消する。サブコマンドは `<ID>` と、`--planned`・`--unplanned`・`--match-impl` のどれかを取る。スキルが 1 件ずつ人に質問してから実行する |
| `rename <以前の ID> <新しい英語名>` | 名前から ID を作るすべての種類を改名する (下の説明) |
| `setup` | 新しいプロジェクトに、ディレクトリ・設定・入口のスクリプトを作る。整形ツールを質問し、prettier なら `.prettierignore` に生成したファイルのパターンを書き、それ以外なら除外するパターンの一覧を表示する。選ばれたときだけ Issue と PR のテンプレートを作る (sub-issue 16 で足す選択肢) |

- スキルは、直し方が 1 つに決まるものは実行し、内容の判断は人に質問する。
- スキルは、インストール済みのプラグインのバージョンと設定の `version` が違うとき、1 行で伝えてから続ける。
- **`rename`**: 種類は ID の最後の記号から判断し、種類ごとにサブコマンドを分けない。2 つ目の引数は名前の部分だけで、別の親へ移す操作は扱わない。例: `rename d-orders purchases`、`rename d-orders-m-order purchase`、`rename d-orders-t-orders-c-sold_out is_sold_out`、`rename sg-staff-s-menu_items menus`。エラー: ID が無い・同じ親に同じ名前がある・snake_case でない・名前を持たない種類 (`concept` など)。オプションは持たない (結果は git diff で見る)。書き換えるもの: YAML の名前と、現在の仕様の文書・テスト・コード (設定にパスがあるとき) の中の ID。書き換えないもの: 実装 (コードの識別子・実際のテーブル名とカラム名。カラムの改名は、同じ PR のマイグレーションで検査 j が成功する)・リンクにせず文中に書いた名前・記録。スキルは、名前で依頼されたら用語の索引から ID を探し、コマンドを示して確認してから実行し、対応が要るもの (マイグレーションなど) を伝える。

**ディレクトリ `.claude/rules/`**

- 規則の文面は、プラグインの文書を対象ごとに分けて書き、スキル `generate` がそのコピーを `.claude/rules/doc-structured-<対象>.md` として生成する。
- ファイル: `doc-structured.md` (常に読み込む。数行)、`-docs.md`、`-domains.md`、`-screens.md`、`-tests.md`、`-records.md`、`-impl.md`。`-manual.md` は範囲外。
- プロジェクト固有の規則は、名前が `doc-structured` で始まらない手書きのファイルに書く。ツールはそれらを変えない。
- 規則の文書には、上の「書き方の指針」と「参照の向き」の読み方の説明、「未分類の用語」が「未分類のアプリケーション用語」の略称であること、設定の `version` を `version: 1.2.3` の形の 1 行で書く制約も書く。

### (4) 配り方

- 設定はファイル `.claude/akm-claude-plugins/doc-structured/config.yaml`。書くのは、`version` (プロジェクトが使うツールのバージョン)・`paths` (テストコード・マイグレーション・ルート・コードのパス)・導入する範囲。設定ファイルは 1 つのまま。
- 設定の `version` のツールを、手元でも CI でも実行する。スクリプト `bin/doc-structured` は、設定ファイルの `version: 1.2.3` の形の行だけを文字列の一致で取り出す。ツールは起動時に設定の全体を YAML として読み、形が違えばエラーにする。
- 入口はスクリプト `bin/doc-structured` の 1 つ。スキル・人間・CI が同じスクリプトを実行する。スクリプトは生成したファイルで、バージョンを上げる手順の `generate` で一緒に更新される。変更が少なくて済むように最小にする。
- 開発中のツールを実際のプロジェクトで実行するために、手元のチェックアウトのツールを使う指定 (環境変数など。開発のためだけに使う) を持つ。指定が無いときは `version` のとおりに取得し、別の方法は試さない。
- ツールは、知らないサブコマンドを受け取ったらエラーで終了する (プラグインのバージョンが新しく、ツールが古いとき)。
- プロジェクトが使うツールのバージョンを上げる手順: 設定の `version` を書き換える → スキル `generate` → スキル `check` で増えた検査の失敗を直す。これを 1 つの PR で行う。
- 公開の手順 (タグの名前の形・タグを作る手順) は sub-issue 1 で決める (決めた手順は [release.md](release.md))。材料: このリポジトリにはバージョンのタグもリリースも無く、プラグインのバージョンは各プラグインの `.claude-plugin/plugin.json` にあるだけで、インストールは `main` から行っている。公式のプラグインのリリースのタグの形は `<プラグイン名>--v<バージョン>`。
- ツールの言語は sub-issue 1 で決める (決めた言語と取得の方法と理由は [README](../README.md) の「言語と取得の方法を決めた理由」)。条件: バージョンを指定して取得し実行できる・ランナー `ubuntu-slim` で時間がかからない・YAML のコメントと並び順を保って書き換えられる・取得に失敗したら別の方法を試さずエラーで終了する。材料: `ubuntu-slim` (1 vCPU・5 GB・ジョブの上限 15 分) に入っている言語は Node.js 24.22.2 と Python 3.12.3 だけで、Go は無い (pipx・git・gh・jq はある)。実際のプロジェクトは手元が Node.js 26 と pnpm 12 で、CI のランナーは `ubuntu-latest`。このリポジトリの CI が実行する自動テストは Python と Go。実行ファイルを配れる言語なら、ランナーに Go が無くても実行できる。
- 導入済みのプロジェクトに後から加わる開発者向けの案内 (プラグインが無くても `bin/doc-structured` の検査と生成は実行できる・スキルと hook にはプラグインのインストールが要る) をどこに書くかは sub-issue 9 で決める。

## 問 13: 以前の ID・検証用のリポジトリ・Issue と PR のテンプレート・CHANGELOG

- **以前の ID との対応**: 文書を新しい構成に移す計画 (記録) に、以前の ID と v1 の識別子から新しい ID への表を 1 つ置く。移行が完了したら書き換えない。各文書の「v1 との対応」の表は、この表に移して消す。YAML に以前の ID は書かない。実際のプロジェクトの作業で、適用 A1 で行う。
- **検証用のリポジトリの記録**: 外部の URL として reference-style のリンクで参照するだけにする。プラグインは特別な扱いを決めない。
- **Issue と PR の本文**:
  - 仕様を言い換えて書かず、仕様の ID を書く。この規則はプラグインの文書に置く。
  - ID は `[ID]` と書き、末尾の定義の行の URL は permalink (`https://github.com/<owner>/<repo>/blob/<コミットの SHA>/<パス>#<ID>`) にする。
  - サブコマンド `links-fix --stdin` が、本文の `[ID]` があることを確認し、定義の行を足す。指すコミットは手元の HEAD。push されていなければエラーで終了する。確認する対象は HEAD のコミットの内容。
  - Claude は、Issue と PR を投稿する前に、本文をスキル `links-fix` に渡す。
  - CI は本文を検査しない。
- **テンプレート**: PR は「何を変えるか・なぜ変えるか・参照する仕様の ID・確認したこと」、Issue は「問題・関係する仕様の ID・経緯」。先頭に、上の規則のコメントを入れる。スキル `setup` が、選ばれたときだけ作る (sub-issue 16 で足す)。作った後はプロジェクトのファイルで、生成物ではない。
- **CHANGELOG**: 持たない。変更の記録は PR と ADR で足りる。

## 問 14: 限定付きの名前と初出

- **名前の形**: 限定付きの名前はツールが作る。親から順に「種類 + 名前」を「の」でつなぐ。形の表はプラグインに 1 つだけ置く (sub-issue 2 で作った表は [rules/doc-structured-docs.md](../rules/doc-structured-docs.md) の「限定付きの名前」)。
  - ユーザーレベルの種類 (モデル・属性・値・操作・画面・ロール・未分類のアプリケーション用語) は、日本語名をかぎ括弧で書く: モデル「注文」、属性「提供状態」、値「品切れ」。
  - 開発レベルの種類 (ドメイン・画面グループ・テーブル・カラム) は、英語名をコードの書式で書く: ドメイン `orders`、テーブル `menu_items`。
  - ドメインには日本語名を持たせない。英語名と説明の文だけにする。
  - 例: ドメイン `orders` のモデル「注文」。
- **長さ**: 完全な名前 (すべての親を書く) を、定義の行の title と用語の索引に書く。本文で最初に参照する箇所は、その定義自身の「種類 + 名前」を必ず書き、親は文から分からないときに、直近の親から順に足す。「未分類のアプリケーション用語」は、完全な名前では正式名称、本文で最初に参照する箇所では略称「未分類の用語」でもよい。検査 b はどちらも受け付ける。
- **定義の行の title**: サブコマンド `links-fix` が完全な名前で書く。人は手で書かない。検査 b が確認し、古くなった title は `links-fix` が書き換える。外部の URL の定義の行には title を求めない。
- **初出の単位**: ファイル。各ファイルで、ある参照先を最初に指す箇所だけ `[種類 + 名前][ラベル]` と書き、2 回目以降は名前が見える形 (`[ラベル]` か `[名前][ラベル]`) で書く。対象は手書きの Markdown。記録は対象にしない。`links-fix` が、最初の箇所の `[ラベル]` を長い形に、2 回目以降の箇所のうち表示の文が ID か書ける形のものを名前が見える形に書き換える。最初の箇所の `[文][ラベル]` は書き換えず、スキルが利用者に質問する (sub-issue 4b で決めた。経緯は [#197](https://github.com/akm/claude-plugins/issues/197)。規則は [rules/doc-structured-docs.md](../rules/doc-structured-docs.md) の節「参照先を最初に指す箇所」)。
- **初出の検査**: 検査 b に含める。最初に使う箇所の表示の文が、完全な名前の先頭から親を 0 個以上省いた形のどれかと同じことを確認する。違えばエラーにし、書ける形の候補をメッセージに出す。

## 問 15: 文書の一部のコピー (2026-11-07 に足した)

読みやすさのために、ほかの文書の一部をコピーした文書を作ることを、SSOT が分かる形で許す仕組み。

- **コピーの単位**: ID (明示のアンカー) を持つ手書きの節の本文。コピー元は、現在の仕様の手書きの Markdown に限る。記録と生成したファイルはコピー元にしない (生成したファイルの内容は YAML から生成すればよいため)。
- **どちらがコピーかの明記**: コピー先に、コピー元の ID を書いたマークで囲んで書く (例 `<!-- doc-structured copy-from: 相対パス#ID -->` 〜 `<!-- doc-structured copy-end -->`。マークの形は sub-issue 4d で決める)。コピー元には何も書かない。コピー元がどこにコピーされているかは、サブコマンド `refs <ID>` で知る (被参照の一覧のファイルを作らない決定と同じ扱い)。
- **不一致の検出と再コピー**: コピーのブロックを、手書きのファイルの中の生成した部分として扱う。`generate` がコピー元の内容で上書きし、検査 a (生成し直して差分が無い) が不一致を報告する。新しいサブコマンドは作らない。hook はファイル単位でしか判定しないので、コピーのブロックへの直接の編集は防がず、検査 a で見つける。
- **コピー元が無くなったとき**: 検査 a が「コピー元 (ID) が無い。コピー先の内容を見直す」というエラーを出す。`generate` はブロックを消さず、書き換えもしない。人が、ブロックを消すか、マークを外して自分の文章にするかを決める。
- **参照としての扱い**: コピーは、コピー先からコピー元への参照として、参照の向きの規則 (検査 i) と循環の検査 (検査 c-2) の対象にする。
- **行数の検査 k**: コピーしたブロックの行数も数える (読者はその行を読むため)。
- 指針「1 つの節の中で、同じ内容を 2 度書かない」の例外。

## 計画で決めること・確認したこと

**sub-issue で決めること**

- ツールの言語と、バージョンを指定して取得する方法、公開の手順 (sub-issue 1)。
- 種類ごとの名前の形の表のうち、まだ決めていない種類 (イベント・シナリオ・シーンなど)。実際の名前に当てた案を示して確認する (その種類を足す sub-issue)。
- テストの名前の ID を、文字列で書くか、テストランナーの一覧から取るか (sub-issue 13)。
- 各 YAML の具体的な形式 (それを必要とする sub-issue)。

**確認したこと** (2026-11-06〜07。実装の前に確認した)

- プラグインが、ディレクトリ `.claude/rules/` のファイルを配れないこと: 公式ドキュメントのプラグインが配れる構成要素の一覧に、ルールのファイルは無い (「配れない」と直接書いた文は無い)。プラグインの直下の `CLAUDE.md` は読み込まれない。
- 接頭辞の無いスキル名: プラグインのスキルは必ず `doc-structured:check` の形で呼べる。接頭辞の無い `check` は、ほかのコマンドがその名前を使っていないときだけ使える。組み込みに `check`・`generate`・`setup` は無い。規則の文書とスキルの本文では、接頭辞を付けた形で書く。
- GitHub のファイルの表示で、`#ID` を付けた URL が明示のアンカーの位置を開くこと: 公開リポジトリの Markdown (`<a name="GUI+parent"></a>`) を `#GUI+parent` 付きで開くと、その位置 (固定ヘッダの下) までスクロールした。GitHub はアンカーの name を `user-content-` 付きの小文字に書き換えるが、URL の `#ID` は元の表記で届く。ID は小文字の snake_case なので影響は無い。
- squash でマージしてブランチを消した後も、PR のブランチの先頭だったコミットの URL が開けること: 公開リポジトリの squash マージ済み (ブランチは削除済み) の PR の先頭コミットは、commit の URL も blob の URL も開けた。GitHub が `refs/pull/<番号>/head` として保持している。PR に無いコミット (PR を作らずに消したブランチ・force push で置き換えた前のコミット) には同じ保証が無い。
- Issue と PR の本文で、相対パスのリンクが使えないこと: 公開リポジトリの PR の本文の `](CONTRIBUTING.md)` は相対のまま描画され、ブラウザが PR の URL を基準に `/pull/CONTRIBUTING.md` に解決する (新しい PR を作る画面に飛ぶ)。Issue では `/issues/<パス>` になり 404。GitHub の Markdown の描画 API (mode=gfm) も相対の href を書き換えない。
- ラベルにコードの書式を含める書き方 (`` [`orders`] ``) の表示: Markdown の描画 API で、Issue・PR の描画 (gfm) でもファイルの描画でも、リンクの中にコードの書式 (`<a><code>orders</code></a>`) で描画される。
- 実際のプロジェクトの prettier (`singleQuote: true`) は、定義の行の title の引用符を `'` に書き換え、表の列の幅をそろえ、`<a name>` と見出しの間に空行を入れる。`.prettierignore` は `docs/` を除いていない。
- PreToolUse の hook は、Edit と Write のファイルのパスを受け取り、拒否と理由を返せる。hook が起動できないときは、編集はそのまま実行される。
- git の merge driver `ours` は、組み込みの driver ではない (2026-11-08 に sub-issue 3 で確認した)。組み込みは `text`・`binary`・`union` の 3 つだけで、知らない名前を指定すると通常の 3-way マージになり、競合のマークが入る。`binary` は、競合のマークを入れず、ファイルを競合の状態のままにする (残る内容は、規則の文書 [rules/doc-structured-docs.md](../rules/doc-structured-docs.md) の「生成したファイル」)。git 2.50.1 の一時的なリポジトリで確認した。
- `.claude/rules/` の `paths` の規則は、Claude が Read・Write・Edit か読み取りのコマンドで対象のファイルを扱ったときに読み込まれる。frontmatter が YAML として読めないと、常に読み込む規則になる。1 ファイルが 40,000 文字を超えると先頭だけになる。
- プラグインの自動更新のデフォルトは、公式以外のマーケットプレイスでは無効。
- GitHub の必須の検査は、ワークフローが起動しないと完了せずマージできない。ジョブを条件で実行しないと成功として扱われる。

## 適用先と順序

このリポジトリにプラグイン `doc-structured` を作ってから、実際のプロジェクトの 1 つのサブドメイン (メニュー) で、main にマージしない動作確認のブランチで試す。進め方は親の Issue と sub-issues に書く。
