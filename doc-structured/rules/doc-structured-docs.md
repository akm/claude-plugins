# doc-structured: 文書に共通する規則

プラグイン `doc-structured` の構成で書く、文書に共通する規則です。ドメインのディレクトリの規則は [doc-structured-domains.md](doc-structured-domains.md) にあります。規則の SSOT (single source of truth。ある事実を定めている唯一の記述) はプラグインのこのファイルで、プロジェクトのファイル `.claude/rules/doc-structured-docs.md` はそのコピーです。

## 用語

- **未分類のアプリケーション用語** (略称「未分類の用語」): このアプリケーションのために定義した言葉のうち、モデル・属性・値・操作などの、ほかのどの種類にも当たらないもの。モデルや属性として扱うことになったら、その種類へ移す。
- **限定付きの名前**: 定義を指す名前に、その種類と親を添えたもの (下の節「限定付きの名前」)。
- **定義の行**: reference-style のリンクの参照先を書く行 `[ラベル]: <href> "<title>"` (CommonMark の link reference definition)。
- **手書きのファイル**: 生成したファイルでない Markdown。人と Claude が書く。

## ID

ID は、定義のアンカーの名前であり、リンクのフラグメント (URL の `#` の後ろ) でもあります。

- 種類の記号と名前をハイフンで交互につなぎ、親から子の順に並べる (例 `d-loans-m-loan-a-status-v-on_loan`)。
- 名前は英語名で、snake_case (英小文字で始まり、英小文字・数字を 1 つの `_` で区切る。正規表現 `^[a-z][a-z0-9]*(_[a-z0-9]+)*$`) にする。
- 親になれる種類は決まっている: モデルと未分類の用語はドメインの下、属性はモデルの下、値は属性の下。
- ファイルの ID は、親の ID にファイルの種類の記号を足したもの。ファイルの種類の記号は名前を取らない (例 `d-loans-models`)。
- 手書きのファイルの節の ID は、ファイルの ID に `-h-<名前>` を 1 回だけ足したもの (例 `d-loans-concept-h-return_deadline`)。名前は書く人が決める。
- 子のファイル (100 行を超えたファイルを分けた先。[doc-structured-domains.md](doc-structured-domains.md) の節「手書きの Markdown」) の ID は、親のファイルの ID に `-f-<名前>` を足したもの (例 `d-loans-design-f-overdue_notice`)。ファイルの種類の記号は名前を取らないので、記号 `f` を挟んで節の `-h-` と区別する。子のファイルの節の ID は `d-loans-design-f-overdue_notice-h-<名前>`。

| ID の例 | 指すもの |
|---|---|
| `d-loans` | ドメイン `loans` |
| `d-loans-m-loan` | モデル |
| `d-loans-m-loan-a-status` | 属性 |
| `d-loans-m-loan-a-status-v-on_loan` | 値 |
| `d-loans-ut-business_day` | 未分類の用語 |
| `d-loans-models` | ファイル `models.md` |
| `d-loans-concept` | ファイル `concept.md` |
| `d-loans-concept-h-return_deadline` | ファイル `concept.md` の節 |
| `d-loans-design-f-overdue_notice` | 子のファイル `design/overdue_notice.md` |

## 限定付きの名前

親から順に「種類 + 名前」を「の」でつなぎます。ユーザーレベルの種類は日本語名をかぎ括弧で、開発レベルの種類 (ドメイン) とファイルは英語名をコードの書式で書きます。ドメインは日本語名を持ちません。この表は、ツールが名前を作るときの表と同じです (同じであることは、ツールのテストが検査します)。

| 種類 | 記号 | 名前の形 | 例 |
|---|---|---|---|
| ドメイン | `d` | ドメイン `<英語名>` | ドメイン `loans` |
| モデル | `m` | モデル「<日本語名>」 | モデル「貸出」 |
| 属性 | `a` | 属性「<日本語名>」 | 属性「貸出状態」 |
| 値 | `v` | 値「<日本語名>」 | 値「貸出中」 |
| 未分類のアプリケーション用語 | `ut` | 未分類のアプリケーション用語「<日本語名>」 | 未分類のアプリケーション用語「開館日」 |
| 節 | `h` | 節「<見出しの文>」 | 節「返却期限」 |
| ファイル | `models`・`terms`・`unclassified_app_terms`・`concept`・`problem`・`design` | ファイル `<ファイル名>` | ファイル `models.md` |
| 子のファイル | `f` | ファイル `<ドメインのディレクトリからのパス>` | ファイル `design/overdue_notice.md` |

- すべての親を書いた名前を、完全な名前と呼ぶ。例: `d-loans-m-loan-a-status-v-on_loan` の完全な名前は「ドメイン `loans` のモデル「貸出」の属性「貸出状態」の値「貸出中」」。
- 完全な名前は、定義の行の title と、用語の索引に書く。完全な名前では、未分類の用語を正式名称「未分類のアプリケーション用語」で書く。
- 節の名前は見出しの文 (行頭の `#` と前後の空白、末尾の閉じの `#` を除いたもの。コードの書式は残す)。例: `d-loans-concept-h-return_deadline` の完全な名前は「ドメイン `loans` のファイル `concept.md` の節「返却期限」」。
- 子のファイルの完全な名前には、親のファイルを書かない (例「ドメイン `loans` のファイル `design/overdue_notice.md`」)。

## アンカー

手書きのファイルには、ファイルと節のアンカーを書きます。

- ファイルの先頭の行 (空行を除く) に、ファイルの ID のアンカー `<a name="<ファイルの ID>"></a>` を書き、その次の行 (空行を除く) に `#` の見出しを書く。
- 節のアンカー `<a name="<節の ID>"></a>` の次の行 (空行を除く) に、`##` から `######` の見出しを書く。
- 同じ ID のアンカーを 2 つ書かない。生成したファイルのアンカーと同じ ID も書かない。
- アンカーを付けた見出しに、リンクを書かない (見出しの文が、その節を参照する定義の行の title になるため)。
- どこからも参照されていない節のアンカーも残してよい (Issue・PR・コードからも参照されうるため)。

## リンク

手書きのファイルでは、文書の参照を、reference-style のリンク `[ラベル]` か `[文][ラベル]` と、定義の行で書きます。外部の URL も同じです。

- `[文](URL)`・`<URL>`・文中にそのまま書いた URL・`[ラベル][]` の形で書かない。リンクにしない URL は、インラインコードにする。
- コードブロック・インラインコード・mermaid の図・HTML のコメントの中、エスケープした `\[`、脚注 `[^1]`、タスクリストのチェックボックス `[ ]`、GitHub の注記 `[!NOTE]` は、ラベルとして扱わない。リンクのつもりの無い角括弧 (`[a, b]` など) は、インラインコードにするか、`\[` とエスケープする。
- 画像 `![説明](パス)` は、この規則の対象にしない。
- ラベルは、CommonMark のとおり、英字の大文字と小文字の違いと、連続する空白の違いを無視して比べる。
- 定義の行は、ファイルの末尾に、本文の最後の行との間に空行を 1 つ挟んでまとめて書く。本文の途中に書かない。
- 1 つのファイルで、1 つのラベルの定義の行は 1 つだけにする。使われていない定義の行を残さない。
- href は、参照先が同じファイルなら `#<ID>`、ほかのファイルなら、そのファイルからの相対パスに `#<ID>` を付けたもの。
- title は、参照先の完全な名前。引用符は `"` と `'` のどちらでもよい。外部の URL (`http://`・`https://` で始まるもの) の定義の行には、title を書かなくてよい。
- 定義の行と title は手で書かず、スキル `doc-structured:links-fix` で足す・書き換える。見出しや日本語名を変えると title が古くなり、検査 b が報告する。

## 手書きの Markdown の大きさ

- 手書きのファイルの行数の指針は 50 行、上限は 100 行。数えるのは、ファイルの先頭から、末尾の定義の行のまとまり (定義の行と、その間と前後の空行) の直前まで。本文の中の空行・コードブロック・HTML のコメントも数える。
- 100 行を超えるときは、話題ごとにファイルを分ける (ドメインのファイルの分け方は [doc-structured-domains.md](doc-structured-domains.md) の節「手書きの Markdown」)。分けない理由があれば、`#` の見出しの次の行 (空行を除く) に、理由のコメントを 1 行で書く。

  `<!-- 行数が上限を超える理由: <理由> -->`

- 50 行を超えただけでは、検査は報告しない。理由のコメントの中身は、検査せずにレビューで人が見る。

## 書き方の指針

検査はしません。

- 手書きの節 1 つには、1 つのこと (1 つの規則・1 つの判断・1 つの概念) だけを書く。
- 1 つの節の中で、同じ内容を 2 度書かない。要約と詳細の両方を書かない。表に書いた内容を、文で繰り返さない。

## 生成したファイル

生成したファイルかどうかは、先頭の 3 行の中に次の形の 1 行があるかで判別します。この形は、バージョンをまたいで変えません。

- frontmatter の無い Markdown (1 行目): `<!-- doc-structured:generated 生成元: <パス> コマンド: <コマンド> (このファイルを直接編集せず、生成元を直して生成し直す) -->`
- frontmatter のある Markdown (frontmatter の中の 2 行目)・YAML (1 行目)・シェルスクリプト (shebang の次の 2 行目): `# doc-structured:generated 生成元: <パス> コマンド: <コマンド> (…)`

生成元は、リポジトリのルートからの相対パスです。複数の YAML から作るファイルでは、ディレクトリを末尾に `/` を付けて書きます。ファイルの先頭の BOM (エディタが保存のときに付けることがある) は、判定に影響しません。検査 a と generate は、生成したファイルの改行の CRLF と CR を LF として読みます (git の設定 core.autocrlf やエディタが改行を変えても、内容は変わらないため)。

生成したファイルへの Edit・Write・NotebookEdit は、プラグインの hook が、編集が実行される前に拒否します。Bash での編集と人のエディタでの編集は、検査 a が検出します。

ディレクトリ `docs/` の下の生成したファイルには、生成するファイル `docs/.gitattributes` で、git の組み込みの merge driver `binary` を設定します。生成したファイルが競合したときは、git が自分の側 (ours) とする内容が、競合のマーク無しで残ります。どの側が ours になるかは、git のコマンドによって違います。

- 生成したファイルを直接編集しない。直すときは生成元を直し、スキル `doc-structured:generate` (コマンド `bin/doc-structured generate`) で生成し直す。
- ツールで生成したファイルの競合を手動で解決せず生成し直す。
- 生成したファイルはコミットする。スキル `doc-structured:check` の検査 a が、生成し直した内容と違うファイルを報告する。
- 生成したファイルを、整形ツール (prettier など) の対象から外す (例: ファイル `.prettierignore` に、生成したファイルのパスのパターンを書く)。整形ツールが表の列の幅や引用符を書き換えると、検査 a が、生成し直した内容と違うと報告するため。
