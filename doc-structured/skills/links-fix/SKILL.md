# doc-structured:links-fix: 定義の行とファイルのアンカーを直す

手書きの Markdown の定義の行 (`[ラベル]: <href> "<完全な名前>"`) と、先頭のファイルの ID のアンカーを直す。リンクとアンカーの規則の SSOT (single source of truth。ある事実を定めている唯一の記述) は、プラグインの規則の文書 [doc-structured-docs.md](../../rules/doc-structured-docs.md) の節「アンカー」と「リンク」。

定義の行の href と title は、ツールが作る。このスキルは定義の行を手で書かない。本文の文も書き換えない。

## 手順

1. **前置き**: プロジェクトのルートで、次のコマンドを実行する。出力があれば、その 1 行をそのまま利用者に伝えてから続ける。終了コードが 1 なら、標準エラー出力の文を利用者に伝えて中断する。

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/plugin-version-notice"
   ```

2. **直す**: プロジェクトのルートで `bin/doc-structured links-fix` を実行する。ファイルのパスを受け取ったら、そのまま引数に渡す。
3. **終了コードが 0 のとき**: 出力の「書き換えた」のファイルの一覧を、そのまま利用者に伝える。「直すものは無かった」なら、そう伝える。
4. **終了コードが 1 で、出力に「判断の要るものが … 件ある」があるとき**: 直し方が 1 つに決まるものは、ツールが直してある。残りの「パス:行:列: メッセージ」は参照先の判断なので、このスキルは決めない。1 件ずつ、次のとおりに利用者に質問する。
   - **「参照先の候補が N 件ある」**: メッセージの候補 (ID と完全な名前) を選択肢にして、どれを指すかを質問する。
   - **「参照先の候補が無い」**: 参照先の ID か外部の URL を質問する。ラベルの書き間違い (同じファイルに「使われていないが消さなかった」定義の行があれば、その定義の行のラベルが候補になる) のときは、本文のラベルを直すかどうかも質問する。
   - **「定義の行が本文で使われていないが、… 消さなかった」**: 定義の無いラベルの回答を受け取った後、もう一度実行すると、ツールが消す。この定義の行だけを質問しない。
   - **「定義の行が … 行目にもあり、参照先が違う」**: 2 つの参照先のどちらを指すかを質問する。

   回答を受け取ったら、ラベルごとに `--choose <ファイル> <ラベル> <ID か URL>` を付けて、手順 2 のコマンドを実行する (`--choose` は何度でも付けられる)。本文のラベルを直すと回答されたら、本文を直してから手順 2 に戻る。
5. **そのほかの終了コード 1 のとき**: 標準エラー出力の文を扱う。
   - **YAML の誤り** (「パス:行:列: 検査 h: メッセージ」の形): ツールは何も直していない。スキル `doc-structured:check` の検査 h の扱いのとおり、利用者に質問して YAML を直してから、手順 2 に戻る。
   - **「--choose の参照先 … が無い」「--choose のラベル … は … 使われていない」**: 回答を渡すときの書き間違いか、参照先がまだ無い。利用者に伝えて、参照先を質問し直す。
   - **「… は、ドメインのディレクトリの下の手書きの Markdown でない」**: 引数のパスの誤り。利用者に伝えて中断する。
6. **完了したら**: スキル `doc-structured:check` を実行して、検査 b が成功することを確認する。

## このスキルがしないこと

- 定義の行の href と title を手で書くこと。
- 参照先を、利用者に質問せずに決めること。候補が 1 件のものは、ツールが決める。
- 本文の文とラベルを、利用者に質問せずに書き換えること。
- アンカーの名前と見出しを直すこと。検査 b が報告したものは、スキル `doc-structured:check` の扱いのとおりに直す。
