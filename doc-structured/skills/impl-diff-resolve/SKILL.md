# doc-structured:impl-diff-resolve: 設計と実装の差分を 1 件ずつ解消する

設計 (ファイル名が `schema` で始まる YAML のテーブルとカラム) と実際のスキーマの差分を、1 件ずつ利用者に質問してから、サブコマンド `impl-diff-resolve` で YAML を書き換えて解消する。件の ID・フラグの意味・YAML に書く形の SSOT (single source of truth。ある事実を定めている唯一の記述) は、プラグインの規則の文書 [doc-structured-impl.md](../../rules/doc-structured-impl.md) の節「差分の解消」。

このスキルは、YAML をサブコマンドでだけ書き換える。マイグレーション・設定・手書きの Markdown は書き換えない。

## 手順

1. **前置き**: プロジェクトのルートで、次のコマンドを実行する。出力があれば、その 1 行をそのまま利用者に伝えてから続ける。終了コードが 1 なら、標準エラー出力の文を利用者に伝えて中断する。

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/plugin-version-notice"
   ```

2. **全体を示す**: プロジェクトのルートで `bin/doc-structured impl-diff` を実行する。
   - 終了コードが 0 なら、「設計と実装に差分は無かった」と伝えて完了する。
   - 終了コードが 3 なら、手元にデータベースが無い。標準エラー出力の文 (何が無いかと用意の仕方) をそのまま伝え、実行できないと伝えて終了する。ほかの方法 (別のデータベースやコマンド) は試さない。
   - 終了コードが 1 で、標準エラー出力に「YAML に … 件の誤りがあるので、設計と実装を比べなかった」があれば、YAML の誤りを一覧にして伝え、スキル `doc-structured:check` で直すよう案内して終了する。「設定に paths.migrations と database を書く」「マイグレーションを … に適用できない」の行だけなら、その行を伝えて終了する (スキル `doc-structured:check` が扱う)。
   - 終了コードが 1 でほかのときは、標準出力の unified diff (`--- 設計` と `+++ 実装` で始まる部分) をコードブロックでそのまま示し、削除の行 (`-`) は設計にだけ、追加の行 (`+`) は実装にだけある事実であることを添えて、手順 3 に進む。
3. **件を選ぶ**: `bin/doc-structured impl-diff-resolve --list` を実行する。出力は 1 行に 1 件の「`<ID>` | 使えるフラグ | 指示の行のメッセージ」で、解消する順に並んでいる。このスキルの実行でまだ質問していない件のうち、先頭の件を選ぶ。そのような件が無ければ、手順 7 に進む。終了コードが 3 なら、手順 2 と同じく伝えて終了する (それまでに行ったことの一覧も伝える)。
4. **質問する**: 選んだ件の ID・指示の行のメッセージと、手順 2 の unified diff のうちその項目の行 (先頭が `table <テーブル名>` で、カラムなら `column <カラム名>:`、インデックスなら `index <カラム名>, …` を含む行) を示し、質問のダイアログで、どう解消するかを 1 問で質問する。選択肢は、使えるフラグを次の言葉にしたものに、「実装 (マイグレーション) を直す」と「この件を飛ばす」を加える。「ここで中断する」は、ダイアログの自由入力で受け付ける。

   | フラグ | 選択肢の言葉 |
   |---|---|
   | `--planned` | planned: true を付ける (未実装として残す) |
   | `--unplanned` | planned を外す |
   | `--match-impl` (メッセージが「実装にあるが YAML に無い」) | YAML に足す |
   | `--match-impl` (メッセージが「実装に無い」) | YAML から消す |
   | `--match-impl` (メッセージが「実装されたので、planned を外す」) | planned を外し、YAML を実装に合わせる |
   | `--match-impl` (メッセージが「… が違う」) | YAML を実装に合わせる |

   - 「実装 (マイグレーション) を直す」と「この件を飛ばす」を選んだ件は、記録して手順 3 に戻る。このスキルの実行の中では、その件を再び質問しない。マイグレーションは書き換えない。
   - 「ここで中断する」と回答されたら、手順 7 に進む。
5. **足すものを質問する**: 「YAML に足す」を選び、件がテーブルかカラムなら、続けて次のことを 1 問ずつ質問する。件がインデックスなら、質問せずに手順 6 に進む。
   - **テーブルのドメイン** (件の ID が `d-<ドメイン>-t-…` のとき): ディレクトリ `docs/domains/` の下のドメインを選択肢にする。回答のドメインで、ID の `<ドメイン>` を置き換える。
   - **足すファイル** (テーブルのとき): そのドメインのディレクトリの下に、ファイル名が `schema` で始まる YAML が 2 つ以上あれば、どれに足すかを質問し、`--file <パス>` に渡す。1 つ以下なら質問せず、`--file` を付けない (ドメインのディレクトリの直下の `schema.yaml` に足す)。
   - **テーブルとカラムのそれぞれの対応か定義の文**: テーブルには、対応するモデル (`--model`)・対応する属性 (中間テーブル。`--attribute`)・定義の文 (`--definition`) のどれか 1 つを質問する。テーブルを足すときは、その下のカラムのそれぞれにも、カラムを足すときはそのカラムに、対応する属性 (`--attribute`。テーブルに `model` があるときだけ) か定義の文 (`--definition`) を質問する。カラムの ID は `<テーブルの ID>-c-<カラム名>`。対応の候補 (ドメインのモデルと、テーブルの `model` のモデルの属性のうち、名前が近いもの) と、定義の文の案 (1〜2 文) は示してよいが、決めるのは利用者。
6. **実行する**: 回答から組み立てたコマンドを示し、実行する (選んだ時点で承認とみなし、実行の前にもう一度は確認しない)。

   ```bash
   bin/doc-structured impl-diff-resolve <ID> --match-impl [--file <パス>] [--definition <ID> <文>]... [--model <テーブルの ID> <モデルの ID>]... [--attribute <テーブルかカラムの ID> <属性の ID>]...
   ```

   - 終了コードが 0 なら、出力 (書き換えた・作った・消したファイル、YAML に書けなかったもの、消した ID を指すリンク) を記録し、手順 3 に戻る。最後の行の「bin/doc-structured generate を実行する」は、手順 7 でまとめて行う。
   - 終了コードが 1 で、標準エラー出力に「先に <ID> を解消する」があれば、その件を先に扱う。その件を選んで手順 4 から進め、その件を解消したら元の件に戻る。
   - 終了コードが 1 でほかのとき (検査 h の誤りで元に戻した、定義の文が足りない、など) は、標準エラー出力をそのまま伝え、この件をどうするか (回答を変えて実行し直す・実装を直す・飛ばす) を質問する。
   - 終了コードが 3 なら、手順 2 と同じく伝えて終了する (それまでに行ったことの一覧も伝える)。
7. **確認する**: 手順 6 で YAML を 1 度でも書き換えていれば、`bin/doc-structured generate` を 1 度実行する。その後に `bin/doc-structured impl-diff` を実行し、次のとおりに伝えて完了する。
   - 最初に、このスキルの実行で行ったことを件ごとに一覧にする (ID・選んだ扱い・実行したコマンド・YAML に書けなかったものの出力・消した ID を指すリンクの出力)。
   - 終了コードが 0 なら、「設計と実装に差分は無かった」と伝える。
   - 終了コードが 1 なら、残った指示の行を「実装を直すと回答した件」「飛ばした件」「そのほか (中断した後の件など)」に分けて伝え、unified diff もコードブロックで示す。「実装を直す」件には、マイグレーションで何を変えるか (指示の行のメッセージ) を添えるが、マイグレーションは書かない。
   - 「docs/system/schema-actual.md … 生成し直した内容と違う」の行があれば、スキル `doc-structured:generate` で生成し直せることを伝える (マイグレーションが変わって古くなったもので、このスキルの解消とは別なので、実行はしない)。
   - 消した ID を指すリンクを出力していたら、スキル `doc-structured:check` で検査 b を確認するよう添える。
8. **終了コードが 2 のとき** (どの手順でも): 引数の誤り。出力をそのまま利用者に伝えて中断する。

## このスキルがしないこと

- YAML を、サブコマンド `impl-diff-resolve` を使わずに書き換えること。
- マイグレーション・設定・手書きの Markdown (`design.md` を含む) を書き換えること。マイグレーションを直すのは、スキル `doc-structured:check` か利用者。
- 定義の文・対応・足すドメインとファイルを、利用者に質問せずに決めること。
- 1 件ずつの質問を省いて、まとめて解消すること。
- データベースが無いときに、ほかの方法で実際のスキーマを読むこと。
- 生成したファイルを手で直すこと。
