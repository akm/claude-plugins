# doc-structured:check: 文書を検査し、直す

プラグイン doc-structured の構成の文書を検査する。検査の内容と直し方の SSOT (single source of truth。ある事実を定めている唯一の記述) は、プラグインの規則の文書 [doc-structured-domains.md](../../rules/doc-structured-domains.md) の節「検査」と、検査 j については [doc-structured-impl.md](../../rules/doc-structured-impl.md)。

## 手順

1. **前置き**: プロジェクトのルートで、次のコマンドを実行する。出力があれば、その 1 行をそのまま利用者に伝えてから続ける。終了コードが 1 なら、標準エラー出力の文を利用者に伝えて中断する。

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/plugin-version-notice"
   ```

2. **検査する**: プロジェクトのルートで `bin/doc-structured check` を実行する。引数 (`--light`・`--heavy`・`--all`・`--only <検査>`) を受け取ったら、そのまま渡す。指定が無ければ軽い群 (`--light`) を実行する。
3. **終了コードが 0 のとき**: 最後の行 (検査の結果) を利用者に伝えて完了する。
4. **終了コードが 1 のとき**: 出力の誤り (「パス[:行:列]: 検査 <記号>: メッセージ」の形) を検査ごとに分け、次のとおりに扱う。
   - **検査 h と、検査 i のうち YAML の参照についてのもの** (「refers_to の参照先 … は、祖先のディレクトリの … にある」「操作 lend の targets の参照先 … は、祖先のディレクトリの … にある」「状態の遷移の attribute の参照先 … は、祖先のディレクトリの … にある」の形): YAML の内容の判断なので、このスキルは決めない。誤りごとに直し方の候補を示して利用者に質問し、回答のとおりに YAML を直す。検査 i の直し方の候補は、参照される定義をサブディレクトリに移すことで、参照しているファイルを移すことではない。ただし状態の遷移の `attribute` では、状態の遷移のファイルを属性と同じディレクトリに移すことも候補にする (規則の文書の節「検査」の表)。検査 h の「状態の遷移を属性の下に書けない」では、状態の遷移をファイル名が `state-machines-` で始まる YAML に移すことを候補にし、ファイル名と置くディレクトリを規則の文書の節「状態の遷移」と「書き方の指針」から示す。検査 h の「… に対応するカラムが無い」では、その属性に対応するカラムに `attribute` を書くことと、中間テーブルの `attribute` でその属性を指すことを候補にする。保存せずに求める属性のように、どのテーブルにも対応しない属性は、今の形式では書けない (Issue #307) ことを伝える。
   - **検査 c-1** (「ドメインの依存が循環している」「モデルの参照が循環している」「テーブルの外部キーが循環している」): YAML の内容の判断なので、このスキルは決めない。誤りごとに直し方の候補を示して利用者に質問し、回答のとおりに YAML を直す。ドメインの依存の循環の直し方の候補は、出力の循環のどれかの参照を外すことと、参照される定義を、それを参照するドメインか、新しいドメインに移すこと。どの定義の参照が依存の元かは、ドメインごとの生成したファイル `dependencies.md` の表で示す。モデルの参照の循環の直し方の候補は、外部キーを持たないモデルの `refers_to` を外すこと。テーブルの外部キーの循環の直し方の候補は、出力の循環のどれかの外部キーの `references` を外すこと (外部キーの制約を付けずに、カラムは残してよい)。直した後は、スキル `doc-structured:generate` で生成し直す。
   - **検査 i のうち「リンク … の参照先 … は、祖先のディレクトリの手書きのファイル … にある」と、検査 c-2**: 手書きの Markdown の内容の判断なので、このスキルは決めない。誤りごとに直し方の候補を示して利用者に質問し、回答のとおりに直す。検査 i の直し方の候補は、参照される内容を別のサブディレクトリの子のファイル (`concept/<名前>.md` など) に移すことと、リンクを外すこと。検査 c-2 の直し方の候補は、出力の循環のどれかのリンクを外すことと、参照される内容を別の節に移すこと。直した後は、スキル `doc-structured:links-fix` で定義の行を直す。
   - **検査 a のうち「生成し直した内容と違う」「生成するはずのファイルが無い」「生成したファイルの中身が無い」「生成し直すと消えるファイルが残っている」**: 直し方は生成し直すことだけなので、利用者に、どのファイルが YAML と違っていたか (手で変えた内容は生成し直すと消える) を伝えてから、スキル `doc-structured:generate` を実行する。
   - **検査 a のうち「生成元が無い」**: ファイルを消すか生成元を戻すかは内容の判断なので、利用者に質問する。
   - **検査 a のうち「手で書いたファイルが、生成するファイルの場所にある」**: 手で書いた内容をどこへ移すか、消してよいかは内容の判断なので、利用者に質問する。出力にある直し方を候補として示し、回答のとおりにしてから、スキル `doc-structured:generate` を実行する。
   - **検査 b のうち、定義の行についてのもの** (「定義の行が無い」「本文で使われていない」「title が … と違う」「title が無い」「末尾のまとまりに書く」「定義の行として読まれない」「定義の行は、… 行目にもある」) と、「先頭の行に、ファイルの ID のアンカー … が無い」: スキル `doc-structured:links-fix` を実行する (参照先の判断は、そのスキルが利用者に質問する)。
   - **検査 b のうち「… を最初に指す箇所の表示の文 … が、書ける形のどれとも違う」**: スキル `doc-structured:links-fix` を実行する (`[ラベル]` の箇所はツールが書ける形に直し、`[文][ラベル]` の箇所は、そのスキルが利用者に質問する)。
   - **検査 b のうち、そのほかのもの** (手書きの Markdown の名前と場所・アンカーの ID の形・アンカーの次の見出し・同じ ID のアンカー・`[文](URL)` などのリンクの書き方・href の誤り): ファイル名・アンカーの名前・見出し・リンクの書き方をどう直すかは内容の判断なので、このスキルは決めない。誤りごとに出力の直し方を候補として示して利用者に質問し、回答のとおりに直す。リンクの書き方を reference-style に直した後は、スキル `doc-structured:links-fix` で定義の行を足す。
   - **検査 k**: 話題ごとに子のファイルに分けるか、分けない理由をコメントに書くかは内容の判断なので、このスキルは決めない。どちらにするか (分けるなら分け方、書くなら理由) を利用者に質問し、回答のとおりにする。
   - **検査 j のうち、設計と実装の違い** (「… の … が違う」「… は実装されたので、planned を外す」「… が実装に無い」「… が実装にあるが YAML に無い」): YAML で直すか実装 (マイグレーション) で直すかは内容の判断なので、このスキルは決めない。違いがあることを伝えてから、スキル `doc-structured:impl-diff-resolve` の手順で 1 件ずつ質問して解消する (YAML を直接は書き換えない)。そのスキルで「実装 (マイグレーション) を直す」と回答された件は、適用済みのマイグレーションを書き換えるか、新しいマイグレーションを足すかを質問し、回答のとおりにマイグレーションを直す。
   - **検査 j のうち「docs/system/schema-actual.md」の「生成し直した内容と違う」「生成するはずのファイルが無い」**: 直し方は生成し直すことだけなので、スキル `doc-structured:generate` を実行する (設定に `database.schema_actual: true` があるので、`generate --all` を実行する)。
   - **検査 j のうち「設定に paths.migrations と database を書く」**: 設定に何を書くか (マイグレーションのパターン・データベースの種類・イメージ) は内容の判断なので、このスキルは決めない。規則の文書 [doc-structured-impl.md](../../rules/doc-structured-impl.md) の節「検査 j」のキーを示して利用者に質問し、回答のとおりに設定を書く。
   - **検査 j のうち「マイグレーションを … に適用できない」「PostgreSQL のコンテナを起動できない」**: ファイルとデータベースのメッセージを利用者に伝え、どう直すかを質問する。
   - **「YAML に誤りがあるので、検査 … を実行しなかった」**: 検査 h の誤りを直した後に実行される。
   直した後は、手順 2 に戻る。
5. **終了コードが 2 のとき**: 引数の誤り。出力をそのまま利用者に伝えて中断する。
6. **終了コードが 3 のとき**: 手元にデータベースが無いので、検査 j を実行できなかった。標準出力にほかの検査の誤りがあれば、それも一覧にして伝える。標準エラー出力の文 (何が無いかと用意の仕方。「Docker を起動する」など) をそのまま伝え、検査 j を実行できないと伝えて終了する。ほかの方法 (別のデータベースやコマンド) は試さない。

## このスキルがしないこと

- 生成したファイルを手で直すこと。検査 a の失敗は、スキル `doc-structured:generate` で生成し直して直す。
- YAML の内容 (名前・定義・参照先・ファイルの配置先) を、利用者に質問せずに決めること。
- 手書きの Markdown の本文・ファイル名・アンカーの名前・見出しを、利用者に質問せずに書き換えること。
- 定義の行を手で書くこと。定義の行は、スキル `doc-structured:links-fix` が足す・書き換える。
- 検査の結果を記録すること。
