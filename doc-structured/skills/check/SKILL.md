# doc-structured:check: 文書を検査し、直す

プラグイン doc-structured の構成の文書を検査する。検査の内容と直し方の SSOT (single source of truth。ある事実を定めている唯一の記述) は、プラグインの規則の文書 [doc-structured-domains.md](../../rules/doc-structured-domains.md) の節「検査」。

## 手順

1. **前置き**: プロジェクトのルートで、次のコマンドを実行する。出力があれば、その 1 行をそのまま利用者に伝えてから続ける。終了コードが 1 なら、標準エラー出力の文を利用者に伝えて中断する。

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/plugin-version-notice"
   ```

2. **検査する**: プロジェクトのルートで `bin/doc-structured check` を実行する。引数 (`--light`・`--heavy`・`--all`・`--only <検査>`) を受け取ったら、そのまま渡す。指定が無ければ軽い群 (`--light`) を実行する。
3. **終了コードが 0 のとき**: 最後の行 (検査の結果) を利用者に伝えて完了する。
4. **終了コードが 1 のとき**: 出力の誤り (「パス[:行:列]: 検査 <記号>: メッセージ」の形) を検査ごとに分け、次のとおりに扱う。
   - **検査 h と、検査 i のうち「refers_to の参照先 … は、祖先のディレクトリの … にある」**: YAML の内容の判断なので、このスキルは決めない。誤りごとに直し方の候補を示して利用者に質問し、回答のとおりに YAML を直す。検査 i の直し方の候補は、参照される定義をサブディレクトリに移すことで、参照しているファイルを移すことではない。
   - **検査 i のうち「リンク … の参照先 … は、祖先のディレクトリの手書きのファイル … にある」と、検査 c-2**: 手書きの Markdown の内容の判断なので、このスキルは決めない。誤りごとに直し方の候補を示して利用者に質問し、回答のとおりに直す。検査 i の直し方の候補は、参照される内容を別のサブディレクトリの子のファイル (`concept/<名前>.md` など) に移すことと、リンクを外すこと。検査 c-2 の直し方の候補は、出力の循環のどれかのリンクを外すことと、参照される内容を別の節に移すこと。直した後は、スキル `doc-structured:links-fix` で定義の行を直す。
   - **検査 a のうち「生成し直した内容と違う」「生成するはずのファイルが無い」「生成したファイルの中身が無い」「生成し直すと消えるファイルが残っている」**: 直し方は生成し直すことだけなので、利用者に、どのファイルが YAML と違っていたか (手で変えた内容は生成し直すと消える) を伝えてから、スキル `doc-structured:generate` を実行する。
   - **検査 a のうち「生成元が無い」**: ファイルを消すか生成元を戻すかは内容の判断なので、利用者に質問する。
   - **検査 a のうち「手で書いたファイルが、生成するファイルの場所にある」**: 手で書いた内容をどこへ移すか、消してよいかは内容の判断なので、利用者に質問する。出力にある直し方を候補として示し、回答のとおりにしてから、スキル `doc-structured:generate` を実行する。
   - **検査 b のうち、定義の行についてのもの** (「定義の行が無い」「本文で使われていない」「title が … と違う」「title が無い」「末尾のまとまりに書く」「定義の行として読まれない」「定義の行は、… 行目にもある」) と、「先頭の行に、ファイルの ID のアンカー … が無い」: スキル `doc-structured:links-fix` を実行する (参照先の判断は、そのスキルが利用者に質問する)。
   - **検査 b のうち「… を最初に指す箇所の表示の文 … が、書ける形のどれとも違う」**: スキル `doc-structured:links-fix` を実行する (`[ラベル]` の箇所はツールが書ける形に直し、`[文][ラベル]` の箇所は、そのスキルが利用者に質問する)。
   - **検査 b のうち、そのほかのもの** (手書きの Markdown の名前と場所・アンカーの ID の形・アンカーの次の見出し・同じ ID のアンカー・`[文](URL)` などのリンクの書き方・href の誤り): ファイル名・アンカーの名前・見出し・リンクの書き方をどう直すかは内容の判断なので、このスキルは決めない。誤りごとに出力の直し方を候補として示して利用者に質問し、回答のとおりに直す。リンクの書き方を reference-style に直した後は、スキル `doc-structured:links-fix` で定義の行を足す。
   - **検査 k**: 話題ごとに子のファイルに分けるか、分けない理由をコメントに書くかは内容の判断なので、このスキルは決めない。どちらにするか (分けるなら分け方、書くなら理由) を利用者に質問し、回答のとおりにする。
   - **「YAML に誤りがあるので、検査 … を実行しなかった」**: 検査 h の誤りを直した後に実行される。
   直した後は、手順 2 に戻る。
5. **終了コードが 2 のとき**: 引数の誤り。出力をそのまま利用者に伝えて中断する。

## このスキルがしないこと

- 生成したファイルを手で直すこと。検査 a の失敗は、スキル `doc-structured:generate` で生成し直して直す。
- YAML の内容 (名前・定義・参照先・ファイルの配置先) を、利用者に質問せずに決めること。
- 手書きの Markdown の本文・ファイル名・アンカーの名前・見出しを、利用者に質問せずに書き換えること。
- 定義の行を手で書くこと。定義の行は、スキル `doc-structured:links-fix` が足す・書き換える。
- 検査の結果を記録すること。
