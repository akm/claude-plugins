# doc-structured:impl-diff: 設計と実装の差分を示す

設計 (ファイル名が `schema` で始まる YAML のテーブルとカラム) と、実際のスキーマの差分を示す。比べ方・結果の表・正規化した形の SSOT (single source of truth。ある事実を定めている唯一の記述) は、プラグインの規則の文書 [doc-structured-impl.md](../../rules/doc-structured-impl.md)。

このスキルは、YAML もマイグレーションも書き換えない。

## 手順

1. **前置き**: プロジェクトのルートで、次のコマンドを実行する。出力があれば、その 1 行をそのまま利用者に伝えてから続ける。終了コードが 1 なら、標準エラー出力の文を利用者に伝えて中断する。

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/plugin-version-notice"
   ```

2. **比べる**: プロジェクトのルートで `bin/doc-structured impl-diff` を実行する。
3. **終了コードが 0 のとき**: 「設計と実装に差分は無かった」と伝えて完了する。
4. **終了コードが 1 のとき**: 出力を次のとおりに扱う。
   - **標準エラー出力に「YAML に … 件の誤りがあるので、設計と実装を比べなかった」がある**: YAML の誤りを一覧にして伝え、スキル `doc-structured:check` で直すよう案内して完了する。
   - **そのほか**: 標準出力の unified diff (`--- 設計` と `+++ 実装` で始まる部分) をコードブロックでそのまま示し、削除の行 (`-`) は設計にだけ、追加の行 (`+`) は実装にだけある事実であることを添える。続けて、指示の行 (「パス[:行:列]: 検査 j: メッセージ」の形) を一覧にして伝える。どれを YAML で直し、どれを実装 (マイグレーション) で直すかは、利用者が決めることなので、このスキルは決めず、直すことも提案しない。「設定に paths.migrations と database を書く」の行があれば、設定のキーの意味が規則の文書の節「検査 j」にあることを添える。「マイグレーションを … に適用できない」の行があれば、そのファイルとデータベースのメッセージを伝える。「docs/system/schema-actual.md … 生成し直した内容と違う」の行があれば、スキル `doc-structured:generate` で生成し直せることを添える。
5. **終了コードが 3 のとき**: 手元にデータベースが無いので、検査 j を実行できない。標準エラー出力の文 (何が無いかと用意の仕方。「Docker を起動する」など) をそのまま伝え、実行できないと伝えて終了する。ほかの方法 (別のデータベースやコマンド) は試さない。
6. **終了コードが 2 のとき**: 引数の誤り。出力をそのまま利用者に伝えて中断する。

## このスキルがしないこと

- YAML・マイグレーション・設定を書き換えること。差分を 1 件ずつ解消するのは、別のスキル (sub-issue 11c で作る) の役目。
- データベースが無いときに、ほかの方法で実際のスキーマを読むこと。
- 生成したファイルを手で直すこと。
