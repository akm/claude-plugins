# コミットルール

commit-rules-guard プラグイン同梱の既定ルール。
ユーザーが `~/.claude/rules/commit-rules.md` を持つ場合はそちらが優先される。

## 基本原則

コミットは **ファイルの種類** (コード/設定/ドキュメント等) ではなく、**そのファイルを変更した動機** でグルーピングする。
一つのコミットに複数の動機を混ぜない。動機の例:

- ファイルの内容の追加/変更/削除
- ファイルの内容の修正 (問題の修正)
- linter による指摘への対応
- リファクタリング
- ツールによる自動のファイルの作成/更新/削除

特に linter やレビューが複数の指摘を出したときは、一つのコミットにまとめず、指摘ごとに別のコミットに分ける。

## コミット分割とテスト・検査の優先順位

**動機ごとの分割を、各コミットでのテスト・検査のパスより優先する。**

- テスト・lint・各種検査 (CI やローカルの `make` ターゲットを含む) は、
  最終的に (ブランチを push する時点・レビューに出す時点で) パスすればよい。
  **途中の個々のコミットでパスしている必要はない。**
- 「各コミットでグリーンを保つ」ことを理由に、本来別々の動機の変更を
  1 つのコミットにまとめてはならない。動機の分割を優先する。
- 生成物 (図・スキーマなど) と、その元になる手書きの変更が別コミットに
  またがり、途中のコミットで生成物と元がずれても構わない。
  最終的に整合していればよい。

## 関連する変更はまとめる

- 機能追加のコード変更 + 関連ドキュメント更新 → 同一コミット
- バグ修正のコード変更 + テスト追加 → 同一コミット
- リファクタリング + それに伴う関連コード修正 → 同一コミット
- インターフェース変更 + 全呼び出し元の修正 → 同一コミット
- 関数の削除 + 参照元の修正 → 同一コミット

## 無関係な変更は分離する

- リファクタリングと新機能追加は別コミット
- コードのリファクタリングとドキュメントの更新は別コミット
- バグ修正と新機能の追加は別コミット
- コードの変更と無関係な設定ファイルの変更は別コミット
- 手で書いたコードと、ツールによる自動生成物 (ロックファイル・生成コード等) は別コミット
