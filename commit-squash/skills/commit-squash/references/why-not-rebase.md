# なぜ rebase ではなく積み直しなのか

`git rebase -i` で squash するのが一般的な方法だが、このスキルは**起点から積み直す**方式を採る。理由は 3 つ。

## 1. この環境で `-i` が使えない

対話的なフラグ (`git rebase -i`、`git add -i`) はこの環境ではサポートされていない。todo をファイルで渡す回避策はあるが、順序の入れ替えを含む todo を手で書くのは間違えやすく、間違えたことに気づくのが衝突が起きた後になる。

## 2. 順序を入れ替えると衝突が頻発する

まとめる作業では、コミットの順序をグループごとに並べ替えることになる。ところが元の履歴では、同じファイルを触るコミットが時間順に散らばっている。

例: `A(file1) → B(file2) → C(file1) → D(file2) → E(file1)` を `[A,C,E] → [B,D]` に並べ替える。rebase では C を A の直後に持ってくる時点で、B が作った file2 の状態を前提にしていた部分が衝突する。**衝突解決のたびに人手の判断が入り、そこで中身が変わる危険がある。**

積み直しなら、最終形から `git checkout <最終> -- <ファイル>` で取り出すだけなので、**衝突は原理的に起きない**。

## 3. 最終ツリーの一致を機械的に証明できる

積み直しでは、最後に次が成り立つことを確かめられる。

```bash
git rev-parse HEAD^{tree}     # まとめる前に控えた値と完全に一致する
```

ツリーのハッシュが一致すれば、**中身が 1 バイトも変わっていないことの証明になる**。rebase でも結果的に一致はするが、途中の衝突解決で変わっていないことを別途確かめる必要がある。

積み直しは「最終形を分解して並べ直す」操作なので、**一致するのが当たり前で、一致しなければ取りこぼしがある**という明快な判定になる。

## 積み直しの弱点

正直に書いておく。

- **中間状態を経るグループは手間がかかる。** 「lint 対応の前と後」のように 1 つのファイルが複数のコミットに分かれる場合、それぞれの時点のコミットから取り出す必要がある。
- **author の情報が失われる。** 全コミットが実行者のものになる。複数人が書いたコミットをまとめるときは向かない (そもそも他人のコミットは書き換えない)。
- **コミット日時が現在時刻になる。** 元の作業時刻を残したい場合は `--date` で指定する。

これらが問題になる場合は、rebase を検討する余地がある。ただし**衝突解決で中身が変わる危険は残る**ので、その場合も最終ツリーの一致検証は必ず行う。
