## Context

`pr-teeth` に、利用者が名指しした PR を解説する `/pr-teeth-pick` コマンドを追加した（issue #16）。利用者はこう打つ。

```
/pr-teeth-pick owner/repo#123 https://github.com/owner/repo/pull/456
```

この文字列を `{repo, number}` にする作業は、**機械的に決まる**。そして、この種の作業をスキルの本文（LLM への自然文の指示）に書くのは非常に安い。「URL から owner/repo/number を読み取る」と1行書けば、たいていの入力では実際に動く。

その安い道を採らず、Python モジュール `pr-teeth/scripts/prteeth/prspec.py` と `resolve` サブコマンドを書き、単体テストを付けた。判断の理由はモジュールの docstring にそのまま書いてある。

> **解釈をモデルに任せない理由:** URL から owner/repo/number を取り出す作業は、見た目には簡単でも取り違えが起きる（`/pull/123/files` の末尾、`#issuecomment-...` のフラグメント、末尾スラッシュ、`www.` の有無）。取り違えると**別の PR の解説を正しい体裁で出してしまい、読み手には誤りだと分からない**。範囲判定と同じく、機械的に決まるものはここで確定させる。

`SKILL.md` の側も、この分担を明示的に禁止の形で書いている。

> **URL や番号の解釈を自分で行わない。** 次に渡す。

つまりこれは「実装が面倒だからコードにした」話ではない。**取り違えたときに何が起きるか**を先に見積もって、置き場所を決めた話である。

## Guidance

**識別子を非構造テキストから取り出す作業は、取り違えが「自信に満ちた誤り」として現れるなら、LLM ではなくテスト済みのコードに置く。**

判断の基準は、作業の難しさではない。**失敗の見た目**である。

| 失敗の形 | 例 | 置き場所 |
| --- | --- | --- |
| 大きく目に見える（例外・空・明らかな欠落） | 解釈できず「解釈できません」と返る／出力が空になる | LLM でもよい |
| 正しい体裁のまま、中身が別物 | 打っていないリポジトリの PR を、完璧な書式で解説する | **コード。テスト必須** |

これを実際に使える形にすると、着手前の問いは1つになる。

> **取り違えた結果を、出力だけ見て誤りと判別できるか。**

判別できないなら、その抽出は LLM の外に出す。`pr-teeth` の場合、答えは明確に「できない」だった。`owner/repo` を1文字取り違えても、生成される HTML はタイトルも差分もサマリも揃った、どこにも欠落のない完成品になる。**LLM 自身にも、人間の読み手にも、それが誤りだと分かる手がかりが1つも無い。** 出力が「壊れて見える」ことが一切ないため、レビューでも捕まらない。

コードに置くと決めたあとの、具体的なルール。

- **識別子を確定させる場所を1箇所に絞る。** `prspec.parse_one()` の `return` が、利用者の打った文字列が正規の識別子になる唯一の地点である。正規化はすべてそこでやる。下流に散らすと、下流が増えるたびに漏れる。

  ```python
  return {"repo": (owner + "/" + repo).lower(), "number": int(m.group("number"))}
  ```

  この1行に、3つの正規化（`.git` 除去は直前、大文字小文字の畳み込み、`int()` による先頭ゼロの吸収）が集約されている。

- **同一性の次元を数え上げる。** 「同じものを指す別の書き方」がいくつあるかを列挙する。`pr-teeth` では `.git` の有無、先頭ゼロ、大文字小文字の3つだった。1つでも漏らすと、そこだけ別物として扱われる。

- **正規表現を緩くするときは、何を食われるかを考える。** ホスト部を `[^/\s]+` と書くのは自然だが、これは「スラッシュ以外なら何でもホスト」という意味であり、素のパスの先頭を吸い込む。

- **解釈できない入力は捨てずに理由付きで返す。** `parse()` は `(targets, errors)` を返し、`SKILL.md` は `invalid` を必ず出力に載せるよう指示している。黙って落とすと、渡したはずの PR が出力に無いことに気づけない。

- **ドメインの制約を、パーサを狭める根拠に使う。** GitHub のアカウント名はドットを含まない。この事実を `_OWNER` に入れると、失われる正当な入力がゼロのまま、誤解釈の経路が1つ消える。**情報を失わずに狭められる制約は、必ず入れる。**

### 型で縛る学びとの違い（[typed-contract-for-agent-input.md](typed-contract-for-agent-input.md)）

両者は同じパイプラインの**別の段**を守っており、失敗の質も違う。混同すると、どちらか片方しか手当てしていない状態になる。

| | この学び（抽出段） | 型で縛る（検証段） |
| --- | --- | --- |
| 対象 | 利用者が打った**非構造テキスト** | LLM が組み立て終えた**ペイロード（dict）** |
| 段階 | ペイロードが存在する**前** | ペイロードが存在した**後** |
| 守るもの | フィールドの**中身が正しい対象を指すか** | フィールドが**揃っているか・形が正しいか** |
| 失敗の形 | 完成品が出る。**主題が違う** | 空欄になる。セクションが消える |
| 気づけるか | LLM も人間も気づけない | 見れば分かる（`認証のリファクタ推奨 #`） |
| 手段 | テスト済みパーサ + 単一地点での正規化 | dataclass の位置引数・未知キーの拒否・`@property` 導出 |

要するに、**型による検証は「渡された `repo` が `"akm/claude-plugins"` という文字列であること」までは保証するが、それが利用者の指した PR かどうかは何も言わない。** 抽出段が間違っていれば、型検証はすべて通過する。逆に抽出が完璧でも、ペイロードの組み立てでキー名を間違えれば型検証が要る。両方必要である。

なお、両者には共通する上位の原理がある。**入力として受け取らずに済むものは受け取らない。** 型の方では `url` を `repo`+`number` から導出することで注入経路ごと消し、こちらでは URL のホスト部を「照合するだけで捨てる」。取り出すのは `owner`/`repo`/`number` の3つだけで、リンクは `document.GITHUB_HOST` から組み立て直す。

### パーサを増やすこととの関係（`avoid-dual-parser-implementations.md`）

一見矛盾して見えるので明示しておく。あちらは「同じ対象に対する実装を2つ持つな」であり、
こちらは「パーサを1つ書いた」話である。**両者は同じ結論を別の角度から言っている。**

`prspec.py` を書く前、この抽出が無かったわけではない。`SKILL.md` のプロースを読んだ
LLM が、**実行のたびにその場で**解釈していた。つまり既存の実装を持ったまま2つ目を
足したのではなく、**暗黙で毎回揺れる実装を、明示的で1つの実装に置き換えた。**

むしろ置き換え前の状態は、あちらの事例より悪い。PyYAML と自前パーサはどちらも
決定的で、テストを書けば挙動を固定できた。LLM のその場の解釈は**決定的ですらなく、
単体テストで再現する手段が無い。** 同じ穴が実行のたびに引き直される。

まとめると、あちらは「パーサは1つに」、こちらは「その1つは、LLM の実行時の判断では
なくテスト済みのコードであるべき」と言っている。

## Why This Matters

**この判断は、書いた数日のうちに、その判断のもとで書かれたパーサ自身によって正しさを証明された。**

`prspec.py` に対してマルチエージェントのコードレビューを掛けたところ、**3件の誤解釈が実際に再現した。しかも3件とも、このモジュールが防ぐと宣言していたまさにその形**——「打っていないリポジトリに解決され、正しい体裁の解説が出る」——だった（修正: `4621f68`）。

これが意味するところは重い。**この失敗モードを明確に言語化し、それを防ぐためにわざわざコードを書いている最中の著者ですら、3つ取りこぼした。** 注意深さでは足りない、という証拠がここにある。もしこの抽出を `SKILL.md` のプロースに書いていたら、同じ3つの穴が存在した上に、**単体テストで再現する手段が無く、レビューで見つける足場も無かった。** コードに置いたことの価値は「バグが無くなること」ではなく、**バグが再現可能・検証可能な場所に集まること**にある。

### 3件の内訳

**1. ホストがパスの先頭を食う。** `_URL` のホスト部は `[^/\s]+` で、スキームは省略可だった。結果、素のパスの先頭がホストとして消費された。

```
foo/bar/baz/pull/9  →  {'repo': 'bar/baz', 'number': 9}
```

`foo` が消え、**利用者が一度も打っていない `bar/baz` に解決される。** 修正はホストに「スキームが付いている」か「ドットを含む」ことを要求した。

**2. 短縮形へのすり抜け。** `github.com/akm/123` は `_URL`（`/pull/` が無いため）に一致せず、`_SHORT`（`owner/repo/123` を受ける）に落ちた。

```
github.com/akm/123  →  {'repo': 'github.com/akm', 'number': 123}
```

修正は `owner` にドットを許さないこと。GitHub のアカウント名は元々ドットを含まないので、**正当な入力を1つも失わない引き締め**である。

**3. 大文字小文字——最も示唆に富む1件。** `parse_one` は `repo` を打たれたまま返していた。GitHub は `Akm/Claude-Plugins` と `akm/claude-plugins` を同じリポジトリとして扱うが、このコードは扱わなかった。そして下流の `config.resolve_language()` と `scope.classify_files()` は、`config.toml` の `[repos."owner/repo"]` に対する**素の辞書引き**である。実際に再現した結果:

```
config.resolve_language('akm/claude-plugins', cfg)              -> 'ja'
config.resolve_language('Akm/Claude-Plugins', cfg)              -> 'en'   # 設定を取りこぼす

scope.classify_files(['src/auth/token.go'],'akm/claude-plugins',cfg) -> 'must_review'
scope.classify_files(['src/auth/token.go'],'Akm/Claude-Plugins',cfg) -> 'should_review'
```

つまり**打鍵時の大文字小文字の揺れだけで、出力言語とレビュー範囲の分類が黙って変わる。** 利用者が明示的に `must_review` に指定していた `src/auth/token.go` が `should_review` に格下げされる——これは `avoid-dual-parser-implementations.md` で記録した「プラグインの中心的な価値提供が、エラーもクラッシュも出さないまま静かに機能しなくなる」のと同じ壊れ方であり、経路だけが違う。

### 3件目が最も重要な理由

**既存の `/pr-teeth`（巡回）にはこのバグが存在しなかった。** 巡回はリポジトリ名を `gh search prs --json repository` から得る。GitHub API が返す表記であり、**既に正規化済み**である。だから `repos` の辞書引きは常に一致した。

`/pr-teeth-pick` は、**同じ辞書引きに「利用者が打った文字列」を初めて流し込んだコマンド**だった。バグは、識別子の出自が**機械が正規化したもの**から**人間が打ったもの**へ変わったその瞬間に出現した。下流のコードは1行も変わっておらず、何も悪くない。

ここから引き出せる一般則がある。**識別子の消費側は、供給側が正規化済みであることに暗黙に依存して育つ。** その依存は、正規化済みの供給元しか無いあいだは不可視である。新しい供給元を1つ足した瞬間、消費側のすべてが同時に危険になる。「変更していないコードは安全」という直感が、ここでは成り立たない。

さらに細かいが重要な点として、`prspec` は**他の2つの同一性の次元を既に正しく正規化していた**。`.git` サフィックスを剥がし、`int()` が先頭ゼロを畳んでいる。つまり大文字小文字は「考慮していなかった次元」ではなく、**既に認識していた責務の中の、一貫性の穴**だった。責務を自覚していても、その次元を数え上げていなければ漏れる。

## When to Apply

次のいずれかに当てはまるなら、抽出をコードに置く。

- **非構造テキストから識別子を取り出しており、取り違えの結果が完成品として出る。** レポート生成、通知、要約、コード生成——出力が「それらしく」完成するものはすべてここに入る。逆に、取り違えが即座に例外や404になるなら、LLM に任せる余地はある。

- **識別子の出自が、機械が正規化したものから人間が打ったものに変わった。** これは単独でチェック可能な明確な合図である。既存の消費側コード（辞書引き、キャッシュキー、パス組み立て、ID 比較）を**1つ残らず**洗い出し、正規化の前提に依存していないか確かめる。API・DB・既存 ID から来ていた値に、フォーム入力・CLI 引数・チャットのプロンプト・貼り付けた URL という経路を追加するときが、その瞬間である。**下流を変更していないことは、安全の根拠にならない。**

- **同じものを指す表記が複数ある。** 大文字小文字、サフィックス（`.git`、末尾スラッシュ）、先頭ゼロ、`www.` の有無、URL エンコード、Unicode 正規化など。次元を紙に書き出して数える。1つでも漏れれば、そこだけ別物として扱われる。

- **抽出結果が、設定の引き当てや権限判定のキーになる。** キーが1文字違えば設定は「無い」ものとして既定値に落ちる。しかも既定値は正常動作に見える。

逆に、LLM に任せてよい場面もある。**抽出結果がすぐ利用者の目に触れ、誤りが自明な場合。** 例えば会話の中で「どの PR の話ですか」と確認しながら進めるなら、取り違えはその場で訂正される。今回のように**無人で走り切って成果物だけが残る**経路では、その訂正の機会が存在しない。

## Examples

### Before: ホストを緩く受ける（`4621f68` 以前）

```python
_URL = re.compile(
    r"^(?:https?://)?[^/\s]+/"
    r"(?P<owner>[^/\s]+)/(?P<repo>[^/\s]+)/pull(?:s)?/(?P<number>\d+)"
    r"(?:[/?#].*)?$"
)

# owner/repo#123 と owner/repo/123。`#` は shell で消えやすいので後者も受ける。
_SHORT = re.compile(r"^(?P<owner>[^/\s#]+)/(?P<repo>[^/\s#]+)(?:#|/)(?P<number>\d+)$")
```

`[^/\s]+` は「スラッシュと空白以外なら何でも」なので、ホストにもオーナーにも何でも入る。

```
foo/bar/baz/pull/9  →  {'repo': 'bar/baz',        'number': 9}
github.com/akm/123  →  {'repo': 'github.com/akm', 'number': 123}
```

### After: ドメインの制約でパーサを狭める

```python
# owner / repo に許す文字。GitHub のアカウント名は英数字とハイフンだけで、
# **ドットを含まない**。この制約が「ホストらしい文字列を owner と誤認しない」
# 保証になっている。
_OWNER = r"[A-Za-z0-9](?:[A-Za-z0-9-]*[A-Za-z0-9])?"
_REPO = r"[A-Za-z0-9._-]+"

# **ホストは必ずドットを含むか、スキームが付いていること**を要求する。
# ここを `[^/\s]+` と緩くすると、`foo/bar/baz/pull/9` のような素のパスの先頭が
# ホストとして食われ、`bar/baz` という**打っていないリポジトリ**に解決される。
_URL = re.compile(
    r"^(?:https?://[^/\s]+|[^/\s]*\.[^/\s]+)/"
    r"(?P<owner>" + _OWNER + r")/(?P<repo>" + _REPO + r")/pull(?:s)?/(?P<number>\d+)"
    r"(?:[/?#].*)?$"
)
```

`_REPO` はドットを許し（`my-org/my.repo` は実在する）、`_OWNER` は許さない。**同じ「ドット」でも、位置によって意味が違う**ことを型に落としている。

### Before / After: 識別子の確定

```python
# Before
return {"repo": owner + "/" + repo, "number": int(m.group("number"))}

# After
return {"repo": (owner + "/" + repo).lower(), "number": int(m.group("number"))}
```

`.lower()` の1語だが、これが入る場所は1箇所しかない。下流（`config.resolve_language`、`scope.classify_files`）を触っていない点が重要で、**修正は識別子が生まれる地点にのみ入る。**

### 実際に再現した下流への影響

`config.toml` が次のとき:

```toml
language = "en"

[repos."akm/claude-plugins"]
language = "ja"
must_review = ["src/auth/**"]
```

修正前の挙動（実測値）:

| 打った文字列 | 解決される repo | 出力言語 | `src/auth/token.go` の分類 |
| --- | --- | --- | --- |
| `akm/claude-plugins#1` | `akm/claude-plugins` | `ja` | `must_review` |
| `Akm/Claude-Plugins#1` | `Akm/Claude-Plugins` | `en` | `should_review` |

同じ PR を指しているのに、**言語もレビュー範囲も変わる。** どちらの出力も完成品として正常に見える。

### 修正の品質基準

回帰テストを5件追加し、**ソース側の修正だけを戻すと確実に落ちる**ことを確認している（テストは残したまま）。テストのコメント自体が失敗の形を記録している。

```python
def test_hostlike_prefix_does_not_become_the_repo(self):
    # 素のパスの先頭がホストとして食われると、打っていないリポジトリに
    # 解決される（`foo/bar/baz/pull/9` -> `bar/baz`）。これが起きると
    # 「別の PR の解説が正しい体裁で出る」= 読み手が誤りに気づけない。
    for bad in ("foo/bar/baz/pull/9", "orgs/owner/repo/pull/5"):
        with self.assertRaises(prspec.InvalidSpec):
            prspec.parse_one(bad)
```

**引き締めが正当な入力を壊していないことも実測で確認した。** 実際に現れる14の書き方はすべて通り、誤解釈の3形と、元から弾いていた issue / commit / compare の URL は拒否される。

| 通る（14形） | 拒否（6形） |
| --- | --- |
| `owner/repo#123` / `owner/repo/123` | `foo/bar/baz/pull/9` |
| `https://github.com/o/r/pull/9` とその派生（`/files`、`#discussion_r1`、`?w=1`、末尾 `/`） | `orgs/owner/repo/pull/5` |
| `github.com/o/r/pull/9`（スキーム無し）、`www.` 付き | `github.com/akm/123` |
| `https://github.com/o/r.git/pull/9` | `https://github.com/o/r/issues/9` |
| `my-org/my.repo#3`（repo のドット） | `https://github.com/o/r/commit/abc` |
| `Akm/Claude-Plugins#1` → `akm/claude-plugins`、`owner/repo#007` → `7` | `https://github.com/o/r/compare/a...b` |

`https://ghe.example.com/o/r/pull/5` も通るが、これは**ホストを照合して捨てている**だけで、GHE 対応ではない。リンクは `document.GITHUB_HOST`（公開 github.com）から組み立てられるため、GHE の URL を貼ると同名の公開リポジトリを指す。この点はモジュールの docstring に明記してあり、対応するにはホストを設定に持たせ、戻り値に載せて `gh --hostname` まで通す必要がある。**今は `gh` が引けずエラーになる**——つまり loud に失敗するので、この学びが問題にしている「静かに間違う」形にはなっていない。

### 残った課題

- **ホストを捨てる設計は、この学びの原則から見ると借金である。** ホストは識別子の一部でありながら、抽出されずに落とされている。GHE 対応の時点で、`{repo, number}` は `{host, repo, number}` にならなければならない。現状で救われているのは、その先の `gh` が失敗してくれるからに過ぎず、**設計として正しいのではなく、たまたま loud な失敗に守られているだけ**である。
- **正規化は `parse_one` に閉じているが、下流はそれを知らない。** `config.resolve_language()` も `scope.classify_files()` も、渡される `repo` が小文字である保証を型では持っていない。巡回経路（`gh` 由来）と番号指定経路（`prspec` 由来）の2つがたまたま両方とも小文字を渡しているだけで、**3つ目の供給元が増えれば同じバグが再発する。** 本来は識別子を単なる `str` ではなく型にして、正規化済みであることを型で運ぶべきだった。今回はこの一段手前——「確定させる場所を1箇所に絞る」——で止めている。
