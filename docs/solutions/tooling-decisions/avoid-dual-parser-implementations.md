## Context

`pr-teeth` は人間が手で編集する設定ファイルを必要とする Claude Code プラグインである。この手書き設定というユースケースには、素直に考えれば YAML が第一候補になる。コメントが書け、階層構造を表現でき、設定ファイルの表現力として十分だからだ。

しかし `pr-teeth` にはハウスルールとして「stdlib のみで動く（ユーザーに pip install を強いない）」という制約があった。ここで問題になるのが、**PyYAML は Python 標準ライブラリに含まれない**という事実である。YAML を読むには外部依存が要る。

この制約と要件の衝突に対して選ばれた妥協案が、デュアルバックエンド構成だった。PyYAML がインストールされていればそれを使い、なければプラグインに同梱した約103行の自前サブセットパーサーにフォールバックする。

```python
try:
    import yaml
    _HAS_YAML = True
except ImportError:
    yaml = None
    _HAS_YAML = False
```

このとき手を抜いたわけではない。値のないキー（`key:` のみの行）を PyYAML は `None` として解釈するが、自前パーサーの初期実装ではそれが `{}` になり得るため、両バックエンドの解釈を揃える正規化ステップまで用意した。テストも両方のバックエンド構成で実行していた。それでも壊れた。

## Guidance

**ルール: 「あるフォーマットを読むために、ライブラリがあればそれを使い、なければ自前の簡易パーサーで代替する」という設計は避ける。標準ライブラリが最初から解釈できる別フォーマットに要件そのものを寄せられないか、シムを書く前に必ず確認する。**

シムを書きたくなったら、着手前に次を確認する。

- 対象フォーマット（YAML など）に近い意味論を持ち、かつ標準ライブラリがネイティブに扱える別フォーマットは存在しないか（例: TOML と `tomllib`、JSON と `json`）。
- そのフォーマットへの乗り換えで失われる表現力は、実際の設定ファイルの中身にとって本当に必要か。
- 乗り換えの代償として許容できる制約（対応 Python バージョンの引き上げなど）はあるか、あるならそれをドキュメントに明記できるか。

`pr-teeth` の場合、`tomllib` が標準入りしたのは Python 3.11 からであり、これを採用することは Python 3.11 以上を必須にするという代償を伴う。この代償は受け入れた上で、README の前提条件（prerequisites）に明記した。「代償がある」こと自体は問題ではない。代償を認識せず、二重実装の恒久的なメンテナンスコストを暗黙に払い続けることが問題である。

## Why This Matters

二重実装が危険なのは、単に「面倒だから」ではない。次の2つの性質が組み合わさると、通常のテストプラクティスでは検出できないバグになるからだ。

**1. 分岐は静かに発生し、クラッシュではなく「挙動の違い」として現れる。**
二つのパーサーが同じ入力に対して異なる結果を返しても、多くの場合どちらも例外を投げずに「それらしい」値を返す。呼び出し側はその値を正しいものとして扱い続ける。

**2. 分岐は環境依存であり、テストスイートが全環境を代表しない。**
どちらのバックエンドが使われるかは、そのマシンに PyYAML がインストールされているかどうかで決まる。開発者のマシンにはインストールされていて、ユーザーのマシンにはインストールされていない、あるいはその逆——という状況が普通に起こる。テストは「その時そのマシンで使われたバックエンド」しか検証しない。

`pr-teeth` で実際に起きたのはこうだ。次は妥当な YAML である。

```yaml
repos:
  o/r:
    must_review:
    - "src/auth/**"
```

リスト項目が親キーと同じインデント幅に置かれている（YAML では合法な書き方）。PyYAML はこれを問題なくパースする。しかし自前パーサーは `ValueError: 'ignore' の入れ先がマッピングではありません` を送出した。

さらに悪いことに、この例外は fail-soft なローダーに捕捉され、警告に変換された上で `{}` が返された。つまり **レビュー対象設定全体が黙って空になった**。

これを製品の言葉で言い直すと深刻さがわかる。`pr-teeth` は変更ファイルを must_review / should_review / ignore に分類するのが中核機能である。設定が失われた結果、ユーザーが明示的に `must_review` に指定していたファイル（`src/auth/token.go`）が `should_review` に格下げされた。プラグインの中心的な価値提供が、エラーもクラッシュも出さないまま静かに機能しなくなっていた。

そして決定的だったのは、**69個のテストが両方のマシンでパスしていた**という事実である。PyYAML がインストールされている環境では設定は正しく動作し、されていない環境では動作しなかった。開発者のマシンとユーザーのマシンで結果が食い違っていても、テストスイートはそれを検出できなかった。テストはその時使われたバックエンドしか通らないからだ。

## When to Apply

この教訓が一般化するのは、「ライブラリ X が使えるならそれを使い、使えなければ自分のミニ実装で代替する」という設計を、**フォーマット（構文・データ表現）** に対して行おうとしている場面である。設定ファイル、シリアライズ形式、プロトコルのパースなど、入力の構文解釈をシムしようとしているなら、まず標準ライブラリに寄せられないか検討すべきである。

一方で、これが当てはまらない正直な例外もある。標準ライブラリに隣接する代替フォーマットが存在せず、かつフォーマット自体が自分ではコントロールできない外部契約によって固定されている場合（例: 相手システムが吐き出す固定の YAML/XML を読まざるを得ない、規格として YAML が指定されている等）は、フォーマットを変える選択肢自体がない。その場合は二重実装ではなく、単一の実装（できれば外部ライブラリへの依存を許容する、あるいは stdlib で完全に賄える範囲まで要件を切り詰める）を選び、フォールバックによる分岐そのものをなくす方向で設計するべきである。

## Examples

**壊れた入力（妥当な YAML）:**

```yaml
repos:
  o/r:
    must_review:
    - "src/auth/**"
```

**各バックエンドの挙動:**

| バックエンド | 結果 |
|---|---|
| PyYAML | 正常にパースし、`must_review: ["src/auth/**"]` を返す |
| 自前パーサー（約103行） | `ValueError: 'ignore' の入れ先がマッピングではありません` を送出 → fail-soft ローダーが捕捉し警告化 → `{}` を返す |

**移行後の TOML 設定（例）:**

```toml
[repos."owner/repo"]
must_review = ["src/auth/**"]

[repo_defaults]
should_review = ["**/*.go"]
```

リポジトリ名にスラッシュが含まれるため `[repos."owner/repo"]` のようにクォートが必要になる。また、リポジトリごとのデフォルト設定は `[repos.defaults]` ではなく `[repo_defaults]` という独立したテーブル名にした。これにより、`defaults` という名前のリポジトリが実在した場合でもキーが衝突しない。

**行数の変化:**

この移行の時点で `store.py` は216行から103行に縮小した(約140行の削減)。削除されたのは自前パーサーそのものだけでなく、二つのバックエンドの挙動を突き合わせて監視するためだけに存在していた等価性テスト群も含まれる。(その後このファイルには別の目的で機能が追加されたため、現在の行数はこれより多い。ここで意味があるのは削減量であって現在値ではない。)
