# 実装依頼: プラグイン `pr-teeth`(GitHub レビュー依頼PRを噛み砕いて解説)

> このドキュメントは Claude Code に渡す実装依頼です。
> 既存のプラグイン配布リポジトリ(マーケットプレイス)に、新しいプラグイン **`pr-teeth`** を追加する形で実装してください。
> 名前の由来: 硬くてとっつきにくい(コンテキスト依存が強い/技術スラングが多い)PRを、歯で噛み砕くように
> 飲み込める形にほぐす、というコンセプト。噛み砕いて理解できた語は「栄養」として用語集に蓄積される(第8節)。
> まずは **on-demand(手動呼び出し)で動くこと**をゴールにし、定期実行(スケジュール)は後続フェーズとします。

---

## 1. 目的 / ゴール

自分にレビュー依頼が来ている GitHub の PR を巡回し、**その言語圏のエンジニアが初見で理解できる解説**を、
ユーザーが設定した**出力言語**で作って通知する skill を作る。

- 対象一覧は次のGitHub検索と同じ:
  `is:pr review-requested:@me state:open archived:false`
  (Web: `https://github.com/pulls/reviews?q=is%3Apr+review-requested%3A%40me+state%3Aopen+archived%3Afalse`)
  - これは**巡回(`/pr-teeth`)の対象定義**。番号やURLで明示的に指定して読む経路は
    別コマンドに切り出した(第16節)。そちらは open/closed を問わない。
- 各PRを丁寧に精査し、**文脈依存の語は関連ソース・ドキュメントを検索して裏取り**してから解説する。
- **リポジトリごとに設定した「レビュー範囲」に照らして、そのPRがどの範囲に該当するかを示す**(第7節)。
- 説明が必要な用語は、**ユーザー単位の用語集**で管理し、理解が進むにつれ説明を減らす(第8節)。
- 出力は**ローカルのブラウザで開ける単一HTML**とし、関係や構造を**図(Mermaid)**で補う(第9節)。
- **出力言語はユーザーが設定できる**(第5節)。既定は日本語。設定はユーザー全体の既定と
  リポジトリ単位の上書きの2段階で解決する。

### 言語ルール(出力言語に対して適用)

- 解説は設定された出力言語で書き、不必要な他言語の混入は避ける。
  (出力言語が日本語なら、不必要な英語混じりを避ける。)
- ただし「説明不要」と判断した用語(初期値として SSoT, PoC, CI, PR, diff, API, OSS 等。以降は第8節の用語集で成長)は
  原語のまま使う。**これは出力言語が何であっても同じ**で、原語表記のまま説明を省く。
- 固有名詞・識別子(リポジトリ名、ファイルパス、関数名、コマンド、ラベル名など)は翻訳せず原文のまま扱う。
- 出力言語が変わっても、解説の構成・粒度・裏取りの厳しさは変えない。

## 2. 進め方(フェーズ)

- **フェーズ1(今回のゴール): on-demand skill** — 手動で呼ぶと、その時点でオープンなレビュー依頼PRを全件解説。
- **フェーズ2(後続): 定期実行** — 同じ skill を1時間ごとのスケジュールから `mode=changes-only` で呼び、差分だけ通知。
  → skill 本体のロジックは共通化し、スケジュール側は薄く保つ(ロジックの二重化を避ける = SSoT)。

## 3. 成果物と配置

- **プラグイン名: `pr-teeth`**。既存の配布リポジトリ(マーケットプレイス)に新規プラグインとして追加。
- 中身は skill(例: `<plugin-root>/pr-teeth/skills/pr-teeth/SKILL.md`。ディレクトリ規約はリポジトリに合わせる)。
- 提供コマンド(名前は任意。**`review` は名前に含めない** — レビューはユーザー自身が行うため):
  - `/pr-teeth` … 本体(レビュー依頼PRの巡回・噛み砕き解説)
  - `/pr-glossary` … 用語ポートフォリオの表示・編集(第8節)
- `SKILL.md` frontmatter:
  - `name`: 例 `pr-teeth`
  - `description`(自動トリガー用、日本語+英語キーワード): 例
    > 自分にレビュー依頼が来ているGitHubのPRを巡回し、各PRを差分とチェックアウトしたブランチまで見て精査し、リポジトリ別の範囲設定に照らして、硬くてとっつきにくい部分を噛み砕いて、設定した出力言語(既定: 日本語)で分かりやすい解説をHTMLで作る。Use when: レビュー依頼のPRを噛み砕いて確認したい, review-requested PRs, PR巡回, PRの内容を分かりやすく説明, explain review-requested PRs, /pr-teeth。
    - `description` 自体は skill の発見用テキストなので、出力言語設定の影響を受けない(固定文言でよい)。

## 4. 実行環境と前提

- 実行ランタイムは Cowork(Claude アプリ)/ Claude Code CLI の双方を想定。skill 実行時に次が使える前提:
  - シェル(`git` 利用可。`gh` は未インストールなら `apt-get install -y gh`、もしくは `curl` で REST API を直接)
  - ローカルファイルシステム(設定・状態・用語集の置き場所。第5節)
  - ファイル配信、プッシュ通知
- 通知は環境に応じて**フォールバック**できるように書く(プッシュ通知が無い環境ではHTMLのパス案内で代替)。

## 5. 設定ファイルと出力言語

### 5.1 設定ディレクトリ

設定・状態・用語集は**ローカルファイルシステム**に置く。Google Drive などのクラウド連携には依存しない。

- 設定ディレクトリ: `$HOME/config/<plugin-source>/pr-teeth/`
  - `<plugin-source>` は**このプラグインの配布元**を `<host>/<owner>/<repo>` の形で表したもの。
    プラグイン配布元ごとに設定が一意に分かれ、他のマーケットプレイス由来の同名プラグインと衝突しない。
  - このリポジトリから配布する場合の実パス: `$HOME/config/github.com/akm/claude-plugins/pr-teeth/`
- **`<plugin-source>` はコードにリテラルで書く(実行時に推定しない)。**
  - 理由: 実行中のプラグインに配布元を伝える**公式な手段が無い**ため。
    `${CLAUDE_PLUGIN_ROOT}`(公式。SKILL.md 内で展開される)はインストール先パスを返すだけで、配布元は含まない。
    キャッシュのパス構造から辿って `~/.claude/plugins/known_marketplaces.json` を引けば逆引きは可能だが、
    **どちらも非公式・内部実装**であり、変わると設定と用語集を見失う(ユーザーには「学習が消えた」ように見える)。
  - プラグインは自分の配布元をビルド時に知っているので、リテラルで持てば十分であり壊れない。
  - **fork して別のマーケットプレイスから配布する場合は、この値を fork 側の配布元に書き換える。**
    書き換え箇所は `scripts/prteeth/config.py` の `PLUGIN_SOURCE` の**1箇所だけ**とし、
    書き換え箇所であることをコメントで明示する。SKILL.md 側には書かない
    (3つの SKILL.md に散ると書き換え漏れが起き、コマンドによって別の設定ディレクトリを
    見る状態になる。利用者からは「学習が消えた」ように見え、原因が分かりにくい)。
- 環境変数 `PR_TEETH_CONFIG_DIR` が設定されていれば、それを設定ディレクトリとして優先する。
  (リテラル値が実環境に合わない場合の逃げ道もこれで確保する。)
- ディレクトリ・ファイルが無い場合は**エラーにせず既定値で動く**(初回実行を設定作業でブロックしない)。
  必要に応じて雛形を作成し、その旨を出力に添える。

配置するファイル(詳細は第11節):

| ファイル | 役割 |
| --- | --- |
| `config.toml` | 設定一式(出力言語・リポジトリ別のレビュー範囲と言語)。第5.2節・第7節 |
| `glossary.json` | ユーザー用語集。第8節 |
| `state.json` | 通知済み状態(フェーズ2)。第11節 |

### 5.2 出力言語の設定

設定は `config.toml` 1枚にまとめる。ユーザー全体の既定も、リポジトリ別の上書きも同じファイルに書く。

```toml
# 出力言語(ユーザー全体の既定)。BCP 47 の言語タグ(ja, en, ko, zh-Hant ...)
language = "ja"
```

**形式に TOML を使う理由:** 設定はユーザーが手で書くので構造化テキストが要るが、YAML は
標準ライブラリに無い。当初は PyYAML があればそれを使い、無ければ同梱の簡易パーサに落とす
二重実装にしたが、両者を永続的に一致させ続けるのは現実的でなく、実際に食い違った
(リスト項目を親キーと同じインデントに置く正当な YAML を簡易パーサが拒否し、レビュー範囲設定が
丸ごと無効化された)。しかも PyYAML の有無で挙動が変わるため、利用者のマシン構成によって
発現する不具合になっていた。`tomllib` は Python 3.11 以降の標準ライブラリなので、
依存ゼロのまま実装を1つにできる。

- **未設定・ファイルなしの場合の既定は `ja`(日本語)。**
- 値は BCP 47 の言語タグで受け取る。skill 側で対応言語を列挙して制限はしない
  (解説文を書くのは Claude 自身なので、書ける言語ならそのまま通す)。

### 5.3 言語の解決順序(優先度: 高 → 低)

1. **実行時引数** — `/pr-teeth lang=en`(第10節)。その実行にだけ効き、設定ファイルは書き換えない。
2. **リポジトリ単位設定** — `config.toml` の `[repos."<owner>/<repo>"]` の `language`(第7節)。
   そのリポジトリのPRの解説だけがこの言語になる。
3. **ユーザー既定** — `config.toml` の最上位 `language`。
4. **組み込み既定** — `ja`。

- 解説本文・レビュー範囲サマリ・用語解説・プッシュ通知・`/pr-glossary` のダッシュボードは、
  すべて解決された出力言語で書く(用途別に言語を分けることはしない)。
- **プッシュ通知は複数リポジトリのPRを1通にまとめるため、リポジトリ単位の言語がPRごとに異なりうる。**
  通知全体の地の文(「レビュー依頼 N件」など)は**ユーザー既定の言語**で書き、各PRの1行要約は
  そのPRの解決言語で書く。
- HTMLの `<html lang="...">` には、そのページの主たる言語(ユーザー既定、実行時引数があればそれ)を入れる。
  リポジトリ単位で言語が異なるセクションには、その要素に `lang` 属性を付ける。

## 6. 認証(読み取り専用PAT)

- `review-requested:@me` はトークン所有者本人としての認証が必要。**備え付けの環境トークンでは不可**
  (repo 限定スコープに縛られ、グローバル検索が弾かれることを確認済み)。
- ユーザー本人の **読み取り専用 PAT**:
  - Fine-grained: `Contents: Read-only`, `Pull requests: Read-only`, `Metadata: Read-only`(対象リポジトリにアクセス可)
  - fine-grained で `review-requested:@me` 検索が空振りする場合は `repo`(read相当)の classic token にフォールバック
- **トークンの受け渡し(平文をプロンプト/コードに書かない)。次の順に探す:**
  1. 環境変数 `GITHUB_TOKEN` … 値を直接使う。
  2. 環境変数 `GITHUB_TOKEN_FILE` … そのファイルの中身を使う。
  3. `gh auth token` … 正常終了したらその出力を使う。
  4. どれも取れなければ、その旨だけ通知して終了する。
- **取得したトークンは前後の改行・空白を trim する。** ファイルや `gh auth token` の出力には
  末尾に改行が付く。そのまま HTTP ヘッダに入れると認証が通らず、原因も分かりにくい。
  空文字だけの値は「未設定」とみなして次の段に進む。
- `GITHUB_TOKEN_FILE` が指定されているのに読めない場合は、**理由を添えて伝える**
  (設定ミスなので黙って次に進むと原因が分からない)。読めないときも後続の段は試す。
- **トークンを設定ディレクトリに置く経路は設けない。** 設定ディレクトリに秘密情報が混ざると、
  バックアップや同期の対象にしたときに漏れる。ファイルで渡したい場合は
  `GITHUB_TOKEN_FILE` で任意の場所を指す。
- **トークンの値はログ・生成物・通知・コミットに一切出さない。** gh には環境変数経由で渡す。
  表示に使ってよいのは「どこから取れたか」だけ。

## 7. リポジトリ別設定(レビュー範囲・出力言語)

開発者は複数リポジトリのPRをレビューするが、リポジトリごとに自分の役割・見るべき範囲が違う。
これを**リポジトリごと**に、**ディレクトリ/ファイル単位(glob)**で設定できるようにする。
また、リポジトリによって**読みたい言語が違う**(社内リポジトリは日本語、OSSは英語など)ため、
出力言語もリポジトリ単位で上書きできるようにする。

- これは「そのリポジトリでの、そのユーザー個人の役割・好み」を表す設定なので、リポジトリ本体ではなく
  **ユーザーの設定**として持つ(置き場所: 設定ディレクトリの `config.toml`。第5.1節)。
  対象リポジトリ内に同等ファイル(例 `.github/review-scope.yml`)があれば、そちらを優先的に読む対応をしてもよい(任意)。
  ただし**言語設定はユーザー個人の好みなので、リポジトリ内ファイルからは読まない。**
- 3つの範囲を定義する:
  - `must_review`(レビュー必須)
  - `should_review`(見たほうが良い)
  - `ignore`(見なくてよい)
- 設定例:

  ```toml
  # リポジトリ別設定の既定値
  [repo_defaults]
  unmatched = "should_review"   # どの範囲にも一致しない変更の既定分類

  [repos."owner/service-api"]
  must_review  = ["src/payments/**", "src/auth/**"]   # レビュー必須
  should_review = ["src/api/**"]                      # 見たほうが良い
  ignore = ["docs/**", "**/*.md", "test/fixtures/**"] # 見なくてよい

  [repos."owner/frontend"]
  must_review = ["src/components/checkout/**"]
  ignore = ["**/*.stories.tsx"]

  [repos."someorg/oss-library"]
  language = "en"               # このリポジトリのPRだけ英語で解説する
  should_review = ["src/**"]
  ```

  リポジトリ名は `owner/repo` 形式で `/` を含むため、テーブル名は `[repos."owner/repo"]` と
  引用符で囲む。既定値のテーブルを `[repo_defaults]` としているのは、**リポジトリ別設定の既定値**
  であることを名前で示すため(`[repos.defaults]` だと `defaults` という名前のリポジトリと区別できない)。

- `language` を書かないリポジトリは最上位の `language`(ユーザー既定)に従う(第5.3節)。
- **判定ルール**:
  - PRの変更ファイル一覧(`gh pr view --json files` 等)を取得し、各ファイルを glob で分類。
  - 1ファイルが複数範囲に一致したら **優先度 must_review > should_review > ignore** で最上位を採用
    (重要な範囲を ignore で誤って隠さないため)。
  - どの範囲にも一致しないファイルは `repo_defaults.unmatched`(既定 `should_review`)として扱う。
  - リポジトリ自体が未設定なら、全ファイルを `should_review` 扱い(安全側)。
- **出力への反映**:
  - 各PRの解説に「レビュー範囲サマリ」を付ける。例:
    「このPRの変更 12ファイルのうち、**レビュー必須**(src/auth/)3、見たほうが良い(src/api/)5、見なくてよい(docs/)4。
     → 必須範囲に該当あり。src/auth/ の変更を中心に確認を推奨。」
  - **深掘り(第10節ステップ5)や文脈依存語の裏取りは、must_review / should_review の範囲を中心に行う。**
    ignore のみの変更は軽く要約する程度でよい。
  - **PRの並び順は「must_review に該当 → should_review のみ → ignore のみ」の優先度で。**
    ignore のみのPRは1行要約に畳んでよい(リンクは残す)。

## 8. ユーザー用語集(学習が進むと説明が減る)

「説明が必要な用語」は使い込むほど理解が増え、いずれ説明不要になる。これを**ユーザー単位**で管理する
(リポジトリ単位ではない。全リポジトリ横断で1つ)。置き場所: 設定ディレクトリの `glossary.json`(第5.1節)。

- **各用語のエントリ(概念)**:
  - `term`(表記)、`status`(`new` / `learning` / `known`)
  - `definitions`(**言語ごとの説明文**。キーは言語タグ、値がその言語での定義)
  - `provenance`(初出の repo / PR / ファイル・行など根拠)
  - `occurrences`(通算出現回数)、`first_seen` / `last_seen`、`known_since`(理解済みにした日時)
  - 任意メモ。**同じ表記でもプロジェクトによって意味が違う語(多義語)は、文脈別の定義を併記**できるようにする。
  - 初期値(seed)として、現在の「流通した英語」(SSoT, PoC, CI, PR, diff, API, OSS 等)を `known` で登録。
- **言語との関係**:
  - **`term`・`status`・`occurrences` は言語非依存**で、エントリごとに1つ。
    「その語を理解しているか」は出力言語によって変わらないため、**出力言語を切り替えても学習の進み具合は共有される。**
    (`known` にした語は、英語で出力しても日本語で出力しても同じように説明が省かれる。)
  - **説明文だけが言語ごと。** 出力言語 L で解説するとき、`definitions[L]` があればそれを使う。
    無ければその場で L の説明を生成し、`definitions[L]` として書き戻す(次回から再利用)。
  - エントリ例:

    ```json
    {
      "term": "reconciliation loop",
      "status": "learning",
      "definitions": {
        "ja": "あるべき状態と実際の状態を突き合わせて差分を埋め続ける処理。",
        "en": "A loop that continuously compares desired state to actual state and closes the gap."
      },
      "occurrences": 4,
      "provenance": "owner/service-api#123 src/controller/sync.go:88"
    }
    ```
  - 多義語の文脈別定義も、各文脈の下に言語ごとの説明を持たせる(同じ入れ子の形を使う)。
- **ステータス遷移**:
  - 未登録の語に遭遇 → `new` として登録し、**フルで説明**。
  - 出現が一定回数(例: 通算3回)を超える → `learning` に自動昇格。**説明は1〜2行の軽い再掲**に短縮。
  - `known` への昇格(=以降は説明省略)は**確定に人の確認を挟む**。次のいずれか:
    1. **明示指定**: `/pr-glossary` 上でユーザーが「理解済み」にする(これが最終的な真実)。
    2. **会話からの推定→提案**: インタラクティブ実行時、ユーザーがその語を自分から正しく使う/別の説明に用いる/
       その語を前提にした踏み込んだ質問をする等の兆候があれば、Claude が「この語は理解済みにしますか?」と**提案**し、
       ユーザーの承認で確定。**推定だけで自動確定はしない(偽陽性で説明が勝手に消える事故を防ぐ)。**
  - 降格は自動で行わない(ユーザーが望んだ時のみ)。
- **説明挙動はステータス駆動**: `new`=フル説明 / `learning`=軽い再掲 / `known`=省略(SSoT等と同じ扱い)。
- **無人(スケジュール)実行時の扱い**: 会話が無いので会話推定は行わない。用語集(登録済み内容・出現回数・明示指定)
  と機械的シグナルのみで判断する。会話推定による昇格提案はインタラクティブ実行時に限る。
- **ポートフォリオ表示(`/pr-glossary`)**:
  - 用語集をHTMLダッシュボードで表示。`known`(件数・理解済み日・定義・出てきたリポジトリ)、`learning`(進捗)、
    最近の `new` を並べ、理解済み語数の推移も見えるようにする(ユーザーが到達度をポートフォリオとして確認できる)。
  - この画面(またはコマンド引数)から、用語のステータス変更(理解済みにする/戻す)、定義の編集ができる。
  - 画面の地の文は**ユーザー既定の出力言語**(第5.3節)で書く。各用語の定義はその言語の `definitions[L]` を表示し、
    未生成なら他言語の定義があることを示して切り替えられるようにする(既存の定義を隠さない)。

## 9. HTML出力と図(diagram)

- 解説は**自己完結の単一HTMLファイル**として出力し、**ローカルのブラウザで開いて確認**できるようにする。
  - CSS/JS はインライン。ユーザーに配信し、ダウンロードしてローカルで開ける状態にする。読みやすいスタイルを付ける。
  - 画像は data: URL で埋め込む等、外部依存を最小化(オフラインでも開けることを優先)。
- **図の生成**: PRとIssueの関係や、文脈上に現れる構造・関係を図で示す。**Mermaid** を用い、HTML内でクライアントサイド描画する。
  - Mermaid.js は CDN(cdnjs)から読み込む。ライブラリが 3.2MB あり、図は補助でしかない
    (単純なら省略する)ため、PR ごとに埋め込むのは割に合わないと判断した。
  - **改竄検知のため `integrity`(SRI)を付ける。** バージョンを上げるときは
    SRI も必ず更新する(不一致だとブラウザが読み込みを拒否し、図が出なくなる)。
  - **読み込めない場合(オフライン・CDN 障害・SRI 不一致)でも本文は読める**ようにする。
    図は Mermaid のコードがそのまま `<pre>` で表示される形にフォールバックさせる。
  - 図のラベルは PR 由来の文字列を含みうるため、`securityLevel: 'strict'` と
    `htmlLabels: false` を明示する(ライブラリの既定値に依存しない)。
  - **図が無い場合は CDN を含む外部参照を一切出さない**(その場合は完全にオフラインで開ける)。
  - 図の対象・種類は内容に応じて適切なものを選ぶ:
    - **PR/Issue関係図**: そのPRが close / 関連する Issue、依存・ブロック関係、関連PR(stacked / 連番)など → flowchart / graph。
    - **構造・フロー図**: 深掘りで判明した、変更が関わるコンポーネント/モジュールの関係、処理の流れ、主要なエンティティ関係など
      → 関係は flowchart、順序のある流れは sequenceDiagram、構造は classDiagram / ER。
  - **ノードのラベルはそのPRの出力言語で書く**(識別子・ファイル名などの固有名は原文のまま)。
    図は小さく読みやすく保つ(1枚に詰め込みすぎない)。
- **省略の判断**: 単純な場合は図を省略してよい。例: **1つの Issue と 1つの PR が1対1で、他の Issue/PR に関係せず、
  構造的にも図で示すほどの関係が無い場合**。図は理解を助ける時だけ付け、無理に生成しない。
- `/pr-glossary` のポートフォリオも同様にHTMLで表示する。
- Cowork ではファイル配信し、デスクトップ接続時は artifact としても残す。CLI 実行時はHTMLファイルをローカルに保存してパスを案内する。

## 10. 動作仕様(skill 本体)

引数:
- **モード**
  - `mode=full`(既定 / on-demand): 現在オープンのレビュー依頼PRを**全件**解説。
  - `mode=changes-only`(フェーズ2のスケジュール用): 前回以降の**新規・更新分のみ**。
- **言語**
  - `lang=<言語タグ>`(任意): その実行の出力言語を上書きする(第5.3節の最優先)。
    指定時は**リポジトリ単位設定より優先し、全PRをこの言語で解説する**。設定ファイルは書き換えない。

処理の流れ:

1. **認証取得**(第6節)。無ければ通知して終了。
2. **設定・状態の読み込み** — 設定ディレクトリ(第5.1節)から `config.toml`(第5.2節・第7節)、
   `glossary.json`(第8節)、`state.json`(第11節)を読む(無ければ空/既定)。
   ここで**ユーザー既定の出力言語**を確定する(第5.3節)。
3. **PR一覧取得(軽い段)** — `is:pr review-requested:@me state:open archived:false` を検索し、各PRの
   `owner/repo`, `number`, `title`, `author`, `head SHA`, `updated_at`, ラベル, 関連Issue, **変更ファイル一覧**を取得。
4. **対象の決定 + 範囲分類 + 言語解決**
   - `mode=full`: 全PRが対象。
   - `mode=changes-only`: state(第11節)と比べ、次のいずれかを対象にする。対象0件なら静かに終了。
     - **新規**(state に無い)
     - **更新**(`sha` または `updated_at` が前回と違う)
   - 更新の場合は、前回の `sha` を**差分の起点**として保持する(ステップ5・6で使う)。
   - 各対象PRについて、第7節の判定で変更ファイルを must/should/ignore に分類し、レビュー範囲サマリと優先度を確定。
   - 各対象PRの**出力言語を第5.3節の順序で解決**し、以降の解説生成に用いる。
5. **各対象PRの深掘り(ブランチを取ってきて調べる)** — must_review / should_review 範囲を中心に:
   - リポジトリを clone(既存ならfetch)し、そのPRのブランチ(head ref)を checkout
     (`gh pr checkout <番号>` / `git fetch origin pull/<番号>/head:pr-<番号> && git checkout pr-<番号>`)。
   - PR本文・変更・差分を把握(必須/推奨範囲を優先。ignoreのみは軽く要約)。
   - **更新されたPRでは、前回の `sha` からの差分(`git diff <前回SHA>..<現在SHA>`)を中心に見る。**
     前回SHAがローカルに無い場合(fetch 済みでない等)は、その旨を注記して全体を対象にする。
   - **文脈依存の語**は憶測せず**そのブランチ上で裏取り**(`ripgrep` で定義・使われ方・呼び出し元を検索、一次情報で意味確定、
     根拠が無ければ「(コード上で定義を確認できず)」と注記)。用語集にある `known` 語は裏取り・説明を省略してよい。
   - PR/Issueの関係や、変更が関わる構造・フローを把握し、第9節の基準で図に落とす(単純なら省略)。
6. **解説の作成**(各PR。**そのPRの解決済み出力言語で書く**):
   - 見出し: `owner/repo #番号 「タイトルを出力言語で要約したもの」`
   - **レビュー範囲サマリ**(必須/推奨/対象外の該当と推奨アクション)
   - **更新されたPRでは、冒頭に「前回からの変更」を置く**(新規のPRでは出さない)。
     前回SHAからの差分を中心に、コードが何がどう変わったかを説明する。
     そのうえで、全体の解説(以下の項目)を続ける。時間が空くと前回の内容を覚えていないため、
     差分だけでは読めない。
     - **本文(description)が変わっていれば、その差分も示す**(第15節)。
       レビューを受けて本文が補足されることは多く、コードの差分と同じくらい重要な更新である。
       前回の本文が保管されていない場合は、本文には触れず全体の解説だけを行う。
   - このPRは何をするものか(1〜3文) / なぜ必要か・背景
   - **図**(第9節。PR/Issue関係や構造・フロー。単純なら省略)
   - 主な変更点(初見でも追える粒度。必須・推奨範囲を厚めに)
   - レビューで見るべきポイント・注意点(あれば)
   - 用語解説(用語集で `new`=フル、`learning`=軽く、`known`=省略。裏取りした根拠付き。
     説明文は `definitions[出力言語]` を使い、無ければ生成して書き戻す。第8節)
   - 言語ルール(第1節)を厳守。曖昧な点は「推測」と明示。
   - (インタラクティブ実行時)理解済みへ昇格を提案できる語があれば、末尾で軽く確認する。
7. **通知/出力**
   - 対象PRを優先度順に並べた **自己完結HTML(第9節)**を生成して届ける。ローカルブラウザで開けること。
   - **プッシュ通知**は件数と各PRの1行要約(+必須該当の有無)。地の文はユーザー既定の言語、
     各PRの要約はそのPRの言語(第5.3節)。例:「レビュー依頼 2件(必須1): owner/api#123 認証リファクタ[必須] / owner/fe#88 文言修正[対象外]」。
8. **状態・用語集の保存**
   - `mode=changes-only` のときのみ `state.json` を更新(第11節)。
   - `glossary.json` は、新出語の登録・出現回数の加算・**新しく生成した言語別定義の追加**・
     (確認済みの)昇格を反映して書き戻す。トークンは含めない。

## 11. 設定・状態ファイル一覧(設定ディレクトリ。第5.1節)

既定: `$HOME/config/<host>/<owner>/<repo>/pr-teeth/`
(このリポジトリ由来なら `$HOME/config/github.com/akm/claude-plugins/pr-teeth/`。
環境変数 `PR_TEETH_CONFIG_DIR` で上書き可)

- `config.toml` … 設定一式。出力言語の既定、リポジトリ別のレビュー範囲と言語(第5.2節・第7節)。ユーザーが編集。
- `glossary.json` … ユーザー用語集(第8節)。skill が更新、`/pr-glossary` で編集。
- `state.json` … 通知済みの記録(第2/10節、フェーズ2の重複抑制)。
  `mode=full` では変更しない。

  ```json
  {
    "notified": {
      "<owner>/<repo>#<number>": { "sha": "<head SHA>", "updated_at": "<updatedAt>" }
    }
  }
  ```

  **`sha` と `updated_at` のどちらかが変われば「更新」**と判定する(第10節ステップ4)。
  `sha` だけでは、PR 本文の書き直しやレビューコメントの追加を取りこぼす。
  レビュー依頼の文脈では本文の補足も重要な更新なので、`updatedAt` も見る。

  **記録の更新は既定でマージ、掃除は明示的に宣言したときだけ**行う。渡された一覧が
  「オープンな依頼の全件」とは限らないため(取得が途中で失敗した・件数上限で
  切り詰められた・処理した分だけ渡した)。これを完全な一覧とみなして全置換すると、
  **まだオープンな PR の記録が消えて再通知される**。
  そのため CLI の引数を「今回処理した分(マージ)」と「全件(掃除つき)」に分け、
  呼び出し側が何を渡しているかを名前で宣言する形にしている。
  閉じた PR の記録は、次に全件を取得できたときに掃除される。

- `bodies/` … 前回時点の PR 本文(第15節)。更新時に本文の差分を出すための材料。
  `state.json` に混ぜず1件1ファイルで置き、state を人が開いて確認できる大きさに保つ。
  **キャッシュなので消えてよい**(無ければ差分を出さずに全体を説明する)。
- `repos/` … PR を読むための作業リポジトリ(第12節)。これもキャッシュ。

**この設定ディレクトリにトークンは置かない**(第6節)。秘密情報を含まないため、
設定を同期・共有しても資格情報が漏れることはない。

## 12. 制約・非機能要件

- **読み取り専用に徹する。** コメント/承認/マージ等 GitHub への書き込みは一切しない。
- トークン等シークレットを出力・コミットしない。
- 取得・解析に失敗したPRがあっても全体を止めず、注記して成功分だけでも通知する。
- 巨大PRは中心的変更(特に必須/推奨範囲)に絞って読み、無制限な clone/解析でディスク・時間を浪費しない。
  - **clone の置き場所・取得量・保持数はコード側で決める**(`scripts/prteeth/repos.py`)。
    散文の指示には強制力が無く、実際に上限も掃除も存在しない状態になっていた。
  - 取得は `--filter=blob:none` の部分クローンにする。PR の差分を読むのに全履歴の blob は要らない。
  - 保持は「最終利用から30日」「20件」「合計5GiB」で頭打ちにし、超えた分は**最終利用が古い順**に消す。
    掃除は `repo` サブコマンドの中で自動的に行う(別コマンドにすると呼ばれないまま溜まる)。
  - 作業リポジトリは**再取得できる**ので消してよい。蓄積データ(用語集・状態)とは扱いが違う。
- 1時間ごと(フェーズ2)を見据え、対象0件なら安価に静かに終わる。

## 13. 受け入れ基準(Definition of Done)

- [ ] `/pr-teeth` で on-demand 実行でき、現在のレビュー依頼PRが全件解説される。
- [ ] **設定が無い状態でも動き、解説が日本語で出る**(既定 `ja`)。
- [ ] `config.toml` に `language = "en"` を書くと、**全PRの解説・用語解説・通知が英語になる。**
- [ ] `[repos."<owner>/<repo>"]` に `language` を書いたリポジトリのPRだけがその言語になり、
      他のPRはユーザー既定の言語のままになる。
- [ ] `/pr-teeth lang=<言語タグ>` が設定より優先され、その実行だけ全PRがその言語になる(設定ファイルは変わらない)。
- [ ] 出力言語が変わっても `known` 語の説明省略は同じように効き、**用語のステータス・出現回数が言語間で共有される。**
- [ ] 未生成の言語で用語を説明したとき、その説明が `glossary.json` の `definitions[言語]` に追加される。
- [ ] 設定・状態・用語集が**ローカルの設定ディレクトリ**(第5.1節)に読み書きされ、クラウドストレージに依存しない。
- [ ] 設定ディレクトリの解決が**非公式なファイル・パス構造に依存していない**
      (`known_marketplaces.json` やキャッシュのディレクトリ構造を読まない)。
      配布元は SKILL.md のリテラル、上書きは `PR_TEETH_CONFIG_DIR` のみで決まる。
- [ ] 出力が**単一の自己完結HTML**で、**ローカルブラウザで開ける**。
      図が無ければ外部参照を一切含まない。図がある場合は CDN から Mermaid を読むが、
      SRI を付け、読み込めなくても本文と図のコードは読める。
- [ ] PR/Issueの関係や文脈上の構造が非自明なPRで**図(Mermaid)**が生成され、**単純なケース(Issue↔PR 1対1で他に関係なし等)では省略**される。
- [ ] 各PRに、`config.toml` に基づく**レビュー範囲サマリ**(必須/推奨/対象外の該当)が表示される。
- [ ] PRが範囲優先度(必須→推奨→対象外)で並び、対象外のみのPRは1行に畳まれる。
- [ ] 深掘り・用語裏取りが must/should 範囲を中心に行われる。
- [ ] 各PRで、少なくとも1語の文脈依存語について、ブランチ上のソース/ドキュメントを検索した根拠付き解説が出る。
- [ ] 用語が `glossary.json` に蓄積され、`new`→`learning` は自動、`learning`→`known` は確認を経て昇格する。
- [ ] `known` 語は説明が省略され、`new`/`learning` は説明される(ステータス駆動)。
- [ ] `/pr-glossary` で理解済み・学習中の用語をポートフォリオとして確認・編集できる。
- [ ] 会話からの理解推定は「昇格の提案」までにとどまり、自動確定しない。無人実行では会話推定を行わない。
- [ ] トークンが `GITHUB_TOKEN` → `GITHUB_TOKEN_FILE` → `gh auth token` の順に探され、
      前後の空白・改行が trim される。
- [ ] トークン未設定時に、その旨だけ通知して安全に終了する。GitHub への書き込みを一切行わない。
- [ ] `mode=changes-only` で新規・更新のみが対象になり、無ければ静かに終了する(フェーズ2の下地)。
- [ ] 更新の判定が `sha` **または** `updated_at` の変化で行われ、コミットを伴わない更新
      (本文の書き直し、レビューコメントの追加)も検知される。
- [ ] 更新されたPRの解説では、冒頭に**前回SHAからのコード差分**を中心とした
      「前回からの変更」が置かれ、そのうえで全体の解説が続く。
- [ ] skill 本体が共通化され、スケジュールから同じ skill を呼ぶだけで定期実行にできる。

## 14. フェーズ2(参考: 後で足す定期実行)

- スケジュールタスク(1時間ごと、または平日日中のみ)を作り、プロンプトは実質「この skill を `mode=changes-only` で実行」だけにする。
- 認証・設定・状態・用語集・通知は skill 側にあるため、スケジュール側は薄く保つ。
- **出力言語は設定ファイル(`config.toml`)だけで決まる。**
  スケジュール側で `lang=` を渡す必要はなく、第5.3節の 2〜4 段だけで解決する。
- 頻度は運用しながら調整(通知過多・コスト対策として「2〜3時間ごと」「平日日中のみ」も検討)。
- **対話実行と定期実行の併走は起こる前提で書く。** 用語集・状態の read-modify-write は
  `store.locked()` で直列化済み(`docs/design/data-integrity.md`「同時に書かない」)。
  ロックが無いと、どちらのファイルも壊れないまま片方の記録だけが失われる。

## 15. PR本文(description)の差分表示

(第15節はもともと「将来対応」の置き場だったが、未着手の項目は無くなった。
以下は対応済みの経緯として残す。)

### 経緯と判断

「前回からの変更」はコードの差分のみを扱っていた
([#11](https://github.com/akm/claude-plugins/issues/11))。レビューを受けて本文が
更新されるケースは多く、その差分も示すようにした。

差分を出すには前回時点の本文が要る。当初の案は `state.json` に本文そのものを
持つか、ハッシュだけを持つかの二択だったが、**どちらも採らなかった。**

- 本文そのものを `state.json` に持つ → 「どの PR をどこまで通知したか」を読むための
  ファイルに数十 KB の本文が混ざり、人が開いて確認できなくなる
- ハッシュだけを持つ → 肥大化は避けられるが**差分が出せず、目的を満たさない**
  (検知は既に `updated_at` で足りている)

そこで**本文は `bodies/` に1件1ファイルで置く**。`state.json` には従来どおり
`sha` と `updated_at` だけが載り、大きさが変わらない。1件ずつ独立して消せるため、
state の記録を残したまま本文だけ捨てられる。

本文は**キャッシュ**であり蓄積データではない(第12節・`docs/design/data-integrity.md`)。

## 16. 番号指定でPRを読む(`/pr-teeth-pick`)

→ [#16](https://github.com/akm/claude-plugins/issues/16)

第1節の巡回は「レビュー待ちを消化する」ためのもので、取得クエリが `--state=open` の
ためクローズ済み・マージ済みのPRは対象にできない。しかし目的の違う読み方がある。

- **マージ済みPRを後から読んで学習したい**(レビューではなく理解のため)
- **自分がレビューし損ねたPRを振り返りたい**

どちらも「レビュー待ちの巡回」とは目的が違い、`open` に限定する理由がない。
**除外していたのは取得クエリだけ**で、分類・用語集・言語解決・HTML生成の下流は
open/closed を一切見ていないため、そのまま再利用できる。

### 別コマンドにする理由

`/pr-teeth` に引数を足すのではなく、別の skill として切り出す。
`/pr-teeth` の `description` は「レビュー依頼を巡回」で自動トリガーもその文脈にある。
用途の違うものを同じコマンドに載せると description が曖昧になり、
**どちらのトリガー精度も落ちる**。CLI(`scripts/`)は共用する。

コマンド名に `review` は含めない(第3節と同じ理由。レビューはユーザー自身が行う)。

### 巡回との違い

| | `/pr-teeth`(巡回) | `/pr-teeth-pick`(番号指定) |
| --- | --- | --- |
| 対象 | レビュー依頼が来ているオープンなPR | 指定されたPRのみ(open/closed問わず) |
| `state.json` | `mode=changes-only` で読み書き | **読み書きしない** |
| 「前回からの変更」 | 更新されたPRで出す | **出さない**(毎回全体を解説) |
| レビュー範囲の表示 | 必須 / 推奨 / 対象外 | **重点 / 参考 / 周辺** |
| 用語集 | 蓄積する | **同じように蓄積する** |

**`state.json` を読み書きしない**のは、あれが通知の重複抑制用であり番号指定とは
無関係なため。`base_sha` は state の記録から取るものなので、state を見ない番号指定には
「更新差分」の概念自体が無い。毎回全体を解説する。

**用語集は巡回時と同じように蓄積する。** 用語集は全リポジトリ横断でひとつであり
(第8節)、振り返りで読んだ語も同じように積み上がるのが自然。理解が進めば、
どちらの経路でも説明が減っていく。

### レビュー範囲は表示するが、文言を変える

分類自体は有用(大きいPRでどこから読むべきかの手がかりになる)なので残す。
ただしマージ済みPRに「レビュー必須」と出るのは意味がずれる(レビューはもう
終わっている)ため、**読み方の指標として見せる**。

| 内部の値 | 巡回時 | 番号指定時 |
| --- | --- | --- |
| `must_review` | 必須 | 重点 |
| `should_review` | 推奨 | 参考 |
| `ignore` | 対象外 | 周辺 |

**内部の値は変えない。** 変えるのは表示だけで、分類ロジック・並び替え・保存は共通の
ままにする。内部の値まで文脈で分けると、分類・並び替え・保存のすべてに文脈が波及し、
共用しているCLIが二重化する。文言は `scripts/prteeth/labels.py` に文脈別
(`CONTEXT_PATROL` / `CONTEXT_PICK`)の上書き表として持ち、`render --context pick` で
切り替える。

### PRの指定形式

`owner/repo#123` と PR の URL の両方を受ける。URL は末尾に `/files` などが付いていても
同じPRとして扱う。`#` はシェルで消えることがあるため `owner/repo/123` も受ける。

**解釈をモデルに任せない。** URLから owner/repo/number を取り出す作業は、見た目に
簡単でも取り違えが起きる(`/pull/123/files` の末尾、`#issuecomment-...` のフラグメント、
末尾スラッシュ)。取り違えると**別のPRの解説を正しい体裁で出してしまい、読み手には
誤りだと分からない**。範囲判定と同じく、機械的に決まるものはCLI(`prspec`)で確定させる。

解釈できなかった指定は**捨てずに理由付きで返す**(黙って落とすと、渡したはずのPRが
出力に無いことに気づけない)。1件の誤りで全体は止めず、解釈できた分は解説する。
同じPRの重複指定は1件に畳む(2回解説しても情報が増えないため。利用者の誤りではないので
警告にはしない)。
