# データ種別と失敗時の態度

pr-teeth が扱うデータを3種類に分け、**読めない・壊れているときに取るべき態度**を種別ごとに定める。

## なぜこの区別が要るか

当初は「fail-soft（壊れていても既定値で続行する）」という方針を、扱うデータすべてに
一律で適用していた。第5.1節の「ファイルが無い場合はエラーにせず既定値で動く
（初回実行を設定作業でブロックしない）」という意図自体は正しい。

しかしこの方針は**設定ファイルに対してのみ正しい**。同じ態度を蓄積データと
エージェント入力に適用した結果、次の不具合が同時に発生した。

- 破損した `glossary.json` を seed で上書きし、**蓄積した用語が失われた**
  （`load_json` が「ファイルが無い」と「壊れて読めない」を区別せず、どちらも `{}` を返すため）
- `--input` の JSON でトップレベルキーを間違えると、**警告も出さず0件を記録して成功扱い**
  （`payload.get("terms") or []` が設定ファイル向けの書き方だったため）
- `term` キーを書き忘れた項目が1つあると、**そのバッチの正常な語もすべて失われた**
  （`None` がキーになり、保存直前に `sort_keys` が落ちるため）

これらは個別のバグではなく、**種別の異なるデータに同じ態度を適用した**という
1つの設計判断から出た症状である。

## 3つの種別

| 種別 | 例 | 失われるもの | 読めない/壊れているとき |
| --- | --- | --- | --- |
| **設定** | `config.toml` | 利用者が書いた数行 | **既定値で続行**し、警告を出す |
| **蓄積データ** | `glossary.json` / `state.json` | 数ヶ月分の学習 | **保存を拒否して停止**する |
| **エージェント入力** | `--input` / `--state` の JSON | その実行分 | **エラーで停止**、項目単位の不備は**スキップして件数を報告** |

### 設定 — 既定値で続行してよい

失われるのは利用者が書いた数行であり、書き直せる。初回実行を設定作業でブロックしないほうが
利用者の利益になる。ただし**黙って続行してはならない**。設定したのに効いていない状態は、
利用者から見て「設定が無視されている」としか分からないため、必ず理由を warnings に載せる。

### 蓄積データ — 壊れているなら触らない

`glossary.json` はこのプラグインの中核価値である。数ヶ月使い込んで `known` に育てた語が
失われると、説明が延々と繰り返される状態に戻る。しかも利用者から見ると
「学習が消えた」という原因の分かりにくい形で現れる。

**読めないときに新しく作って上書きするのは、回復可能な問題（バイト列の破損）を
回復不能な問題（データの消失）に変える。** そのため:

- 読めない場合は**保存せず** exit=1 で終了する
- 「読めないので上書きを避けた」ことと、退避・復旧の手順を伝える
- 自動での退避やリネームは行わない（利用者の判断を介す）

「ファイルが無い」は正常な初回実行なので、この規則の対象外。**無いことと壊れていることを
区別できる形で読む**必要がある。

### エージェント入力 — 信頼しない

`--input` の JSON は**エージェントが毎回ゼロから組み立てる**。人間が書く設定ファイルより
間違いが起きやすく、しかも間違いに気づく手段がエージェント側にない。

`payload.get("terms") or []` のような「無ければ空」という書き方は設定ファイル向けであり、
エージェント入力に対しては**「無いなら間違っている」**と扱う。

- トップレベルの形が違う（キー名の誤り、配列を直接渡した等）→ **エラーで停止**し、期待する形を示す
- 項目単位の不備（`term` が無い等）→ **その項目だけスキップ**し、受理件数とスキップ件数を返す
  - 正常な項目を巻き添えにしない。1件の不備でバッチ全体を失うのは損失が大きすぎる
- 成功時も**受理件数を返す**。エージェントが「0件だった」ことに気づけるようにする

## 実装上の指針

- `store` の読み込みは「見つからなかった」と「壊れていた」を呼び出し側が区別できる形にする
- 蓄積データを扱うコマンド（`record` / `promote`）は、読み込みが壊れていたら保存に進まない
- エージェント入力の検証は1箇所にまとめ、各コマンドはそれを通してから処理する
- どの経路でも、**警告を計算したなら必ず返却に含める**。集めて捨てるくらいなら集めない
