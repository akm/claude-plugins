# work-log-gh-comment の評価

スキルを変更したときに、意図した効果が出ているかを測るための一式。

## 中身

| ファイル | 内容 |
| --- | --- |
| `evals.json` | 6 つのテストケース (プロンプトと判定項目) |
| `fixtures/` | テストで実行するスクリプト |
| `grade.py` | 出力を機械的に採点する |
| `test_grade.py` | 採点そのもののテスト |

## テストケースが見ているもの

6 つは、Alert の使い分けと機密の扱いが分かれるように選んである。**どれか 1 つだけでは、規定の片側しか検証できない。**

| # | 題材 | 何を見るか |
| --- | --- | --- |
| 0 | `deploy.sh` (exit 1) | 失敗の記録。8 行の繰り返しを省略しないこと。ANSI エスケープの除去 |
| 1 | `list-sites.sh` | 値の違う一覧を省略しないこと |
| 2 | git の調査 | 複数段階の記録。見出しでの区切り |
| 3 | `check-logs.sh` (exit 0 だが出力に ERROR) | **成功したコマンドに CAUTION を付けないこと** |
| 4 | `apply-config.sh` (状態を変えて成功) | **成功を TIP で強調すること** |
| 5 | `register-site.sh` (トークンを含む出力) | **機密を貼らないこと。機密でない値は残すこと** |

表の「何を見るか」は規範を eval の題材に対応づけたもので、規範そのものではない。Alert の使い分けは [references/format.md](../references/format.md) の「Alert (強調)」、ANSI エスケープの除去と貼る範囲は [references/output-handling.md](../references/output-handling.md)、省略しないものは [SKILL.md](../SKILL.md) の「省略してよい 2 つの例外」が正本。規範を変えたら、この表と `grade.py` の判定も見直す。

3 と 4 は対になっている。**3 だけだと「TIP を付けない」方向にしか調整されず、4 だけだと「常に TIP」になる。** 両方あって初めて使い分けを測れる。

`check-logs.sh` はサマリが `3 errors` なのに `ERROR` 行が 2 行しかない。**この食い違いは意図的に残してある** — 実際のログでも起こることで、気づけるかどうかが記録の質を左右する。

## 5 は効果の測定と退化の検知を兼ねる

`register-site.sh` は架空のトークン 2 つと、機密でない値 (拠点 ID・有効期限・ファイル名) を混ぜて出す。**「全部隠す」でも「全部貼る」でも不正解**になる題材。

**漏えいそのものは、スキルなしでも起きない。** モデルは指示がなくてもトークンをマスクする。フィクスチャから「架空の値」というヒントを外しても変わらなかった。

**それでも残すのは、漏えいの検知が効果の測定とは別の役割だから。** ここが見ているのは退化で、将来スキルを変えたときに漏えいが起きれば捕まえられる。機密は漏れてからでは取り返しがつかない。

**判定器が見るのはフィクスチャの 2 トークンだけ。** 接頭辞を持たない機密 (パスワード・Webhook URL・内部 IP・接続文字列) は対象外で、これは網羅的な機密スキャナではない。網羅は規範 ([references/sensitive-data.md](../references/sensitive-data.md) の「迷ったら伏せる」) が担い、ここは eval-5 の題材で効果と退化を測る役に徹する。

**差が出ないことを理由に、漏えいの判定を消さないこと。** 消してよいのは、機密を扱う規定 (`references/sensitive-data.md` と、そこを参照する SKILL.md の手順) がスキルから無くなったときだけ。

## 回し方

1. 実行結果の置き場を作る (`.gitignore` の対象なので追跡されない)

   ```sh
   mkdir -p <作業用ディレクトリ>/iteration-<N>
   ```

2. 各テストケースを、スキルあり・なしの 2 通りで実行する。サブエージェントに次を渡す。

   - スキルあり: このスキルの `SKILL.md` と `references/` を読ませてから、`evals.json` の `prompt` を実行させる (`prompt` 中の `<evals>` は evals ディレクトリの絶対パスに置き換える)
   - スキルなし: 同じ `prompt` だけを渡す
   - 出力先: `iteration-<N>/eval-<ID>-<名前>/{with_skill,without_skill}/outputs/comment.md`

   **`gh` を実行させないこと。** 実際の Issue / PR に書き込まないため、投稿する本文をファイルに書かせるだけにする。

3. 各ディレクトリに `eval_metadata.json` を置く (`evals.json` の該当エントリから作る)

4. 採点する

   ```sh
   python3 <evals>/grade.py <作業用ディレクトリ>/iteration-<N>
   ```

   各ランに `grading.json` が書かれ、標準出力に得点が出る。

## 判定を足すとき

**先に `test_grade.py` へ反例を書き、Red を見てから `grade.py` を直す。** テストは evals ディレクトリで回す (python3 と make だけで動く)。

```sh
make -C <evals> test
```

判定器は 6 つの eval すべての結論を左右する単一障害点で、ここが誤ると測定そのものが信用できなくなる。実際、このスキルの前身では、テストが無い間に判定の反転・恒真・すり抜けが繰り返し入った。

**「通ること」だけを確かめるテストは書かない。** 恒真の判定を通してしまう。**不合格になるべき入力が不合格になること**を先に検証する。書くべき反例は次の 3 種類。

- **すり抜け** — 判定を回避する書き方 (部分マスク、行折り返し、言い換え)
- **誤検出** — 規定を守った書き方が不合格にならないか (否定形、丁寧語、短い正しい記録)
- **題材との重なり** — フィクスチャの出力を貼るだけで通らないか

そのうえで `grade.py` の `CHECKS` に検査を足す。**目視の揺れを避けるため、機械的に判定できる形にする。**

判定を足したら、**過去のイテレーションを測り直して差が出るか確かめる。** 差が出ないなら、その検査は何も見ていない。
