# 出力の扱い

コマンドの出力をそのまま貼ると壊れることがある。貼る前に処理が要る場面と、その方法をまとめる。

## 色付き出力は ANSI エスケープを除去する

`terraform` や `gcloud` は端末以外に出力するときも色を付けることがある。エスケープを含んだまま貼ると、コードブロックが `[0m[1m` だらけになって読めない。

**貼る前に除去する。**

```sh
sed -e 's/\x1b\[[0-9;]*m//g' <ログ> > <除去後のログ>
```

除去できたかは、先頭を見れば分かる。

```sh
head -3 <除去後のログ>
```

**元のログは消さない。** 除去は貼るためのもので、判定には使わない。判定で `grep` を使う場合、エスケープの有無で結果が変わる ([terraform destroy は途中で失敗しても終了コード 0 を返すことがある](https://github.com/tecowl/lappds/blob/main/docs/solutions/integration-issues/terraform-destroy-exits-zero-on-failure-2026-08-28.md))。

> **色を出させない選択もある。** `terraform` なら `-no-color` を付ければエスケープ自体が出ない。ただし**マニュアルの手順に無いオプションを勝手に足さない。** 手順どおりに実行した記録を残すのが目的なので、記録の都合で実行を変えない。除去は貼る側で行う。

## 出力が長いコマンドはファイルに落とす

数百行を超える出力は、ターミナルに流すと後から拾えない。

```sh
<コマンド> > <スクラッチパス>/<名前>.log 2>&1
```

- **`2>&1` を付ける。** 標準エラーだけに出るメッセージ (Terraform のエラー・警告) を落とさない
- **スクラッチディレクトリに置く。** リポジトリを汚さない

長時間かかるコマンドはバックグラウンドで実行し、完了を待つ。ログはファイルに残るので、完了後に読める。

## 貼る範囲を決める

全文が原則。ただし、**同じ内容が別のコメントに既にある場合**は、その旨を書いて省いてよい。

```
(Plan: 0 to add, 0 to change, 67 to destroy. までの削除対象の一覧は、上のコメントの state list と同じ内容のため省略)
```

判断に迷う典型は `terraform` の `plan` 出力。**削除対象の一覧そのものは `state list` と重複する**ため、既に貼ってあれば省ける。一方、**属性の差分 (`+ create` / `- destroy` の中身) は他に無い情報**なので、それを見せたい場合は貼る。

実行部分の開始行を見つけて、そこから切り出す。

```sh
grep -n 'Plan:' <ログ>          # 実行の開始位置を見つける
sed -n '<開始行>,$p' <ログ> > <抜粋>
```

## 出力にバッククォートが含まれる場合

出力中に ` ``` ` が現れると、コードブロックが途中で閉じてしまう。

**囲みのバッククォートを 4 つ以上にする。**

````markdown
````
$ cat some-markdown.md
```sh
echo hello
```

出力に含まれる連続したバッククォートより 1 つ多くすれば囲める。

## 本文はファイルに書いてから渡す

```sh
gh issue comment <番号> --repo <owner/repo> --body-file <本文のパス>
```

**`--body` に長文を直接渡さない。** シェルの引用でバッククォート・`$`・改行が壊れる。ヒアドキュメントで書く場合は、終端子をクォートして展開を止める。

```sh
cat > <本文のパス> <<'BODY'
(本文。$ や ` をそのまま書ける)
BODY
```

`<<'BODY'` のようにクォートするのが要点。クォートしないと `$?` や `` `cmd` `` が展開される。

## 投稿できたことを確認する

`gh issue comment` は成功するとコメントの URL を返す。**この URL を控えて報告に含める。**

投稿に失敗した場合 (本文が長すぎる・権限が無い) はエラーが返る。長すぎて弾かれたら、作業の区切りで分けて複数のコメントにする。**区切りごとに投稿していれば、そもそも 1 つが長くなりにくい。**
