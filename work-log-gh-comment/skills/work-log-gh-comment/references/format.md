# 記録の書式

**この文書の例は、lappds という配信基盤の実際の作業記録から採っている** (Terraform・gcloud で検証環境を作り直した回)。コマンドやリソース名はその題材のものなので、**読むときは形と使い分けだけを見る。** 抽象的な例に置き換えていないのは、実際の出力にしか現れない食い違い (終了コードと本文の矛盾、サマリと明細の不一致) が、この書式が扱う対象そのものだからである。

## 全体の骨格

見出しで作業の段階を区切り、その中にコマンドの記録を並べる。

````markdown
## 1. プラットフォームの削除

[手動テストのためのプラットフォームの初期化](...) に従って実施する。

### 0. 事前確認

<details><summary> gcloud config get-value project </summary>

```
$ gcloud config get-value project
lappds
```

</details>

> [!WARNING]
> 終了コードは 0 だが、実際には失敗している。完了の判断に終了コードを使わず、ログの末尾を読む必要がある。
````

## コマンドと出力

**`<details>` で折りたたむ。** 出力が数行でも折りたたむ (読む人が展開の有無で重要度を誤解しないよう、扱いを揃える)。

````markdown
<details><summary> make -C terraform init </summary>

```
$ make -C terraform init
terraform -chdir=environments/prod init
Initializing the backend...
(以下、実際の出力を全文)
```

</details>
````

- **`<summary>` にはコマンドを書く。** 前後に半角スペースを入れると GitHub 上で読みやすい
- **コードブロックの言語指定は付けない。** コマンドと出力が混在するため、シンタックスハイライトは害になる
- **`$ ` を付けて実際に打った形を書く。** 変数を展開した後の形ではなく、打った通りに
- **`<details>` の前後に空行を入れる。** 入れないと Markdown として解釈されない

複数のコマンドをまとめて 1 つの `<details>` に入れてよい。事前確認のように、一連で意味を持つものは分けない方が読みやすい。

## Alert (強調)

**GitHub の Alert には 2 つの制約がある** ([GitHub のドキュメント](https://docs.github.com/ja/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#alerts))。

- **他の要素にネストできない。** `<details>` の中には置けない。折りたたみの外に出す
- **連続して置かない。** 並べると読み飛ばされる。1 つのコメントに 1〜2 個を目安にする

種類の使い分けは次のとおり。

| 記法 | 用途 | 作業ログでの例 |
| --- | --- | --- |
| `> [!NOTE]` | 知っておくと役に立つ情報 | 残したもの・その理由。所要時間の実測 |
| `> [!TIP]` | うまくやるための助言 | 成功の確認。次に同じ作業をするときの近道 |
| `> [!IMPORTANT]` | 目標の達成に必要な情報 | この後の手順で必ず要る前提 |
| `> [!WARNING]` | 問題を避けるため、すぐ注意が要る | 判断を誤らせる挙動。次の手順に影響する未完了 |
| `> [!CAUTION]` | 行動のリスク・悪い結果 | 失敗したコマンド。不可逆な操作の副作用 |

5 種類の使い分けを、実際の作業から挙げる (lappds で検証環境を作り直したときの記録)。**題材はこのプラグインと無関係だが、Alert の選び分けは題材によらない。**

```markdown
> [!TIP]
> `Destroy complete! Resources: 16 destroyed.` — Terraform 管理のリソースはすべて削除された。次は管理外のリソースの確認に進める。
```

```markdown
> [!NOTE]
> `serverless-ipv4-*` の解放を 11:14 に確認。1 回目の `destroy` の開始から約 54 分だった。マニュアルの目安 (1〜2 時間、実測 75 分・115 分の例) の範囲に収まっている。
```

```markdown
> [!IMPORTANT]
> 配備をやり直す前に `terraform.tfvars` の `application_images` を空に戻す。この初期化でアプリケーションの登録が消えたため、残っているキーはどのアプリケーションも指していない。
```

```markdown
> [!WARNING]
> 終了コードは 0 だが、実際には失敗している。完了の判断に終了コードを使わず、ログの末尾に `Destroy complete!` があるかを読む必要がある。
```

```markdown
> [!CAUTION]
> Cloud SQL のデータは失われ、元に戻せない。バックアップも取得していない。運用中のプロジェクトでは実行しない。
```

**NOTE と IMPORTANT の違いは、読み飛ばしたときに困るかどうか。** 上の NOTE は所要時間の記録で、知らなくても次の手順は踏める。IMPORTANT は空に戻し忘れると次の配備が壊れるので、読み飛ばされては困る。

**WARNING と CAUTION の違いは、対象が判断か行動か。** WARNING は「その判断は誤り」を止める。CAUTION は「その操作をすると戻せない」を止める。

**状態を変える処理が成功したら `> [!TIP]` で書く。** 記録は失敗だけを目立たせるものではない。うまくいったことも同じ強さで見えるほうが、読む人は次に何をすればよいか判断しやすい。

**一覧の確認や状態の調査だけなら、TIP は要らない。** 何も変えていない作業に「成功」の印を付けても、読む人の判断は変わらない。そこで強調する値打ちがあるのは、結果から分かった事実のほう (`> [!NOTE]` や `> [!WARNING]`)。

**その処理が失敗しているなら、TIP は使わない。** 失敗した作業に「成功」の印が付くと、読む人は結局どちらだったのかを本文から読み直すことになる。**1 つの処理に 1 つの Alert** で、結論をどちらか一方に決める。

途中まで通っていた事実は、Alert ではなく **CAUTION の中か、その前後の地の文**に書く。強調が要るのは結論 (失敗した) であって、途中経過ではない。

```markdown
> [!CAUTION]
> manifest のアップロードで失敗し、終了コードは 1。チャンクの同期は 8 個すべて完了しているので、原因は転送ではなく manifest の生成側にある。
```

この形なら、失敗したことと、どこまで通ったかが 1 つの Alert で分かる。

**Alert は、それが結論であるコマンドの直後に置く。** 読む人は直前の `<details>` の結果だと受け取る。**ログを読み返す `cat` や、確認のための `grep` の直後に警告を置かない** — それらは成功しているので、警告の対象が何なのか分からなくなる。

失敗したコマンドと Alert の間に別のコマンドが挟まるなら、Alert の中で対象を名指しする。

```markdown
> [!CAUTION]
> **`deploy.sh` が終了コード 1 で失敗した** (上の 2 つ目の折りたたみ)。manifest の検証で拒否されている。
```

**出力にエラーの文字列が含まれていても、そのコマンド自体が成功しているなら Alert は付けない。** ログの中身を見せるための `cat` は、エラーを含むログを表示しても `cat` としては成功している。そこに `> [!CAUTION]` を置くと、`cat` が失敗したように読める。

ただし、**その出力が今まさに判断を要する事実を含むなら、Alert を置いてよい**。例えばログの調査で想定外のエラーを見つけたときは、`grep` は成功していても、見つけた事実のほうが結論になる。**Alert が何を指しているかを本文で名指しできるなら置ける、できないなら置かない** と考える。

**Alert には結論を書く。** コマンドの出力をそのまま貼らない。

```markdown
> [!CAUTION]
> Error: The subnetwork resource '...' is already being used by '...'
```

これは出力の貼り付けであって、強調になっていない。次のように書く。

```markdown
> [!CAUTION]
> 67 個のうち 51 個を削除した時点で、サブネットの削除に失敗した。原因は Cloud Run が確保した内部アドレスの非同期解放待ちで、解放まで待つ以外にできることはない。
```

エラーの原文は `<details>` の中に全文があるので、Alert では**それが何を意味するか**を書く。

## 失敗と代行依頼の記録

**成功と同じ形式で記録する。** 失敗を省くと、次に同じ作業をする人が同じ穴に落ちる。

````markdown
### 3. Terraform 管理のリソースを削除する (2 回目)

アドレスの `USERS` が空だったため、解放済みかを確かめる意図で再実行した。

<details><summary> terraform destroy (2 回目。末尾のみ) </summary>

```
$ terraform -chdir=terraform/environments/prod destroy -auto-approve
(Plan までの一覧は省略。1 回目と同じ内容)
module.network.google_compute_subnetwork.subnet: Destroying...
╷
│ Error: ...
╵
```

</details>

同じエラーで失敗。`USERS` が空であることは解放の完了を意味しない、というマニュアルの記載どおりだった。
````

**なぜその操作をしたか**を地の文に書く。上の例では「`USERS` が空だったので確かめる意図で」が該当する。これが無いと、後から読む人には無駄な再実行に見える。

代行を依頼したコマンドは、依頼した理由と結果を書く。

````markdown
`gcloud secrets delete` は権限で実行できなかったため、実行を依頼した。

<details><summary> gcloud secrets delete (7 個。人間が実行) </summary>

```
$ for s in env-... site-...; do gcloud secrets delete "$s" --project lappds --quiet; done
Deleted secret [env-0f885394-962e-4062-bce5-47e3ede9c457-db_password].
(以下 6 件、同じ形式)
```

</details>
````

## 省略を書くときの形

省略は地の文か、コードブロック内の丸括弧で示す。**何を省いたかが分かる形にする。**

```
(TCP / UDP の転送に関する info 行が続くが、同じ形の繰り返しのため省略)
```

```
(Plan: 0 to add, 0 to change, 67 to destroy. までの削除対象の一覧は、上のコメントの state list と同じ内容のため省略)
```

2 つ目は「同じ内容が別の場所にある」ことを示している。この形なら、読む人はどこを見ればよいか分かる。

**次の書き方はしない。**

- 「(中略)」だけ — 何を省いたか分からない
- 「以下同様」 — 何件あったかが消える
- 件数を書かない繰り返しの省略 — 「同じ形式で 6 件」のように数を残す

## 作業の記録としての締めくくり

一連の作業が終わったら、経緯を表にまとめたコメントを最後に置く。**個々のコマンドの記録とは別に置く。**

```markdown
## 実施の記録

| 時刻 | 出来事 |
| --- | --- |
| 10:20 頃 | 1 回目の `destroy`。67 個中 51 個を削除して失敗 |
| 11:14 | `serverless-ipv4-*` の解放を確認 (約 54 分) |
| 11:14 以降 | 3 回目の `destroy` で残り 16 個を削除 |
```

時刻は、待ち時間が意味を持つ作業で特に効く。「1〜2 時間かかることがある」という記述に対して、実測が 54 分だったという記録が残る。
