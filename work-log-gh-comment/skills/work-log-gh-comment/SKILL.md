# work-log-gh-comment: 作業の記録を Issue / PR のコメントに残す

実行したコマンドとその出力を、GitHub の Issue / PR へコメントとして残す。後から読む人 (未来の自分を含む) が、何が起きたかを実際の出力で確認できるようにするためのもの。

**このスキルは明示的に依頼されたときだけ使う。** 通常の作業では発動しない。

## 二本柱 — 貼ってよいものだけを、省略せず全部貼る

記録は次の 2 つの原則に立つ。**この順で優先する。**

1. **機密は貼らない。** Issue と PR のコメントは全世界から読め、編集しても履歴が残り、回収できない。詳細は [references/sensitive-data.md](references/sensitive-data.md)
2. **それ以外は省略も要約もしない。** 出力のどの部分が後で効くかは、記録する時点では分からない

順序が要点になる。「省略しない」を先に立てると、機密が「例外」の位置に落ち、気づかなかったときに漏れる。**先に貼らないものを決め、残りを全部貼る。**

### なぜ省略しないか

要約は、書いた人が「重要でない」と判断したものを捨てる。**その判断は、後から読む人の目的を知らないまま行われる。** 実際に起きた例を挙げる。

- `terraform destroy` の終了コードが `0` なのに失敗していた。要約して「destroy を実行した」とだけ書けば、この矛盾は記録から消える
- `serverless-ipv4-*` の `USERS` 列が空でも解放は済んでいなかった。「アドレスが残っていた」と要約すると、`USERS` が空だった事実が落ちる

### なぜ機密が先か

省略しないのは、後から読む人のため。機密を貼ると、読む相手が全世界に広がる。**機密の判定はコマンドの実行前に行う** — 出力を見てから気づく形だと、見落としたときに何も働かない。判定の仕方と伏せ方は [references/sensitive-data.md](references/sensitive-data.md) に従う。

## 記録するもの

| 対象 | 記録するか |
| --- | --- |
| 実行したコマンド | する (`$ ` を付けて、実際に打った形のまま) |
| 標準出力・標準エラー | する (全文。機密の値だけマスク) |
| **失敗したコマンド** | **する** (成功と同じ形式で。エラーは Alert で強調) |
| **人間に代行を依頼したコマンド** | **する** (依頼した理由と、返ってきた結果) |
| 事前の状態確認 | する (何を確かめてから実行したか) |

**失敗と代行依頼を省かない。** 試行錯誤の経路そのものが、次に同じ作業をする人への情報になる。到達点だけを残すと、同じ穴に再び落ちる。

**出力の中の食い違いは、解釈で均さずに食い違いとして書く。** サマリと明細の数が合わない (`3 errors` なのに `ERROR` 行が 2 行しかない)、終了コードと本文が矛盾する (exit 0 なのに失敗の文言が出ている) など。もっともらしい説明を思いついても、数や状態が一致していない事実を先に書き、説明は仮説として添える。「なぜ省略しないか」の 2 つの実例は、どちらもこの種類の食い違いだった。

## 手順

1. **記録先を確かめる。** 引数の番号が Issue か PR かを判別する。

   ```bash
   gh api repos/<owner/repo>/issues/<番号> --jq '.pull_request != null'
   ```

   `true` なら PR、`false` なら Issue。GitHub の API では PR も issues の番号空間を
   共有しており、PR だけが `pull_request` を持つ。

   **終了コードで判別しない。** `gh issue view <番号> --json ...` は PR 番号でも
   終了コード 0 を返すので、`||` のフォールバックが発火せず PR を Issue と
   誤判定する (`--json` を付けない場合とは挙動が違う)。

2. **コマンドを実行する前に、機密を出すものかを判定する。** [references/sensitive-data.md](references/sensitive-data.md) の「いつ気づくか」に該当するコマンドを 1 つでも実行する作業は、投稿の前にユーザーへの確認が要ると、この時点で決まる。

3. **作業しながらログを控える。** 出力が長いコマンドは、ファイルに落としてから読む。

   ```bash
   <コマンド> > <スクラッチパス>/<名前>.log 2>&1
   ```

   **色付き出力は ANSI エスケープを除去してから貼る** ([references/output-handling.md](references/output-handling.md))。除去しないとコードブロックが読めなくなる。

4. **区切りごとにコメントを投稿する。** 作業が一段落したらその都度投稿する。全部終えてからまとめない。

   - 途中で中断しても、そこまでの記録が残る
   - 長い待ちを挟む作業では、進捗が見える

   手順 2 で機密該当と決まっていた区切りは、マスクを施した本文を用意し、**投稿の前にユーザーに確認する**。

   ```bash
   # 手順 1 が false なら Issue
   gh issue comment <番号> --repo <owner/repo> --body-file <本文のパス>
   # true なら PR
   gh pr comment <番号> --repo <owner/repo> --body-file <本文のパス>
   ```

   **取り違えても投稿は成功してしまう。** `gh issue comment` は PR 番号に対しても
   通り、その PR にコメントが付く (GitHub の API で PR と Issue のコメントは
   同じ経路)。**失敗して気づく仕組みは無いので、手順 1 の判別を省かない。**

   **本文は必ずファイルに書いてから渡す。** `--body` に長文を直接渡すとシェルの引用で壊れる。

5. **投稿できたことを確認する。** 返る URL を控え、報告に含める。

## 書式

詳細は [references/format.md](references/format.md)。要点は次のとおり。

- **コマンドと出力は `<details>` で折りたたむ。** `<summary>` にはコマンドを書く
- **重要な結果は GitHub の Alert で強調する** (`> [!NOTE]` `> [!TIP]` `> [!IMPORTANT]` `> [!WARNING]` `> [!CAUTION]`)。**状態を変える処理が成功したら `> [!TIP]`、失敗したら `> [!CAUTION]`。1 つの処理には片方だけ** — 両方付けると、読む人はどちらが結論か分からない。**成功のほうを書き落としやすいので気をつける**
- **Alert は、それが結論であるコマンドの直後に置く。** 読む人は直前の折りたたみの結果だと受け取る。ログを読み返す `cat` の直後に警告を置くと、`cat` が失敗したように読める
- **見出しで作業の段階を区切る。** 読む人が目的の箇所へ飛べるようにする

## 省略してよい 2 つの例外

**次の 2 つだけ。** それ以外は省略しない (機密のマスクは省略ではない — [references/sensitive-data.md](references/sensitive-data.md))。

1. **出力中に明確に現れる、同じ形の行の連続**
2. **同じ内容が別のコメントに既にある場合** (詳細は [references/output-handling.md](references/output-handling.md) の「貼る範囲を決める」)

どちらも**省いた事実と、何を省いたかを地の文で書く**。**迷ったら省かない** — 判断が難しいと感じた時点で、それは「明らか」ではない。

1 つ目の判定は次のとおり。

- **同じ形の行が連続している箇所に限る。** 離れた場所にある似た行は対象外
- **何行を、何の繰り返しとして省いたかを明記する**

```
(TCP / UDP の転送に関する info 行が続くが、同じ形の繰り返しのため省略)
```

2 つ目は、**どこを見れば同じ内容があるかを書く**。

```
(Plan: 0 to add, 0 to change, 67 to destroy. までの削除対象の一覧は、上のコメントの state list と同じ内容のため省略)
```

**次のものは繰り返しに見えても省略しない。**

- 行ごとに値が違うもの (リソース名・ID・タイムスタンプ) — 一覧そのものが記録の対象
- 進捗の経過を表すもの (`Still destroying... [10s elapsed]` など) — 所要時間が分かる
- 同じ形でも件数が意味を持つもの — 何個あったかが後で効く

## 原則

- **要約しない。** 「要するに」と書き始めたら手が止まっている合図。実際の出力を貼る
- **成功だけを残さない。** 失敗・待ち・やり直しは、次に同じ作業をする人への情報
- **投稿は記録であって、コミットではない。** リポジトリを変えないので、コメントの投稿は毎回の確認を要さない。**ただし機密を出すコマンドを実行した作業では確認する** ([references/sensitive-data.md](references/sensitive-data.md) の「投稿前の確認」)
