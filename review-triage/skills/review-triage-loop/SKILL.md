# review-triage-loop: レビューから修正までの周回

レビューの起動・[review-triage](../review-triage/SKILL.md)・[review-triage-fix](../review-triage-fix/SKILL.md) を 1 周として、**終了条件に当たるまで繰り返す。** 成果物は周回の結果の報告であって、判断でも修正でもない — 判断は `review-triage`、修正は `review-triage-fix` が持つ。

**このスキルは 2 つのスキルを呼ぶだけで、それらの中身を代行しない。** 採否を決めたり、修正の方針を決めたりはしない。

## 前提知識

- **周回は必ず止まる。** 上限に達したら、採択が残っていても止める (上限を設ける理由の正本は [project-config.md](../review-triage/references/project-config.md) の「`loop`」)。
- **検知と選択待ちは、既存のスキルが人間の判断を求めて止まった結果である。** 周回がそれを越えて進むと、判断を求めた意味が消える。上限はそれとは別で、収束しない周回を止めるためにこのスキルが持つ関門である。
- **周回の途中でモデルを変えない。** どの回も同じモデルで走らせる。回ごとに変えると、指摘の粒度の違いがモデルの違いによるものか収束によるものかを、記録から区別できなくなる。

## 手順

1. **設定と引数を読む**: `.claude/akm-claude-plugins/review-triage/config.json` の `loop` を読み、引数で上書きする (キーと既定値の正本は [project-config.md](../review-triage/references/project-config.md) の「`loop`」。引数の様式は [references/arguments.md](references/arguments.md))。
   - **`review_skill` が設定にも引数にも無ければ、人間に尋ねる。** 推測して決めない。
   - 決まった値 (上限・レビュースキル・そのオプション) を周回の開始前に報告する。**どの条件で回るかを、回り始める前に人間が知っている状態にする。**
2. **周回**: 以下を 1 周として、手順 3 の終了条件に当たるまで繰り返す。**各回の冒頭で、いま何回目かと上限を報告する。**
   - **レビューを起動する** ([references/review-invocation.md](references/review-invocation.md) が経路・依頼文・範囲の正本)。
   - **`review-triage` を呼ぶ。** 記録への追記・サマリの再生成・コミットは `review-triage` が行う。
   - **収束と検知を判定する** (手順 3)。当たれば `review-triage-fix` を呼ばずに周回を抜ける。
   - **`review-triage-fix` を呼ぶ。** 修正・検証・コミットは `review-triage-fix` が行う。
   - **選択待ちと上限を判定する** (手順 3)。当たれば周回を抜ける。
3. **終了条件の判定**: 記録 YAML の当該回を読み、次のいずれかに当たれば周回を止める。**判定の材料は記録であって、スキルの報告の文面ではない** — 報告は要約なので、`recurrence` や `awaiting-human` の有無を取りこぼしうる。

   | 条件 | 記録のどこを見るか | いつ判定するか |
   | --- | --- | --- |
   | 収束 | 今回の `findings` に `verdict: adopted` が無い | `review-triage` の後 |
   | 検知 | 今回の `recurrence.status` が `detected` | `review-triage` の後 |
   | 選択待ち | 全回の `plans` に `status: awaiting-human` がある | **`review-triage-fix` の後** |
   | 上限 | 周回の回数が `max_rounds` に達した | `review-triage-fix` の後 |

   **判定は 2 か所に分かれる。** 収束と検知は `review-triage` が書く項目なので、`review-triage-fix` を呼ぶ前に判定して修正に進ませない (検知は `review-triage-fix` の手順 2 が人間の回答を待つと定めている)。選択待ちは `review-triage-fix` の手順 6 が書くので、呼んだ後にしか判定できない。

   - **選択待ちは全回を見る。** 過去の回で人間に返したまま回答が無い問題は、回が進んでも残る。
   - **未着手 (`status: pending`) は終了条件にしない。** `review-triage-fix` が中断した合図なので、周回を止めるのではなく報告に出す。
4. **報告**: 止まった理由と、周回で何が起きたかを出す ([references/reporting.md](references/reporting.md) が形の正本)。**採択件数の回ごとの推移を必ず出す** — 収束に向かっていたのか、減らないまま止まったのかは、件数の推移にしか現れない。
   - 上限で止まった場合は、推移を示したうえで**継続するか俯瞰に移るかを人間に問う。勝手に周回を再開しない。**
   - 検知・選択待ちで止まった場合は、次に何を人間に求めているかを書く。

## 原則

- **このスキルは判断も修正もしない。** 呼ぶだけ。判断を代行すると、`review-triage` の記録に残らない判断が生まれる。
- **上限に達したら止める。** 「あと 1 回で終わりそう」でも延長しない。延長の判断は人間が行う。
- **人間に返した状態を越えて進まない。** 検知と選択待ちは、既存のスキルが人間の判断を求めて止まった結果である。
- **周回の途中で条件を変えない。** 上限・レビュースキル・オプション・モデルは、手順 1 で決めたものを最後まで使う。途中で変えると、回どうしの比較が成り立たなくなり、検知の判断が壊れる。

## このスキルが検出しないもの

- **採否の判断が正しいか** — `review-triage` の結果をそのまま使う。
- **修正の内容が正しいか** — `review-triage-fix` の検証に委ねる。
- **収束したことが「欠陥が無い」ことを意味するか** — 意味しない。採択が 0 件になったのは、そのレビュースキル・そのモデル・その範囲で指摘が出なかったということである。
