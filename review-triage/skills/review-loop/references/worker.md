# ワーカー

**このファイルが、ワーカー (スクリプト `review-triage/scripts/review-loop-worker.sh`。人間が端末で起動し、依頼文ごとに使い捨ての作業ツリーを作って、その中で `claude -p` を走らせるプロセス) の振る舞いの正本。** スクリプトはこの文書のとおりに実装し、テスト `review-triage/tests/test_review_loop_worker.py` が確かめる。ワーカーが書くファイル (`worker.yaml`・完了の印) の様式の正本は [loop-files.md](loop-files.md) で、ここでは言い直さない。

**ワーカーは、レビュアの実行 (`claude -p` の 1 回) 以外の判断をすべてスクリプトで行う。** 起動時の確認・依頼文の探索・HEAD と作業ツリーの確認・作業場所と複製と写しの作成・上限・結果の確認と複写・ログからの判定・完了の印・終わり方は決定的なコードで、LLM の手順書に頼らない。

この文書で使う語:

- **作業側** — スキル `review-loop` を実行するセッションと、その作業ツリー (周回を始めたリポジトリの作業ツリー)。
- **回の作業場所** (以下「作業場所」) — ワーカーが依頼文ごとに環境変数 `TMPDIR` の下に作り、回の終わりに消す一時ディレクトリ。複製・写し・レビュアの実行が書く結果を置く。
- **複製** — 作業側のリポジトリを作業場所の中に複製し、依頼の `head` をチェックアウトしたもの (使い捨ての作業ツリー)。レビュアの実行はこの中で動き、確認のための変更もこの中でだけ許す。
- **写し** — 作業側の依頼文を作業場所に写し、出力先・作業ツリーのパス・作業ツリーの扱いを示す行を書き換えたもの。レビュアの実行にはこちらを渡す。
- **サンドボックス** — Claude Code の機能で、Bash のコマンドを、OS の仕組み (macOS では `sandbox-exec`) でファイルの書き込みとネットワークの接続を制限して実行するもの。`Write`・`Edit` などのツールには効かない。
- **auto モード** — 権限モード `auto`。許可の一覧に無いツールの呼び出しを、人間に問い合わせる代わりに Claude Code の判定 (以下「auto モードの判定」) が呼び出しごとに許すか拒むかを決める。

## 0.13.0 からの変更点

バージョン 0.14.0 のワーカーは、レビュアの実行を作業側の作業ツリーではなく複製の中で走らせる。0.13.0 から変わった振る舞いのうち、使う人と、0.13.0 で始めた周回に関わるものは次の 3 つ。

- **権限モードのデフォルトが `default` から `auto` になった** (理由は下の「レビュアの実行の権限」)。0.13.0 でプローブを許すために勧めた `--permission-mode acceptEdits` は要らない — 確認のための変更は複製の中で行い、複製は回ごとに消す。
- **結果を置き場に書くのは、レビュアの実行ではなくワーカーになった。** どのファイルを誰が書くかの正本は [loop-files.md](loop-files.md) の「ファイルの一覧」で、レビュアの実行が置き場に書いたときの扱いは、下の「回の処理」の表の「置き場が不変」の行。
- **0.13.0 との互換は、ワーカーのバージョンで判定する。** ワーカーは完了の印と `worker.yaml` に自分のバージョン (キー `worker_version`) を書く。バージョンの決め方の正本は [loop-files.md](loop-files.md) の「`worker.yaml`」、0.14.0 で足したキーを、レビュアの実行を起動しなかった回の印にどう書くかの正本は同じファイルの「`delivered-<識別子>.yaml`」。作業側は、印にバージョンが無いか 0.14.0 より古ければ、その回をレビュー不成立 (RA1) にし、ワーカーのバージョンが古いことを報告する (突き合わせの正本は [round.md](round.md) の RL1 の手順 c)。判定に使うのはバージョンで、0.14.0 で足したキーの有無ではない — バージョンが印にあれば、作業側は印の様式から推測せずに、ワーカーが古いことをそのまま報告できる。このほかの互換の扱いは次のとおり。
  - 0.13.0 で始めた周回の権限モードと、`loop.yaml` に無いキーの扱いの正本は [arguments.md](arguments.md) の「様式」。0.13.0 の案内のコマンドでワーカーを起動したときの扱いは、下の「止められたときの直し方」の「権限モードの指定の食い違い」の行。
  - 0.13.0 の `review-request` が書いた依頼文は、作業ツリーの扱いを示す行が無いので、写しを作れずに `failed` になる (回の処理の手順 8)。

## 起動の仕方

```
review-loop-worker.sh <周回の置き場の絶対パス> --model <指定> --effort <値>
    [--permission-mode <値>] [--allowed-tools <ツール>]...
    [--sandbox-allow-write <パス>]... [--sandbox-allowed-domain <ドメイン>]...
    [--idle-minutes <分>] [--review-timeout-minutes <分>] [-- <claude に渡す追加の引数>...]
```

| 引数 | 意味 | 省略時 |
| --- | --- | --- |
| `<周回の置き場の絶対パス>` | 周回の置き場。**絶対パスに限る** — 相対パスは起動した端末の cwd (カレントディレクトリ) を基準に解決されるので、作業側が意図した置き場と違う場所を指すことがある | 省略できない |
| `--model <指定>` | レビュアの実行のモデル (`claude -p --model` にそのまま渡す) | **省略できない** — どのモデルでレビューするかは人間が決める |
| `--effort <値>` | レビュアの実行の effort (`low` / `medium` / `high` / `xhigh` / `max`) | **省略できない** (同上) |
| `--permission-mode <値>` | レビュアの実行の権限モード。`bypassPermissions` は受け付けない (下の「レビュアの実行の権限」) | `auto` |
| `--allowed-tools <ツール>` | レビュアの実行に許すツール。繰り返して指定でき、**1 回でも指定すれば既定の一覧を置き換える** | 下の「既定の許可の一覧」 |
| `--sandbox-allow-write <パス>` | サンドボックスの中の Bash に、作業場所のほかに書き込みを許す場所 (Go のビルドのキャッシュなど)。繰り返して指定できる。絶対パスか、`~` で始まるパス (`~` はホームに展開する) に限る。許せる場所の条件は下の「起動時の確認」 | 無し (書き込みを許すのは作業場所だけ) |
| `--sandbox-allowed-domain <ドメイン>` | サンドボックスの中の Bash に接続を許すホスト。繰り返して指定できる。利用者の設定の `WebFetch(domain:…)` の許可も、接続を許すホストに加わる (下の「ネットワーク」) | 無し |
| `--idle-minutes <分>` | 印の無い依頼文が無いまま待つ上限 | 180 |
| `--review-timeout-minutes <分>` | 1 回の上限。依頼文を受け取ってから、レビュアの実行が終わるまで (準備を含む) を測る。回の終わりの処理は含まない (下の「回の処理」) | 60 |
| `-- <引数>...` | `claude -p` に渡す追加の引数。受け付けるのは `--plugin-dir <ディレクトリ>` と、`enabledPlugins` だけを持つ JSON を値にした `--settings` の 2 つ (理由はこの表の下) | 無し |

**ワーカーはプラグインの設定ファイル (`config.json`) を読まない。** 値はすべて引数で受け、作業側が設定の `review_loop` 節の値を案内のコマンドに埋める (キーの正本は [project-config.md](../../review-triage/references/project-config.md) の「`review_loop`」)。プラグインの展開先と利用者のリポジトリは別の場所にあり、スクリプトから設定を探すと、どのリポジトリの設定を読むかの基準を取り違える。Claude Code の設定ファイル (利用者の `~/.claude/settings.json` と、複製の `.claude/settings.json`・`.claude/settings.local.json`) は読むが、使うのは検査と表示だけで、読んだ値をレビュアの実行の引数には使わない (下の「起動時の確認」と「回の処理」)。

**追加の引数は、受け付けるものの一覧で検査する。** 制限を弱めるフラグ (`--add-dir`・`--mcp-config`・`--setting-sources`・`--dangerously-skip-permissions` など) は列挙しきれないので、禁止するものの一覧では検査しない。受け付ける 2 つは、ブランチ版のプラグインを通し確認するときに、インストール済みの同名のプラグインを無効にするために要る。`--settings` の `enabledPlugins` は、ワーカーが組み立てる `--settings` の JSON に合成し、`claude` には `--settings` を 1 つだけ渡す。**`--plugin-dir` で読み込んだプラグインのフックはレビュアの実行の中で動くので、信頼するブランチのプラグインにだけ使う。** 一覧に収まらない引数は、起動時の確認で `unavailable` にする。

| 終了コード | 意味 |
| --- | --- |
| 0 | `end` を見て終わった |
| 124 | 印の無い依頼文が無いまま `--idle-minutes` が過ぎた。**周回は終わっていない** — 同じコマンドで起動し直せる |
| 2 | 引数の誤り・起動時の確認が通らない・他のワーカーが動いている |
| 128 + シグナル番号 | 割り込み (INT なら 130、TERM なら 143、HUP なら 129) |

**要るもの**:

- **macOS。** サンドボックスの振る舞いを macOS でだけ実測したので、ほかの OS (Linux・Windows) では起動時の確認で止まる。
- **環境変数 `TMPDIR`。** 作業場所をその下に作る (条件は下の「起動時の確認」)。
- bash (macOS の `/bin/bash` 3.2 で動く)・git・python3 (レビュアの実行と準備のコマンドを専用のプロセスグループで起動する・`--settings` の JSON を組み立てる・設定ファイルを検査する・写しを作る・ログを読むのに使う)・`claude` (端末の `claude` は Claude Desktop app とは別に認証が要る)。
- **ワーカーはサンドボックスの外 (人間の端末) で起動する。** Claude Code のセッションの Bash ツールのように、サンドボックスの中から起動すると、サンドボックスを二重にできないので、レビュアの実行の Bash はどれも `sandbox-exec: sandbox_apply: Operation not permitted` で失敗する (サンドボックスの外で実行されることはない)。その回は、サンドボックスが止めた確認が数えられて RA1 になる。

## サポートする配置

| 配置 | 扱い |
| --- | --- |
| 作業側と同じマシンの、同じ作業ツリー | サポートする。作業ツリーの中のサブディレクトリで起動してもよい (ルートに解決して比べる) |
| 同じリポジトリの別の worktree | サポートしない。起動時の確認で「別の worktree」として `unavailable` にする — ワーカーが確かめる HEAD と作業ツリー (複製の元) が、作業側のものと違う |
| 別のクローン・別のリポジトリ | サポートしない。「別の作業ツリー」として `unavailable` にする |
| 作業側が `TMPDIR` の下にある、または作業側か周回の置き場がサンドボックスの一時ディレクトリの下にある | サポートしない。起動時の確認で `unavailable` にする (条件と理由は「起動時の確認」の表) |
| 別のマシン | サポートしない。置き場の共有と、他のワーカーの判定 (`kill -0`) が同じマシンを前提にしている |

リポジトリの種類では、submodule を含むもの・Git LFS を使うもの・partial clone と shallow clone で作ったものをサポートしない (下の「回の処理」の手順 6)。

## 起動時の確認

**上から順に確かめる。** 1 だけは通らなくても `worker.yaml` に触れない (動いている他のワーカーの状態を上書きしないため)。2 は確認ではなく前の起動の後始末で、結果に関わらず次に進み、`worker.yaml` を書かない。3〜14 は、最初に通らなかった項目を理由に `worker.yaml` を `unavailable` で書いて、終了コード 2 で終わる。15 は表示だけで、止めない。

| 順 | 状況 | 確かめ方 | 通らないときの扱い |
| --- | --- | --- | --- |
| 1 | 他のワーカーが動いていない | `worker.yaml` の `state` が `idle` / `reviewing`・ファイルの更新時刻が 30 秒以内・`pid` のプロセスが動いている (`kill -0`) の **3 つがすべて成り立てば、動いている** | `worker.yaml` に触れず、PID と止め方 (そのワーカーの端末で Ctrl-C か `kill -TERM <PID>`) を標準エラーに出力して終了コード 2 |
| 2 | 前の起動の作業場所を片付ける (掃除) | `worker.yaml` のキー `workspace` に作業場所のパスがあれば (無いか空なら、「回の処理」の手順 5 の決まったパス)、その中を cwd にしているプロセスを止め (TERM を送り、数秒後に残っていれば KILL を送る)、作業場所を消す。止めて消すのは、パスが作業場所の名前の形 (「回の処理」の手順 5) に合い、シンボリックリンクでないディレクトリのときだけで、消し方は回の終わりの処理の「作業場所を消す」と同じ | 止めない。消さなかった・消せなかった作業場所は、パスを標準エラーに出力する |
| 3 | macOS で動いている | `uname -s` が `Darwin` | `unavailable` |
| 4 | 置き場に `loop.yaml` があり、`repo_dir` が読める | ファイルの有無と、トップレベルの `repo_dir` の行 | `unavailable` |
| 5 | 作業側と同じ作業ツリーで起動した | `git rev-parse --show-toplevel` を実体パス (`cd` して `pwd -P`) に解決したものが、`repo_dir` の実体パスと一致する | 一致しなければ、`git rev-parse --git-common-dir` の実体パスが同じなら「別の worktree」、違えば「別の作業ツリー」を理由に `unavailable` |
| 6 | HEAD が読める | `git rev-parse --short HEAD` | `unavailable` |
| 7 | 周回が終わっていない | 置き場に `end` が無い | `unavailable` |
| 8 | 使うコマンドがある | `command -v claude` と `command -v python3` | `unavailable` |
| 9 | 作業場所を置ける一時ディレクトリがある | 環境変数 `TMPDIR` があり、その実体パスがホームの外と作業側の外にあり、作業側が `TMPDIR` の実体の下に無い | `unavailable`。`TMPDIR` が無くても `/tmp` に代えない |
| 10 | 作業側と置き場が、サンドボックスの一時ディレクトリの外にある | 作業側と周回の置き場の実体パスが、サンドボックスの一時ディレクトリ (`/private/tmp/claude-<利用者の番号>`。サンドボックスの中の Bash がデフォルトで書ける場所) の下に無い | `unavailable` |
| 11 | パスを許可と拒否の規則に書ける | 作業側・周回の置き場・`TMPDIR` の実体パスに、`( ) [ ] { } * ? ! #` のどの文字も無い | `unavailable` |
| 12 | 書き込みを許す場所が、守る場所を含まない | `--sandbox-allow-write` の各値が、絶対パスか `~` で始まるパスで、ホーム・作業側・周回の置き場のどれとも同じでなく、どれの祖先でもない | `unavailable` |
| 13 | 追加の引数が、受け付ける一覧に収まる | `--` 以降が `--plugin-dir <ディレクトリ>` と `--settings <JSON>` だけで、`--settings` の値が JSON として読め、トップレベルのキーが `enabledPlugins` だけで、その値がプラグイン名から真偽値への対応 | `unavailable` |
| 14 | 利用者の設定が、コマンドをサンドボックスの外で実行させない | 利用者の設定ファイル `~/.claude/settings.json` が無いか、JSON として読めて、設定キー `sandbox.excludedCommands` が無いか空 | `unavailable` (JSON として読めないときも。検査できないため) |
| 15 | (表示) 接続を許すホストに加わるドメイン | `~/.claude/settings.json` の許可の規則のうち `WebFetch(domain:<ドメイン>)` の形のものを読み、サンドボックスの接続を許すホストに加わるドメインを表示する。`WebFetch(domain:*)` があれば、レビュアの実行の Bash が外のすべてのホストに接続できることを表示する | 止めない |

1 の判定に更新時刻を加えるのは、`kill -9` で終了させたワーカーの PID が別のプロセスに再利用された場合に、動いていないワーカーを動いていると判定しないため。名前や乱数の値でワーカーを見分けない。

2 を 1 の直後に行い、`worker.yaml` を書くどの処理よりも前にするのは、`end` がある周回や、ほかの確認で `unavailable` になる起動でも、前の起動が残したプロセスと作業場所を片付けるため。`kill -9` で消えたワーカーのレビュアの実行と、その Bash の子は動き続けている (下の「終わり方」)。残ったプロセスは cwd で見つける (macOS ではコマンド `lsof` で)。プロセスグループでは見つけられない — Bash のコマンドはレビュアの実行とは別のプロセスグループで動く (実測)。名前 (`claude`) でも照合しない — 利用者の対話セッションも同じ名前で動く。止めて消す範囲を名前の形に合う作業場所に限るのは、`worker.yaml` に書かれた値だけを根拠に、ワーカーが作ったのではないディレクトリの中のプロセスを止めたり、そのディレクトリを消したりしないため。`workspace` の値が無いか空 (前の起動が `idle` のときに消えた場合など) でも決まったパスを見るのは、回の終わりに消せなかった作業場所も片付けるため。

3〜14 の理由は次のとおり。

- **3** — 上の「要るもの」。
- **9** — 作業場所はレビュアの実行に書き込みを許す場所で、ホームと作業側は拒否の規則で守る場所 (下の「レビュアの実行の権限」)。`TMPDIR` がホームの下だと、作業場所への結果の書き込みが拒否の規則 `Edit(~/**)` に当たる。作業側と `TMPDIR` のどちらかがもう一方を含むと、許す場所と守る場所が重なる。`/tmp` に代えないのは、`/tmp` は他の利用者も書ける場所で、作業場所の名前も予測できるため。
- **10** — サンドボックスの中の Bash は、サンドボックスの一時ディレクトリにはデフォルトで書けるので、その下にある作業側と置き場を守れない。
- **11** — 実体パスを、許可の規則 (`Edit(//<パス>)`) と拒否の規則 (`Edit(//<パス>/**)`) に埋める。Claude Code は、これらの文字を含むパスの規則を正しく扱えない。
- **12** — そうでないと、サンドボックスの中の Bash に、ホームの全体か作業側か置き場への書き込みを許してしまう。
- **13** — 上の「起動の仕方」の「追加の引数は、受け付けるものの一覧で検査する」。
- **14** — 設定キー `sandbox.excludedCommands` に当たるコマンドは、仕様としてサンドボックスの外で動くので、Bash をサンドボックスの中で動かす前提が成り立たない。レビュー対象のブランチの設定は、回ごとに複製で確かめる (「回の処理」の手順 7)。

15 の理由は下の「ネットワーク」。

すべて通れば `worker.yaml` を `idle` で書き (ワーカーのバージョン・書き込みを許す場所・接続を許すドメインも書く)、更新時刻を 5 秒おきに進めるバックグラウンドの処理を始める。

## 回の処理

**回の処理は、準備 (手順 2〜8)・レビュアの実行 (手順 9)・回の終わりの処理 (手順 10) に分かれる。**

1. **探す**: 5 秒おきに、置き場の `review-request-<識別子>.md` のうち完了の印 (`delivered-<識別子>.yaml`) が無いものを、識別子の順で 1 つ選ぶ。一時名 (`.` で始まる名前) は見ない。**回の処理の間 (受け取ってから印を書くまで) に置き場に現れた依頼文は、この起動の間は選ばない** — レビュアの実行が置いたものとみなす (作業側は、ワーカーが印を書くまで次の依頼文を書かない)。
2. **受け取る**: `worker.yaml` を `reviewing` にし、識別子と作業場所のパスを書く。上限の計測を始め、置き場のファイルの一覧と各ファイルの更新時刻を控える (`worker.yaml`・`loop.yaml`・その回のログを除く)。`loop.yaml` を除くのは、作業側が再開 (`--resume`) や停止のときに、レビュー中でも書き換えるため — 含めると、作業側の正当な書き換えでその回が `failed` になる (通し確認で、レビュー中に打った `--resume` がこれを起こした)。その回の結果は除かない — レビュアの実行は結果を作業場所に書き、置き場の結果はワーカーが手順 10 で複写するので、それより前に置き場の結果が変われば、レビュアの実行が置き場に書いたことになる。
3. **依頼文を確かめる**: 埋め残しの `{{` が無い、`## 出力様式` の行がある、`head: "<SHA>"` の行がある。
4. **作業側の HEAD と作業ツリーを確かめる**: 依頼文の `head` と作業側の HEAD が同じコミットを指し (`git rev-parse` で完全な SHA にして比べる)、作業側の `git status --porcelain` が空であること。
5. **作業場所を作る**: パスは、`TMPDIR` の実体の下の、周回ごとに決まるディレクトリ (例: `<TMPDIR の実体>/review-loop-<周回 id>-<ハッシュ>/`)。周回 id は置き場のディレクトリ名、ハッシュは周回の置き場の実体パスから作る短い値 (SHA-256 の 16 進の先頭 8 文字) で、どちらも周回の間は変わらない。前の回の作業場所が残っていれば、回の終わりの処理と同じ手順 (残ったプロセスを止め、作業場所を消す) で消してから作る。パスにシンボリックリンクが残っていれば (前の回の終わりに、置き換えられていたので消さなかったもの)、リンクだけを消す (リンクの先は消さない)。作ったディレクトリが自分の所有で、シンボリックリンクでないことを確かめる。
   - パスを周回の間使い回すのは、レビュアの実行の cwd が回ごとに変わると、Claude Code が cwd ごとに作る `~/.claude/projects/` の下のディレクトリが回の数だけ増えるためと、起動時の確認 2 の掃除の範囲をこのディレクトリに限るため。
   - ハッシュを足すのは、別のクローンで同じブランチの周回を同じ分に始めたときに、名前が重ならないようにするため。
6. **複製を作る**: 作業側のリポジトリを `git clone --shared --no-checkout` で作業場所の `tree/` に複製し、remote の設定を消し、作業側のブランチ・リモート追跡ブランチ・タグ (`refs/heads/*`・`refs/remotes/*`・`refs/tags/*`) を取り込んでから、依頼の `head` (作業側で解決した完全な SHA) を detached HEAD (ブランチではなくコミットを直接指す状態) でチェックアウトする。
   - `git worktree` で作らないのは、その管理情報が作業側のリポジトリの中 (多くはホームの下) に置かれ、サンドボックスの中の git の書き込み (インデックスの更新など) が止まるため (実測)。`--shared` の複製は git のオブジェクトを作業側と共有するので、増えるのは作業ツリーを展開した分だけ。
   - ブランチ・リモート追跡ブランチ・タグを取り込むのは、全量の回の `base` がブランチ名 (`main` など) でも、複製の中で作業側と同じコミットに解決できるようにするため。
   - remote の設定を消すのは、`git push origin` の行き先 (作業側のリポジトリ) を無くすため。
   - 複製に submodule の項目 (モード 160000) があれば、複製の作成の失敗とする。Git LFS・partial clone・shallow clone のリポジトリもサポートしない (複製の作成かチェックアウトが失敗すれば、同じく複製の作成の失敗になる)。
   - git が追跡しないファイル (依存のディレクトリ・`.env`・`.claude/settings.local.json` など) は複製に無い。そのため確認が失敗することがあり、その回はレビュアの報告か RA1 で分かる。
7. **複製の設定を確かめる**: 複製の `.claude/settings.json` と `.claude/settings.local.json` のどちらかに、空でない `sandbox.excludedCommands` があるか、JSON として読めなければ通らない。理由は起動時の確認の 14 と同じ。
8. **写しを作る**: 作業側の依頼文を、作業場所の `review-request-<識別子>.md` に写し、次の順に文字列を置き換える。
   1. 元の出力先の絶対パスの、すべての出現 → 作業場所の結果のパス (`<作業場所>/review-<識別子>.yaml`)
   2. バッククォートで囲んだ元の作業ツリーのパス → 複製のパス
   3. 作業ツリーの扱いを示す行 (雛形 [review-request-template.md](../../review-triage/references/review-request-template.md) の「対象」の節の「作業ツリーの扱い」) の値 → 「使い捨て」

   出力先は作業ツリーのパスで始まる (置き場は作業ツリーの中にある) ので、この順でないと出力先が複製の中のパスになる。元の出力先は依頼文の「出力先:」の行から読み、置き場から組み立てたもの (実体が周回の置き場で、名前が `review-<識別子>.yaml`) でなければ通らない。元の作業ツリーのパスは作業側の実体パスで、バッククォートで囲んだものが 1 つも無ければ通らない (写しが作業側を指したままになるため)。置き換えの後に、元の出力先か元の作業ツリーのパスが残っているか、扱いの行がちょうど 1 つでなければ通らない。作業側の依頼文は変えない。**依頼文を写して書き換えるのは、依頼文とプロンプトが食い違わないようにするため** — プロンプトで「依頼文の出力先ではなくここに書く」と伝えると、レビュアが依頼文に従うことがある。
9. **レビュアの実行を起動して待つ** (下の「レビュアの実行」)。
10. **回の終わりの処理**: 次の順に行う。
    1. **残ったプロセスを止める**: 作業場所の中を cwd にしているプロセスが残っていれば、TERM を送り、5 秒後に残っていれば KILL を送る。正常に終わった回でも行う — 後始末の途中で、作業場所に書かれないようにするため。上限と割り込みの回は、先にレビュアの実行のプロセスグループを止めてから行う (下の「レビュアの実行」)。プロセスの cwd は、macOS ではコマンド `lsof` で読む (`/proc` があるときは `/proc/<PID>/cwd` を読む。CI (ubuntu) のテストはこちらを通る)。
    2. **ログを読む** (下の「ログの読み方」)。
    3. **確かめる**: 下の表の項目を確かめる。1 つでも当たれば `failed` で、当たった項目をすべて `error` に書く (`; ` で区切る)。
    4. **結果を複写する**: 作業場所の結果が、通常のファイルで、実体パスが作業場所の実体の下にあり、大きさが上限 (1 MiB。1,048,576 バイト) 以下なら、置き場の出力先に [loop-files.md](loop-files.md) の「一時名と改名」のとおり書く。複写するときは、結果と一時名をシンボリックリンクを辿らずに開く。`failed` の回でも、この条件を満たせば複写する — RA1 の報告から人間が結果を読めるようにするため。
    5. **作業場所を消す**: 作業場所のパスがシンボリックリンクでなく、実体が作ったときと同じであることを確かめてから、中のディレクトリに所有者の書き込みの権限 (中に降りられるように、読み取りと実行の権限も) を足し (Go のモジュールのキャッシュなど、読み取り専用のディレクトリを作るツールがあるため)、`rm -rf` で消す。git は使わない。消せなければ、パスをワーカーの出力に書いて続け、印の `status` は変えない。残った作業場所は、次の回の手順 5 で消す。
    6. **完了の印を書き** (一時名から改名)、`worker.yaml` を `idle` に戻す (作業場所のパスを空にする)。**印を書かずに次の依頼文に進まない。**

    **1〜6 の間に受けたシグナルは、印を書き終えてから処理する。** 印の無い回と、消し残した作業場所を作らないため。端末の Ctrl-C のようにワーカーのプロセスグループ全体に届くシグナルで、1〜6 が起動したコマンド (結果の複写や作業場所の削除) が止まらないように、1〜6 は INT・TERM・HUP を無視するサブシェルで行う (無視はコマンドに引き継がれる)。ワーカー自身はサブシェルを待つ間に受けたシグナルを控えておき、印を書き終えてから `left` で終わる。

**準備 (手順 3〜8) のどれかが通らなければ、レビュアの実行を起動しない。** 作業場所があれば回の終わりの処理の 1 と 5 の手順で消し、`failed` の印を書いて `idle` に戻る。

**上限は、依頼文を受け取ってから (手順 2) レビュアの実行が終わるまでを測る。** 準備のコマンド (手順 6 の各段の git と、手順 8 の写しを作る処理) もレビュアの実行と同じく専用のプロセスグループでバックグラウンドに起動して待ち、上限を越えたらプロセスグループごと止める。手順 7 は通常のファイルを読むだけなので、ワーカーのプロセスで行う。上限を越えたかは、準備の各段の前とレビュアの実行を起動する前にも確かめる — 準備の段の合間に越えたときに、レビュアの実行を起動しないため。越えたかどうかはワーカーが時計で確かめる。上限を測るバックグラウンドの処理は、上限の時刻を過ぎたら、止められるまで 1 秒おきにワーカーに `USR1` を送り、ワーカーが待っている `wait` を途中で戻す (1 度だけだと、`wait` を始める直前に届いた `USR1` は `wait` を戻さない)。準備の途中で越えた回は、レビュアの実行を起動せずに `failed`・`error: timeout` の印を書く。回の終わりの処理 (手順 10) は上限の対象にしない — 途中で止めると、印の無い回や消し残した作業場所ができる。

**不変条件: ワーカーは、レビュアの実行を起動した後、複製の中で git を実行しない。** レビュアの実行は複製を変えてよいので、git が後で実行するコマンドを複製の `.git/config` に書いたり (`core.fsmonitor`・`core.hooksPath`・`filter.<名前>.clean` など)、`.git/hooks/` にフックを置いたりできる。ワーカーがその複製で git を実行すると、そのコマンドがサンドボックスの外で動く。サンドボックスと拒否の規則もこれらの書き込みを止めるが (下の「レビュアの実行の権限」)、ワーカーはそれに頼らない。複製に対する git は手順 6 でだけ行い、作業場所は `rm -rf` だけで消す。手順 4 と回の終わりの確認で使う git は、複製ではなく作業側のリポジトリに対して実行する。

| 項目 | 確かめ方 | `error` に書くもの |
| --- | --- | --- |
| 依頼文の形 (手順 3) | 上のとおり | `request malformed (unfilled placeholder)` / `request malformed (no output format section)` / `request malformed (no head line)` |
| HEAD (手順 4) | 上のとおり | `head mismatch (expected <依頼文の head>, actual <HEAD>)` |
| 作業ツリー (手順 4) | 上のとおり | `tree not clean (<汚れたファイルの一覧>)` |
| 作業場所 (手順 5) | 残っていた作業場所が消え、新しい作業場所ができ、それが自分の所有でシンボリックリンクでない | 作業場所を作れなかったことと理由 (`workspace failed (<理由>)`) |
| 複製 (手順 6) | 各段 (複製・remote の設定の削除・取り込み・チェックアウト) が成功し、submodule の項目が無い | 失敗した段と理由 (`clone failed (<段>: <git の出力の最後の行>)`。段の名前は `clone`・`remove remote`・`fetch refs`・`checkout`。submodule の項目があれば `clone failed (submodule: <パスの一覧>)`) |

作業場所・複製・複製の設定・写し・結果のファイル・結果の複写の `error` には、何が通らなかったかと理由を 1 行で書く。先頭の語 (`workspace failed` など) はほかの項目と同じく英語の決まった形で、括弧の中の理由の細部はスクリプトが決める。作業場所は回ごとに作り直すので、作業場所にある結果は、この回のレビュアの実行が書いたものである。

レビュアの実行を起動しなかった回 (準備で通らなかった回) は、通らなかった項目だけを `error` に書く。レビュアの実行を上限か割り込みで止めた回は、結果の 4 項目 (ある・ファイル・形・`run_id`) を確かめない — 止めた実行の結果は使わない。権限モード・HEAD・作業ツリー・置き場は確かめる (止める前にレビュアの実行が変えていれば、それも人間が片付けるものなので `error` に並べる)。

**`ok` の印は、置き場の出力先に結果が通常のファイルとして在ることを確かめてから書く** — 手順 10 の 4 (結果の複写) の後に 6 (完了の印) を行い、4 では上の表の「結果の複写」の行のとおり、改名の後に通常のファイルとして在ることを確かめる。**拒否された呼び出しとサンドボックスが止めた確認は、`failed` の条件にしない** — 件数を印に書くだけで、その回を使うかはワーカーが決めない。**レビュアの実行の終了コードも条件にしない** — 印の `exit_code` に残すだけで、使えるかは結果の形と前後の状態で決める。

**置き場の比較は、作業ツリーの確認とは別に行う。** 置き場は git に無視されているので、`git status` では検出できない。レビュアの実行が依頼文や `end` を置くと、ワーカーや作業側がそれに従ってしまう。レビュアの実行が結果を置き場の出力先に直接書いた場合も、この比較で検出する。

## レビュアの実行

```
claude -p "<プロンプト>" --model <指定> --effort <値> --permission-mode <値> \
  --settings '<JSON>' --strict-mcp-config \
  --allowedTools <許可の一覧>... --disallowedTools <拒否の規則>... \
  --output-format stream-json --verbose [--plugin-dir <ディレクトリ>]
```

- **プロンプトは決まった形の 1 文「依頼文 `<写しの絶対パス>` のとおりに作業し、結果を依頼文が指す出力先に書く。」で、依頼文の中身を写さない。** 依頼文はレビュアが読む前提で書かれている (雛形の冒頭)。写すと、貼り方が回ごとに変わる元の問題 ([review-request.md](../../review-triage/references/review-request.md) の「依頼文はファイルに書き出し、パスだけを渡す」) に戻る。プロンプトが指すのは作業側の依頼文ではなく写しで、写しの出力先は作業場所の結果を指す (「回の処理」の手順 8)。
- `--settings`・`--strict-mcp-config`・`--allowedTools`・`--disallowedTools` の中身と理由は、下の「レビュアの実行の権限」。`--settings` は、追加の引数の `enabledPlugins` を合成した 1 つだけを渡す。
- cwd は複製 (作業場所の `tree/`)、標準入力は `/dev/null`。標準出力と標準エラーは、置き場の `<識別子>.log` にそのまま書く。ログを置き場に置くのは、レビュアの実行から書けない場所に置くため (下の「ログの読み方」の「ログを信頼できる前提」)。
- **専用のプロセスグループで、バックグラウンドで起動し、`wait` で終わりを待つ。** フォアグラウンドで待たないのは、bash がフォアグラウンドのコマンドを待っている間は trap (シグナルを受けたときの処理) をそのコマンドが終わるまで遅らせるためと、専用のプロセスグループにしないと端末の Ctrl-C がワーカーとレビュアの実行に同時に届き、止める順序を制御できないため。待っている間も更新時刻を進める。
- **上限を越えたとき・割り込みを受けたときは、プロセスグループ全体に TERM を送り、5 秒後に残っていれば KILL を送り、止まったことを確かめる。** そのあと回の終わりの処理で、作業場所の中を cwd にしているプロセスも止める — Bash のコマンドはレビュアの実行とは別のプロセスグループで動くので (実測)、プロセスグループを止めても残ることがある。印の `exit_code` はレビュアの実行の終了コード (上限と割り込みでは、プロセスグループを止めた後の値) で、cwd で見つけたプロセスを止めても変えない。

`-p` の中でも Skill と Agent のツールは使える。レビュアの実行には、利用者の設定 (許可と拒否の規則・フック・サンドボックスの設定)・インストール済みのプラグイン・CLAUDE.md も効く。MCP サーバーと自動メモリは使わせない (下の「MCP サーバーと自動メモリ」)。レビュー対象のブランチの設定 (複製の `.claude/settings.json`) も効く — `-p` では、その許可の規則は使われず、拒否の規則・フック・環境変数・サンドボックスの設定が使われ、auto モードを無効にする設定 `disableAutoMode` も効く。このうち `sandbox.excludedCommands` だけはワーカーが確かめ (「回の処理」の手順 7)、ほかは作業側の作業ツリーで走らせていた 0.13.0 と同じ扱いにする。

## レビュアの実行の権限

**レビュアの実行は、複製の中で、auto モード・サンドボックス・拒否の規則の 3 つを組み合わせて走らせる。** 確認のための変更 (テストの実行・プローブ・ミューテーション) は複製と作業場所の中でだけ許し、その外 (作業側の作業ツリー・周回の置き場・ホームの下) は変えさせない。3 つは受け持つものが違う — auto モードの判定は、許可の一覧に無い呼び出しを 1 つずつ許すか拒むかを決める。サンドボックスは、Bash のコマンドによる書き込みと接続を、場所と接続先で制限する。拒否の規則は、ツールを問わず、規則に当たる呼び出しを止める。

この節と「ログの読み方」の「実測」は、Claude Code 2.1.273 と macOS 26.5 で 2026-09-27 に行ったもの。記録は [#68 のコメント](https://github.com/akm/claude-plugins/issues/68#issuecomment-5852454987) と、計画 `docs/plans/2026-09-27-1431-feat-review-loop-sandbox-plan.md` の「Dependencies / Assumptions」にある。

### 権限モードと許可の一覧

**デフォルトの権限モードは `auto`。** 権限モード `default` では、依頼文の雛形の「検証の前払い」が求める確認 (テストの実行・プローブ・ミューテーション) の呼び出しの多くが、安全のための検査 (コマンドの置換・ヒアドキュメント・環境変数つきの実行・作業ディレクトリの外への書き込みなど) で拒否され、許可の一覧を足しても防げなかった ([#68](https://github.com/akm/claude-plugins/issues/68))。auto モードでは、同じ形の呼び出しが拒否されなかった (実測)。

**auto モードでは、許可の一覧は、判定の前にその場で許すものを決めるだけの役割を持つ。** 一覧に無い呼び出しは、auto モードの判定が許すか拒むかを決める。任意のコードの実行を許す広い規則 (`Bash(*)`・インタプリタのワイルドカード・`Agent` など) は、auto モードでは使われず、それらの呼び出しも判定が決める。そのため、デフォルトの一覧は読み取りのツールと `Skill`・`Agent` だけにし、テストのコマンドなどを足さない — 確認の実行と sub-agent の起動は判定に任せる。

既定の許可の一覧:

- git の読み取り — `Bash(git diff:*)`・`Bash(git log:*)`・`Bash(git show:*)`・`Bash(git status:*)`・`Bash(git rev-parse:*)`・`Bash(git merge-base:*)`・`Bash(git ls-files:*)`・`Bash(git blame:*)`・`Bash(git cat-file:*)`・`Bash(git grep:*)`
- ファイルの読み取り — `Read`・`Grep`・`Glob`
- スキルと sub-agent — `Skill`・`Agent`

**結果ファイルへの書き込みの許可 `Edit(//<作業場所の結果の絶対パス>)` は、ワーカーが毎回足す** (`--allowed-tools` で一覧を置き換えたときも)。`//` の後に、ルートからのパスを続ける (Claude Code の許可の規則で、絶対パスを表す書き方)。結果のパスは識別子から導出する。

- **`bypassPermissions` は受け付けない** (引数の誤りとして終了コード 2)。すべての呼び出しを、問い合わせも判定も経ずに許すモードで、許可の一覧と auto モードの判定が意味を持たなくなる。
- `default` など、ほかの権限モードは受け付ける (0.13.0 で始めた周回を `default` のまま続けられるようにするため)。
- **`-p` は許可の問い合わせに答えられないので、拒否された呼び出しは拒否されるだけで、レビュアは実行を続ける。** 拒否には、拒否の規則に当たったもの・auto モードの判定が拒んだもの・安全のための検査で拒否されたものがある。調べられなかった範囲の指摘が欠けたまま結果が書かれるので、ワーカーは拒否の件数とツール名を完了の印の `permission_denials` に書き、作業側がレビュー不成立 (RA1) として止める。**拒否された回を取り込まないのは、実行できなかった確認を「実行した」と書いた結果を記録に入れないためでもある** — 0.13.0 の通し確認で、`python3` の実行を 2 度とも拒否されたレビュアが、結果の `evidence` に「実行して確認」と書いた。
- 利用者の設定の許可と拒否の規則も効く。拒否の規則はワーカーの拒否の規則と合わさる。
- Claude Code は、auto モードでも、安全のための検査で呼び出しを拒否することがある。その拒否も `permission_denials` に数えられ、RA1 になる (頻度の見直しは [#65](https://github.com/akm/claude-plugins/issues/65))。

### サンドボックス

**レビュアの実行の Bash は、サンドボックスの中で動かす。** ワーカーは `--settings` で次の値を渡す。

| 設定キー | 値 | 理由 |
| --- | --- | --- |
| `sandbox.enabled` | `true` | Bash をサンドボックスの中で動かす |
| `sandbox.autoAllowBashIfSandboxed` | `true` | サンドボックスの中で動く Bash の呼び出しを、問い合わせずに許す |
| `sandbox.allowUnsandboxedCommands` | `false` | サンドボックスに止められたコマンドを、Bash の引数 `dangerouslyDisableSandbox` でサンドボックスの外で実行し直させない。実測で、レビュアはこの実行し直しを行い、auto モードの判定はそれを許した |
| `sandbox.failIfUnavailable` | `true` | サンドボックスを起動できないときに、サンドボックスの外で実行せずにエラーで終わらせる (CLI のデフォルト値は `false` で、警告を出してサンドボックスの外で実行する) |
| `sandbox.filesystem.allowWrite` | 作業場所と、`--sandbox-allow-write` の値 | 書き込みを許す場所。作業場所は、一時ディレクトリのデフォルトの扱いに頼らずに明示する |
| `sandbox.network.strictAllowlist` | `true` | 下の「ネットワーク」 |
| `sandbox.network.allowedDomains` | `--sandbox-allowed-domain` の値 | 同上 |
| `autoMemoryEnabled` | `false` | 下の「MCP サーバーと自動メモリ」 |

**サンドボックスの中の Bash が書けるのは、cwd (複製)・`allowWrite` の場所・サンドボックスの一時ディレクトリの 3 つだけ** (実測)。ほかの `/private/tmp` の下・利用者の一時ディレクトリ (`TMPDIR` が指す `/var/folders/…`。作業場所だけは `allowWrite` で許す)・ホームの下には書けない。作業側と周回の置き場も、この 3 つの外にある (起動時の確認の 10 と 12 で確かめる)。複製の中でも、`.git/config`・`.git/hooks/`・`.claude/settings.json`・`.mcp.json` には書けない (サンドボックスが保護するパス。`git checkout -- <ファイル>` と `git stash list` は通る)。

- **テストがホームの下のキャッシュに書くなら、その場所を `--sandbox-allow-write` で許す** (続けて使うなら設定 `review_loop.sandbox_allow_write` に書く)。実測で、`go test` は Go のビルドのキャッシュ (`~/Library/Caches/go-build`) への書き込みが止まって失敗し、キャッシュを許すと、拒否の規則 `Edit(~/**)` と一緒でも通った。
- 利用者の設定とレビュー対象のブランチの設定の `sandbox.filesystem.allowWrite` は、ワーカーの値と合わせて使われる。ワーカーはこれを確かめない (下の「このワーカーが検出しないもの」)。
- サンドボックスが効くのは Bash だけで、`Write`・`Edit` のツールには効かない。ツールによる書き込みは、次の拒否の規則で止める。

### 拒否の規則

**ワーカーは `--disallowedTools` に次の規則を渡す。** 拒否の規則は auto モードの判定より優先し、sub-agent の呼び出しにも効く。sub-agent の中で拒否された呼び出しも、最上位の `result` の行の `permission_denials` に数えられる (実測)。`Edit` の規則は、ファイルを書き換えるすべての組み込みのツール (`Write`・`NotebookEdit` を含む) に効く。

| 規則 | 止めるもの |
| --- | --- |
| `AskUserQuestion` | 人間への問い。`-p` は人間に問えないので、外しておくとレビュアは問わずに進む (外したツールはレビュアに示されない) |
| `Edit(~/**)` | ツールによるホームの下への書き込み |
| `Edit(//<作業側の実体パス>/**)`・`Edit(//<周回の置き場の実体パス>/**)` | ツールによる作業側と置き場への書き込み。ホームの外にあるリポジトリも守る |
| 複製の中の `.claude/`・`.git/`・`.mcp.json` への `Edit` | Claude Code と git が後で読んで実行するもの (設定・フック・MCP サーバーの定義) の書き換え |
| `Bash(git push:*)` | 名前が `git push` で始まるコマンド。書き方を変えたもの (`git -C . push` など) には当たらないが、複製には remote の設定が無く、作業側のリポジトリへの Bash の書き込みはサンドボックスが止める |

### ネットワーク

**ネットワークは利用者の設定に従う。** ワーカーは `--settings` で `sandbox.network.strictAllowlist` を `true` にし、`sandbox.network.allowedDomains` に `--sandbox-allowed-domain` の値を渡す。サンドボックスの中の Bash が接続できるのは、接続を許すホストの一覧 (この値と、利用者の設定から加わるもの) にあるホストだけになる。

- **利用者の設定の許可の規則 `WebFetch(domain:<ドメイン>)` は、サンドボックスの接続を許すホストに加わる** (Claude Code の仕様。実測で確かめた)。`WebFetch(domain:*)` があれば、レビュアの実行の Bash は外のすべてのホストに接続できる。利用者が許可をドメインごとに絞れば、ワーカーを変えずに、接続できるホストを絞れる。
- **ワーカーはこれを止めず、起動時に表示する** (起動時の確認の 15)。利用者が `WebFetch(domain:*)` で許しているなら、レビュアの実行もそれで動いてよい、という判断による。
- `strictAllowlist` を `true` にするのは、auto モードでサンドボックスが有効なとき、一覧の外のホストへの接続を auto モードの判定がコマンドごとに許すことがあるため (Claude Code 2.1.271 以降の仕様)。`true` にすると、この許し方は使われない。
- `WebFetch` と `WebSearch` のツールも利用者の設定に従う (拒否しない)。ネットワークのコマンド (`curl` など) を名前で拒否する規則は足さない — 接続できるかは、接続を許すホストの一覧で決まる。
- 一覧の外への接続は `CONNECT tunnel failed, response 403` などで失敗し、Bash の結果の本文に `<sandbox_violations>` のタグが付く。これはサンドボックスが止めた確認として数えられる (下の「ログの読み方」)。

### MCP サーバーと自動メモリ

- **`--strict-mcp-config` を付けて、MCP サーバーを読ませない** (`--mcp-config` を渡さないので、1 つも読まない)。実測では、利用者の claude.ai のコネクタ (Slack など) がレビュアの実行の `init` の行に並んでいた。レビューには要らず、外へ書き込む手段にもなる。
- **自動メモリ (Claude Code がセッションをまたいで覚えたことを書くファイル) を、設定キー `autoMemoryEnabled` を `false` にして使わせない。** 自動メモリの置き場はホームの下で、書き込めば拒否の規則に当たる。

### 止められたときの直し方

**この表が、レビュアの実行を止めたもの (拒否・サンドボックス・権限モードの食い違い・ワーカーのバージョン) ごとの、人間が行う直し方の正本。**

| 止めたもの | どこに現れるか | 直し方 |
| --- | --- | --- |
| 拒否の規則 | 印の `permission_denials`。拒否の理由はログの `tool_result` の文面 | 当たった規則を確かめる。上の「拒否の規則」にある規則は、複製と作業場所の外を変える呼び出しを止めるためのもので、引数では外せない。利用者の設定かレビュー対象のブランチの `.claude/settings.json` の規則なら、その設定を見直す |
| auto モードの判定 | 同上 | 拒否の理由を読んで判断する。判定の前に許す必要があれば、その呼び出しに当たる規則を `--allowed-tools` (設定 `review_loop.allowed_tools`) に足す。ただし、広い規則 (`Bash(*)` など) は足しても使われない (正本は上の「権限モードと許可の一覧」) |
| 安全のための検査 | 同上 | 許可の一覧では直せない (許可の規則に当たる呼び出しでも拒否される)。起動のコマンドは変えない |
| サンドボックス | 印の、サンドボックスが止めた確認 (コマンドと、止められたパスかホスト) | 止められたのがパスなら設定 `review_loop.sandbox_allow_write` に、ホストなら `review_loop.sandbox_allowed_domains` に足す。サンドボックスと関係の無い、操作が許されないことを示すエラー (macOS 自身の保護など) なら、設定では直せない |
| 権限モードの指定の食い違い | 作業側が、印の権限モードの指定を `loop.yaml` と比べる | 作業側が案内するコマンドでワーカーを起動し直す。0.13.0 の案内は `default` のときに `--permission-mode` を付けなかったので、そのコマンドで起動するとデフォルトの `auto` になる |
| 実効の権限モードの食い違い | 印の `error` の `permission mode mismatch` | 指定したモデルが auto モードに対応しているかを確かめる (実測で、`haiku` を指定すると `default` になった)。サーバー側で auto モードが一時的に使えないこともあり、`--resume` で同じ回をやり直せる |
| ワーカーのバージョン | 作業側が、印のワーカーのバージョンを確かめる | 0.14.0 以降のワーカーで起動し直す |

## ログの読み方

**ログは 1 行ずつ JSON として読み、読めない行 (フックの出力や標準エラーの行など) は飛ばす。** `parent_tool_use_id` が空でない行 (レビュースキルが起動した sub-agent の行) は、実効モデル・`skill_called`・実効の権限モードには使わない。サンドボックスが止めた確認だけは sub-agent の行も数える — sub-agent の中の Bash もサンドボックスに止められ、同じ形でログに残る (実測)。

| 印の項目 | 読み方 | 読めないとき |
| --- | --- | --- |
| `model.effective` | `type` が `system` で `subtype` が `init` の行のうち最初のものの `model` (モデル ID) から、先頭の `claude-` を除いたもの | `unknown` |
| `skill_called` | `type` が `assistant` の行の `message.content` にある `tool_use` のうち、`name` が `Skill` のものがあれば `true`、無ければ `false`。**ツールの結果 (`type` が `user` の行の `tool_result`) の中身は読まない** — レビュー対象のファイルに `Skill` やモデル名の文字列が含まれていても判定が変わらないようにするため | `assistant` の行が 1 つも無ければ `unknown` |
| `permission_denials` | 最後の `type` が `result` の行の `permission_denials` (配列) の要素数と、各要素の `tool_name` (重複を除く) | `result` の行が無いか、`permission_denials` が配列でなければ件数を `unknown` |
| 実効の権限モード (`permission_mode.effective`) | `parent_tool_use_id` の無い最初の `init` の行の `permissionMode`。指定と違えば、その回を `failed` にする (「回の処理」の表) | `init` の行か `permissionMode` が無ければ `unknown`。それだけでは `failed` にしない — 手動のモードに戻った回は、拒否として別に現れる |
| サンドボックスが止めた確認 (`sandbox_blocked`) | 件数と、各呼び出しのコマンドと文面。下の「サンドボックスが止めた確認の数え方」 | `result` の行が無ければ (実行が最後まで行かなかった) 件数を `unknown` |

**effort はログのどの行にも記録されない。** 印の `effort` はワーカーに渡した値で、実行時の値は確かめられない。

**実効の権限モードは `init` の行だけから読む。** 起動の後にモードを決め直す経路が Claude Code の本体にあるらしいが、ログに現れないので扱わない。実測では、auto モードに対応していない `haiku` を指定すると、`init` の行の `permissionMode` が `default` だった。

### サンドボックスが止めた確認の数え方

**サンドボックスが止めた書き込みと接続は、Bash の `tool_result` の本文にだけ残る** — `permission_denials` にも `init` の行にも現れない (実測)。そのため、この項目に限ってツールの結果の中身を読む。

1. ログの全行 (sub-agent の行を含む) から、`tool_use` の `id` と、ツールの名前と入力の `command` の対応を作る。`tool_use` は `type` が `assistant` の行の `message.content` から、`tool_result` は `type` が `user` の行の `message.content` から読む。
2. `tool_result` のうち、次の 3 つをすべて満たすものを数える。対応する `tool_use` が見つからない結果は、ツールが `Bash` と分からないので数えない。
   - 対応するツールが `Bash`
   - `is_error` が真
   - 本文 (文字列か、`text` の要素を改行で連結したもの) が、`operation not permitted` (大文字と小文字を区別しない) か `<sandbox_violations>` を含む
3. 数えた呼び出しごとに、`tool_use` の `command` と、本文のうち文面を含む行 (止められたパスかホストを含む) を、それぞれ 1 行に直して先頭 200 文字までを印に書く。止められたのが書き込みか接続かで、直し方 (上の「止められたときの直し方」) が変わるため。
   - 文面を含む行は、`operation not permitted` を含む行と、`<sandbox_violations>` の行から `</sandbox_violations>` の行 (無ければ本文の終わり) までの行。接続を止められたときは、止められたホストがタグの次の行にあるので、タグの中の行も含める。複数の行は空白で繋ぐ。
   - 1 行に直すときは、改行・タブなどの制御文字・行の区切りの文字 (U+2028 など)・対になっていないサロゲート (JSON の `\ud800` のように、2 つ組で 1 文字を表す符号の片方だけをエスケープで書いたもの) を 1 文字ずつ空白に置き換え、前後の空白を除く。どれも、印の YAML の文字列にそのまま書けないか、書くと行が分かれるため。

| ログの形 | 扱い |
| --- | --- |
| Bash の `tool_result` で `is_error` が真、本文に `Operation not permitted` / `operation not permitted` | 数える (sub-agent の行も) |
| Bash の `tool_result` で `is_error` が真、本文に `<sandbox_violations>` (接続を止められたとき) | 数える |
| Bash の `tool_result` で `is_error` が偽 (文面を含む文書を `grep` した結果など) | 数えない |
| Bash 以外 (`Read` など) の `tool_result` | 数えない |
| `result` の行が無い | 件数を `unknown` |

- **`is_error` を条件にするのは、この文面を含む文書 (このファイルや Issue) を `grep` して成功した結果を数えないため。** その代わり、最後の部分が成功して終了コード 0 で終わる複合コマンド (`touch ~/x; echo done` など) の中で止められた書き込みは数えない。
- **サンドボックスと関係の無い、操作が許されないことを示すエラー (EPERM。macOS 自身の保護や、他のユーザーのプロセスへの `kill` など) も数える。** 確認を実行できなかった点は同じなので、その回は RA1 になる。
- **文面は Claude Code 2.1.273 で実測したもの。** ファイルの書き込みを止められたときの本文は `(eval):1: operation not permitted: <パス>`・`open <パス>: operation not permitted`・`touch: <パス>: Operation not permitted`・`mkdir: <パス>: Operation not permitted`・python の `PermissionError` (`Operation not permitted`)・`fatal: Unable to create '<パス>/index.lock': Operation not permitted` などで、`<sandbox_violations>` のタグは付かない。接続を止められたときは `<sandbox_violations> deny network-outbound <ホスト>:<ポート> (host is not on the allow list)` のタグが付く。ファイルの書き込みにもタグが付くバージョンになったら、タグだけで数えるように見直す。

### ログを信頼できる前提

- **ログは、ワーカーが開いた置き場のファイルで、レビュアの実行からは書けない。** 置き場はサンドボックスの中の Bash が書ける場所の外にあり (起動時の確認の 10 と 12)、ツールによる書き込みは拒否の規則で止める。
- **Bash の出力は `tool_result` の文字列の中に入る** ので、レビュアが出力した JSON の行が、ログの `init` や `result` の行として現れることはない (実測)。
- **件数は、レビュアが確認を実行できなかった回を RA1 にするためのもの。** レビュアが意図して件数を隠す場合 (エラーの出力を捨てる・終了コードを 0 にする) までは検出しない。

## 終わり方

- **`end` を見たら**、作業場所が残っていれば消し (シンボリックリンクなら、リンクだけを消してリンクの先は消さない)、`worker.yaml` を `left` にし、この起動で応じた回の一覧 (識別子・`status`・モデル・effort・所要時間・`error`) を標準出力に書いて、終了コード 0 で終わる。`end` は依頼文を探す前に見る。回の処理の途中 (受け取ってから印を書くまで) に `end` が現れたら、その回を終えて印を書いてから見る (その回は置き場が変わったとして `failed` になる)。
- **印の無い依頼文が無いまま `--idle-minutes` が過ぎたら**、`worker.yaml` を `expired` にし、周回は終わっていないことと同じコマンドで起動し直せることを出力して、終了コード 124 で終わる。期限は最後に回を終えた時刻 (無ければ起動した時刻) から数える。
- **割り込み (INT / TERM / HUP。HUP は端末を閉じたとき) を受けたら**、いつ受けたかで次のようにしてから、更新時刻を進める処理を止め、`worker.yaml` を `left` にして終わる。
  - 準備の途中 (「回の処理」の手順 2〜8): 準備のコマンドのプロセスグループを止め、作業場所があれば消す。**印は書かない** — レビュアの実行を起動していないので、起動し直したワーカーが同じ依頼文を初めから処理する。
  - レビュアの実行中: レビュアの実行を止め、回の終わりの処理を行って、`failed`・`interrupted` の印を書く。
  - 回の終わりの処理の途中: その回の印を、割り込みを受けなかったときと同じに書き終えてから終わる。

  更新時刻を進める処理と上限を測る処理はワーカーと同じプロセスグループで動くので、プロセスグループに届いた HUP と TERM では、ワーカーと同時に終わる (INT は、バックグラウンドのコマンドなので無視する)。**ワーカーはこれらを止めるとき、プロセスが残っていなければ終わりを待たない。** bash 5 (Linux の 5.2 で確かめた) は、trap を設定したシグナルで `wait` を途中で抜けるとき、その `wait` の中で回収した子の終わりを記録しないことがある。終わりを記録しなかった子を `wait` すると、ほかの子がすべて終わるまで戻らないので、まだ止めていない準備のコマンドやレビュアの実行が残っていると、ワーカーが終わらない (Linux のテストで、HUP と TERM をプロセスグループに送ったときに起きた)。
- **`kill -9` で終了させられたときは trap が実行されない。** 更新時刻を進めるバックグラウンドの処理と、上限を測るバックグラウンドの処理は、どちらも周期ごとにワーカーのプロセスが動いているか (終わったのに親が回収していないプロセスは動いていないとみなす) を確かめ、動いていなければ自分も終わる。上限を測る処理は、消えたワーカーには `USR1` を送らない — その PID が別のプロセスに再利用されていると、そのプロセスを終了させてしまう (`USR1` の既定の動作は終了)。**準備のコマンドとレビュアの実行は専用のプロセスグループで動いているので残り、Bash の子も残る。** レビュアの実行は最後まで走って作業場所に結果を書くことがあるが、置き場への複写も完了の印も行われず、作業場所も残る。`worker.yaml` の更新時刻が止まるので、作業側は停滞として気づく。同じコマンドで起動し直すと、起動時の確認の 2 が、`worker.yaml` に記録された作業場所の中を cwd にしているプロセスを止めて作業場所を消し、そのあと印の無い依頼文としてもう一度処理する。前の実行を止めてから新しいログを書くので、新しいログに前の実行の行は混ざらない。

## このワーカーが検出しないもの

- **結果の中身が正しいか** — 確かめるのは、結果の形 (`findings` と `run_id`)・作業側と置き場の前後の状態・ログから読む項目 (実効モデル・実効の権限モード・拒否とサンドボックスが止めた確認の件数) だけ。
- **effort が実際に効いたか** — ログに記録されないので、渡した値を印に残すだけ。
- **サンドボックスの一時ディレクトリへの書き込み** — サンドボックスは、自身の一時ディレクトリ (`/private/tmp/claude-<利用者の番号>`。サンドボックスの中の `TMPDIR`) への Bash の書き込みを止めない。そこにある他のプロセスの一時ファイルは守られず、そこへの書き込みも検出しない。
- **ホームと作業側の外への `Write`・`Edit`** — Bash による同じ書き込みはサンドボックスが止めるが、ツールには効かない。拒否の規則で止めるのはホーム・作業側・置き場だけで、その外 (`/opt/homebrew` など) への書き込みは auto モードの判定に任せる。
- **終了コード 0 で終わる複合コマンドの中で、サンドボックスが止めた書き込み** — 上の「サンドボックスが止めた確認の数え方」。
- **レビュアが意図してログの件数を隠す場合** — 上の「ログを信頼できる前提」。
- **作業場所の外に cwd を移して動き続けるプロセス** — 回の終わりの処理でも、起動し直したときの掃除でも、残ったプロセスは作業場所の中の cwd で見つけるので、止まらない。
- **利用者の設定とレビュー対象のブランチの設定の `sandbox.filesystem.allowWrite`** — ワーカーの値と合わせて使われ、書き込みを許す場所を広げうるが、ワーカーは確かめない。
- **管理設定 (組織が配布する設定) の `sandbox.excludedCommands`** — 利用者が変えられないので確かめない。
- **利用者の設定が接続を許すホストを広げている場合の、外への送信** — 利用者の設定が `WebFetch(domain:*)` を許していれば、レビュー対象に埋め込まれた指示に従ったレビュアが、手元の情報を外へ送れる。ワーカーは起動時にそのことを表示するだけで、仕組みでは止めない (上の「ネットワーク」)。
