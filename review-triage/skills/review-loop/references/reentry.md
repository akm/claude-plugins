# 待機と再入の手順

**このファイルが、作業側の待機 (RL1 の手順 b) と、再入の手順 (待機の通知と `--resume` が入る 1 つの入口) の正本。** 待機スクリプトの絶対パスは [SKILL.md](../SKILL.md) の「同梱のスクリプト」にある。

## 待機

**待機はプラグイン同梱の待機スクリプトを、Bash ツールでバックグラウンドで (`run_in_background: true`) 起動する。** フォアグラウンドで待たない — フォアグラウンドの `sleep` は拒否され、待っている間ほかの操作ができない。バックグラウンドの待機はターンをまたいで走り、終わると通知で次のターンが始まる。待っている間はトークンを消費しない。

```
bash "<待機スクリプトの絶対パス>" [--await-worker] "<置き場の絶対パス>" "<識別子>" <分> <停滞の秒数>
```

- **`<分>`**: 置き場に `worker.yaml` が無いとき (回 1 の最初の待機) と `--await-worker` を付けるときは `wait.worker_wait_minutes`、それ以外は `wait.wait_minutes` (どちらも `loop.yaml`)。
- **`<停滞の秒数>`**: `loop.yaml` の `wait.worker_stale_seconds`。
- **`--await-worker`**: `--resume` でワーカーが動いていないと判定したとき (下の「再入の手順」の 6) だけ付ける。**`--resume` の起動の中で待機を起動するときは、どの場面でも (再入の手順の 6 でも、G2 から L1 を経て依頼文を書いた後の RL1 の手順 b でも)、先に手順 6 の確かめ方でワーカーが動いているかを確かめる** — 人間がいま `--resume` を打った場面なので、止めずに起動コマンドを案内して待つ (計画の R21)。通知で続く回では確かめずに普通に待ち、ワーカーが期限切れなどで終了していれば、待機がその状態をすぐに返して RA2 になる。起動時の `worker.yaml` のワーカーはもう動いていないものとして扱い、新しいワーカーの出現・完了の印・`end` だけを待つ。
- 呼び出しの形を毎回同じにする — 許可のルール 1 つで済み、既定の権限モードでも毎回の確認を求められない。

**Bash 呼び出しの `description` は、次の形にし、この文だけで周回と回が分かるようにする。** 通知に含まれるのはこの文と終了コードだけなので、compact (会話の自動要約) の後や別の話題の途中でも、この文から手順に戻れる。

```
review-loop <周回 id> 回 <記録の回番号> (<識別子>) [この起動 <k>/<上限> 回・期限切れ <e>・中断 <i>]: 完了の印を待つ (0 = 現れた / 124 = 期限切れ / それ以外 = 中断)。通知を受けたら review-loop の再入の手順へ
```

`<k>` はこの起動で数えた回数 (J5 が見る。数える場所の正本は [round.md](round.md) の手順 a の 7)、`<e>` と `<i>` は下の「期限切れと中断」で数える回数。`--await-worker` のときは「完了の印を待つ」を「ワーカーの起動を待つ」にする。

**待機を起動したターンでは、それ以外のツールを呼ばずにターンを終える。** 人間には 1 行 (何を待っているか) だけ伝える。待機と並べて別の操作をすると、その結果と通知の順序が前後し、再入の手順が前提にする状態 (置き場と記録) が変わる。

## 再入の手順

**待機の通知と `--resume` は、どちらもこの入口に入る。** 入口は会話の文脈に依存せず、`loop.yaml`・記録・置き場のファイルと、通知で入ったときは `description` と終了コードと標準出力の 1 行だけから行き先を決める。**通知は人間の入力ではない** — 人間の答え (S2 の回答など) として扱わない。

1. **`loop.yaml` を読み直す。** 読めなければ止めて知らせる (状態のファイルなので、新規に寄せない。態度の正本は [loop-files.md](loop-files.md) の「ファイルの種類ごとの態度」)。
   - 通知で入ったとき、`state` が `active` でなければ何もせずに終わる (停止や `--end` の後に届いた通知)。
   - `--resume` で入ったとき、`state` が `ended` なら報告して終わる。`stopped` なら `state: active`・`stop_reason: ""` に書き換える。`active` なら、前のセッションが報告せずに終わった (待機中にセッションが閉じられた、など)。**`--resume` で入ったときは、ここで開始の報告を出してから 2 以降に進む** (書くものは下の「`--resume` の開始の報告」)。
2. **通知で入ったとき、その識別子の回が既に取り込み済みなら何もせずに終わる。** 取り込み済みとは、記録に空でない同じ `run_id` の回があるか、`loop.yaml` の `rejected` に含まれること。同じ回について通知が 2 回来た場合 (`--resume` と古い待機が重なったなど) に、2 回目で次の回を始めないため。
3. **通知で入ったときは、事象で分ける** (下の「事象ごとの扱い」)。完了の印の事象なら 4 に進む。識別子を持たない通知 (識別子の衝突を避けるために分が変わるのを待った通知。[round.md](round.md) の手順 a の 5) は、2 と 3 を飛ばして 4 に進む。
4. **取り込む印を探す**: 置き場の `delivered-<識別子>.yaml` のうち、識別子が記録の `run_id` (空でない値との完全一致) に無く、`rejected` にも無いものを、識別子の順で 1 つ選ぶ。あれば [round.md](round.md) の RL1 の手順 c (突き合わせ) に進む。**記録に `run_id: ''` の過去の回があっても、それとは照合しない。**
5. **印の無い依頼文を探す**: 置き場の `review-request-<識別子>.md` のうち、完了の印が無いもの。あれば 6 に進む。
6. **待機を起動する。** このセッションで同じ識別子の待機が既に走っていれば、新しく起動しない (起動すると通知が 2 度届き、2 度目は手順 2 で何もしないだけになる)。`--resume` で入ったときは、先にワーカーが動いているかを確かめる — `worker.yaml` の `state` が `idle` か `reviewing` で、ファイルの更新時刻 (キー `updated` ではない。読み方の正本は [loop-files.md](loop-files.md) の「`worker.yaml`」) が `wait.worker_stale_seconds` 以内なら動いている。**動いていなければ、起動コマンドを案内し ([guide-template.md](guide-template.md))、`--await-worker` で待つ。** 動いていれば、または通知で入ったときは、普通に待つ。
7. **取り込む印も印の無い依頼文も無ければ、G2 に進む** ([loop-flow.md](../../review-triage-loop/references/loop-flow.md) の図)。RA1 で止めた回はここを通り、L1 で新しい依頼文を書く (同じ回番号で、分が違う識別子になる)。

## `--resume` の開始の報告

`--resume` で入ったときは、周回を続ける前に次を出す。**どの条件の周回を、どういう状態から続けるかを、続ける前に人間が知っている状態にする。**

- 周回の id と置き場、`loop.yaml` から読んだ条件 (書き方は [round.md](round.md) の決定表の RG0 と同じ)
- `loop.yaml` が `active` だったら、**前のセッションが報告せずに終わったこと** — そのセッションが最後に何を待っていたかは、置き場のファイル (印の無い依頼文・取り込んでいない完了の印) から分かる範囲で書く
- ワーカーの状態 (`worker.yaml` の `state` と、ファイルの更新時刻の古さ) と、ワーカーの起動コマンド ([guide-template.md](guide-template.md))

この起動が停止で終わるときは、停止の報告にも、`active` の周回を再開した起動であることを書く ([stops.md](stops.md) の「停止の報告に足すもの」)。

## 事象ごとの扱い

待機スクリプトの終了コードと標準出力の 1 行 (事象の定義の正本はスクリプト `review-triage/scripts/review-loop-wait.sh` の冒頭のコメント) で分ける。停止ノードの定義と報告に書くものの正本は [stops.md](stops.md)。

| 終了コード | 標準出力 | 扱い |
| --- | --- | --- |
| 0 | `delivered <識別子>` | 再入の手順の 4 に進む |
| 0 | `end` | 周回の終了として扱う (人間が `end` を直接置いた)。[SKILL.md](../SKILL.md) の「終了」の手順 3 |
| 0 | `worker idle` / `worker reviewing` | ワーカーが起動した (出現した)。`wait.wait_minutes` で待ち直す。数える回数は変えない |
| 0 | `worker unavailable` | RA2。報告に `worker.yaml` の `error` (起動時の確認で通らなかった項目) を書く |
| 0 | `worker expired` / `worker left` / `worker stale` | RA2。**`worker stale` のとき、レビュアの実行 (`claude -p`) が残って動いていることがあるが、判定を覆さない** — ワーカーが `kill -9` などで消えても、専用のプロセスグループで動くレビュアの実行は残る。完了の印を書くワーカーが居ないので、待っても印は現れない。プロセスを調べて待ち直したり、手順に無い方法で待ったりしない |
| 0 | `worker invalid` | RA1 (ワーカーが書くファイルが読めない) |
| 124 | — | 下の「期限切れと中断」 |
| それ以外 | — | 下の「期限切れと中断」 |

## 期限切れと中断

**期限切れ (124) は、宣言する前にもう 1 度ファイルを確かめる。** 完了の印があれば、再入の手順の 4 に進む。無ければ、次の順に見る。

1. **`worker.yaml` の `state` が `reviewing` で、`current_request` が待っている識別子と一致し、ファイルの更新時刻 (6 と同じ読み方) が `wait.worker_stale_seconds` 以内なら、数えずに待ち直す** (`<e>` を 0 に戻す)。ワーカーはその依頼文をレビュー中で、待つ長さの上限はワーカーの `--review-timeout-minutes` が保証する。これが無いと、待機の期限の 2 倍より長くかかる正常なレビューも RA2 で止まる。
2. **ワーカーの起動を待っていた** (`worker.yaml` が無いまま待った回 1 の最初の待機か、`--await-worker` の待機) **なら、待ち直さずに RA2。** 数えない。
3. **それ以外は `<e>` を 1 増やす。** 2 になったら RA2、そうでなければ `wait.wait_minutes` で待ち直す。

**中断 (0 と 124 以外) は `<i>` を 1 増やす。** 1 なら待ち直し、2 になったら RA2。中断は、待機スクリプトが外から止められたか、引数の誤りで起動できなかったことを表す (理由は標準エラーにあり、出力ファイルで読める)。

`<e>` と `<i>` は、待ち直すときに `description` に書き、次の通知で読めるようにする。取り込みが済んで次の回の待機を起動するときは、どちらも 0 から始める。
