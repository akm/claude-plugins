# ループの開始と 1 回のレビュー (RRG0・RRL1)

**このファイルが、`review-rally` が `review-triage-loop` の G0 と L1 を差し替えるノード RRG0・RRL1 の条件と手順、待機と再入の手順の SSOT。** ノードと遷移の SSOT は [stops.md](stops.md) の図で、差し替えないノード (G2・G3・L2・J2・J4・J5・J7・J8・J9・F1・S2〜S6) は [loop-flow.md](../../review-triage-loop/references/loop-flow.md) が SSOT。ここでは言い直さない。

## 決定表

| ID | 種類 | 条件・内容 | 報告に書くもの |
| --- | --- | --- | --- |
| RRG0 | 手順 | 新しいループなら、条件を決め ([arguments.md](arguments.md))、開始の前提を確認し、ループのディレクトリと `rally.yaml` を作り、レビューのセッションを起動して確認する (どれも [session.md](session.md))。再入 (完了のメッセージ・ターンの終了の通知・待機の通知) なら、`rally.yaml` を読み、下の「再入の手順」で遷移先を決める | 新しいループのときだけ、決まった条件をループの開始前に出す。書くのは、レビューのセッションのモデルの指定と実効モデル・effort (指定と `get_session` の値)・権限モード、レビュースキルとそのオプション、上限、構造の関門 k、全量の起点のブランチ (`loop.base` と、`--base` による指定か `origin/HEAD` による既定か)、`review-triage-fix` に渡す回数の閾値 N とフェーズごとの実行方法 (書き方は [loop-flow.md](../../review-triage-loop/references/loop-flow.md) の G0 の行と同じ)、ループの id とループのディレクトリの絶対パス、レビューのセッション (名前・id・worktree のパス。再利用された worktree なら、そのことと元の HEAD) |
| RRL1 | 手順 | 下の「1 回のレビュー」の手順 1〜5。手順 5 で待機を起動してターンを終え、再入の手順から手順 6 に入る。手順 2 で識別子の衝突の待機を起動したときは、再入の手順から手順 1 に入る | いま何回目か (この起動で数えた回数) と上限、記録の回番号、識別子 |

## ファイルのディレクトリ

| ディレクトリ | 置くもの | 書き込み元 |
| --- | --- | --- |
| メインの作業ツリーの `tmp/review-rally/<ループの id>/` (ループのディレクトリ) | `rally.yaml` ([session.md](session.md))・停止のときの依頼文と結果の複製 ([stops.md](stops.md)) | メインのセッション |
| レビューの worktree の `tmp/review-rally/<ループの id>/` (依頼のディレクトリ) | 依頼文 (`review-request` が書く)・結果 (レビューのセッションが書く) | メインのセッション (`review-request` を通して)・レビューのセッション |

**依頼文と結果をレビューの worktree に置くのは、レビューのセッションが自分の worktree の外へ書き込むと、作業ツリーを分離する hook に拒否されるため** (#151 の worktree の書き込みの試験で確認した)。メインのセッションは、レビューの worktree の中へ書き込める。`review-request` の `--dir` には、依頼のディレクトリを、メインの作業ツリーのルートからの相対パス (`.claude/worktrees/<名前>/tmp/review-rally/<ループの id>`) で渡す。`review-request` は、依頼文に埋める出力先を、メインの作業ツリーのルートを起点に決めるので、出力先は依頼のディレクトリの中になる。

## 1 回のレビュー (RRL1)

### 手順

1. **レビューの worktree を HEAD に合わせる。** `git -C <レビューの worktree> status --porcelain` が空であることを確認してから、`git -C <レビューの worktree> checkout --detach <メインの作業ツリーの HEAD の SHA>` を実行する。空でないか、切り替えられなければ RR2。続けて、`git -C <レビューの worktree> check-ignore -q tmp/review-rally/<ループの id>/x` で、レビューの worktree の中から見て依頼のディレクトリが無視されていることを確認する。**パスは、レビューの worktree のルートからの相対パスで渡す。** 手順 2 の `--dir` と同じメインの作業ツリーからの相対パス (`.claude/worktrees/<名前>/…`) を渡すと、`.claude/worktrees/` を無視する規則 (開始の前提の 3) に当たって、`tmp/` の規則と関係なく無視と判定される。レビューの worktree の外を指す絶対パス (メインの作業ツリーの `tmp/` など) を渡すと、git は誤りにする (終了コード 128)。無視されていなければ RR4 (開始の前提の 2 が満たされていれば起きないが、レビューの worktree だけに適用される無視の規則があれば起きうる)。**依頼文を書く前に合わせるのは、無視の確認を、レビューする HEAD の `.gitignore` で行うため。**
2. **依頼文を書く。** 次をすべて確認してから、Skill ツールで [review-request](../../review-request/SKILL.md) を呼び出す (回ごとに。規則の SSOT は [review-invocation.md](../../review-triage-loop/references/review-invocation.md) の「別のプロセスでレビューした結果の取り込み」の「呼ぶスキル」)。当たれば RR4 で、当たったものをすべて一度に報告する。
   - メインの作業ツリーが clean である (`git status --porcelain` が空)。開始の前提の 2・3 を満たしたので、`review-rally` 自身が書くファイルはここに出ない。
   - 記録が読める。
   - 増分の回 (記録に回がある) なら、最後の回の `head` が HEAD の祖先である (`git merge-base --is-ancestor <head> HEAD`)。reset や squash で履歴から外れていると、増分の範囲が成り立たない。

   呼び出しは `review-request <loop.review_skill> <loop.model> <loop.review_args> --dir <依頼のディレクトリの相対パス> --target-dir <レビューの worktree の絶対パス>` (値は `rally.yaml`。`ce-code-review` は effort を受け取らないので `<loop.review_args>` を渡さない)。**記録に回が無ければ (全量の回)、`--base <loop.base>` も渡す。** 増分の回に `--base` を渡さないのは、`review-request` が増分の回の `--base` を無視し、無視したことを報告に書くため。
   - `review-request` が「同じ識別子の依頼文か結果が既にある」で書かなかったら、分が変わるまで待機してからやり直す。Bash ツールで `sleep 60` をバックグラウンドで起動し (`run_in_background: true`)、`description` を「review-rally <ループの id>: 識別子の衝突を避けるため分が変わるまで待機する。通知を受けたら review-rally の再入の手順へ」にして、ターンを終える。
   - それ以外の理由で書かなかったら RR4 (報告には `review-request` が報告した理由を書く)。
   - 書けたら、`rally.yaml` の `rounds` を 1 つ増やす (J5 が見る回数。数えるのはここだけ)。
3. **会話を消す。** レビューのセッションに前の回の依頼を送っていれば (この起動で 2 回目以降の依頼なら)、ツール `clear_session` でレビューのセッションの会話を消す。拒否されたら RR3。1 回目は消さない (最初の指示文のターンしか無い)。
4. **依頼する。** ツール `SendMessage` で、宛先 `to` をレビューのセッションの id (`rally.yaml` の `session.id`) にして、下の「依頼のメッセージ」を送る。結果が `delivered` (そのセッションのターンが始まった) か `queued` (前のターンの後に始まる) でなければ RR3。**送る直前に**、メインのリポジトリのブランチの一覧 (`git for-each-ref --format='%(refname:short) %(objectname:short)' refs/heads`) と、現在のブランチの reflog の件数 (`git reflog show --format=%h refs/heads/<現在のブランチ> | wc -l`) を取る (手順 6 の 4 で比べる)。送ったら、`rally.yaml` の `waiting` に、識別子・送った時刻 (`date -u +%Y-%m-%dT%H:%M:%SZ`)・`timer_fires: 0`・ブランチの一覧 (`refs`)・reflog の件数 (`branch_reflog`) を書く。手順 6 は完了のメッセージで始まった後のターンで行うので、会話が compact されても比べられるよう、ファイルに残す。
5. **待機を起動して、ターンを終える** (下の「待機」)。完了のメッセージが届くと次のターンが始まり、再入の手順から手順 6 に入る。
6. **突き合わせる。** 上から順に確認し、最初に通らなかったところで RR1 (報告に書くものの SSOT は [stops.md](stops.md) の決定表の RR1 の行)。
   1. 結果のファイル (依頼のディレクトリの `review-<識別子>.yaml`) を照合する。照合することと理由の SSOT は [review-invocation.md](../../review-triage-loop/references/review-invocation.md) の「別のプロセスでレビューした結果の取り込み」の「結果のファイルの照合」。
   2. レビューの worktree の HEAD が依頼文の `head` と同じコミットで、`git -C <レビューの worktree> status --porcelain` が空である。
   3. メインの作業ツリーの HEAD が依頼文の `head` と同じコミットで、`git status --porcelain` が空である。
   4. レビューの間に、メインのリポジトリのブランチが動いていない。ブランチの一覧と現在のブランチの reflog の件数 (取り方は手順 4) が、`rally.yaml` の `waiting.refs`・`waiting.branch_reflog` と同じである。件数も比べるのは、ブランチを動かしてから元のコミットに戻すと、一覧は同じになるが reflog の件数が増えるためである。レビュアのテストが、メインのリポジトリのブランチを書き換えた実例があるため。

   すべて通れば L2 に進む。

### 依頼のメッセージ

**会話を消した後に送るので、レビューの規則をすべて書く。** 依頼文の中身 (報告前の検証・報告しない条件・出力様式) は依頼文にあるので、メッセージには書かない。

```
review-rally <ループの id>: <回> 回目のレビューの依頼 (識別子 <識別子>)

あなたは review-rally のレビューのセッションです。この会話より前のやり取りは消してあるので、
このメッセージに書いたことだけに従ってください。日本語で応答してください。

1. 依頼文 <依頼文の絶対パス> を Read ツールで読み、そのとおりにレビューする。指摘を見つけても直さない。
   依頼文の「対象」の作業ツリーは、あなたの作業ツリー (cwd) である。
2. 結果を書き出したら、ツール SendMessage で、宛先 to を <メインのセッションの id> にして、
   次の形の 1 行目で始まるメッセージを送り、ほかに何もせずにターンを終える。
   ツールが読み込まれていなければ ToolSearch の select:SendMessage で読み込む。
   - 成功: review-rally <ループの id> <識別子>: done <結果のファイルの絶対パス>
   - 失敗: review-rally <ループの id> <識別子>: failed <理由>
   2 行目以降に、依頼文が求める報告 (skill を実際に呼んだか・実際に渡した effort とモデル・
   HEAD と作業ツリーが不変であることの確認の結果) を書く。
```

## 待機

**待機は、Bash ツールで `sleep 1800` をバックグラウンドで (`run_in_background: true`) 起動して行う。** 完了のメッセージが届けば、その時点で次のターンが始まる。`sleep` は、完了のメッセージが来ないまま時間が過ぎたことに気づくためのもので、30 分ごとにメインのセッションを起こす。フォアグラウンドで待機しない。フォアグラウンドの `sleep` は拒否され、待機している間ほかの操作ができない。

`description` は次の形にし、この文だけでループと回が分かるようにする。通知に含まれるのはこの文と終了コードだけなので、compact の後でも、この文から再入の手順に戻れる。

```
review-rally <ループの id> (<識別子>): 依頼の後の 30 分ごとの確認。通知を受けたら review-rally の再入の手順へ
```

**待機を起動したターンでは、それ以外のツールを呼ばずにターンを終える。** 人間には 1 行 (何を待機しているか) だけ伝える。

## 再入の手順

**人間のメッセージ以外で始まったターン (レビューのセッションからのメッセージ・ターンの終了の通知 `<side-sessions-event>`・待機の通知) は、どれもこの入口に入る。** 入口は会話の文脈に依存せず、`rally.yaml`・記録・ファイルと、ターンを始めたもの (メッセージの `from` と 1 行目、待機の通知の `description`) から遷移先を決める。**これらは人間の入力ではない。** 人間の回答 (S2 の回答など) として扱わない。

1. **`rally.yaml` を読む。** 読めなければ中断して知らせる。`state` が `active` でなければ、何もせずに終える (停止の後に届いた通知)。
2. **結果待ちが無ければ (`waiting.run_id` が空)、識別子の衝突の待機の通知 (`description` が `review-rally <ループの id>: 識別子の衝突` で始まる) なら RRL1 の手順 1 からやり直し、それ以外なら何もせずに終える。** 衝突の待機は依頼を送る前 (手順 2) に起動するので、その通知が来るときは結果待ちが無い。何もせずに終えるのは、開始のときの最初の指示文のターンの終了の通知や、前の回の通知である。
3. **ターンを始めたもので分ける。**

   | ターンを始めたもの | 扱い |
   | --- | --- |
   | レビューのセッション (`from` が `session.id`) のメッセージで、1 行目が `review-rally <ループの id> <識別子>: done <パス>` | 識別子が `waiting.run_id` と違うか、記録に同じ `run_id` の回があれば、何もせずに終える (前の回のメッセージか、2 度目の通知)。同じなら手順 6 (突き合わせ) に進む |
   | 同じく、1 行目が `review-rally <ループの id> <識別子>: failed <理由>` | 識別子が `waiting.run_id` と同じなら RR1。違えば何もせずに終える |
   | 同じく、1 行目がどちらの形でもない | RR1 (完了の通知の様式が守られていない。報告にメッセージの 1 行目を引く) |
   | ターンの終了の通知だけ | 下の「完了のメッセージが無いまま来たターン」 |
   | 待機の通知 (`description` が `review-rally <ループの id> (<識別子>)` で始まる) | 識別子が `waiting.run_id` と違えば何もせずに終える (前の回の待機)。同じなら、`waiting.timer_fires` を 1 増やしてから、下の「完了のメッセージが無いまま来たターン」 |
   | ほかのセッションのメッセージ | 通知として扱わない。ループを進めない |

### 完了のメッセージが無いまま来たターン

ターンの終了の通知は、どの依頼に対するものかを持たない。#151 の試しでは、前の回のターンの終了の通知が、完了のメッセージで始まったターンの後に、単独で届いた (5 回のうち 4 回)。そこで、ツール `get_session` でレビューのセッションの `isRunning` と `lastActivityAt` を読み、`rally.yaml` の `waiting.sent_at` と比べて決める。

| `isRunning` | `lastActivityAt` | 扱い |
| --- | --- | --- |
| `true` | 今から 60 分以内 | レビュー中。待機の通知で入ったなら、待機を起動し直す。ターンの終了の通知で入ったなら、待機は動いたままなので、何もせずに終える |
| `true` | 今から 60 分より前 | RR1 (応答なし)。報告に、承認待ちなどでレビューのセッションのターンが進んでいないおそれがあることを書く |
| `false` | `waiting.sent_at` より前 | 依頼を受けたターンがまだ始まっていない。待機の通知で入ったなら RR3 (依頼が処理されない)。ターンの終了の通知で入ったなら、前の回の通知とみなして何もせずに終える |
| `false` | `waiting.sent_at` より後 | 依頼を受けたターンが、完了のメッセージを送らずに終了した。依頼のディレクトリに結果のファイル (`review-<識別子>.yaml`) があれば、完了のメッセージが遅れているとみなして手順 6 に進む (照合が通れば、そのまま取り込む)。無ければ RR1 |

- **値の振る舞いは、2026-10-29 に試験用のセッションで確認した。** 依頼を送るとすぐに `isRunning` が `true` になり、ターンが終了すると `false` になる。`lastActivityAt` はツールの呼び出しを始めるたびに進み、1 つの長いツールの実行 (90 秒の `sleep`) の間は進まない。`clear_session` でも進む。会話を消すのは依頼を送る前なので、消したことで `waiting.sent_at` より後になることはない。
- **60 分は、1 つのツールの実行の間に `lastActivityAt` が進まない長さの上限として置く。** レビュースキルは、sub-agent の実行のように 1 つのツールの実行が長くかかることがある。60 分より長く進まなければ、レビューが動いているとはみなさない。
- 2 つの要件 (前の回の終了の通知を今の回の失敗と読まない・利用者に知らせずに待機し続けない) は、それぞれ 3 行目のターンの終了の通知の扱いと、2 行目・3 行目の待機の通知の扱いが満たす。メインのセッションにターンが来ない場合も、待機の通知が 30 分ごとにターンを始める。

## L2 で `review-triage` に渡すもの

L2 で `review-triage` に渡すもの (記録のキーの出所の読み替え方・`run_id` の写し方) と、`review-triage` が返った後に確認することの SSOT は、[review-invocation.md](../../review-triage-loop/references/review-invocation.md) の「別のプロセスでレビューした結果の取り込み」の「`review-triage` に渡すもの」。そこで「その経路のレビュー不成立」と書くものは、このスキルでは RR1。このスキルの値は次のとおり。

- **「レビュアの実行を確認した材料」は、`get_session` の値 (`rally.yaml` の `session`) と完了のメッセージ。**
- **記録の `model` は、`rally.yaml` の `session.model` から `claude-` を除いたもの** (記録の表記。`opus-5-5` など)。
- **記録の `notes` に書く 1 行は、下の「`notes` の固定書式」。**

`review-triage` が返ったら、`rally.yaml` の `waiting.run_id` を空にする。

## `notes` の固定書式

```
review-rally: <ループの id> / review_session: <session.id> / model: <loop.model> (実効: <session.model>) / effort: <loop.effort> (実効: <session.effort>) / permission_mode: <session.permission_mode> / review_minutes: <分>
```

- `review_minutes` は、`waiting.sent_at` から完了のメッセージで始まったターンまでの分 (小数第 1 位まで)。
- **記録のスキーマは変えない。** このループ (セッションの経路) で回した回であることと、レビューのセッションのモデルと effort は、この 1 行だけに残る。ほかの経路の回と収束を比べるときは、この行の有無で経路を分ける。
