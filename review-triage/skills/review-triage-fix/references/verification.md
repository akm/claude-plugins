# 修正の後の検証 (型 A〜F)

**このファイルが検証の型の正本** (型を足す・変えるのはここだけでよい)。

機械検査 (リポジトリの関門と `triagecheck`) と**別に**行う。各型の「起きたこと」は、このスキルの 1 回目の試行で機械検査を緑のまま通り抜けた欠陥の実例から採った。「起きうること (予防)」は、同じ通り抜け方を予防するために先に規則化したもの。

**修正だけでなく、新しく書く文 (規則・例・注記・記録) も検証の対象。** 検証を「修正」にだけかけると、規則や例を書く作業が対象外になる。実測で、型 A を定義するファイル自身の作成が型 A に違反した。

**実装済みの挙動を固定するテストは、先に失敗する状態を作れない。** そのコミットのメッセージには「実装済みの挙動の固定」とだけ書く — 廃止された過去の手順の語を持ち出して否定する定型句を作らない (実測で、その定型句が git log 上で複製され始めた)。

規則は「書いている最中」にかかるもの (A・C・F) と「コミット前」にかかるもの (B・D・E) に分かれる。**コミット前に、その修正に該当する規則をすべて確かめたかを見る。**

## A. 実行で確かめられる主張は、実行してから書く

grep の結果・件数・引用・関門名・コマンドの出力 — **実行すれば数秒で確かめられる主張を、記憶で書かない。** 書くときは、実行したコマンドと出力を対で確かめる。

### 起きたこと

- 例に「grep で 2 箇所が出た」と書いたが、その文字列は 1 箇所にしか一致しなかった (リンク記法が挟まって別の文字列だった)
- 実在しない節見出しを規範文書から引用した (見出しの名前が記憶で書かれ、実物と違っていた)
- 例の集計に書いた個数が、数えると作成時から実物と違っていた

**外して確かめる**: この規則が無いと、例を真似た読者が同じ grep を実行して違う結果を得る。自分の実行が誤りか例が古いかを判別できず、例が判断の材料にならなくなる。

## B. 変更した箇所の「並び」を読み直す

表の行を変えたら**その表の全行**を、節の記述を変えたら**その節全体**を、同じ基準で読み直す。**規範や前提を変えたら、範囲を節ではなく編集したファイルの全文に広げ、直接参照し合うファイルの該当節まで読み直す** — 矛盾は編集した節の近傍に限らず、冒頭の包括文や離れた手順との間に生じる。

**波及先 grep はこの型を捕まえない。** 並んだ行は同じ語を持たないことが多い。lappds の記録「6 則」 の「grep は遠くの辺を歩く道具で、近くの辺は目で見る」の「近くの辺」がこれにあたる。

### 起きたこと

- 表の一部の行を直したが、同じ表の残りの行に同種の誤りが残った
- 表の関門名を直したが、同じ節の数行下の同じ関門名が残った
- 表の直後に注記を足したとき、表の直前の既存の文を読み直さず、節の中で記述が矛盾した
- 手順を書き換えたとき近傍だけを読み直し、同じファイルの冒頭の包括文との矛盾が残った

**外して確かめる**: この規則が無いと、指摘された行だけが直り、並んだ行の同種の誤りが次のレビューまで残る。実測でこの型は繰り返し起きた。

## C. 数える単位と範囲を、数字より先に決める

件数・回数・内訳を書くときは、**何を 1 と数えるか (単位) と、どこまで数えるか (範囲) を先に 1 行で書く。** 決めずに数えると、行ごとに違う基準で数えて表の中で矛盾する。既存の数を別の文脈に使い回すときも、**単位が同じかを確かめる**。

### 起きたこと

- 「4 箇所が当たった」と書いたが、ヒット数なら 5・ファイル数なら 4 で、どちらを数えたのか決めていなかった
- 原因で数える規則の表を、コミットの分かれ方で数えた
- 広い類 (誤記・欠落を含む) の数を、狭い主張 (欠落だけ) にそのまま移植した

**外して確かめる**: この規則が無いと、後から検算する読者が、自分の数え方が誤りか表が誤りかを判別できない。

> v2 では記録の集計を機械が計算するので、この型の主な発生源 (手書きの累計・ピン値) は消えている。残る適用先は、修正の本文や報告に書く数字。

## D. 方法を変えたら、前後の差分を確かめる

grep のパターン・検索の範囲・検査の条件を変えたら、**変更の前後で両方実行し、増えた一致と消えた一致を列挙して**、意図どおりかを見る。片方だけ実行すると、変更で消えた一致に気づけない。

### 起きうること (予防)

検索の範囲を「リポジトリ全体では当たりすぎるので `docs/` に絞る」と決めたら、絞る前と後で両方実行し、絞ったことで消える一致 (`.claude/skills/` など機械検査が一部しか届かない領域) を列挙してから決める。

**外して確かめる**: この規則が無いと、範囲を狭める変更で一致が静かに消える。検索は緑も赤も出さないので、消えたことに気づく仕組みが他に無い。

## E. 規範を変えたら、それを実体化している例を列挙して読み直す

規範 (規則・手順・判定の方式) を変えたら、**その規範をその場に展開している例・worked example を列挙して、すべて読み直す。** 例は規範を言い換えて書くので、波及先 grep には掛からない — 型 B の「近くの辺」の、例における現れ。対象は両スキルの references/ 配下の `*-examples.md` 全ファイルと、変更した規範を例示している他の節。

### 起きたこと

- 判定の構造を変えたとき、指摘された例は直したが、同じ規範を展開していた**同じファイルの別の例**が残り、次のレビューの指摘になった — 例の取りこぼしは 2 ラウンド連続で同じ形だった

**外して確かめる**: この規則が無いと、規範の変更のたびに古い規範の姿が例の中に生き残る。例は境目の判断で突き合わせる素材なので、古い例は誤った判定を再生産する。

## F. 全称の主張は、書く前に反例を挙げる

「必ず」「すべて」「閉じている」「今後増えない」などの全称の文は、過去のデータと照合して真でも、まだ存在しない状態が偽にする — 実測の検証 (型 A) は過去にしか届かない。**書く前にその主張を偽にする状態を挙げ、実際に起きうるなら条件を明記するか主張を弱める。** 文だけでなく、**正規表現・grep パターン・glob も全称である** — 「誤って一致する実在の行」「一致すべきなのに外れる実在の行」を挙げてから確定する。

### 起きたこと

- 「この集合は閉じていて今後増えない」と書いたが、書く時点で想定できた状態 (採択 0 の回) に反例があった
- 照合の正規表現を非アンカーの部分一致で書き、正しい運用 (誤った行の逐語引用) に誤って一致することを見落とした

**外して確かめる**: この規則が無いと、全称の文やパターンが過去のデータへの検証だけで確定し、最初の反例が現れたとき、規範や検査そのものが誤りの側に立つ。
