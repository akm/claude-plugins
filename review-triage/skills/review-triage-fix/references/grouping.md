# 原因で束ねる

**このファイルが、原因の書き方と束ねる基準の正本。**

## 原因の書き方

指摘ごとに「なぜそうなったか」を 1 文で書く。**現象ではなく、それを生んだ作業を書く。**

| 指摘 (現象) | 原因 (作業) |
| --- | --- |
| 実在しないテスト関数名が残っている | 前回の修正が表だけを直し、5 行下の同じ語に追随しなかった |
| 実測回数が表と記録で食い違う | 回数を記録から数えず、記憶で書いた |
| 宣言した機能に到達できない | 分岐を足す位置を、既存の手順との前後関係を見ずに決めた |

**書けなければ束ねられない。** 原因が分からないまま直すと、同じ原因の別の現れが残る。書けない指摘は、その旨を報告してその指摘だけ単独の問題にする。

## 束ねる基準

**同じ原因なら 1 つの問題。** 判断の軸は原因だけ。

- **ファイルが同じでも、原因が違えば別の問題。** 1 つのファイルに複数の原因の欠陥が同居しうる。
- **ファイルが違っても、原因が同じなら 1 つの問題。** 正本と参照側に同じ誤りが伝播した場合など。
- **指摘の番号が連続していることは根拠にならない。** 上流のレビュアが並べた順であって、原因の順ではない。
- **束ならない回もある。** 全指摘の原因が異なれば、指摘の数だけ問題ができる。無理にまとめない。

## 捉え直しがあるとき

対象の回に合意した捉え直し (`recurrence.status: reframed`。定義の正本は [CONCEPTS.md](../../../../CONCEPTS.md) の「レビューの収束」) があれば、**指摘ごとの原因より `reframe.root_cause` を優先して束ね、修正の単位は `reframe.fix_unit` にする。** 捉え直しの型に当たる採択は、指摘ごとの原因が別の文で書けても 1 つの問題にし、修正計画の `cause` は捉え直しの原因を指す。型に当たらない採択は、上の基準どおり原因で束ねて別の問題にする。捉え直しに至る手順は [reframing.md](reframing.md) が正本。

## 実測の数え方

**数える単位は原因 (= 問題)、範囲はその回の採択分。** コミットは原因と 1 対 1 とは限らないので、コミットの数では数えない。

**実測値はこの文書に持たない。** 数えるときは記録 YAML ([スキーマ](../../review-triage/references/record-schema.md)) の `runs[].plans` を数える — 問題の数は `plans` の要素数、指摘の数はその回の `verdict: adopted` の件数で、どちらも機械的に一意に決まる。生成サマリの推移の表にも同じ値が出る。
