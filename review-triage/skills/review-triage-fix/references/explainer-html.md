# 説明の HTML

**このファイルが、`review-triage-fix` が作る説明の HTML (判断のための HTML と確認のための HTML) の、作る場面・出力先・構成・作り方の SSOT。** 人間の回答の扱いは [SKILL.md](../SKILL.md) の手順 1 の「人間の回答の反映」、案のパッチの作り方と当て方は同じファイルの「案のパッチ」が定める。ここでは言い直さない。

## Markdown が SSOT

**判断の材料の SSOT は、記録 YAML と生成サマリ (記録 YAML から設定の `triage_summary_command` が生成する Markdown)。** 生成サマリには、選択待ちの問題の案の文とパッチ、直した問題の修正方法と SHA が出るので、HTML を開かなくても人間は案を選べ、直した内容を確認できる。HTML は、同じ内容を、このブランチの作業を知らない技術者向けに前提から説明し直した任意の表示形式である。**HTML を作れなくても、修正と判断は続ける。** 作れなかったことと理由を報告に書く。

## 2 つの HTML と作る場面

| HTML | 載せる問題 | 作る場面 | 開き方 |
| --- | --- | --- | --- |
| 判断のための HTML | 記録に残っているすべての選択待ち (`status: awaiting-human`) の問題。前の回のものも含む | この起動を終了するときに、記録に選択待ちの問題があれば、回番号に関わらず作る | ブラウザで開く |
| 確認のための HTML | 最後の回の問題のうち `status: done`・`done-external` のすべてと、この起動で直した前の回の問題 | この起動で問題を直し (`done` か `done-external` にし)、回番号が回数の閾値 N を越えているとき (N+1 以上) | 開かない。ループが次の回に進むことがあるため |

- 回番号は、記録の最後の回の番号 (`runs` の要素数)。立案者の選択 (SKILL.md の手順 4) で N と比べるものと同じ。
- 確認のための HTML に、前の起動で直した最後の回の問題も載せるのは、同じ回に 2 回以上起動したとき (ループが選択待ちで停止し、人間が回答して直したときなど) に、上書きで前の起動の問題が HTML から消えないようにするためである。ただし、前の回の問題を同じ回番号の前の起動で直していた場合は、上書きでその問題が HTML から消える。その問題は、前の起動の報告と記録に残る。
- 現在のブランチの記録でない記録を渡したとき (SKILL.md の手順 1) は作らない。
- 作らなかったときは、作らなかった理由を報告に書く。

## 出力先

- 判断のための HTML: `tmp/review-triage-fix/<ブランチ名>-<回番号>-decision.html`
- 確認のための HTML: `tmp/review-triage-fix/<ブランチ名>-<回番号>-fixed.html`

`tmp/` はリポジトリのルートの下に作る。ブランチ名の `/` は `-` に置き換える (記録 YAML のファイル名と同じ規則)。同じ回で作り直すときは上書きし、前の回の HTML は残す。記録のディレクトリ (設定 `record_dir`) に作らないのは、設定によってはそこが git の追跡内になるため。

**作る前に、`git check-ignore tmp/review-triage-fix/` で、このディレクトリが git に無視されていることを確認する。** 無視されていなければ HTML を作らず、作らなかったことと、`.gitignore` に `tmp/` を足すよう案内する文を報告に書く。修正そのものは続ける。`mermaid-preview` は「`.gitignore` に足す」と定めているが、`review-triage` は利用者の `.gitignore` を変えない ([record-schema.md](../../review-triage/references/record-schema.md) の冒頭) ので、こちらを優先する。

## 作り方

**HTML の生成と表示の方法の SSOT は `mermaid-preview` skill** (テンプレート・CDN・読み込みに失敗したときの表示の制約も、あちらが持つ)。別のプラグインなので、入っていなければ HTML を作らず、そのことを報告に書く。

1. `mermaid-preview` のテンプレートをコピーし、下の「構成」の項目を書く。図が要らなければ、図のブロックを消す。
2. **差分を載せる位置には、差分の文字列ではなくマークのコメントを書く。差分をコピーしない。** 理由は [tools/diffhtml/README.md](../../../tools/diffhtml/README.md) の冒頭の「なぜ要るか」。マークには、案のパッチを指すものと、コミットを指すものがある。書き方の SSOT は同じ README の「マーク」。
3. 同梱のツール `diffhtml` で、マークを差分に置き換える。ツールは差分をエスケープし、行の種類で色を分ける。使い方の SSOT は同じ README の「使い方」。**ツールがエラーで終了したら、その HTML を消し、作らなかったこととツールの出力を報告に書く。**
4. 判断のための HTML だけ、`mermaid-preview` の手順のとおりブラウザで開き、描画を確認する。

## 構成

どちらの HTML も、問題ごとに節を立てる。**経緯は書かず、問題は今の状態として書く。** ページの先頭には、ブランチ・回番号と、SSOT である記録 YAML と生成サマリの絶対パスを書く。

### 判断のための HTML

ページの先頭に、**案のパッチが検証を通していないたたき台であること** (SKILL.md の「案のパッチ」) と、人間が選んだ後に修正フェーズが検証し、通らなければ当てた変更を戻して選択待ちに戻すこと (同じ節の「当て方」の 4) を、囲みで書く。

| 項目 | 書くこと | 材料 |
| --- | --- | --- |
| 前提 | 対象のファイルや仕組みの説明。このブランチの作業を知らない技術者が読んで分かるように書く。関係が込み入っていれば mermaid の図を添える | 調査の結果 (`investigation`) と、対象のファイル |
| 問題 | 何回目の問題か。いまの状態の何が問題か。指摘の箇所 (ファイル:行) と原因 | `findings`・`cause`・`investigation` |
| 案 | 案ごとに、`options` の行の文と、パッチの差分のマーク。パッチの見出しに「未検証」と添える。ファイルを変えない案 (`no_change`) はそう書く。`covered_by` の案は差分を載せず、「<problem_id> の案 <ラベル> と同じ修正で直す」と書いて、その案へのリンクを付ける。パッチを作れなかった案は、作れなかったことを書く | `options`・`option_patches` |
| 質問 | 何を決めてほしいか。回答の形 (案のラベルを選ぶ・`options` に無い案を伝える・「決めない」) と、回答の渡し先 (`review-triage-fix` に会話で伝える)。1 つの修正で覆う問題があれば、それらの問題にはまとめて同じ案を選ぶ必要があること | SKILL.md の手順 1 の「人間の回答の反映」 |

### 確認のための HTML

| 項目 | 書くこと | 材料 |
| --- | --- | --- |
| 前提 | 判断のための HTML と同じ | 判断のための HTML と同じ |
| 問題 | 何回目の問題か。直す前の状態の何が問題だったか。指摘の箇所 (ファイル:行) と原因 | `findings`・`cause`・`investigation` |
| 直したこと | 修正方法の文と、人間が案を選んだ問題なら選んだ案のラベル。コミットの短縮 SHA とメッセージの 1 行目。コミットの差分のマーク | `approach`・`chosen_option`・`sha` |
| 検証 | 通した機械検査の関門と、観点 A〜F の結果の要点。doc-dag の結果 | `verification`・`doc_dag` |

- 差分は、人間が案を選んだ問題でも、案のパッチではなく実際のコミットから取る。確認したいのは、実際にコミットした内容であるため。
- 同じ `sha` を持つ問題 (1 つのコミットが複数の問題を覆ったとき) は、`order` が最も小さい問題の節にだけ差分を載せる。ほかの問題の節には「<problem_id> と同じコミットで直した」と書いて、その節へのリンクを付ける。
- `done-external` の問題は、項目「直したこと」に、差分の代わりに次を書く。修正方法の文、反映先の URL (`applied_external_url`。リンクにする) と `notes`、コミットが無いので差分を示せないこと、URL の先は現在の内容で反映した時点の内容とは限らないこと。
