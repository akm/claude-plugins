# 直す前の調査 (類似箇所と影響範囲)

**このファイルが、修正方法を決める前に行う調査 — 同じ原因の別の箇所を探す前向きの調査と、直した後に影響を受ける箇所を確かめる後ろ向きの調査 — の正本。** 問題どうしの順序は [ordering.md](ordering.md)、コミット前の検証は [verification.md](verification.md) が持つ。

**調査は修正方法を決める前 (SKILL.md の手順 4) にかかり、検証 (型 A〜F) はコミット前にかかる。** フェーズが違う。調査の結果は修正の範囲を変え、検証は決めた修正が正しく行われたかを見る。調査を省くと、指摘された箇所だけを直して同じ原因の別の現れを残し、次のレビューの指摘になる。

## 前向きの調査: 同じ原因が生んだ別の箇所

指摘は現れた場所に立つが、原因は場所を選ばない。**原因を起点に、同じ原因が生みうる別の箇所を探す。** 探し方は 2 つあり、片方では届かない。

### 語で探す (grep)

**直す語・直す事実が他にどこにあるかを、リポジトリ全体で grep する** (lappds の記録「6 則」)。範囲を狭めるのは、語が明らかに 1 つのディレクトリにしか現れないと分かっているときだけ。**迷ったら全体にする** — 検索は安いが、取りこぼしは次のレビューまで残る。

**「変えた語」だけでなく「変えた主張と衝突しうる語」でも引く。** 量化子 (「全件」「必ず」) や反対側の言い回しは、変えた語と同じ文字列を持たない。

### 構造・役割で探す

**語の grep は、語が違う類似実装に届かない。** 原因が作業の仕方 (表だけ直して本文に追随しなかった・経路ごとに規則を書いた) なら、同じ作業をした他の場所は別の語で書かれている。原因から「同じ作業をした場所」を導き、候補を列挙してから読む。

| 原因の型 | 探す場所 |
| --- | --- |
| 同じ規則を経路・分岐ごとに個別に書いた (または片方にだけ当てた) | 同じ規則を当てるべき他の経路・分岐 — 他の `case`、他のコマンドの引数処理、同じテンプレートの他の値 |
| 正本の規則を参照側に書き写した | 同じ正本を参照している他のファイル。同じ役割 (README・references) の他の文書 |
| 表の見出し・列を変えて、行を埋める側に追随しなかった | 同じ構造 (見出しと、それを埋める側) を持つ他の表・他の生成関数 |
| 正本と生成物のうち片方だけ直した | 同じ生成の関係にある他の対 |
| 実測値・件数を記憶で書いた | 同じ値を持つ他の文、同じ種類の値 (件数・回数) を書いている他の箇所 |

実例: ラッパーに焼き込む値の引用の規則を、指摘された 1 箇所 (`-summary-command`) にだけ当てたのが原因だった回では、同じテンプレートの他の焼き込み値が同じ作業の産物なので、レビュアが挙げなかった箇所も同じ問題に含めて直した。語 (`-summary-command`) で grep しても、他の焼き込み値には届かない。

## 後ろ向きの調査: 直した後に影響を受ける箇所

**修正は指摘された箇所の外に効く。** 直す前に、何がその箇所を前提にしているかを列挙する。

| 直すもの | 影響を受けうる箇所 |
| --- | --- |
| 関数のシグネチャ・戻り値・エラーの有無 | 呼び出し元すべて。コンパイルが捕まえない呼び出し (テンプレート・設定・スクリプト・文書中のコマンド例) |
| 振る舞い (条件・既定値・順序) | その振る舞いを固定しているテスト。その振る舞いを前提に書かれた処理と文書 |
| データの形 (スキーマ・キー・列挙値) | 読む側と書く側の両方。検査。生成物 (サマリなど)。**既存のデータ** (旧い形の記録が検査で赤くならないか) |
| 規範・手順の文 | それを参照している文書。その規範を実体化している例 (型 E の対象と同じ)。リンクのアンカー (見出しを変えたとき) |
| 表の見出し・列 | 行を埋める側 — 見出しだけ変えると中身とずれる |

影響先のうち、**修正に合わせて変える必要があるものは同じ問題に含める** — インターフェースの変更とその全呼び出し元の修正は 1 つの動機で、分けると中間のコミットが壊れる。変える必要が無いと判断したものは、理由とともに記録に留める (下記)。

## 見つけた箇所の扱い

- **同じ原因なら、指摘されていなくても問題に含めて直す。** 束ねる基準は原因であって、指摘の有無ではない ([grouping.md](grouping.md))。SKILL.md の原則「採択されたものだけを直す」は採否の判断を蒸し返さないという意味で、同じ原因の別の現れを残す意味ではない。
- **原因が同じとは言えず、構造が似ているだけのものは直さない。** 記録の `investigation.excluded` に理由とともに残す。直したければ次のレビューの指摘か別の Issue に回す — 動機の違う修正を同じ問題に混ぜない。
- **過去の記録 (設定の `frozen_paths`) と、トリアージの記録の過去の回に当たった箇所は直さない。** 過去の記録は当時の記録として残す ([project-config.md](../../review-triage/references/project-config.md))。トリアージ記録の誤りは後の回の `notes` の訂正で扱う (既存の `runs` 要素は書き換えない)。**指摘が過去の記録を指していたら、直すのではなく現行の文書側に同じ問題が無いかを見る。** 見た結果は `excluded` に残す。
- **grep が届かない「近くの辺」(同じ表の並んだ行・同じ節の前後) は目で読み直す** — これは [verification.md](verification.md) の型 B が担う。調査の段階では、目で読む対象 (表全体・節全体) を `scope` に含めておく。

## 打ち切りの条件

「すべて調べた」は全称の主張で、書く前に反例を挙げる型 (型 F) にかかる — まだ存在しない箇所が偽にする。**調査は範囲を決めて行い、決めた範囲を記録に書く。**「調べきった」ではなく「ここまで調べた」を残す。

- **語の grep は、リポジトリ全体を範囲にする。** 範囲が機械的に決まるので、ここだけは全体でよい。
- **構造・役割の探索は、原因から導いた「同じ作業をした場所」の候補を先に列挙し、その候補を範囲にする。** 候補を読み終えたら打ち切る。候補を挙げられない原因 (「うっかり」のような、作業を特定しない原因) は、原因の書き方が現象に寄っている合図なので、原因を書き直す ([grouping.md](grouping.md))。
- **影響範囲は、直す対象を直接参照するものまで (1 段) を範囲にする。** 2 段先 (参照元の参照元) は、1 段目を変える必要が出た時点で、その 1 段目を起点にもう 1 段調べる。
- **見つからなかったときも記録する。** `scope` だけを書き、`included` / `excluded` を空にする。「調査済みで波及なし」と「未調査」を記録上で区別するため — 次のレビューで同じ型の指摘が来たとき、前回の `scope` と突き合わせて、範囲の外だった (調査漏れ) のか新規なのかを判別する。

## 記録に書くもの

記録の `plans[].investigation` に、調べた範囲 (`scope`)・含めた箇所 (`included`)・含めなかった箇所と理由 (`excluded`) を書く。**様式の正本は [記録 README](../../review-triage/references/record-schema.md) の `plans[].investigation` の表** — ここには写さない。`scope` は実行したコマンドと目で読んだ対象を、**実行してから**書く ([verification.md](verification.md) の型 A)。
