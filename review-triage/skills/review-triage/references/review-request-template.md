# レビューの依頼: {{repo}} の {{branch}} ({{scope}})

このファイルは review-triage プラグインの `review-request` スキルが生成した依頼文である。レビュアはこの依頼文だけを読んで作業し、結果を「出力様式」のとおり `{{output_path}}` に書き出す。依頼文の作り方と各節の理由の正本は review-triage スキルの `references/review-request.md` — レビュアが読む必要は無い。

## 対象

- リポジトリ: {{repo}} (作業ツリー: `{{repo_dir}}`)
- ブランチ: `{{branch}}`
- 差分の範囲: `{{base}}..{{head}}`
- scope: {{scope}} — {{scope_note}}

## 読み取り専用の厳守

- ファイルの編集・作成・削除をしない。git の状態 (HEAD・作業ツリー・インデックス・ブランチ) を変えない。
- 例外は出力先の 1 ファイル (`{{output_path}}`) だけ。他のファイルを作らない。
- 指摘を見つけても直さない。直すかどうかは受け取る側が判断する。
- レビューの前後で HEAD と作業ツリーが不変であることを確認して報告する。

## 呼ぶ skill・effort・モデル

- skill: `{{skill}}` / effort: `{{effort}}` / モデル: `{{model}}` — **この値で呼ぶ。** 自分で別の値を選ばない (`ce-code-review` のように effort やモデルを受け取らない skill では、その旨が上に書かれている)。
- **報告に、skill を実際に呼んだか (呼んだ / 呼ばずに自分で読んだ) と、実際に渡した effort とモデルを含める。** 受け取る側はこの報告を上の指定と突き合わせる。

## 検証の前払い (すべての指摘に必須)

- evidence には次のいずれかを含める。どちらも含められない指摘は confidence を low にする。
  - 実行した確認 — コマンドと出力の要点、またはプローブ・ミューテーションの手順と結果
    (実施後は必ず revert し、作業ツリーが不変であることを確認して報告する)
  - 対象箇所の逐語引用 (行番号つき)。矛盾の主張なら、矛盾する 2 箇所の両方を引く
- 「〜の可能性がある」「余地がある」という形の主張には、それを実際に起こす入力・状態を 1 つ添える。
- テスト・検査の不在を主張する指摘 (「この入力のテストが無い」「この分岐が実行されていない」)
  は、その入力を実際に通して報告が出ないことを確かめてから出す。確かめられなければ
  confidence を low にする。テスト関数名の列挙や grep だけで結論しない — 別名のテストが
  同じ分岐を踏んでいることがある。

## 報告しない条件と residual

報告しない条件 (トリアージで却下される種類):

- 壊れる入力・状態を具体に挙げられない一般的懸念
- 既存の関門 (テスト関数名・検査項目名で挙げられるもの) が顕在化を検出する欠陥
- 対象そのものより大きい防御・再現の仕掛けを要求する指摘
- プロセスの遵守が diff から証明できない、という種類の観察
- 整理・統一の好み (放置して壊れるものが無いもの)。リファクタ提案は 1 件まで、その旨を明記して

上に当たるが捨てるには惜しいものは、findings に入れず、末尾の residual リストに
1 行ずつだけ書く (id 無し・summary のみ)。判断の材料は残すが、指摘としては数えない。

## 出力様式

出力先: `{{output_path}}` — **この 1 ファイルだけ。** 名前を変えない。`tmp/` が無ければ作る。コミットしない。

次の構造に厳密に従う。**ここに無いキーを足さない。** 足したい情報があれば `attrs` (トップレベル・指摘の両方にある) に入れる。受け取る側は様式を確かめ、様式に無いキーがあれば判定を始めずに差し戻す。

```yaml
skill: {{skill}}
model: {{model}}
level: "{{effort}}"
run_id: ""
scope: {{scope}}
base: "{{base}}"
head: "{{head}}"
date: "{{date}}"
attrs: {}
findings:
  - id: 1
    file: path/to/file.md
    line: 12
    summary: "1〜2 文の要旨"
    evidence: "検証の前払いの節のとおり"
    attrs:
      severity: P2
      confidence: high
residual: []
```

| キー | 内容 |
| --- | --- |
| `skill` / `model` / `level` / `scope` / `base` / `head` / `date` | 上に埋めた値のまま書く。`level` は指定された effort。`head` は作業開始時の HEAD の短縮 SHA と一致すること |
| `run_id` | run 識別子があれば書く。無ければ空文字のまま |
| `attrs` (トップレベル) | 上に挙げたキー以外に残したい情報 (PR 番号など)。無ければ `{}` |
| `findings[].id` | 1 からの連番 |
| `findings[].file` / `line` | 指摘の位置。`line` は不明なら省略 |
| `findings[].summary` | 1〜2 文の要旨 |
| `findings[].evidence` | 「検証の前払い」の節のとおり |
| `findings[].attrs` | レビューが付けた属性 (`severity` / `confidence` など) をそのまま。無い属性を補完しない |
| `residual` | 「報告しない条件」に当たるが残す 1 行メモの列。無ければ `[]` |

注意:

- 指摘が 0 件なら `findings: []` と書く。キーを省かない。件数の集計は書かない (読み手が計算する)。
- 行内コメント (` #` 以降) を書かない。YAML は「半角スペース + `#`」以降をコメントとして取り除くので、値が警告なく切り詰められる。値に `#` を含めるときは引用符で囲む。
- 指摘の取捨は「報告しない条件」に従い、それ以外は全件書く。修正はしない。
- 書き出したら、レビューの前後で HEAD と作業ツリーが変わっていないことを確認して報告する。
