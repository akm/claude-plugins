# 境界の指摘例

各ゲート・免除条項・空虚 (R2)・前からある欠陥 (D8) について、「引っかかる例」と「引っかからない例」を対で置く。**ゲートを外すと判定が変わることを確かめる**ための素材。定義は再掲しない — ゲートと免除条項の正本は [rejection-gates.md](rejection-gates.md)、判定の順序と分岐の正本は [judgment-flow.md](judgment-flow.md)。

判定を確かめるときは、実際にこの例を入力として通し、期待どおりの判定になるかを見る。1 回きりの確認で終わらせない — 過去に、回帰テストの 1 件が修正を戻しても失敗せず、正誤の判定基準として機能していなかった障害がある (lappds の記録「安全網の迂回」)。

**指摘の文に出るファイルパスは、実在するものと説明のために作ったものが混ざる。** 例の主題はゲートの判定なので、対象が実在するかは問わない。

**ここに出るパスと関門名は、このスキルが生まれた lappds という Go のリポジトリのもの。** 自分のリポジトリで使うときは、**関門の名前だけは自分のリポジトリの実在するものに読み替える** — 実在しない関門名を書いた例を真似ると、その名前で却下が通ってしまう (1 回目の試行で実際に起きた)。関門の一覧は設定の `gates` が持つ ([project-config.md](project-config.md))。

## 免除条項

### 成立する例: テストが消えている

> `internal/lfdsclient/client_test.go` から資格情報の回帰テスト 3 件が消えている。実装は残っているので `make lint` も `make test` も合格したまま通る。

| 条件 1 (検出能力の欠落・消失) | 「テストが消えている」= 検出能力そのものが失われる → **成立** |
| --- | --- |
| 条件 2 (検出する関門が無い) | make: `make test` は合格する / 検査項目: テストの不在を見る項目は無い / テスト関数: 消えたテスト自身しか見ていない → **成立** |

**判定: A1 (採択・免除)**。他のゲート (開発者の領域など) に引っかかっても却下しない。

**外して確かめる**: 免除条項を無効にすると、対象が `*_test.go` で被害者が開発者なので R3 で却下になる。lappds の記録「範囲削除の記録」 が示す、最も見逃してはならない種類の欠陥が対象から漏れる。

### 成立しない例: テストの一時ファイル削除が雑

> `internal/store/store_test.go` の一時ディレクトリの削除がエラーを無視している。

条件 1 が**不成立** — テストファイル上の欠陥だが、検出能力の欠落ではない。何も検出しなくなるわけではない。

**判定: D6 へ進む** → 開発者の領域に発火 → 被害者が開発者 → **R3 (却下)**

**外して確かめる**: 条件 1 を「対象が関門である」に緩めると、この例が免除で採択になる。テストに disk full 級の堅牢性は求めないという要求水準の区別が通らなくなる (1 回目の試行では、条件 1 をこの形で置いたために実際に区別が通らなくなった)。

## 開発者の領域

### 引っかかる例: テストヘルパの disk full 対応

> `test/scenario/helper.go` が一時ファイルの作成失敗を握りつぶしている。disk full のとき原因が分からなくなる。

| 書くもの | 内容 |
| --- | --- |
| 対象のパス | `test/scenario/helper.go` (種類: test) |
| 壊れても製品の利用者に届かない理由 | シナリオテストは CI と開発者しか実行しない。製品の動作に影響しない |

**判定: R3 (却下)**

### H6 で保留になる例: テストヘルパの欠陥がプロダクションの欠陥を隠す

> `internal/dbtest/dbtest.go` のクリーンアップが不完全で、前のテストのデータが残る。そのため本番コードの制約違反がテストで検出されない。

対象は開発者専用だが、**壊れるとプロダクションの欠陥を隠す**ので被害者を利用者へ上書きする (D2)。

**この例でもすべてのゲートを評価し、結果を記録に残す** (E2)。「開発者の領域」は第 3 条件 (壊れてもプロダクションの欠陥を隠さない) を満たさず不成立。そのうえで、被害者に製品の利用者が含まれるので、ゲートが何個発火しても行き先は H6 — 評価結果は判定を変えないが、記録が「どのゲートが機能しているか」の材料になる。

**判定: H6 (保留)**

## 仮定の条件

### 引っかかる例

> `tools/doccheck/main.go` が、ディスクが読み取り専用のときエラーを握りつぶす。

| 書くもの | 内容 |
| --- | --- |
| 再現に必要な条件 | ファイルシステムを読み取り専用にする |
| テストで作れない理由 | FS の権限を下げる仕掛けが要り、テスト自身より大きい |

**判定: R3 (却下)** (被害者が開発者のため)

### 引っかからない例

> `tools/doccheck/glossary.go` が、`categories` が空配列のときに panic する。

再現できる (空の設定ファイルを渡すだけ)。このゲートは引っかからない。

他のゲートにも発火せず、**判定: A2 (採択)**。

**外して確かめる**: 「仮定の条件」を外すと、読み取り専用の例 (上) がどのゲートにも引っかからず採択になる。テストで作れない条件のために防御コードを書くことになり、避けたかった過剰修正が通る。

## 不相応なコスト

### 引っかかる例

> `tools/manual-test-run` の判定器が、SIGKILL された場合に中間ファイルを残す。

| 書くもの | 内容 |
| --- | --- |
| 防御コードの見積り | シグナルハンドラと後片付けで 40 行程度 |
| 対象の行数 | 該当関数は 12 行 |

**判定: R3 (却下)**

### 引っかからない例

> 同じ関数が、正常終了時にも中間ファイルを消していない。

`defer` 1 行で済む。対象の行数を超えない。他のゲートにも発火せず、**判定: A2 (採択)**。

**外して確かめる**: 「不相応なコスト」を外すと、SIGKILL の例 (上) が採択になる。12 行の関数に 40 行のシグナルハンドラが付き、対象より大きい修正が入る。

## 既に見える

### 引っかかる例

> `tools/doccheck/style.go` の `fullwidthParenProblems` が、全角括弧を含む行の行番号を 1 つずれて報告する。

| 書くもの | 内容 |
| --- | --- |
| 失敗する関門の名前 | `TestStyleProblems` (`tools/doccheck/anchors_test.go`。`fullwidthParenProblems` を呼ぶ) |
| その関門が失敗する時点 | 被害が出る前 — 行番号のずれをテストが検出して失敗し、マージの前に止まる |

既存のテストがこの欠陥を検出する。

**判定: R3 (却下)**

### 引っかからない例

> 同じ関数が、BOM 付きのファイルで行番号を誤る。

BOM 付きのファイルを扱うテストが無いので、失敗する関門を名前で挙げられない。このゲートは引っかからない。

他のゲートにも発火せず、**判定: A2 (採択)**。

**外して確かめる**: 「既に見える」を外すと、行番号が 1 つずれる例 (上) が採択になる。`TestStyleProblems` が既に失敗して検出している欠陥に対し、トリアージが二重に対処を求めることになる。

### 引っかからない例: 被害そのものが目に見える

> `CLAUDE.md` の節は、レビュアに実行させないテストを、呼び出す関数の名前で挙げていて、パッケージの名前で挙げていない。そのため、あるパッケージのテストがデータベースを使うことを、節から読み取れない。レビュアがそのパッケージのテストを実行すると、サンドボックスに止められ、周回がレビュー不成立で止まる。

| 書くもの | 内容 |
| --- | --- |
| 関門として挙げられそうなもの | 周回が完了の印を確かめる手順 (サンドボックスが止めた確認が無いか) |
| その関門が失敗する時点 | 周回が止まった後 — 検出するのは節の欠陥ではなく、周回の停止という被害そのもの |

被害が出る前に節の欠陥を検出する関門が無いので、このゲートは引っかからない。他のゲートにも発火せず、**判定: A2 (採択)**。

**外して確かめる**: 「被害が出る前に」の条件を外すと、この例は「既に見える」に引っかかり、被害者が開発者だけなので R3 (却下) になる。周回の停止を防ぐための節への指摘が、防ごうとしている周回の停止そのものを関門として却下される (実際に起きた。経緯は [#94](https://github.com/akm/claude-plugins/issues/94))。

## 空虚 (R2 — ゲートではない)

### 空虚で却下する例

> `internal/worker/agent.go` のエラーハンドリングが不十分。

| 書くもの | 内容 |
| --- | --- |
| 指摘をどう読んだか | 「エラーハンドリングが不十分」としか書かれておらず、どのエラーがどう扱われるべきかが無い。帰結の 4 項目を書けない |

**判定: R2 (却下)**

### 読み取れずに保留する例

> `internal/worker/agent.go` の R-3 の扱いが仕様と違う。

「R-3」が何を指すか分からない。**指摘の意味を読み取れないので H4 (保留)** — 空虚ではない。

**外して確かめる**: 空虚の決着 (D3) を外すと、エラーハンドリングの例 (上) が先の判定へ進む。帰結の 4 項目を書けないまま被害者を決めることになり、どのゲートも評価できずに採択される。

## 前からある欠陥 (D8 — ゲートではない)

D8 の条件の正本は [judgment-flow.md](judgment-flow.md) の D8 の行、確かめ方の正本は [premise-check.md](premise-check.md) の「前からある欠陥の確かめ方」。

### 当たる例: 前の回の修正が、前からある節を参照した

> 増分の回の指摘。前の回の修正が、新しく書いた段落に「詳しくは節 X を参照」と書き足した。節 X の手順は、記録が途中まで入ったデータベースでは役に立たない。修正が読み手を節 X に導くようになったので、増分が欠陥を持ち込んだ。

| 条件 | 確かめたこと |
| --- | --- |
| (1) 対象の行が変わっていない | 節 X の行を最後に変えたコミットは、どれも全量の起点の祖先 (このブランチは節 X を変えていない) |
| (2) 全量の起点でも同じ欠陥が成り立つ | 全量の起点の内容でも、節 X の手順は同じで、記録が途中まで入ったデータベースでは役に立たない |

指摘は「増分が欠陥を持ち込んだ」と主張するが、増分が持ち込んだのは節 X への参照で、欠陥そのもの (節 X の手順が役に立たないこと) は全量の起点の内容にもある。参照を足したことは (2) を否定しない。

**判定: H7 (保留)**。ブランチの変更 (前の回の修正) が節 X を参照するようになったことを添えて、このブランチで直すか、別の Issue にするかを人間に渡す。

**外して確かめる**: D8 を外すと、どのゲートにも引っかからず A2 (採択) になる。節 X を直すと、直した文に次の指摘が出て、ブランチの範囲が回ごとに広がる (実際に起きた。経緯は [#92](https://github.com/akm/claude-plugins/issues/92))。

### 当たらない例: ブランチの変更が、前からある文を誤りにした

> 文書 `docs/manual.md` は「関数 `Load` は設定ファイルが無ければ空の設定を返す」と書いているが、`Load` は設定ファイルが無いとエラーを返す。

| 条件 | 確かめたこと |
| --- | --- |
| (1) 対象の行が変わっていない | `docs/manual.md` の該当行は、このブランチで変わっていない (成り立つ) |
| (2) 全量の起点でも同じ欠陥が成り立つ | 全量の起点の `Load` は空の設定を返していた。エラーを返すように変えたのはこのブランチ (成り立たない) |

ブランチの変更が文を誤りにしたので、D8 には当たらない。先の判定へ進む。

**外して確かめる**: (2) を外して (1) だけで決めると、この例が H7 になる。ブランチが持ち込んだ食い違いが、前からある欠陥として扱われ、このブランチで直されないまま残りうる。

### 当たらない例: ブランチの変更が、変わっていない行の周りを変えた

> `README.md` の 14 行目のコードの囲みの記号 (3 つのバッククォートの行) が閉じられておらず、ファイルの終わりまでがコードとして表示される。

ブランチは、起点の「## Usage」の前に「## Build」と、閉じていないコードの囲みを挿入した。Markdown は囲みの記号を上から順に対にするので、起点で Usage の囲みを開いていた行が、挿入した囲みを閉じる行になり、起点で Usage の囲みを閉じていた行 (ブランチの内容では 14 行目) が新しい囲みを開くようになった。

| 条件 | 確かめたこと |
| --- | --- |
| (1) 対象の行が変わっていない | 14 行目は、道具の内訳が、起点の Usage の囲みを閉じていた行に対応させた行 (成り立つ) |
| (2) 全量の起点でも同じ欠陥が成り立つ | 主張は囲みの記号の対に依存するので、対になる記号も起点の内容で読む。起点では記号が正しく対になっている。対を変えたのは、このブランチが挿入した囲み (成り立たない) |

対象の行の内容は起点と同じだが、欠陥はどの記号とどの記号が対になるかにあり、それをブランチの挿入が変えた。D8 には当たらない。先の判定へ進む。

**外して確かめる**: 依存する箇所を起点の内容で読む規則 ([premise-check.md](premise-check.md) の「(2) 全量の起点の内容でも同じ欠陥が成り立つか」) を外し、対象の行だけを読み直すと、起点にも同じ記号の行があるので (2) が成り立つように見え、この例が H7 になる。ブランチが持ち込んだ欠陥が、前からある欠陥として扱われる。

## ゲートの適用範囲の外

トリアージで防げるものと防げないものの正本は [premise-check.md](premise-check.md) の「何が防げて、何が防げないか」。ここは例だけを置く。

### 却下ゲートで防げない例

> `reports` に `release_id` 列を足すべき。昇格ゲートがどのリリースの報告か分からない。

これは **E1 (根拠の検証) の仕様・設計との照合で `wrong` になり、R1 で却下される**。照合で `deployments` が同じ事実を持つこと、`ReportRequest` に書き込み経路が無いことが分かる。この例でも E2 は行われ、ゲートの評価結果は記録に残る (判定は D4 が決める — 評価と判定の分離)。

**判定: R1 (却下・根拠誤り)**

### 修正の遂行の問題 (トリアージの対象外)

> 稼働状態の報告に部分停止と全停止の区別が無い。

指摘は正しい。**採択**される。しかしこの種類の障害は「指摘が正しく、修正の遂行が雑だった」ために起きた (lappds の記録「設計文書の修正の連鎖」)。**トリアージでは防げない** — `review-triage-fix` の検証と 6 則が担う。ゲートの適用範囲を示すために置く。

## ゲートの機能のしかたについて分かっていること

- **ゲートの評価結果は、判定に対して「1 つ以上発火したか」(D6) としてしか影響しない。** どのゲートに発火したかは判定を変えない (記録には残る)。正本は [judgment-flow.md](judgment-flow.md) の方針「評価と判定を分ける」。
- **実際のレビューでは、発火はまれである。** 1 回目の試行の実測では、対象が文書かコードかは発火を分けなかった (「文書への指摘では発火しない」という当初の切り分けは実測で否定された)。ただし、却下ゲートはどれもコードの欠陥 (再現・環境の異常・防御コード・関門の失敗) を前提にしているので、文書への指摘はどのゲートにも引っかからずに採択されることがある (実例は [#92](https://github.com/akm/claude-plugins/issues/92))。ブランチより前からある欠陥への指摘は、ゲートではなく D8 が扱う。
- **この文書の例は、実際の指摘より発火率が高い。** 例はゲートの境目を示すために作られているためで、発火の実測は記録 ([スキーマ](record-schema.md)) の値だけを根拠にする。例の発火数・判定の集計はここに持たない — 集計のコピーは例を足すたびに同期が要り、置き去りになって実物とずれる。
- **却下ゲートが実際のレビューで有効かは、まだ実証されていない。** 記録にゲートごとの内訳を貯め、後から確かめる。正本は [rejection-gates.md](rejection-gates.md) の「却下ゲートは仮説である」。
