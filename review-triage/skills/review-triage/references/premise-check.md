# 根拠の検証

**このファイルが、根拠の照合の呼ばれ方・仕方と、記録に残す値の正本。前からある欠陥の確かめ方 (D8) の正本も兼ねる。** 評価の位置づけ (E1) と、結果がどの判定になるか (D4・D8) は [judgment-flow.md](judgment-flow.md) が正本 — ここでは言い直さない。

## 呼ばれ方

E1 に入った指摘について、次の順で行う。

1. **コードとの照合を全件に行う。** 指摘が主張する「コードがこうなっている」を、該当箇所を読んで確かめる (仕方は下の「コードとの照合」)。
2. **次の 3 つのいずれかに当たる指摘だけ、続けて仕様・設計とも照合する** (仕方は下の「仕様・設計との照合」)。当たらなければ 1 で終わる。
   - 列・フィールド・用語・設定項目・表の**新設**を求める
   - 仕様・設計の**違反**を主張する
   - 既存の仕組みの**不在**を前提にする (「〜が無いので追加すべき」)

**コードとの照合が先で、飛ばさない。** コードと合っていない主張は、仕様と照合するまでもない。**仕様・設計との照合だけを行う経路は無い** — どこまで照合したかを記録に残す値にも、仕様・設計だけを表す値は無い (下の表)。

## 記録に残す値

`premise_check` には、どこまで照合したか (`stages`) と結果 (`result`) を書く。

| `stages` | 呼び方 | 意味 |
| --- | --- | --- |
| `none` | 照合なし | D1〜D3 で決着し、E1 を行わなかった |
| `A` | コードとの照合 | 指摘が言うコードの状態だけを確かめた |
| `A+B` | コード・仕様・設計との照合 | それに加えて仕様・設計とも照らした |

**値の綴り (`A` / `A+B`) は記録の様式であって、呼び方ではない。** 過去の記録がこの綴りで書かれているので変えない (様式の正本は [record-schema.md](record-schema.md))。文章では呼び方を使う。

**`result` に書くトークンは、検証の 3 値と対象外の印の計 4 つ** (検証の 3 値の定義は以下の各節の表)。

| トークン | 意味 |
| --- | --- |
| `verified` | 根拠を確かめられた (コードとの照合を通り、当たれば仕様・設計との照合も通った) |
| `wrong` | 根拠が誤っている |
| `unverifiable` | 確かめられなかった |
| `skipped` | 検証の対象外 — D1〜D3 で決着し E1 を行わなかった (`stages: none` と対で書く)。検証の結果ではなく対象外の印 |

## なぜ要るか

上流レビューの `confidence` のアンカーは「レビュアが diff と周辺のコードだけから確かめられたか」を基準にしており、**仕様書・設計書との照合は範囲外**である。そのため次の形の指摘が高い確度で通る。

- 「このコードは X をしている」— 正しい
- 「X は仕様違反である」— **誤り**。だが引用するのはコードの行なので、根拠の要求も通過する

**根拠が誤っている指摘は「直す意味がない」のではなく「そもそも成り立たない」** — 価値を論じる前に除外する。

## コードとの照合

E1 に入った指摘の全件に行う (上の「呼ばれ方」の 1)。sub-agent は要らない。

**結果は 3 値。**

| 見つかったもの | 結果 |
| --- | --- |
| 主張と**逆**のコードがある | `wrong` — 何がどう違うかを書く |
| 主張どおりのコードがある (別の行でもよい) | 位置を補正して検証を続け、仕様・設計との照合に当たらなければ `verified` |
| 対象を**特定できない** | `unverifiable` — どこを探したかを書く |

**行番号のずれだけで `wrong` にしない。** rebase や後続の編集で行がずれるのは普通に起きる。指定行に無ければ、同じファイル内を検索してから判断する。

**確かめるのは「主張とコードが合っているか」まで。** コードが正しいかどうかの検証ではない。

## 仕様・設計との照合

上の「呼ばれ方」の 2 に当たる指摘だけに行う。sub-agent を要するので重い。

### 確かめること

lappds の記録「6 則の規則 2 (新要素ゲート)」 をそのまま使う。同記録は `release_id` の障害が「このゲートだけで防げた」と書いている。

| 問い | どこを見るか |
| --- | --- |
| 主張された仕様・設計は本当にそう書いてあるか | そのリポジトリの仕様・設計文書の該当箇所 |
| 新設するものを運べる既存の仕組みは無いか | 設計のデータモデル・通信スキーマ |
| 新設するものに書き込み経路はあるか (誰がいつ値を入れるか) | 設計・実装 |
| 用語は定義どおりに使われているか | そのリポジトリの用語集 (あれば) |

**「既存の仕組みが無い」を証明しようとしない。** 悪魔の証明になる。**探した範囲を書き、その範囲で見つからなかったことを示す。** 範囲を書けなければ `unverifiable`。

**「調べたが分からなかった」を「正しい」として扱わない** (lappds の記録「診断ツールの偽陰性」)。

## sub-agent に依頼する場合

仕様・設計との照合は sub-agent に依頼してよい。ただし**結果は検証してから反映する。** 依頼した側が確かめずに通すと、検証の層が 1 つ増えたように見えて実際には増えていない。

**「仕様に書いてある」という答えは、引用を伴わなければ採らない。** 該当箇所を逐語で引かせ、自分でその箇所を読んで確かめる。検証する側が検証されない構造だと、同じ失敗を一段深いところで繰り返す。

依頼するときに渡すもの:

- 指摘の要旨と、主張されている仕様・設計の箇所
- 上の 4 つの問い
- 「引用できない場合は『分からなかった』と答える」ことの明示

## 前からある欠陥の確かめ方 (D8)

D8 の条件 (1)(2) と、確かめられないときの行き先は [judgment-flow.md](judgment-flow.md) の D8 の行が正本。ここでは、全量の起点の決め方と、(1)(2) の確かめ方 (何をレビューした内容とするかと、改名・移動した行の扱いを含む) を定める。

### 全量の起点

**全量の起点は、ブランチの作り始めのコミットで、次の順で決める。**

1. レビュー結果の `scope` が `full` なら、その `base` をそのまま使う。`review-request` が、起点のブランチと HEAD の merge-base (共通祖先のコミット) として求めたものである (正本は [review-request の SKILL.md](../../review-request/SKILL.md) の手順 2)。
2. 周回の中で呼ばれ、周回が起点のブランチを決めていれば、そのブランチと HEAD の merge-base (`review-triage-loop` は [loop-flow.md](../../review-triage-loop/references/loop-flow.md) の G0 で決めたブランチ、`review-loop` は `loop.yaml` の `review.base`)。
3. それ以外は、`origin/HEAD` が指すブランチ (`review-request` が引数 `--base` の無いときに使うものと同じ) と HEAD の merge-base。

全量の起点が、レビューした内容のコミット (作業ツリーの内容なら HEAD) と同じとき (このブランチにコミットが無い。既定ブランチの先端でレビューした、など) は、ブランチより前からある欠陥と、このブランチで入った欠陥を区別できないので、(1) を確かめられないとする。

派生元が別の作業ブランチで、起点を `origin/HEAD` から求めたときは、派生元の作業ブランチの変更もこのブランチの変更として扱われ、(1) が成り立たない行が増える。そうなった指摘は、D8 が無かったときと同じ判定になる — 前からある欠陥を、このブランチの欠陥として判定するだけで、却下が増えることはない。

### (1) 対象の行が変わっていないか

**確かめるのは、指摘の対象の行 (`file` と `line`。複数の行にまたがる指摘はそのすべて) が、全量の起点からレビューした内容まで、同じパスのファイルの中で変わっていないか — 起点にあった行が、途中のどのコミットでも (コミットしていない変更も含めて) 書き換えられずに残っているか。** 残っている行は、起点のファイルに同じ内容の行としてある。どの行が残ったかは、コミットごとの差分で決まる (決め方の正本は、道具の [README](../../../tools/lineorigin/README.md) の「どう確かめるか」)。レビューした内容は、レビューが見た内容である。結果のファイルで受け取ったレビューなら、その `head` のコミットの内容。同じセッションのレビューなら、そのレビューが見た内容で、コミットしていない変更を含めて見たなら作業ツリーの内容、含めていなければ HEAD のコミットの内容。レビューした内容がコミットの内容のとき、判定するときに指摘の `file` にコミットしていない変更 (ステージしたものを含む) があれば、(1) を確かめられないとする。結果のファイルで受け取ったレビューは、それを見た可能性があり、結果のファイルからは分からない (依頼文を作った後に、共有の作業ツリーへ編集が入った場合など)。同じセッションのレビューは、それを見なかったことを道具に伝える手段が無い (道具は、判定するときの作業ツリーを見るだけ)。ほかのファイルの変更は、指摘の `file` の行番号を変えないので数えない。作業ツリーの内容のとき、指摘の `file` がコミットしていない新しいファイル (追跡外) なら、全量の起点にそのパスが無いので、(1) は成り立たない。指摘の行番号は、レビューした内容の行番号として読む。根拠の照合 (E1) で位置を補正したなら、補正した行を使う (補正もレビューした内容の上で行う)。主張どおりの行が複数あって 1 つの行に補正できないなら、候補のすべてを対象の行として道具に渡す (連続しない行はコンマで並べる。形の正本は道具の README のフラグの表の `-lines`)。成り立たない行が 1 つでもあれば (1) は成り立たないので、ブランチが起点の行の複製を足した場合は、足した側の行が成り立たず、D8 は当たらない。候補を 1 つに絞って起点の側の行を選ぶと、足した側の欠陥が前からある欠陥 (H7) として扱われうる。

- このブランチのコミット (マージで取り込んだ、起点の後のコミットを含む) か、コミットしていない変更が、その行を書いた・書き換えたなら、(1) は成り立たない。途中で書き換えて後で元の内容へ戻した行がどちらになるかは、戻し方で決まる (一直線の履歴で戻せば成り立たず、マージで相手の親の内容に戻せば成り立つ。正本は道具の README の「どう確かめるか」)。
- ファイルの間で移した行 (このブランチで改名したファイルの行を含む) は、起点の同じパスのファイルから残った行ではないので、(1) は成り立たない。ただし、1 つのコミットで起点のファイルを消し、別のファイルをそのパスへ移したときは、git がそのパスのファイルの書き換えとして扱うので、起点の内容と差分で対応した行は成り立つ (内容は起点の同じパスの行と同じ。正本は道具の README の「どう確かめるか」の改名の行)。別のファイルから移した行を変わっていないとするには git の移動の検出に頼ることになり、日本語の行などでは検出されないので、扱わない。そうなった指摘は、D8 が無かったときと同じ判定になる。
- ファイルの中で並べ替えた行は、どの行が残ったと見なすかを差分が決める。残ったと見なした行は (1) が成り立ち (内容は起点の行と同じ)、消して足したと見なした行は成り立たない。行の順序や、対象の行の周りの行をブランチが変えたかは、(1) ではなく (2) で見る (下の「(2) 全量の起点の内容でも同じ欠陥が成り立つか」)。

**確かめ方**: 同梱の道具 [lineorigin](../../../tools/lineorigin/README.md) に、レビューした作業ツリーのルート (フラグ `-root`。判定するセッションの作業ディレクトリとは限らない。何を渡すかの正本は、道具の README の「使い方」)・全量の起点 (フラグ `-base`。上の「全量の起点」で決めたコミットの SHA)・指摘の `file` と `line`・レビューした内容 (コミットの内容ならフラグ `-rev <コミット>`、作業ツリーの内容ならフラグ `-worktree`) を渡す。道具は、この節の定義のとおりに、成り立つ (`holds`)・成り立たない (`not-holds`)・確かめられない (`unverifiable`) のどれかを、理由と行ごとの内訳を添えて返す。git のコマンドの振る舞い (改名の追い方・利用者の設定・パスの読み方など) への対処と、それを検証したテストの正本は、道具の README。

- 道具の結果と理由を、D8 の結果として記録に書く (何を書くかの正本は [judgment-flow.md](judgment-flow.md) の D8 の行)。
- 道具が結果を出せずに終わったら、終了コードではなく、標準エラー出力の最初の行の印で見分ける (印の意味と、終了コードで見分けない理由の正本は、道具の README の「何を返すか」)。`input-error:` なら、渡し方 (フラグやパスの書き方・`-root` の絶対パスなど) を直して実行し直す。全量の起点・レビューした内容・指摘の `file` と `line` の値は、この節の定義と根拠の照合 (E1) で決まるもので、結果を出すために変えない — 変えると、指摘が指していない行や、レビューが見ていない版の結果が、D8 の結果として記録される。値そのものが原因で直せないとき (指摘の行がレビューした内容の行数を越える、など) と、道具を実行できないとき (`run-error:` で終わった、どちらの印も無いまま終わった (Go が無い・ビルドに失敗した、など)) は、(1) を確かめられないとし、そのことと理由を記録に書く。同じ値のまま実行し直さない。**道具を使わずに git のコマンドで確かめ直さない** — 規範文書に書いたコマンドの例で確かめていたときは、版の指定・改名と移動・コミットしていない行・実行するディレクトリ・パスの書き方の解釈などで結果が変わり、判定するエージェントが誤ってもエラーが出ないので気づけなかった ([#110](https://github.com/akm/claude-plugins/issues/110))。

### (2) 全量の起点の内容でも同じ欠陥が成り立つか

**全量の起点の内容を、指摘の `file` と同じパスで読み (例: `git -C <リポジトリのルート> show <全量の起点>:<ファイル>`)、指摘の主張が同じく成り立つかを、上の「コードとの照合」と同じ仕方で確かめる。** ただし、読むのは対象の行に対応する起点の行 (道具 lineorigin が、成り立つ行の内訳に出す起点の行番号の行。出力の様式の正本は、道具の [README](../../../tools/lineorigin/README.md) の「何を返すか」) で、起点の別の場所に同じ文があることでは、(2) は成り立たない (「コードとの照合」の「別の行でもよい」は、行番号のずれを補正するための規則で、(2) では使わない)。

**指摘の主張が対象の行の外にある箇所に依存するなら、その箇所も全量の起点の内容で読む。その箇所をこのブランチが変えた (書き換えた・足した・消した・並べ替えた) ために欠陥になったのなら、ブランチの変更が欠陥にしたので、(2) は成り立たない。** 対象の行は (1) で変わっていないことを確かめてあるので、内容は起点の行と同じである。依存する箇所を読まずに対象の行だけを読み直すと、ブランチが持ち込んだ欠陥でも、(2) が成り立つように見える。依存する箇所には、次のようなものがある (例であって、これに限らない)。

- 別の箇所との食い違い (文書と実装の不一致など) — 相手の箇所
- 隣の行や、対になる記号 (コードの囲みの開きと閉じ・括弧など) — その行と、対になる相手
- 番号・順序・件数の並び (番号付きの一覧・手順の順序・「以下の 3 項目」など) — 並び全体
- 消された行 (「X が無い」という主張) — 起点でその位置にあった行

ブランチの変更が、対象の行を参照する・呼び出すようになっただけなら、欠陥そのものは起点の内容にもあるので、(2) を否定しない。

## 何が防げて、何が防げないか

- **防げる種類**: 指摘が正しく見えるが、仕様・設計と照らすと成り立たない場合。`release_id` の障害がこれ — 列を新設する指摘に応えたが、埋めるデータ源がどこにも無く、同じ事実を持つ仕組みが既にあった。
- **防げない種類**: 指摘が正しく、修正の遂行が雑で次の問題を生む場合。これは `review-triage-fix` の検証 (verification.md) が担う。仕様・設計との照合は指摘の根拠を見るのであって、修正案を見るのではない。
