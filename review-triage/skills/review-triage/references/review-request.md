# レビューの依頼の様式

**このファイルが、上流レビューを別セッションで走らせて結果をファイルで受け取るときの、依頼の運用 (依頼文の作り方・範囲の規則・各節の理由・受け渡し様式) の正本。** レビュアに読ませる依頼文そのものの正本は [review-request-template.md](review-request-template.md) (雛形) で、[review-request](../../review-request/SKILL.md) スキルがそれを埋めて書き出す。トリアージ側の読み方は [SKILL.md](../SKILL.md) の手順 1。周回 (`review-triage-loop`) がセッション内の sub-agent にレビューを渡す経路は [review-invocation.md](../../review-triage-loop/references/review-invocation.md) が正本で、依頼文の文面は同じ雛形から取る。

## 依頼文はファイルに書き出し、パスだけを渡す

**依頼文を会話に貼らない。** 貼り方が回ごとに変わると、出力先の名前・様式・読み取り専用の条件も回ごとに変わる (実測: 様式と違う名前のファイルが作られた、様式に無いキーが足された、レビュアが修正を適用した、同じ回に複数のファイルができて対象が判別できなくなった)。**依頼文は `review-request` スキルでファイルに書き出し、新しいセッションにはそのパスだけを渡す。** 出力先のパスは生成の時点で依頼文に埋め込まれるので、レビュアがそこをずらす余地が無い。

埋めるもの (スキル名・モデル名・識別子・出力先・対象・`base` / `head`・scope・日付) と決め方の正本は [review-request スキル](../../review-request/SKILL.md) の手順。識別子の成分と整え方の正本は同スキルの手順 3 で、ここには列挙しない (列挙すると、成分を変えるたびに複数の箇所を追うことになる — 実測)。

## 呼ぶ skill・effort・モデル — 値で明記し、報告させる

**依頼文には、呼ぶ skill (`/code-review` など)、その skill に渡す effort (`code-review` なら `high` のように値そのもの)、レビューを実行するモデルを、値で明記する。** 「effort を報告せよ」と書くだけでは指定にならない — 依頼文に値が無いと、レビュアが前回の記録などから自分で選び、依頼した側が知らない値で走る (実測: 記録の `level` に `xhigh` が並んでいたのを根拠に、依頼に無い `xhigh` で走った)。effort が高いほど、レビュアは不確かな指摘も報告するようになり、「報告しない条件」で落とすはずの指摘が増える。既定にしたいときも既定の値を書く (既定の正本は [review-invocation.md](../../review-triage-loop/references/review-invocation.md) の「effort の既定」と「実効モデル」)。`ce-code-review` は effort もモデルも受け取らないので、その旨を書く。雛形では `{{skill}}` / `{{effort}}` / `{{model}}` がこれに当たり、[review-request スキル](../../review-request/SKILL.md) の手順 1 が値を決める。

**レビュアには、skill を実際に呼んだか (呼んだ / 呼ばずに自分で読んだ) と、実際に渡した effort とモデルを報告に含めさせ、指定と突き合わせる。** 報告が指定と食い違っていれば — skill を呼んでいない、effort やモデルが違う、報告があるはずの経路 (`code-review`) なのに報告が無い — 記録に写す前に人間に報告する (レビュアの判断で変わった値を、依頼どおりの値として記録しないため)。`ce-code-review` のように報告が無い経路では突き合わせない。この項が定めるのは突き合わせまでで、記録の `skill` / `level` / `model` に何を書くかは定めない — 各キーの意味の正本は [record-schema.md](record-schema.md) の `runs[]` の表、周回が経路ごとに何から採るかの正本は [review-invocation.md](../../review-triage-loop/references/review-invocation.md) の「記録のキーの出所」。skill を呼ばずに差分を読んでも指摘の形は同じに見えるため、報告させないと区別できない。

## 範囲の規則

**full (全量) は最初の 1 回と最終確認だけにする。修正後の再レビューは incremental (前回の HEAD からの増分)。** full を繰り返すと、テスト強化系の指摘が際限なく出続ける (実測)。増分の外は、増分が壊した場合のみ報告させる。

## 検証の前払い — なぜ依頼文に入れるか

レビュアに検証を前払いさせるほど、トリアージのコードとの照合 ([premise-check.md](premise-check.md)) が「追認」で済み、全体のコストが下がる (実測でもっとも役に立った時短要素)。文面は雛形の「検証の前払い」の節が正本で、ここには写さない。

## 報告しない条件と residual — なぜ依頼文に入れるか

**トリアージの却下ゲート ([rejection-gates.md](rejection-gates.md)) と空虚の決着 ([judgment-flow.md](judgment-flow.md) の R2) を上流へ写したもの** — 定義の正本はそちらで、雛形の「報告しない条件と residual」の節はその要約。

**痕跡を残さずに捨てさせない。** residual はそのための受け皿 — 上流での取捨は誤りうるので、1 行の痕跡をトリアージが目を通せる形で残す (誤った却下は気づかれないまま残る、の上流版を作らないため)。

## 出力様式

構造の正本は雛形の「出力様式」の節。各キーの意味は記録の `runs[]` と同じで、その正本は [record-schema.md](record-schema.md) (受け取った YAML の `findings` をそのまま記録に写せる形にしてある)。値に `#` を含むときの引用の規則も同じ。

- **拡張を受ける場所は `attrs` の 1 つに決めて、それ以外は閉じる。** 指摘の `attrs` は以前から上流固有の属性のパススルーで、トップレベルにも同じ受け皿を置いた。PR 番号やブランチ名を残したい回はそこへ入れる。受け取る側は、トップレベルの `attrs` のうち残す価値があるものだけを記録の `notes` に写す。
- **`findings` は 0 件でも `findings: []` と書かせる。** キーが無い・値が無い状態を 0 件と読むと、書き出しの途中で止まったファイルが「指摘なし」として通る。
- 出力先は識別子で名前が区別できる (成分の正本は [review-request スキル](../../review-request/SKILL.md) の手順 3)。それでも手順 1 は `head` が現在の HEAD と一致することを確かめる — 名前は経路を示すだけで、内容が現在の HEAD への指摘であることの証拠にはならない。
