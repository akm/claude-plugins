# レビューの依頼の様式

**このファイルが、上流レビューを別セッションで走らせて結果をファイルで受け取るときの、依頼の運用 (依頼文の作り方・範囲の規則・各節の理由・受け渡し様式) の正本。** レビュアに読ませる依頼文そのものの正本は [review-request-template.md](review-request-template.md) (雛形) で、[review-request](../../review-request/SKILL.md) スキルがそれを埋めて書き出す。トリアージ側の読み方は [SKILL.md](../SKILL.md) の手順 1。周回 (`review-triage-loop`) がセッション内の sub-agent にレビューを渡す経路は [review-invocation.md](../../review-triage-loop/references/review-invocation.md) が正本で、依頼文の文面は同じ雛形から取る。

## 依頼文はファイルに書き出し、パスだけを渡す

**依頼文を会話に貼らない。** 貼り方が回ごとに変わると、出力先の名前・様式・読み取り専用の条件も回ごとに変わる (実測: 様式と違う名前のファイルが作られた、様式に無いキーが足された、レビュアが修正を適用した、同じ回に複数のファイルができて対象が判別できなくなった)。**依頼文は `review-request` スキルでファイルに書き出し、新しいセッションにはそのパスだけを渡す。** 出力先のパスは生成の時点で依頼文に埋め込まれるので、レビュアがそこをずらす余地が無い。

埋めるもの (スキル名・モデル名・識別子・出力先・対象・`base` / `head`・scope・日付) と決め方の正本は [review-request スキル](../../review-request/SKILL.md) の手順。識別子の成分と整え方の正本は同スキルの手順 3 で、ここには列挙しない (列挙すると、成分を変えるたびに複数の箇所を追うことになる — 実測)。

## 呼ぶ skill・effort・モデル — 値で明記し、報告させる

**依頼文には、呼ぶ skill (`/code-review` など)、その skill に渡す effort (`code-review` なら `high` のように値そのもの)、レビューを実行するモデルを、値で明記する。** 「effort を報告せよ」と書くだけでは指定にならない — 依頼文に値が無いと、レビュアが前回の記録などから自分で選び、依頼した側が知らない値で走る (実測: 記録の `level` に `xhigh` が並んでいたのを根拠に、依頼に無い `xhigh` で走った)。effort が高いほど、レビュアは不確かな指摘も報告するようになり、「報告しない条件」で落とすはずの指摘が増える。既定にしたいときも既定の値を書く (既定の正本は [review-invocation.md](../../review-triage-loop/references/review-invocation.md) の「effort の既定」と「実効モデル」)。`ce-code-review` は effort もモデルも受け取らないので、その旨を書く。雛形では `{{skill}}` / `{{effort}}` / `{{model}}` がこれに当たり、[review-request スキル](../../review-request/SKILL.md) の手順 1 が値を決める。

**レビュアには、skill を実際に呼んだか (呼んだ / 呼ばずに自分で読んだ) と、実際に渡した effort とモデルを報告に含めさせ、指定と突き合わせる。** 報告が指定と食い違っていれば — skill を呼んでいない、effort やモデルが違う、報告があるはずの経路 (`code-review`) なのに報告が無い — 記録に写す前に人間に報告する (レビュアの判断で変わった値を、依頼どおりの値として記録しないため)。`ce-code-review` のように報告が無い経路では突き合わせない。この項が定めるのは突き合わせまでで、記録の `skill` / `level` / `model` に何を書くかは定めない — 各キーの意味の正本は [record-schema.md](record-schema.md) の `runs[]` の表、周回が経路ごとに何から採るかの正本は [review-invocation.md](../../review-triage-loop/references/review-invocation.md) の「記録のキーの出所」。skill を呼ばずに差分を読んでも指摘の形は同じに見えるため、報告させないと区別できない。

## 範囲の規則

**full (全量) は、記録に回が無いときの最初の 1 回と、収束後の全量レビューだけにする。それ以外の修正後の再レビューは incremental (前回の HEAD からの増分)。** full を繰り返すと、テスト強化系の指摘が際限なく出続ける (実測)。増分の外は、増分が壊した場合のみ報告させる。全量の起点 (`base`) は、派生元のブランチと HEAD の merge-base (共通祖先のコミット) で、求め方の正本は [review-request スキル](../../review-request/SKILL.md) の手順 2。

### 収束後の全量レビューと、その要否

収束後の全量レビューとは、採択 (トリアージで直すと判断した指摘) が 0 件の回が出て直すものが無くなった (収束した) 後に、範囲をブランチの全量に広げて行うレビューのこと。これで終わりとは限らない — 採択が出れば、直して増分の回に戻る。戻った後に収束したら、下の規則で要否を改めて決める。保留 (人間の判断待ち) の扱いは他の回と同じで、出た時点で人間に判断を任せる。

**収束後の全量レビューが要らないのは、記録に次の 2 つをともに満たす回があるときだけ。それ以外は要る。** 要否は記録と git から決め、報告の文面からは拾わない (報告は要約で、取りこぼしうる)。

1. 次の (a) か (b) に当たる。
   - (a) `scope` が `full` で、採択 (`verdict: adopted`) が 0 件の回
   - (b) 収束後の全量の回 (`scope` が `full` で、記録の最初の回ではない回) の直後の回。ただし、直後の回の `scope` が `incremental` で、採択が 0 件のときに限る (全量の回の採択の有無は問わない)
2. その回の `head` からいまの HEAD までに、記録の置き場の外の変更が無い

言い換えると、いまの HEAD の内容 (記録を除く) を全量で見て採択が 0 件だったか、収束後の全量で見た後の変更 (採択や保留の修正) を増分で見て採択が 0 件だったのなら、要らない。

- **収束した回の種類では決めない。** 記録に回が無い状態から 1 回目の全量で採択が 0 件のまま収束した記録は、(a) と 2 つ目の条件を満たすので要らない — 修正の無い同じ内容をもう一度全量で見させることになるため。逆に、収束した回の scope で決めると、1 回目の全量で収束した後にコミットせずに条件 (モデルなど) を変えて周回を起動し直したとき、範囲が空の増分の回で収束して「要る」と誤る。
- **(b) を認めるのは、その時点の内容がすでに 2 つの回で見られているから。** 全量の回の `head` までの内容は全量の回が見ていて、それより後の変更 (その回の採択や保留の修正を含む) は、直後の増分の回が見ている (増分の範囲は全量の回の `head` から始まる)。もう一度全量で見ると、同じ内容を二度見ることになる。直後の増分の回でも採択が出たとき (修正が次の指摘を生んだとき) は (b) に当たらず、収束した後にもう一度全量で見る。
- **(b) は記録の最初の回に当てない。** 最初の全量の回の採択はブランチの作り始めからある欠陥で、それを直した後の全量の見直し (収束後の全量レビュー) を 1 度も行わないまま終わらないようにするため。
- **収束後の全量の回の後に保留を直すコミットは、直後の増分の回が見ていれば (b) に当たり、見ていなければ要る。** 採択が 0 件の全量の回でも、その後に保留を直すコミットがあれば (a) には当たらない。2 つ目の条件は、回の後に加わった修正を内容の変化として見るためのもので、修正が採択によるか保留の判断によるかを問わない。

**2 つ目の条件は、`head` と HEAD の差分から記録の置き場の下のパスを除いて判定する。**

- 記録の `head` は短縮 SHA なので、`git rev-parse --verify --quiet "<head>^{commit}"` で完全な SHA に直してから比べる。**解決できない (履歴から外れた・短縮 SHA が曖昧になった) 回は、2 つ目の条件を満たさないとする** — 比べられない回を「変更が無い」として扱うと、見ていない内容を全量で見たことにしてしまう。「要る」として扱っても、次の全量の回の `head` はいまの HEAD なので解決でき、全量の回は繰り返されない。
- 差分は `git diff --name-only <完全な SHA> HEAD` で列挙し、設定の `record_dir` (既定は `tmp/review-triages/`。リポジトリのルートからの相対パス) の下のパスを除く。1 つも残らなければ「変更が無い」。`record_dir` が作業ツリーの外なら、記録は差分に現れないので何も除かない (git のパスの指定は作業ツリーの外を受け付けないので、除く指定を渡さない)。
- 除く理由: 記録の置き場を追跡内にしたリポジトリでは、`review-triage` と `review-triage-fix` が記録をコミットする (正本は [record-schema.md](record-schema.md) の「コミット」) ので、全量の回を取り込むたびに HEAD が進む。`head` と HEAD の一致で判定すると、採択が 0 件の全量の回の後も「要る」が続き、収束後の全量の回が止まらなくなる (数えないので上限でも止まらない。下の「上限」の段落)。除くのはレビューの対象でない記録の置き場だけなので、修正のコミットは必ず「変更あり」になる。既定の置き場のように追跡外なら、除く対象は差分に現れず、判定は `head` と HEAD の比較と同じ結果になる。

**明示の指定があれば、要否に関わらず全量にする。** 明示の指定とは、要否を問わずに全量を頼むこと。`review-request` では引数 `--full-review` がこれに当たる (周回が、要るときに全量を頼むのにも同じ引数を使う)。周回がどの場合に要否を問わずに全量を頼むか (どの引数・どのノードで頼むか) は、周回の側の文書が決める。要らないときに全量を頼むのは、別のモデルや effort で見直すための手段である。要らない状態で収束したときの報告は、「強いて言えば、別のモデルか effort で行う」と推奨する。

**上限: 収束後の全量の回は、周回の上限 (`max_rounds`) に数えない。** 記録に回が無いときの 1 回目の全量の回は、今までどおり数える。数えなくても周回は止まる — 周回が記録に回がある状態で全量の回に進むのは、収束した後に要るときと、明示の指定があるときだけ。**周回は、明示の指定を 1 つの起動で 1 回までに限る** — 限らない周回では、この段落の論証が成り立たない。全量の回で採択が 0 件なら、その回が上の (a) に当たるので、次は要らない。採択が出れば、直した後に数える増分の回を通る (その回で採択が 0 件なら (b) に当たるので、次は要らない)。したがって、1 つの起動で行う収束後の全量の回は、数えた回数 + 1 を越えない (+1 は、明示の指定による、数える回より前の全量の回)。

**上の「full を繰り返すと、指摘が際限なく出続ける」との関係**: 収束後の全量の回を繰り返すのは、前の全量の回の直後の増分の回でも採択が出たときか、その後に記録の置き場の外の変更が加わったときだけで、回数は周回の上限で抑えられる。

## 検証の前払い — なぜ依頼文に入れるか

レビュアに検証を前払いさせるほど、トリアージのコードとの照合 ([premise-check.md](premise-check.md)) が「追認」で済み、全体のコストが下がる (実測でもっとも役に立った時短要素)。文面は雛形の「検証の前払い」の節が正本で、ここには写さない。

## 報告しない条件と residual — なぜ依頼文に入れるか

**トリアージの却下ゲート ([rejection-gates.md](rejection-gates.md)) と空虚の決着 ([judgment-flow.md](judgment-flow.md) の R2) を上流へ写したもの** — 定義の正本はそちらで、雛形の「報告しない条件と residual」の節はその要約。

**痕跡を残さずに捨てさせない。** residual はそのための受け皿 — 上流での取捨は誤りうるので、1 行の痕跡をトリアージが目を通せる形で残す (誤った却下は気づかれないまま残る、の上流版を作らないため)。

## 出力様式

構造の正本は雛形の「出力様式」の節。各キーの意味は記録の `runs[]` と同じで、その正本は [record-schema.md](record-schema.md) (受け取った YAML の `findings` をそのまま記録に写せる形にしてある)。値に `#` を含むときの引用の規則も同じ。

- **拡張を受ける場所は `attrs` の 1 つに決めて、それ以外は閉じる。** 指摘の `attrs` は以前から上流固有の属性のパススルーで、トップレベルにも同じ受け皿を置いた。PR 番号やブランチ名を残したい回はそこへ入れる。受け取る側は、トップレベルの `attrs` のうち残す価値があるものだけを記録の `notes` に写す。
- **`findings` は 0 件でも `findings: []` と書かせる。** キーが無い・値が無い状態を 0 件と読むと、書き出しの途中で止まったファイルが「指摘なし」として通る。
- **`run_id` は `review-request` が識別子で埋め、受け取る側 (`review-triage` の手順 1) は記録の `runs[].run_id` にそのまま写す。** 同じ結果を 2 度取り込んでいないかを、周回 (`review-loop`) が記録の `run_id` と識別子の照合で確かめるため。
- 出力先は識別子で名前が区別できる (成分の正本は [review-request スキル](../../review-request/SKILL.md) の手順 3)。それでも手順 1 は `head` が現在の HEAD と一致することを確かめる — 名前は経路を示すだけで、内容が現在の HEAD への指摘であることの証拠にはならない。
