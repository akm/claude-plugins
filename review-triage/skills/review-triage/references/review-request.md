# レビューの依頼の様式

**このファイルが、上流レビューを別セッションで走らせて結果をファイルで受け取るときの、依頼文と受け渡し様式の正本。** 依頼するときは、このファイルを読ませるか、各節をそのまま貼る。トリアージ側の読み方は [SKILL.md](../SKILL.md) の手順 1。

## 依頼文に含めるもの

1. **対象**: リポジトリ・ブランチ・差分の範囲 (`<base>..<head>`)・scope (下の「範囲の規則」)。
2. **読み取り専用の厳守**: ファイルの編集・作成・削除・git の状態変更をしない。レビュー前後で HEAD と作業ツリーが不変であること。
3. **検証の前払い** (下の節)。
4. **報告しない条件と residual** (下の節)。
5. **出力様式** (下の節)。

## 範囲の規則

**full (全量) は最初の 1 回と最終確認だけにする。修正後の再レビューは incremental (前回の HEAD からの増分)。** full を繰り返すと、テスト強化系の指摘が際限なく湧き続ける (実測)。増分の外は、増分が壊した場合のみ報告させる。

## 検証の前払い

レビュアに検証を前払いさせるほど、トリアージの段 A ([premise-check.md](premise-check.md)) が「追認」で済み、全体のコストが下がる (実測でもっとも役に立った時短要素)。次を依頼文に入れる。

```
検証の前払い (すべての指摘に必須):
- evidence には次のいずれかを含める。どちらも含められない指摘は confidence を low にする。
  - 実行した確認 — コマンドと出力の要点、またはプローブ・ミューテーションの手順と結果
    (実施後は必ず revert し、作業ツリーが不変であることを確認して報告する)
  - 対象箇所の逐語引用 (行番号つき)。矛盾の主張なら、矛盾する 2 箇所の両方を引く
- 「〜の可能性がある」「余地がある」という形の主張には、それを実際に起こす入力・状態を 1 つ添える。
- テスト・検査の不在を主張する指摘 (「この入力のテストが無い」「この分岐が実行されていない」)
  は、その入力を実際に通して報告が出ないことを確かめてから出す。確かめられなければ
  confidence を low にする。テスト関数名の列挙や grep だけで結論しない — 別名のテストが
  同じ分岐を踏んでいることがある。
```

## 報告しない条件と residual

**トリアージの却下ゲート ([rejection-gates.md](rejection-gates.md)) と空虚の決着 ([judgment-flow.md](judgment-flow.md) の R2) を上流へ写したもの** — 定義の正本はそちらで、ここは依頼文に貼る要約。

```
報告しない条件 (トリアージで却下される種類):
- 壊れる入力・状態を具体に挙げられない一般的懸念
- 既存の関門 (テスト関数名・検査項目名で挙げられるもの) が顕在化を検出する欠陥
- 対象そのものより大きい防御・再現の仕掛けを要求する指摘
- プロセスの遵守が diff から証明できない、という種類の観察
- 整理・統一の好み (放置して壊れるものが無いもの)。リファクタ提案は 1 件まで、その旨を明記して

上に当たるが捨てるには惜しいものは、findings に入れず、末尾の residual リストに
1 行ずつだけ書く (id 無し・summary のみ)。判断の材料は残すが、指摘としては数えない。
```

**利用者に知らせずに捨てさせない。** residual はそのための受け皿 — 上流での取捨は誤りうるので、1 行の痕跡をトリアージが一瞥できる形で残す (誤った却下は気づかれないまま残る、の上流版を作らないため)。

## 出力様式

```
出力先: tmp/review-<スキル名>-<モデル名>.yaml (同じ組み合わせの 2 回目以降は -2nd / -3rd … を付ける)
  - ファイル名は ASCII のみ。tmp/ が無ければ作る (.gitignore 済み)。コミットしない。

形式 (この構造に厳密に従う):

skill: code-review            # code-review / ce-code-review など
model: sonnet-5               # レビューを実行したモデル
level: ""                     # レベルや mode があれば (無ければ空)
run_id: ""                    # run 識別子があれば (無ければ空)
scope: incremental            # full / incremental (範囲の規則のとおり)
base: main                    # 差分の基点 (ブランチ名か SHA)
head: "abc1234"               # レビュー時点の HEAD の短縮 SHA
date: "2026-08-30"
findings:
  - id: 1                     # 1 からの連番
    file: path/to/file.md
    line: 12                  # 不明なら省略
    summary: "1〜2 文の要旨"
    evidence: "検証の前払いの節のとおり"
    attrs:                    # レビューが付けた属性をそのまま。無い属性を補完しない
      severity: P2
      confidence: high
residual: []                  # 報告しない条件に当たるが残す 1 行メモの列 (無ければ空)

注意:
- 指摘が 0 件なら findings: [] とだけ書く。件数の集計は書かない (読み手が計算する)。
- 値に # を含むときは必ず引用符で囲む (YAML は「半角スペース + #」以降をコメントとして落とす)。
- 指摘の取捨は「報告しない条件」に従い、それ以外は全件書く。修正はしない。
- 書き出したら、レビューの前後で HEAD と作業ツリーが変わっていないことを確認して報告する。
```
