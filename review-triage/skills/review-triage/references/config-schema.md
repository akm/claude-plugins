# 設定ファイルの様式

**このファイルが、設定の読み込み方・様式の制約・被害者の上書き規則の正本。** 対象の種類の宣言そのものは `.claude/review-triage.yaml` が持ち、分類の中身はそのファイルの冒頭コメントが説明する。設定を判定のどこで使うかは [judgment-flow.md](judgment-flow.md) の D1・D2。

**スキルは分類の既定値を持たない。** 検証できない既定値は、他のリポジトリで静かに誤判定する。

## 読み込みは 3 値で扱う

| 結果 | 条件 | 振る舞い |
| --- | --- | --- |
| **OK** | 読めて、パスがいずれかの分類に当たった | その分類の `audience` を被害者の初期値にして判定へ進む |
| **対象外** | 読めたが、どのパターンにも当たらない | D1 の「当たらない」— 保留 (種類不明)。件数を報告に出す |
| **読めない** | ファイルが無い / YAML として壊れている / 必須キーが欠けている | **判定を始めずに終了する** |

**「対象外」と「読めない」を畳み込まない。** 畳み込むと、設定のタイポで全件が黙って保留に落ちるのに、誰も設定が壊れていることに気づけない ([YAML の未知キーが移行漏れを隠す](https://github.com/tecowl/lappds/blob/main/docs/solutions/logic-errors/yaml-ignores-unknown-keys-hiding-schema-migration-gaps.md))。

**ファイルが無い場合は `--gen-config` を案内して終了する。** 推測で判定を始めない。

## 必須キーの検査

読み込み時に確かめる。1 つでも欠けていれば「読めない」として扱う。

- トップレベルに `categories` があり、配列である
- 各要素が `id`・`patterns`・`audience` の 3 つを持つ
- `id` が ASCII の識別子 (英小文字・数字・ハイフン) で、重複しない
- `patterns` が 1 つ以上の文字列の配列
- `audience` が `operator` / `admin` / `provider` / `developer` のいずれか

**未知のキーがあれば報告する** (エラーにはしない)。旧いキー名が残ったまま新しいキーを読めず、「エラーなしで空」が返る型を避けるため。

## 並び順が意味を持つ

**上から順に照合し、最初に当たった分類を採る。** 1 つのパスが複数の分類に当たりうるので、狭い分類を上に、広い受け皿を下に置く。

例: `internal/worker/agent_test.go` は `test` にも `production` にも当たる。`test` が上にあるので `test` (被害者は開発者) になる。逆順だと `production` (被害者はオペレータ) になり、テストへの指摘が保留に倒れる。

## パターンの照合

glob で照合する。**表記の揺れで当たり方が変わらないことを確かめる。**

| 揺れ | 扱い |
| --- | --- |
| 末尾のスラッシュ (`docs/manual/` と `docs/manual`) | 同じに扱う |
| `./` の前置 (`./docs/manual/**`) | 取り除いてから照合する |
| 大文字小文字 | 区別する |

**照合はパスの正規化を経てから行う。** 列挙で穴を塞ごうとすると、新しい書き方が現れるたびに穴が開く ([列挙する検査は穴を再生産する](https://github.com/tecowl/lappds/blob/main/docs/solutions/best-practices/enumerating-syntax-in-regex-reproduces-holes.md))。

## 被害者の上書き (D2)

パスから決まる `audience` は初期値で、**指摘の内容を読んで被害者が違うと分かる場合は上書きする**。

**上書きは「より要求水準の高い被害者へ」の向きにのみ行う。**

| 向き | 扱い |
| --- | --- |
| 開発者 → 利用者 (オペレータ・管理者・プロバイダ) | 上書きする。例: テストヘルパの欠陥がプロダクションの欠陥を隠している |
| 利用者 → 開発者 | **上書きしない — ただし初期値のまま確定させることもしない。** 内容から逆向きに見えた時点で D2 は「決められない」— 行き先は判定フローのとおり保留になる |

逆向きの上書きは却下を通しやすくする方向なので、機械的には行わない。

**記録には両方を残す** — パスから決まった分類 (`audience_initial`) と、上書き後の被害者 (`audience`)。

## 設定を変えたとき

**そのリポジトリで実際にレビュー対象になるパスが当たるかを確かめる。** 分類が欠けていると、その配下への指摘が全件「種類不明」に落ちて判定が一度も走らない。受け皿の分類 (`shared`・`doc-other`) を置くのはこの型を避けるため。

## `--gen-config` が生成するもの

**生成先は `.claude/review-triage.yaml`。既存があれば上書きせず、その旨を報告して終了する。**

- `categories` を、そのリポジトリの実際の構成 (`git ls-files`) から作り、パターンと種類・被害者を決める。
- **狭いものから順に並べる。** 先に一致したものが勝つので、広いパターンを先頭に置くと他が効かなくなる。
- 末尾に受け皿を置き、追跡対象のすべてのファイルがどれかに一致する状態にする (種類不明を 0 件にするため)。
- **生成した後、種類不明が 0 件かを確かめて報告する。** 残るなら、どのパスが漏れたかを挙げる。
