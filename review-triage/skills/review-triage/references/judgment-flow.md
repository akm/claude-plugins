# 判定フロー

**このファイルが判定フローの SSOT。** 役割の分担 (owning) は次のとおり。

- **図 (mermaid) が、ノードと遷移の SSOT。** 順序と分岐はここだけが定める。
- **決定表が、各ノードの条件と書くものの SSOT。** 遷移先の欄は持たない (遷移先は図が SSOT)。図と表は同じ事実を二度語らない。
- **散文 (SKILL.md・references) はノード ID で参照し、順序・分岐・量化子を言い直さない。** 1 回目の試行では、散文が状態機械を言い直すたびに量化子がずれ、同種の指摘が続いた。
- 図のノード ID 集合と決定表の ID 集合は 1:1。同梱の `triagecheck` の `judgment-flow` 検査が照合する。

## 方針

- **評価と判定を分ける。** 評価 (E1〜E3) の結果はすべて記録に残し、判定は図の分岐だけで決まる。同じ評価結果から違う判定が出ないようにするため。
- **D1〜D3 で決着した指摘には、E1・E2 を行わない。** 空虚な指摘に、仕様・設計との照合 (sub-agent を要する) やゲート評価のコストを払わないため。ただし D3 の帰結の 4 項目は、D1 に進んだ指摘の**全件に書く** (D9 で当たって判定を省略した指摘には書かない)。D1・D2 で決着した指摘にも、後から判断を検証する材料として残す。
- **D4 以降で決着した指摘には、E1・E2 の結果がすべて記録に残る。** 判定が D4 (根拠) で決まっても、ゲートの評価結果は捨てない。どのゲートが機能しているかは記録の蓄積でしか見えないため。
- **境界上は保留にする。** 決められないときの遷移先は必ず保留 (H1〜H8)。却下ゲートは仮説であり、誤った却下は気づかれないまま残るため、判断できないまま却下へ流さない。

## 決定表 (各ノードの条件と書くものの SSOT)

| ID | 種類 | 条件・内容 | 記録に書くもの |
| --- | --- | --- | --- |
| D9 | 判定 | 指摘が、記録の前の回までの下限未満の指摘 (B1 で決着したもの) と同じ問題で、対象の行が変わっていないか。次の 2 つがともに成り立てば「当たる」。**(1) 問題が同じ** (この指摘が述べる問題が、前の指摘の帰結の「何が」と同じ)。同じ問題の前の指摘が複数あれば、最も後の回のものと比べる。**(2) 対象の行が、前の指摘を判定した回でレビューした内容から、この回でレビューした内容までに変わっていない。** (2) は、D8 の (1) と同じツール lineorigin で確認し、全量の起点の代わりに、前の指摘を判定した回の `head` を渡す (確認の方法の SSOT は [premise-check.md](premise-check.md) の「(1) 対象の行が変わっていないか」)。ただし、この回でレビューした内容が、前の指摘を判定した回の `head` と同じコミットなら、ツールを使わずに (2) が成り立つとする。行は変わっていないが、ツールは、起点とレビューした内容が同じコミットだと「確認できない」を返すため。(1) が成り立たなければ「当たらない」。(1) が成り立ち、(2) が成り立たないか確認できないときも「当たらない」とし、D1 から通常どおり判定する。行が変わっていれば、文の意味も、帰結も、必要度も変わりうるため | (1) が成り立った指摘のすべてで、`below_minimum_ref` に、前の指摘 (回と `id`) と、(2) の結果と理由 |

| D2 | 判定 | 指摘の内容から被害者が分類の `audience` と同じか違うかを決められるか。上書きは「より要求水準の高い被害者へ」(開発者 → 利用者) の向きにのみ行う ([config-schema.md](config-schema.md) の上書き規則) | 初期値 (`audience_initial`) と最終値 (`audience`) |
| D3 | 判定 | 帰結の 4 項目を具体的に書けたか。4 項目は、条件 (どんな状況で起きるか) / 誰に (誰が困るか) / 何が (何が起きるか) / 気づかされるか (帰結が起きたとき、困る人が、何によって、いつ気づかされるか)。「何によって」は、エラーメッセージ・失敗する検査・通常の利用で目に見えて違う結果・後の工程 (その文書をもとにした実装・テスト・レビュー) のどれか。「いつ」は、被害が出る前・被害が出た時・後の工程のどれか。困る人が自分で調べたり疑ったりしたときにだけ分かる場合は、「気づかされない」と書く。文書やコードを検査する関門が無いことは、理由として書かない。指摘文は「何が悪いか」を書くが、判断に要るのは「何が壊れるか」。書き下ろす過程そのものが空虚な指摘をふるいにかける | 帰結の 4 項目 (`consequence`。D1 に進んだ指摘の全件) |
