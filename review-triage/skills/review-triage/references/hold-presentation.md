# 保留の提示

**このファイルが、保留 (H1〜H6) をどう人間に示すかの正本。** 保留になる条件は [judgment-flow.md](judgment-flow.md) — ここでは言い直さない。

## Markdown が正本

**判断の材料の正本は記録 (YAML) とサマリの Markdown。** 判断済みリストと同じ経路に載るので、追加の仕組みが要らない。

保留ごとに次を表で出す。

| 項目 | 内容 |
| --- | --- |
| 指摘 | ファイル・行・要旨 |
| 決着ノード | H1〜H6 のどれか |
| 対象の種類 | パスから決まった分類と、上書きした場合は上書き後の被害者 |
| 帰結の 4 項目 | 条件 / 誰に / 何が / 気づけるか |
| 発火したゲート | すべて。各ゲートで書かせたものを添える (E2 を行った指摘のみ) |
| なぜ決められなかったか | どのゲートと被害者の要求水準が衝突しているか、何が読み取れないか |
| 人間に伺いたいこと | 何を決めてほしいか |

**Markdown だけで判断できる形にする。** HTML を開かなくても人間が決められること。

## HTML は任意の表示形式

同じ内容を人間が見やすくしたもので、判断の流れの mermaid 図を添える。**生成と表示の方法は `mermaid-preview` skill が正本** (出力先・CDN・フォールバックの制約もあちらが持つ)。別のプラグインなので、入っていなければ図は出せない。**図は正本ではないので、生成に失敗しても Markdown があれば判断は完了する。**

**保留 0 件のときは生成しない。** 空のページを出さない。

## 即断できない保留の起票

人間がその場で判断できない保留は `gh issue create` で起票する。**本文は Markdown の正本をそのまま使う。** 起票前に本文を提示して確認を取る。

## 保留が多すぎるとき

**保留は人間が読みきれる量でなければ意味がない。** 多すぎれば読まれず、放置は却下と同じ結果になる。

件数は報告のサマリに必ず出す。想定より多ければ、判定の設計 (とくに D7 の被害者による分岐) を見直す材料になる。
