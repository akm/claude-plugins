# review-request: レビューの依頼文の生成

別セッションで走らせる上流レビューの依頼文を、雛形 ([review-request-template.md](../review-triage/references/review-request-template.md)) を埋めてファイルに書き出す。**成果物は依頼文のファイル 1 つで、レビューは走らせない。** 走らせるのは人間で、新しいセッションに依頼文のパスを渡す。結果を受け取って判定するのは [review-triage](../review-triage/SKILL.md)。

依頼の運用 (なぜファイルに書き出すか・範囲の規則・各節の理由) の正本は [review-request.md](../review-triage/references/review-request.md) — ここでは言い直さない。

## 前提知識

- **依頼文を会話に貼らない。** 貼り方が回ごとに変わると、出力先の名前・様式・読み取り専用の条件も回ごとに変わる (理由と実測は [review-request.md](../review-triage/references/review-request.md))。出力先のパスは生成の時点で依頼文に埋め込まれるので、レビュアがそこをずらす余地が無い。
- **雛形の各節 (読み取り専用・検証の前払い・報告しない条件・出力様式) はそのまま写す。** 生成のたびに言い直さない — 言い直すと、貼り方が回ごとに変わる元の問題に戻る。
- **スキル名とモデル名は推測しない。** 記録の `skill` / `model` にそのまま入るので、依頼したものと違う値が記録に残ると、粒度の比較が狂う。

## 手順

1. **引数と設定を読む**: 引数はスキル名とモデル名。**スキル名の省略時は `code-review`。モデル名は、引数に無ければ設定 (`.claude/akm-claude-plugins/review-triage/config.json`) の `loop.review_model` を使い、それも未設定なら人間に尋ねる** (設定のキーの正本は [project-config.md](../review-triage/references/project-config.md))。あわせて設定の `record_dir` を読む (未設定なら既定の `tmp/review-triages/`)。
2. **回と範囲を決める**: 現在のブランチの記録 (`<record_dir>/<ブランチ名>.yaml`。ブランチ名の `/` は `-` に置き換える) を読み、`runs` の数 + 1 を回とする (記録が無ければ 1)。
   - 記録に回が無ければ scope は `full`、`base` は分岐元 (既定は `main`)。補足は「ブランチの全量」。
   - 回があれば scope は `incremental`、`base` は直前の回の `head`。補足は「前回の HEAD `<sha>` からの増分。増分の外は、増分が壊した場合のみ報告する」。
   - **`tmp/` が `git check-ignore` で無視されていなければ生成せず、「`.gitignore` に `tmp/` を足してコミットしてから再実行する」と案内して終了する** — スキルは `.gitignore` を変えない。依頼文と結果は設定の `record_dir` に関わらず `tmp/` に置くので、記録の置き場と違って「既定の置き場を使うとき」に限らず常に確かめる (前提の正本は [record-schema.md](../review-triage/references/record-schema.md) の冒頭)。
   - `head` は現在の HEAD の短縮 SHA。**作業ツリーが clean でなければ生成せず、その旨を報告する** — レビュアは HEAD と作業ツリーが不変であることを確かめて報告するので、汚れたまま渡すと確認が成り立たない。
3. **識別子と出力先を決める**: 識別子は `<YYYYMMDD>-<hhmm>-<ブランチ名>-<回>` (生成の日時、ブランチ名は記録のファイル名と同じく `/` を `-` に置き換える、回は手順 2)。依頼文は `tmp/review-request-<識別子>.md`、レビュー結果の出力先は `tmp/review-<識別子>.yaml`。ブランチ名を含めるのは、`tmp/` は手元にしか無く、同じリポジトリの別のブランチで同じ回を回すと衝突するため (実測)。日時を先頭に置くのは、一覧が時系列に並び、同じ回に複数のレビュアを走らせても別のファイルになるため。スキル名とモデル名は依頼文の本文と記録に残るので、名前には入れない。
   - **どちらかが既に存在すれば上書きせず、その旨を報告して終了する。** 同じ識別子で作り直したいときは人間が消す。
4. **雛形を埋めて書き出す**: 雛形の `{{…}}` を次で埋める — `repo` (`git remote get-url origin`)・`repo_dir` (`git rev-parse --show-toplevel`)・`branch` (現在のブランチ名)・`base` / `head` / `scope` / `scope_note` (手順 2)・`skill` / `model` (手順 1)・`date` (生成日 `YYYY-MM-DD`)・`output_path` (手順 3)。`tmp/` が無ければ作る (無視されていることは手順 2 で確かめ済み)。書き出したら、埋め残した `{{…}}` が無いことを確かめる。
5. **報告する**: 依頼文のパスと出力先のパス、埋めた値 (対象・範囲・スキル名・モデル名) を出す。**新しいセッションへ渡すのは依頼文のパス 1 つ**であること、結果が返ったら `review-triage` に出力先のパスを渡すことを案内する。

## 原則

- **レビューを走らせない。** 走らせるかどうか、どのセッションで走らせるかは人間が決める。
- **既存の依頼文・結果を上書きしない。** 回の途中で作り直すと、どの結果がどの依頼に対応するかが辿れなくなる。
- **依頼文のファイルはコミットしない。** `tmp/` 配下に置き、記録と同じく git の追跡外にする (無視されていなければ手順 2 で止まる)。

## このスキルがしないこと

- **レビュー結果の様式の検査** — 受け取る側 (`review-triage` の手順 1) が担う。
- **依頼文の文面の設計** — 雛形が正本。文面を変えたいときは雛形を直す。
