# review-request: レビューの依頼文の生成

別セッションで走らせる上流レビューの依頼文を、雛形 ([review-request-template.md](../review-triage/references/review-request-template.md)) を埋めてファイルに書き出す。**成果物は依頼文のファイル 1 つで、レビューは走らせない。** 走らせるのは人間で、新しいセッションに依頼文のパスを渡す。結果を受け取って判定するのは [review-triage](../review-triage/SKILL.md)。

依頼の運用 (なぜファイルに書き出すか・範囲の規則・各節の理由) の正本は [review-request.md](../review-triage/references/review-request.md) — ここでは言い直さない。

## 引数

```
review-request [<スキル名>] [<モデル名>] [<effort>] [--dir <ディレクトリ>] [--full-review] [--base <ブランチ>]
```

| 引数 | 意味 | 省略時 |
| --- | --- | --- |
| `<スキル名>` | 依頼文でレビュアに呼ばせるレビュースキル | 手順 1 |
| `<モデル名>` | レビューを実行するモデル | 手順 1 |
| `<effort>` | レビュースキルに渡す effort | 手順 1 |
| `--dir <ディレクトリ>` | 依頼文と結果の置き場。相対パスはリポジトリのルート (`git rev-parse --show-toplevel`) を基準に解決する。作業ツリーの外は受け付けない (git に無視されていることを確かめられないため) | `tmp/` |
| `--full-review` | 記録に回があっても、範囲を全量 (scope `full`) にする。要否に関わらず全量にする明示の指定 (要否の規則の正本は [review-request.md](../review-triage/references/review-request.md) の「収束後の全量レビューと、その要否」) | 範囲は手順 2 のとおり (記録に回が無ければ全量、あれば増分) |
| `--base <ブランチ>` | 全量の起点を求める派生元のブランチ (別の作業ブランチから派生したブランチなら、その作業ブランチ)。増分の回では使わない | `origin/HEAD` が指すブランチ (手順 2) |

位置引数はこの順で読む。`--dir`・`--full-review`・`--base` は位置引数の前後どちらに置いてもよい。`--full-review` と `--base` は設定のキーを持たない — どちらもブランチや周回ごとに変わる値である。周回の置き場に依頼文を書くスキル (`review-loop`) が、`--dir` を毎回、`--base` と `--full-review` を全量の回に使う。

## 前提知識

- **依頼文を会話に貼らない。** 貼り方が回ごとに変わると、出力先の名前・様式・読み取り専用の条件も回ごとに変わる (理由と実測は [review-request.md](../review-triage/references/review-request.md))。出力先のパスは生成の時点で依頼文に埋め込まれるので、レビュアがそこをずらす余地が無い。
- **雛形の各節 (作業ツリーの扱い・検証の前払い・報告しない条件・出力様式) はそのまま写す。** 生成のたびに言い直さない — 言い直すと、貼り方が回ごとに変わる元の問題に戻る。
- **スキル名とモデル名は推測しない。** 記録の `skill` / `model` にそのまま入るので、依頼したものと違う値が記録に残ると、粒度の比較が狂う。

## 手順

1. **引数と設定を読む**: 引数はスキル名・モデル名・effort と置き場 (様式は上の「引数」)。**スキル名の省略時は `code-review`。モデル名は、引数に無ければ設定 (`.claude/akm-claude-plugins/review-triage/config.json`) の `loop.review_model` を使い、それも未設定なら人間に尋ねる。effort は、引数に無ければ設定の `loop.review_args`、それも未設定なら既定 (正本は [review-invocation.md](../review-triage-loop/references/review-invocation.md) の「effort の既定」)。`ce-code-review` のように effort を受け取らない skill では空にする** (設定のキーの正本は [project-config.md](../review-triage/references/project-config.md))。あわせて設定の `record_dir` を読む (未設定なら既定の `tmp/review-triages/`)。
2. **回と範囲を決める**: 現在のブランチの記録 (`<record_dir>/<ブランチ名>.yaml`。ブランチ名の `/` は `-` に置き換える) を読み、`runs` の数 + 1 を回とする (記録が無ければ 1)。**記録があるのに読めない (YAML として壊れている・`runs` が無い) なら、生成せずにその旨を報告して終了する** — 「読めない」を「無い」に寄せると回が 1 に戻り、過去の回と同じ番号の依頼文ができる。
   - **記録に回が無いか、引数 `--full-review` があれば、scope は `full`。** `base` は、起点のブランチと HEAD の merge-base (共通祖先のコミット) の短縮 SHA (`git merge-base <ブランチ> HEAD` の結果を `git rev-parse --short` で縮めたもの)。起点のブランチは、引数 `--base` があればそれ、無ければ `origin/HEAD` が指すブランチ (`git symbolic-ref --short refs/remotes/origin/HEAD` の結果。`origin/main` のような形のまま使う)。起点を分岐元の `main` に決め打ちしないのは、別の作業ブランチから派生したブランチで、派生元のコミットまで範囲に入るため。**`--base` のブランチが解決できない (`git rev-parse --verify --quiet "<ブランチ>^{commit}"` が失敗する)、`--base` が無くて `origin/HEAD` が無い、または merge-base が求まらない (共通祖先が無い) なら、生成せずにその旨を報告し、起点のブランチを人間に尋ねる** — 起点を推測すると、範囲が広すぎるか狭すぎる依頼文ができ、どちらもレビューの結果からは気づけない。
     - 補足は、記録に回が無く `--full-review` も無ければ「ブランチの全量 (起点: `<ブランチ>` との merge-base)」。`--full-review` があれば「ブランチの全量 (`--full-review` による指定。起点: `<ブランチ>` との merge-base)。増分の外を報告しない規則はこの回には当てはまらない」。書き分けるのは、記録に回がある状態の全量の回で、レビュアが前の回の依頼文にあった増分の規則をこの回に当てはめないようにするため。
   - **それ以外 (記録に回があり、`--full-review` が無い) なら、scope は `incremental`、`base` は直前の回の `head`。** `--base` は使わない (あっても無視し、報告にその旨を書く)。補足は「前回の HEAD `<sha>` からの増分。増分の外は、増分が壊した場合のみ報告する」。
   - **置き場 (`--dir`。省略時は `tmp/`) が `git check-ignore -q <置き場>` で無視されていなければ生成せず、「`.gitignore` に置き場 (既定なら `tmp/`) を足してコミットしてから再実行する」と案内して終了する** — スキルは `.gitignore` を変えない。依頼文と結果は設定の `record_dir` に関わらず置き場に置くので、記録の置き場と違って「既定の置き場を使うとき」に限らず常に確かめる (前提の正本は [record-schema.md](../review-triage/references/record-schema.md) の冒頭)。`git check-ignore` は存在しないパスにも効くので、置き場を作る前に確かめる。
   - `head` は現在の HEAD の短縮 SHA。**作業ツリーが clean でなければ生成せず、その旨を報告する** — 依頼文は作業ツリーの扱いを「共有」(依頼した側と同じ作業ツリーでレビューする) で書くので、レビュアは HEAD と作業ツリーが不変であることを確かめて報告する。汚れたまま渡すと、その確認が成り立たない。周回 (`review-loop`) で「使い捨て」に書き換えた依頼文でも、依頼した側の作業ツリーは確かめる (確かめるのはワーカーで、正本は [review-loop の worker.md](../review-loop/references/worker.md) の「回の処理」の手順 4)。
3. **識別子と出力先を決める**: 識別子は `<YYYYMMDD>-<hhmm>-<ブランチ名>-<回>-<スキル名>-<モデル名>`。依頼文は `<置き場>/review-request-<識別子>.md`、レビュー結果の出力先は `<置き場>/review-<識別子>.yaml` (置き場の既定は `tmp/`)。成分ごとの扱いは下の表が正本で、**成分を足す・外す・変えるときは、その行の全欄を確かめる** — 欄を 1 つ書き残すと、その扱いの欠けは次のレビューまで気づかれない (実測: 成分を変えるたびに、外した成分の役割・足した成分の整え方・参照先の規則、と別の欄で 3 回続いた)。識別子はファイル名に使うので、整え方はファイル名に使える形にするためのもの。識別子の衝突 (同じ名前の依頼文か結果が既にある状態) は 1 つずつやり直せるので、厳密な一意性は求めない。

   | 成分 | 出所 | 整え方 | 欠損時の扱い | なぜ入れるか |
   | --- | --- | --- | --- | --- |
   | 日時 (`YYYYMMDD-hhmm`) | 生成した日時 | 数字だけなのでそのまま | — (必ず取れる) | 先頭に置くと一覧が時系列に並ぶ |
   | ブランチ名 | 現在のブランチ | `/` と、ファイル名に使えない文字を `-` に置き換える (記録の YAML のファイル名の規則とは別に定める。参照しない) | detached HEAD なら `detached-<短縮 SHA>` | `tmp/` は手元にしか無く、同じリポジトリの別のブランチで同じ回を回すと衝突する (実測) |
   | 回 | 手順 2 | 数字だけなのでそのまま | 記録が無ければ 1。記録があるのに読めなければ生成せず報告して終了 (手順 2) | 同じブランチの過去の回と区別する |
   | スキル名・モデル名 | 手順 1 | `/` と、ファイル名に使えない文字を `-` に置き換える (設定や引数の綴りをそのまま入れない) | 未指定なら手順 1 の既定か人間に尋ねる | 同じ回に複数のレビュアを走らせたとき (同じ分に作れば日時は同じ) を分け、依頼文を開かずにどのレビュアの結果かが分かる |

   - **どちらかが既に存在すれば上書きせず、その旨を報告して終了する。** 同じ識別子で作り直したいときは人間が消す。
4. **雛形を埋めて書き出す**: 雛形の `{{…}}` を次で埋める — `repo` (`git remote get-url origin`)・`repo_dir` (`git rev-parse --show-toplevel`)・`branch` (現在のブランチ名)・`base` / `head` / `scope` / `scope_note` (手順 2)・`skill` / `model` / `effort` (手順 1)・`date` (生成日 `YYYY-MM-DD`)・`run_id` (手順 3 の識別子)・`output_path` (手順 3 の出力先を `repo_dir` 起点の絶対パスにしたもの)。置き場が無ければ作る (無視されていることは手順 2 で確かめ済み)。
   - **出力先は絶対パスで埋める。** 相対パスはレビュアの側の cwd (作業ディレクトリ) で解決され、別の場所に書かれた実測がある。
   - **雛形の「対象」の節にある作業ツリーの扱いの行 (`- 作業ツリーの扱い: 共有`) は書き換えず、値「共有」のまま書く** — 「使い捨て」への書き換えは周回 (`review-loop`) のワーカーが行う (正本は [review-loop の worker.md](../review-loop/references/worker.md) の「回の処理」の手順 8)。
   - **依頼文は、同じ置き場の一時名 `.review-request-<識別子>.md.tmp` に書き、埋め残した `{{…}}` が無いことを確かめてから、`mv` で `review-request-<識別子>.md` に改名する。** 置き場を定期的に確かめる側 (`review-loop` のワーカー) は一時名 (`.` で始まる名前) を読まないので、書きかけの依頼文を処理しない。
5. **報告する**: 依頼文のパスと出力先のパス、埋めた値 (対象・範囲・スキル名・モデル名・effort) を出す。**scope が `full` なら、起点のブランチ名と merge-base の SHA、ブランチの出所 (`--base` か、`origin/HEAD` による既定か)、`--full-review` の有無も出す** — 起点を推測しない規則を、人間が報告で確かめられるようにするため。**新しいセッションへ渡すのは依頼文のパス 1 つ**であること、結果が返ったら `review-triage` に出力先のパスを渡すことを案内する。

## 原則

- **レビューを走らせない。** 走らせるかどうか、どのセッションで走らせるかは人間が決める。
- **既存の依頼文・結果を上書きしない。** 回の途中で作り直すと、どの結果がどの依頼に対応するかが辿れなくなる。
- **依頼文のファイルはコミットしない。** 置き場に置き、記録と同じく git の追跡外にする (無視されていなければ手順 2 で止まる)。

## このスキルがしないこと

- **レビュー結果の様式の検査** — 受け取る側 (`review-triage` の手順 1) が担う。
- **依頼文の文面の設計** — 雛形が正本。文面を変えたいときは雛形を直す。
