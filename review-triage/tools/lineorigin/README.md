# lineorigin

レビューの指摘の対象の行が、全量の起点 (ブランチの作り始めのコミット) から、レビューした内容まで変わっていないかを確かめる。`review-triage` の判定ノード D8 (このブランチより前からある欠陥か) の条件 (1) に使う (条件の正本は [judgment-flow.md](../../skills/review-triage/references/judgment-flow.md) の D8 の行、何をレビューした内容とするかの正本は [premise-check.md](../../skills/review-triage/references/premise-check.md) の「前からある欠陥の確かめ方」)。

**なぜ要るか。** この確かめ方を規範文書の文 (git のコマンドの例) で書いていたときは、版の指定・改名と移動・コミットしていない行・実行するディレクトリ・パスの書き方の解釈などで結果が変わり、直すたびに確かめていない場合が次のレビューで見つかった。判定するエージェントが例と違う実行をしても、git はエラーを出さずに別の結果を返すので気づけない ([#110](https://github.com/akm/claude-plugins/issues/110))。道具にして、見つけた場合をテストで検証する。

## 何を返すか

結果は 3 つのどれかで、理由と、行ごとの内訳を添える。

| 結果 | 意味 | 主な場合 |
| --- | --- | --- |
| `holds` (成り立つ) | 対象の行はどれも、全量の起点に同じパスの同じ行としてあったまま変わっていない | — |
| `not-holds` (成り立たない) | 起点から変わった行がある | このブランチのコミットか、起点の後にマージで取り込んだコミットが書いた・書き換えた行。コミットしていない行。起点に同じパスのファイルが無い (このブランチで作った・改名した・移した)。`-worktree` のときに、HEAD に同じパスのファイルが無い (コミットしていないファイル)。このブランチで改名・移動したファイルの行 |
| `unverifiable` (確かめられない) | 成り立つか成り立たないかを決められない | 全量の起点が、レビューした内容のコミットと同じ (このブランチの変更と前からある行を区別できない)。起点がそのコミットの祖先ではない。`-rev` のときに、指摘のファイルにコミットしていない変更がある (レビューがそれを見たかが分からない)。起点より前に分かれた履歴をマージして入った行 |

複数の行を渡したときは、成り立たない行が 1 つでもあれば `not-holds`、それが無く確かめられない行があれば `unverifiable`、すべての行が成り立てば `holds`。

**結果を出せないときは、標準出力に何も書かず、標準エラー出力の最初の行に、次の 2 つの印のどちらかを付けて書く。** 終了コードでも分けるが、`go run` で実行すると、道具の終了コードが 0 でなければ `go run` は 1 を返すので、終了コードでは見分けられない (下の「使い方」)。

| 印 | 意味 | 主な場合 |
| --- | --- | --- |
| `input-error:` | 入力の誤り。道具が自分で確かめられる条件に限る | 必須のフラグが無い・知らないフラグがある・`-rev` と `-worktree` の指定が 1 つでない・`-root` が存在するディレクトリでない・`-root` から上のどこにも `.git` が無い・版が無い・レビューした内容に `-file` のファイルが無い・行がレビューした内容の行数を越える |
| `run-error:` | 道具を実行できない。渡したものを直しても結果は出ない。git の文言を添える | git を起動できない・git が 2.30 より前・`.git` があるのに git がリポジトリとして読めない (権限・所有者など)・git がオブジェクトを読めない (壊れたリポジトリ・部分クローンで取得できない、など)・そのほか git が想定していない失敗をした・git の出力を読めない |

入力の誤りを結果 (確かめられない) にしないのは、指摘の `file` と `line` が根拠の照合 (E1) を通っているので、ここで見つからないなら渡し方の誤りであり、「確かめられない」として扱うと誤りに気づけないため。

## 前提

**Go と git が要る。** [triagecheck](../triagecheck/README.md) と同じく、バイナリは配らず `go run` で都度実行する (理由はそちらの「前提」)。git は 2.30 以降 (`git rev-parse --end-of-options` が 2.30.0 から)。道具は始めに git の版を確かめ、古ければ `run-error:` で終わる。

## 使い方

**`go run -C` でツールのモジュールに入って実行する。** `go run -C` は作業ディレクトリを道具のディレクトリに変えるので、`-root` には調べるリポジトリのルートか、その中のディレクトリの絶対パスを渡す。

`<プラグインの展開先>` は、review-triage のプラグインのディレクトリで、スキル review-triage を読み込んだときに示される基点ディレクトリ (`SKILL.md` のあるディレクトリ) の 2 つ上にあたる。環境によって違い、版ごとに分かれる (見つけ方の例は、triagecheck の README の「[Makefile に置く例](../triagecheck/README.md#makefile-に置く例)」)。

```sh
# 結果のファイルで受け取ったレビュー: レビューした内容はその head のコミット
go run -C <プラグインの展開先>/tools/lineorigin . -root "$(pwd)" -base <全量の起点> -file <ファイル> -lines 12 -rev <head>

# 同じセッションのレビューで、コミットしていない変更を含めて見たとき: 作業ツリーの内容
go run -C <プラグインの展開先>/tools/lineorigin . -root "$(pwd)" -base <全量の起点> -file <ファイル> -lines 12-15 -worktree
```

| フラグ | 必須 | 内容 |
| --- | --- | --- |
| `-root` | ✓ | リポジトリのルートか、その中のディレクトリの絶対パス。ルートは道具が求める |
| `-base` | ✓ | 全量の起点。コミットに解決できる版 (SHA・ブランチ名など) |
| `-file` | ✓ | 指摘の `file`。リポジトリのルートからの相対パス。パターンの文字 (`[` や `*`) や先頭の `:` も、書いたとおりのファイル名として読む |
| `-lines` | ✓ | 指摘の行。`12` か `12-15` の形で、レビューした内容の行番号 |
| `-rev` | `-worktree` とどちらか 1 つ | レビューした内容のコミット |
| `-worktree` | `-rev` とどちらか 1 つ | レビューした内容が作業ツリー (コミットしていない変更を含む) のとき |

出力 (標準出力) の例:

```text
result: not-holds
reason: 対象の行のうち、全量の起点から変わった行がある
line 12: 全量の起点にあったまま
line 13: 全量の起点より後のコミット 1fe637c0a1b2 が書いた・書き換えた行
```

行を調べる前に結果が決まったとき (起点がレビューした内容のコミットと同じ、など) は、`line` の行を出さない。終了コードは、結果を出したら 0、`input-error:` なら 2、`run-error:` なら 3。ただし `go run` で実行すると、道具の終了コードが 0 でなければ `go run` は 1 を返し、標準エラー出力の最後に `exit status 2` のような行を足す。見分けるときは、終了コードではなく標準エラー出力の最初の行の印を読む。

## どう確かめるか

範囲を起点で区切った `git blame <全量の起点>..<コミット>` (`-worktree` なら `--contents` で作業ツリーの内容を渡す) で、行ごとに、その行を最後に変えたコミットとそのときのパスを求める。範囲を起点で区切ると、起点から変わっていない行は起点のコミットが境界 (`boundary`) として報告される。境界が起点で、パスが `-file` と同じなら、その行は起点にあったまま。

git の振る舞いのうち、結果を変えるものには次のように対処している。どれもテスト (ファイル `review-triage/tools/lineorigin/lineorigin_test.go`) で検証している。

| 振る舞い | 対処しないと | 対処 |
| --- | --- | --- |
| `git blame` は、指定が無くてもファイル全体の改名を追い、改名前のパスで起点まで遡る | このブランチで改名したファイルの行が、起点にあったままと報告される | 起点に同じパスのファイルがあることを確かめ、さらに境界のパスが `-file` と同じことを確かめる (起点にあったファイルを消した後に、別のファイルをそのパスへ改名した場合も見分ける) |
| 利用者の環境の `GIT_` で始まる変数が、リポジトリの場所を替える (`GIT_DIR`・`GIT_WORK_TREE`・`GIT_INDEX_FILE` など)、設定を注入する (`GIT_CONFIG_PARAMETERS`・`GIT_CONFIG_COUNT` など)、パスの読み方を替える (`GIT_GLOB_PATHSPECS` など) | `-root` と違うリポジトリや設定を読む。テストでは、テストのコミットやブランチがその変数の指すリポジトリに作られる | git に渡す環境から `GIT_` で始まる変数をすべて取り除き、道具が要るもの (この表の別の行) だけを足す。テストも、始める前に `GIT_` で始まる変数を取り除く |
| diff の textconv (比べる前にファイルを別の形へ変換する設定) を、`git blame` が当てる | 変換で消える部分だけを書き換えた行が、起点にあったままと報告される | `--no-textconv` を付ける |
| `git replace` の置き換えを、`git blame` が見る | 置き換えた後の履歴で、行を最後に変えたコミットを求めるので、書き換えた行が起点にあったままと報告されうる | 環境変数 `GIT_NO_REPLACE_OBJECTS=1` を立てる |
| 設定 `blame.ignoreRevsFile` に挙げたコミットを、`git blame` が無視する | そのコミットが書き換えた行が、起点にあったままと報告される | `--ignore-revs-file ""` で設定を打ち消す |
| 範囲の中のルートのコミット (無関係な履歴のマージ) を、`git blame` が境界として扱う | その履歴から入った行を見分けにくい | `--root` を付け、そのコミットの行として報告させる |
| 起点より前に分かれた履歴をマージすると、行がその分岐点まで遡り、分岐点が境界になる | その行が起点にもあったかは決められない | 境界が起点と違えば、確かめられないとする |
| `-- <ファイル>` の形のパスは、カレントディレクトリを基準に読まれ、pathspec (パターンや先頭の `:` で始まる特別な指定) として解釈される | ルート以外で実行すると、変更があっても無いと判定する。`[a].md` の変更の有無を `a.md` の変更で判定したり、`:c.md` に変更があっても無いと判定したりする | どの git にも `-C <ルート>` を付け、環境変数 `GIT_LITERAL_PATHSPECS=1` を立てる |
| 日本語や `"` を含むパスを、`git blame` が引用符で囲み、バイトを 8 進数で書いて出す | パスの比較が合わない | 引用を解いてから比べる |
| 範囲 `<起点>..<起点>` は空で、コミット済みのどの行も境界として報告される | このブランチにコミットが無いとき、どの行も成り立ってしまう | 起点がレビューした内容のコミットと同じなら、確かめられないとする |

**読むだけで、リポジトリを変えない。** 使う git のコマンド (`rev-parse`・`merge-base`・`cat-file`・`ls-tree`・`ls-files`・`hash-object` (書き込みの `-w` を付けない)・`blame`) は、どれもインデックスもオブジェクトも書かない。`-rev` のときのコミットしていない変更の有無は、`git diff` ではなく、HEAD・インデックス・作業ツリーの内容のハッシュを比べて確かめる。`git diff` は、更新時刻などの控えが古いファイルがあると、環境変数 `GIT_OPTIONAL_LOCKS=0` を立てても控えを更新してインデックスを書き換えるため。インデックスの控えに頼らないので、skip-worktree や assume-unchanged が付いたファイルの編集も変更として扱う。作業ツリーの内容は、git が記録するのと同じ形でハッシュを求める — 通常のファイルは `hash-object --path` (属性によるフィルタを当てる)、シンボリックリンクはリンクの先ではなくリンクの文字列、それ以外の種類 (ディレクトリなど) に置き換わっていれば変更ありとする。

ただし、属性で clean フィルタ (`git add` のときにファイルを変換するプログラム。git-lfs など) が設定されたファイルでは、`hash-object --path` がそのプログラムを実行する。そのプログラムがリポジトリに書くことがある (git-lfs は、オブジェクトを `.git/lfs` に書き込む) ので、そのファイルについては「リポジトリを変えない」が成り立たない。

## 限界

- **ファイルの中やファイルの間で移した行は、成り立たない。** git の移動の検出 (`-M`・`-C`) は使わない。日本語の行などでは検出されないので、使っても移した行を見分けきれない ([premise-check.md](../../skills/review-triage/references/premise-check.md) の「(1) 対象の行が変わっていないか」)。
- **確かめるのは条件 (1) だけ。** 条件 (2) (全量の起点の内容でも同じ欠陥が成り立つか) は、指摘の主張を読み直す判断なので、道具にしない。
- **全量の起点は、渡されたものを使う。** 起点の決め方 (レビュー結果の `base`・周回が決めたブランチ・`origin/HEAD`) の正本は [premise-check.md](../../skills/review-triage/references/premise-check.md) の「全量の起点」で、道具は決めない。
