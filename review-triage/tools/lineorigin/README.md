# lineorigin

レビューの指摘の対象の行が、全量の起点 (ブランチの作り始めのコミット) から、レビューした内容まで変わっていないかを確かめる。`review-triage` の判定ノード D8 (このブランチより前からある欠陥か) の条件 (1) に使う (条件の正本は [judgment-flow.md](../../skills/review-triage/references/judgment-flow.md) の D8 の行、何をレビューした内容とするかの正本は [premise-check.md](../../skills/review-triage/references/premise-check.md) の「前からある欠陥の確かめ方」)。

**なぜ要るか。** この確かめ方を規範文書の文 (git のコマンドの例) で書いていたときは、版の指定・改名と移動・コミットしていない行・実行するディレクトリ・パスの書き方の解釈などで結果が変わり、直すたびに確かめていない場合が次のレビューで見つかった。判定するエージェントが例と違う実行をしても、git はエラーを出さずに別の結果を返すので気づけない ([#110](https://github.com/akm/claude-plugins/issues/110))。道具にして、見つけた場合をテストで検証する。

## 何を返すか

結果は 3 つのどれかで、理由と、行ごとの内訳を添える。

| 結果 | 意味 | 主な場合 |
| --- | --- | --- |
| `holds` (成り立つ) | 対象の行はどれも、全量の起点に同じパスの同じ行としてあったまま変わっていない | — |
| `not-holds` (成り立たない) | 起点から変わった行がある | このブランチのコミットか、起点の後にマージで取り込んだコミットが書いた・書き換えた行。コミットしていない行。起点に同じパスのファイルが無い (このブランチで作った・改名した・移した)。フラグ `-worktree` のときに、HEAD に同じパスのファイルが無い (コミットしていないファイル)。このブランチで改名・移動したファイルの行 |
| `unverifiable` (確かめられない) | 成り立つか成り立たないかを決められない | 全量の起点が、レビューした内容のコミットと同じ (このブランチの変更と前からある行を区別できない)。起点がそのコミットの祖先ではない。フラグ `-rev` のときに、指摘のファイルにコミットしていない変更がある (レビューがそれを見たかが分からない)。指摘のファイルに clean フィルタ (属性 `filter`。`git add` のときにファイルを変換するプログラム) が設定されているか、指摘のファイルが追跡中のシンボリックリンク (どちらも、レビュアが読む内容と `git blame` が見る内容の行番号を対応させられない)。起点より前に分かれた履歴をマージして入った行 |

行ごとの内訳は、成り立つ行に、対応させた起点の行番号を添える (`全量の起点にあったまま (起点の 10 行目)` のように)。起点に同じ内容の行が複数あっても、`git blame` が差分で対応させた行を指す。

複数の行を渡したときは、成り立たない行が 1 つでもあれば `not-holds`、それが無く確かめられない行があれば `unverifiable`、すべての行が成り立てば `holds`。

**結果を出せないときは、標準出力に何も書かず、標準エラー出力の最初の行に、次の 2 つの印のどちらかを付けて書く。** 終了コードでも分けるが、`go run` で実行すると、道具の終了コードが 0 でなければ `go run` は 1 を返すので、終了コードでは見分けられない (下の「使い方」)。

| 印 | 意味 | 主な場合 |
| --- | --- | --- |
| `input-error:` | 入力の誤り。道具が自分で確かめられる条件に限る | 必須のフラグが無い・知らないフラグがある・`-rev` と `-worktree` の指定が 1 つでない・フラグ `-root` が存在するディレクトリでない・`-root` から上のどこにも `.git` が無い・版が無い・レビューした内容にフラグ `-file` のファイルが無い・行がレビューした内容の行数を越える |
| `run-error:` | 道具を実行できない。渡したものを直しても結果は出ない。git の文言を添える | git を起動できない・git が 2.30 より前・`.git` があるのに git がリポジトリとして読めない (権限・所有者など)・git がオブジェクトを読めない (壊れたリポジトリ・部分クローンで取得できない、など)・git が期限 (下の「どう確かめるか」の表) までに終わらない・そのほか git が想定していない失敗をした・git の出力を読めない |

入力の誤りを結果 (確かめられない) にしないのは、指摘の `file` と `line` が根拠の照合 (E1) を通っているので、ここで見つからないなら渡し方の誤りであり、「確かめられない」として扱うと誤りに気づけないため。

## 保証すること

**道具が保証するのは、誤って `holds` を返さないことだけ。** `holds` は、範囲を全量の起点で区切ったコマンド `git blame` が、対象の行のどれもを起点のコミット (範囲の境界。`boundary`) のものと報告し、そのときのパスが `-file` と同じときにだけ返す (下の「どう確かめるか」)。

`holds` が意味するのは、対象の行のそれぞれが、全量の起点の同じパスのファイルに、`git blame` が差分で対応させた同じ内容の行としてあること。誤った `holds` とは、その内容の行が起点に無いのに `holds` を返すことを言う。`git blame` が行を起点のコミットのものと報告する条件は、下の「どう確かめるか」にある。起点の内容はコミットの SHA で決まるので、起点のコミットのものと報告した行は、起点のファイルに同じ内容で必ずある。

- 履歴の親を差し替える仕組み (ファイル `.git/info/grafts` (非推奨) など) があると、結果は本当の履歴と違いうる。親が替わって境界が起点でなくなれば `unverifiable`、行が変わったと見なされれば `not-holds` になる。途中のコミットを隠すと、ブランチが書き換えて元へ戻した行が `holds` になることもあるが、その行の内容は起点と同じなので、誤った `holds` には当たらない。環境変数 `GIT_NO_REPLACE_OBJECTS` が打ち消すのは `git replace` の置き換えだけで、grafts は打ち消さない (下の「どう確かめるか」)。
- 同じ内容の行が並ぶとき (空行・閉じ括弧など) や、ファイルの中で行を並べ替えたとき、どの行を起点の行と対応させるかは、差分が決める (対応させた起点の行は、内訳に行番号で出す。上の「何を返すか」)。どの行が `holds` になっても、その行の内容は起点の行と同じである (扱いの正本は [review-triage/skills/review-triage/references/premise-check.md](../../skills/review-triage/references/premise-check.md) の「(1) 対象の行が変わっていないか」)。
- 誤った `holds` になりうるのは、渡した行番号と、`git blame` が見る内容の行番号が対応しないときである。clean フィルタが設定されたファイルと、追跡中のシンボリックリンクはこれに当たるので、方式 (`-rev` / `-worktree`) によらず確かめずに `unverifiable` を返す (扱いの正本は、下の「どう確かめるか」の表)。

D8 にとって危ないのは誤った `holds` だけで、ほかの誤りは、どれも最後は D8 が「当たらない」になる ([review-triage/skills/review-triage/references/judgment-flow.md](../../skills/review-triage/references/judgment-flow.md) の D8 の行)。

- `not-holds` と `unverifiable` の取り違え、`run-error:` は、そのまま D8 が当たらない。
- `input-error:` は、判定するエージェントがまず渡し方を直して実行し直し、値が原因で直せないときに (1) を確かめられないとして、D8 が当たらない ([review-triage/skills/review-triage/references/premise-check.md](../../skills/review-triage/references/premise-check.md) の「確かめ方」)。エラーの種類を取り違えると、直せない値を直そうとする手間が増えるが、誤った `holds` にはならない。

そのため、珍しいリポジトリの状態では、エラーの種類や結果の理由が、実際の原因と違うことがある (どの状態でそうなるかの正本は、下の[「限界」](#限界))。テストは、コードの条件分岐のうち、誤った `holds` に関わるもの (境界と起点の比較・パスの比較・環境変数と設定の打ち消し・コミットしていない変更の確かめ方・clean フィルタとシンボリックリンクの確認) を検証する。エラーの種類を分ける条件分岐には、テストの無いものがある (環境変数 `LC_ALL=C` など)。

## 前提

**Go と git が要る。** [triagecheck](../triagecheck/README.md) と同じく、バイナリは配らず `go run` で都度実行する (理由はそちらの「前提」)。git は 2.30 以降 (`git rev-parse --end-of-options` が 2.30.0 から)。道具は始めに git の版を確かめ、古ければ `run-error:` で終わる。

## 使い方

**`go run -C` でツールのモジュールに入って実行する。** `go run -C` は作業ディレクトリを道具のディレクトリに変えるので、`-root` には絶対パスを渡す。

**`-root` には、レビュアが指摘の `file` を読んだ作業ツリー (依頼文の「対象」の節に書かれる作業ツリー) のルートか、その中のディレクトリを渡す。** 判定するセッションの作業ディレクトリは、レビューした作業ツリーと違うことがある (別の作業ツリーで判定する場合)。道具は `-root` から上の `.git` を探すだけなので、別の作業ツリーを渡すと、`-worktree` はその作業ツリーの内容を読み、`-rev` のコミットしていない変更の確認もその作業ツリーを見る。

**差し込む値は、単一引用符で囲む。** パスに空白やシェルの特殊文字 (`;`・`$(...)` など) があっても、1 つの引数として渡すため (二重引用符の中では `$(...)` が展開される)。値に単一引用符があるときは `'\''` と書く。

`<プラグインの展開先>` は、review-triage のプラグインのディレクトリで、スキル review-triage を読み込んだときに「Base directory for this skill」として示されるディレクトリ (ファイル `review-triage/skills/review-triage/SKILL.md` のあるディレクトリ) の 2 つ上にあたる。環境によって違い、版ごとに分かれる (見つけ方の例は、triagecheck の README の「[Makefile に置く例](../triagecheck/README.md#makefile-に置く例)」)。

```sh
# 結果のファイルで受け取ったレビュー: レビューした内容はその head のコミット
go run -C '<プラグインの展開先>/tools/lineorigin' . -root '<レビューした作業ツリーのルート>' -base '<全量の起点>' -file '<ファイル>' -lines '12' -rev '<head>'

# 同じセッションのレビューで、コミットしていない変更を含めて見たとき: 作業ツリーの内容
go run -C '<プラグインの展開先>/tools/lineorigin' . -root '<レビューした作業ツリーのルート>' -base '<全量の起点>' -file '<ファイル>' -lines '12-15' -worktree
```

| フラグ | 必須 | 内容 |
| --- | --- | --- |
| `-root` | ✓ | レビュアが指摘の `file` を読んだ作業ツリーのルートか、その中のディレクトリの絶対パス (上の段落)。ルートは道具が求める |
| `-base` | ✓ | 全量の起点のコミット。起点のブランチの先端ではなく、そのブランチと HEAD の merge-base (決め方の正本は [premise-check.md](../../skills/review-triage/references/premise-check.md) の「全量の起点」) なので、ブランチ名ではなくそのコミットの SHA を渡す |
| `-file` | ✓ | 指摘の `file`。リポジトリのルートからの相対パス。パターンの文字 (`[` や `*`) や先頭の `:` も、書いたとおりのファイル名として読む |
| `-lines` | ✓ | 指摘の行。`12`・`12-15` か、それらをコンマで並べた形 (`12,20-23`。連続しない行にまたがる指摘を 1 回で渡す) で、レビューした内容の行番号 |
| `-rev` | `-worktree` とどちらか 1 つ | レビューした内容のコミット |
| `-worktree` | `-rev` とどちらか 1 つ | レビューした内容が作業ツリー (コミットしていない変更を含む) のとき |

出力 (標準出力) の例:

```text
result: not-holds
reason: 対象の行のうち、全量の起点から変わった行がある
line 12: 全量の起点にあったまま (起点の 10 行目)
line 13: 全量の起点より後のコミット 1fe637c0a1b2 が書いた・書き換えた行
```

行を調べる前に結果が決まったとき (起点がレビューした内容のコミットと同じ、など) は、`line` の行を出さない。終了コードは、結果を出したら 0、`input-error:` なら 2、`run-error:` なら 3。ただし `go run` で実行すると、道具の終了コードが 0 でなければ `go run` は 1 を返し、標準エラー出力の最後に `exit status 2` のような行を足す。見分けるときは、終了コードではなく標準エラー出力の最初の行の印を読む。

## どう確かめるか

範囲を起点で区切った `git blame <全量の起点>..<コミット>` (`-worktree` なら `--contents` で作業ツリーの内容を渡す) で、行ごとに、その行を最後に変えたコミットと、そのときのパスと行番号を求める。範囲を起点で区切ると、起点から変わっていない行は起点のコミットが境界 (`boundary`) として報告される。境界が起点で、パスが `-file` と同じなら、その行は起点にあったまま。

`git blame` は、レビューした内容から起点へ、その行の内容が親と同じであるコミットを親へたどり、起点に行き着いた行だけを起点のコミットのものと報告する。マージでは、親のどちらかと同じならそちらへたどる。そのため、一直線の履歴で書き換えて元の内容へ戻した行は、戻したコミットの行として報告する。ブランチで書き換えた行を、マージで相手の親の内容 (起点と同じ) に戻した行は、起点にあったままと報告する (内容は起点と同じなので、誤った `holds` ではない)。

git の振る舞いのうち、結果を変えるものには次のように対処している。どれもテスト (ファイル `review-triage/tools/lineorigin/lineorigin_test.go`) で検証している。

| 振る舞い | 対処しないと | 対処 |
| --- | --- | --- |
| `git blame` は、指定が無くてもファイル全体の改名を追い、改名前のパスで起点まで遡る | このブランチで改名したファイルの行が、起点にあったままと報告される | 起点に同じパスのファイルがあることを確かめ、さらに境界のパスが `-file` と同じことを確かめる (起点にあったファイルを消した後のコミットで、別のファイルをそのパスへ改名した場合も見分ける。1 つのコミットで消して移した場合 (2 つのファイルの入れ替えを含む) は、git が同じパスのファイルの書き換えとして扱うので、起点の内容と差分で対応した行は起点にあったままと報告する。その内容は起点の同じパスにあるので、誤った `holds` ではない) |
| 利用者の環境の `GIT_` で始まる変数が、リポジトリの場所を替える (`GIT_DIR`・`GIT_WORK_TREE`・`GIT_INDEX_FILE` など)、設定を注入する (`GIT_CONFIG_PARAMETERS`・`GIT_CONFIG_COUNT` など)、パスの読み方を替える (`GIT_GLOB_PATHSPECS` など) | `-root` と違うリポジトリや設定を読む。テストでは、テストのコミットやブランチがその変数の指すリポジトリに作られる | git に渡す環境から `GIT_` で始まる変数をすべて取り除き、道具が要るもの (この表の別の行) だけを足す。テストも、始める前に `GIT_` で始まる変数を取り除く。テストがシステムの設定を読ませないための `GIT_CONFIG_NOSYSTEM=1` は、取り除いた後に足す |
| git が、部分クローン (オブジェクトを後から取得するクローン) の欠けたオブジェクトをネットワークから取得し、認証などで利用者に尋ねて待つ | 道具がリポジトリに書き込み、止まったまま終わらない | 環境変数 `GIT_NO_LAZY_FETCH=1` (git 2.44 以降。それより前の git は知らずに取得する) と `GIT_TERMINAL_PROMPT=0` を立てる。git の 1 回の実行に期限 (5 分) を付け、越えたら `run-error:` で終える。期限で止めるのは git のプロセスだけ (下の「読むだけ」の段落) |
| diff の textconv (比べる前にファイルを別の形へ変換する設定) を、`git blame` が当てる | 変換で消える部分だけを書き換えた行が、起点にあったままと報告される | `--no-textconv` を付ける |
| `git replace` の置き換えを、`git blame` が見る | 置き換えた後の履歴で、行を最後に変えたコミットを求めるので、書き換えた行が起点にあったままと報告されうる | 環境変数 `GIT_NO_REPLACE_OBJECTS=1` を立てる |
| `git blame` は、clean フィルタ (属性 `filter`。`git add` のときにファイルを変換するプログラム) の後の内容を見る (コミットの内容はフィルタの後の内容で、`-worktree` で `--contents` に渡した作業ツリーの内容もフィルタで変換してから見る)。レビュアが読む作業ツリーの内容はフィルタの前 | フィルタが行を増やしたり消したりすると、指摘の行番号 (作業ツリーの生の内容の行番号) が別の行に当たり、書き換えた行が起点にあったままと報告される | 指摘のファイルに属性 `filter` が設定されていれば、方式によらず確かめずに `unverifiable` を返す。`git check-attr -a` で調べる (`-a` を付けないと、属性が無いことと、名前が `unspecified` のドライバ (設定 `filter.<名前>.clean` などで登録する、変換のプログラムの名前) を同じ出力で返す)。値が `unset` のときは、`-filter` (フィルタを外す) と名前が `unset` のドライバを区別できないので、そのドライバの設定があれば設定されているとする |
| git は、シンボリックリンクのリンクの文字列を 1 行のブロブとして記録し、`git blame` もそれを見る。レビュアはリンクの先の内容を読む | リンクの先をブランチが書き換えても、リンクの文字列は起点のままなので、書き換えた行が起点にあったままと報告される | レビューした内容のコミット (`-worktree` なら HEAD) で、指摘のファイルがシンボリックリンクなら、方式によらず確かめずに `unverifiable` を返す |
| 設定 `blame.ignoreRevsFile` に挙げたコミットを、`git blame` が無視する | そのコミットが書き換えた行が、起点にあったままと報告される | `--ignore-revs-file ""` で設定を打ち消す |
| 範囲の中のルートのコミット (無関係な履歴のマージ) を、`git blame` が境界として扱う | その履歴から入った行を見分けにくい | `--root` を付け、そのコミットの行として報告させる |
| 起点より前に分かれた履歴をマージすると、行がその分岐点まで遡り、分岐点が境界になる | その行が起点にもあったかは決められない | 境界が起点と違えば、確かめられないとする |
| `-- <ファイル>` の形のパスは、カレントディレクトリを基準に読まれ、pathspec (パターンや先頭の `:` で始まる特別な指定) として解釈される | ルート以外で実行すると、変更があっても無いと判定する。`[a].md` の変更の有無を `a.md` の変更で判定したり、`:c.md` に変更があっても無いと判定したりする | どの git にも `-C <ルート>` を付け、環境変数 `GIT_LITERAL_PATHSPECS=1` を立てる |
| 日本語や `"` を含むパスを、`git blame` が引用符で囲み、バイトを 8 進数で書いて出す | パスの比較が合わない | 引用を解いてから比べる |
| 範囲 `<起点>..<起点>` は空で、コミット済みのどの行も境界として報告される | このブランチにコミットが無いとき、どの行も成り立ってしまう | 起点がレビューした内容のコミットと同じなら、確かめられないとする |

**読むだけで、リポジトリを変えない。** 使う git のコマンド (`rev-parse`・`merge-base`・`cat-file`・`ls-tree`・`ls-files`・`check-attr`・`config` (値を読む `--get-regexp` だけ)・`hash-object` (書き込みの `-w` を付けない)・`blame`) は、どれもインデックスもオブジェクトも書かない。`-rev` のときのコミットしていない変更の有無は、`git diff` ではなく、HEAD・インデックス・作業ツリーの内容のハッシュを比べて確かめる。`git diff` は、インデックスに記録した更新時刻などが作業ツリーのファイルと合わないと、環境変数 `GIT_OPTIONAL_LOCKS=0` を立ててもそれを更新してインデックスを書き換えるため。インデックスに記録した更新時刻などに頼らないので、skip-worktree や assume-unchanged (インデックスの項目に付ける印で、付いたファイルの作業ツリーの変更を git が見ないようにする) が付いたファイルの編集も、変更として扱う。作業ツリーの内容は、git が記録するのと同じ形でハッシュを求める — 通常のファイルは `hash-object --path` (属性によるフィルタを当てる)、シンボリックリンクはリンクの先ではなくリンクの文字列、それ以外の種類 (ディレクトリなど) に置き換わっていれば変更ありとする。

ただし、git 2.30〜2.43 で部分クローンを調べるときは、欠けたオブジェクトを取得してリポジトリに書き込む (上の表の `GIT_NO_LAZY_FETCH` の行)。期限を越えたときに止めるのは git のプロセスだけで、git が起動したプロセス (取得するプロセス) は止めない。それらは道具が終わった後も動き続け、リポジトリに書き込むことがある。

## 限界

- **git の移動の検出 (`-M`・`-C`) は使わない。** 日本語の行などでは検出されないので、使っても移した行を見分けきれない。ファイルの間で移した行と、ファイルの中で並べ替えた行の扱いの正本は、[premise-check.md](../../skills/review-triage/references/premise-check.md) の「(1) 対象の行が変わっていないか」。
- **確かめるのは条件 (1) だけ。** 条件 (2) (全量の起点の内容でも同じ欠陥が成り立つか) は、指摘の主張を読み直す判断なので、道具にしない。
- **次の状態では、エラーの種類や結果の理由が、実際の原因と違う。**

  | 状態 | 道具が返すもの | 実際 |
  | --- | --- | --- |
  | コミットのオブジェクトが欠けている (浅いクローン・壊れたリポジトリ) | `input-error:` (版をコミットに解決できない) | 版はあるが、オブジェクトを読めない |
  | リフログの範囲を越える版 (`HEAD@{99}` など) | git の文言の無い `run-error:` | 版が無い |
  | `-rev` で、指摘のファイルの親のディレクトリが、通常のファイルに置き換わっている | `run-error:` | コミットしていない変更がある |
  | `-worktree` で、指摘のファイルが壊れたシンボリックリンク (リンクの先が無い) | `input-error:` (作業ツリーにファイルが無い) | ファイルはあるが、リンクの先が無い |
  | macOS で、ファイル名の Unicode の正規化の形 (NFC と NFD) が、記録と `-file` で違う | `input-error:` か `not-holds` | 同じファイル |
  | ベアのリポジトリや `.git` の中を `-root` にする | `run-error:` | 渡し方の誤り |
  | `-worktree` で、sparse-checkout から除いたファイルや、作業ツリーから消したファイル | `input-error:` | ファイルが作業ツリーに無い |
  | `-rev` で、sparse-checkout から除いたファイル | `unverifiable` (コミットしていない変更がある) | ファイルが作業ツリーに無いだけ |
  | `-worktree` で指摘のファイルの親のディレクトリを、または (方式によらず) `-root` の親のディレクトリを、権限などでたどれない | `input-error:` (作業ツリーにファイルが無い・`-root` が存在するディレクトリではない) | ファイルやディレクトリはあるが、たどれない。ファイル自体や `-root` 自体を読めないときは、`run-error:` (渡したものを直しても結果は出ない) になる |
- **全量の起点は、渡されたものを使う。** 起点の決め方 (レビュー結果の `base`・周回が決めたブランチ・`origin/HEAD`) の正本は [premise-check.md](../../skills/review-triage/references/premise-check.md) の「全量の起点」で、道具は決めない。
