# リリース Issue の本文と、リリース Issue の計画案

リリース Issue (用語は [terms.md](../../../references/terms.md)) の本文に書く計画の 7 つの項目と、その計画案の書式を決めます。リリース Issue の題名・リリースマイルストーンの名前・リリース Issue を作ったときの本文は、[release-plan-issue.md](../../release-plan/references/release-plan-issue.md) にあります。計画案の先頭の書式と保存先は [draft-plan.md](../../../references/draft-plan.md) にあります。

この文書と、モジュール `issue-practice/scripts/issue_practice/releaseops.py` が、ここで決める形の [SSOT](../../../../CONCEPTS.md#ssot) です。テスト (ファイル `issue-practice/tests/test_releaseops.py`) が、下の計画案の節の表と、手順の表の見出しの行が、モジュールの定数と一致することを確認します。

## 本文の 7 つの項目

本文には計画だけを書き、この順に、レベル 2 の見出しで書きます (計画の R44)。本文の最後の `created-from` の行 (スキル `release-plan` が書いたもの) は残します。

| 項目 | 書くこと |
| --- | --- |
| 参照 | `- リリースマイルストーン: <URL>` の行と、リリースに PR が要るなら `- PR: <URL>` の行 |
| 目的 | このリリースで何ができるようになるか (1〜3 文) |
| 範囲の判断 | 含めた理由と、範囲から外したものとその理由。含める Issue の一覧はマイルストーンが持つので、本文には書かない |
| 順序 | 含める Issue を進める順と、その順にした理由 (表) |
| メモの扱い | メモのコメントごとに、計画に取り込んだか・Issue に切り出したか・次のリリースに回したか |
| リリースの手順 | このリリースで行う手順と省く手順と、その理由 (下の節) |
| 完了の条件 | このリリースに固有の、閉じてよい条件 (下の節) |

- メモは、リリース Issue のコメントに 1 件ずつ書きます (計画の R43)。本文には書きません。メモを書くのに、スキルは使いません。
- 項目「参照」の PR の行は、リリースの PR を作ったときに足します (スキル `release-run`)。PR の本文には、リリース Issue の URL を書きます (計画の R47)。

### 項目「リリースの手順」

リリースの手順の文書の場所は、計画を立てるたびに利用者に質問します (計画の R45)。手順の文書へのリンクは、コミットを指定した URL (`https://github.com/<owner>/<repo>/blob/<40 桁のコミット>/<パス>`) で書きます。手順の文書が後から変わっても、計画を立てた時点の手順を辿れるようにするためです。

```markdown
## リリースの手順

- 手順の文書: https://github.com/o/r/blob/0123456789abcdef0123456789abcdef01234567/docs/release.md

| 手順 | 行う / 省く | 理由 |
| --- | --- | --- |
| タグを打つ | 行う | 版を上げる |
| 告知する | 省く | 内部向けの変更だけ |
```

- 表の見出しの行は `| 手順 | 行う / 省く | 理由 |` です。列「行う / 省く」は `行う` か `省く` のどちらかです。
- 手順の文書が無いプロジェクトでは、`- 手順の文書: なし` と書き、続けてこのリリースの手順を直接書きます。

### 項目「完了の条件」

このリリースに固有の条件だけを、チェックボックスで書きます。固有の条件が無ければ `- なし` と書きます。チェックを入れるときは、[closing-conditions.md](../../../references/closing-conditions.md) と同じく、項目の末尾に `(根拠: <URL>)` を足します。

どのリリースにも共通する次の 4 つの条件は、本文に書きません。スキル `release-close` が、閉じる前に確認します (計画の R48)。

1. 行うと決めたリリースの手順を、最後まで行った
2. リリースに PR が要るなら、その PR がマージされた
3. リリースマイルストーンを設定した Issue が、すべて閉じている
4. 実行の中で見つかった、このリリースでは直さない問題を、Issue に切り出した

## 計画案の書式

計画案は、先頭 ([draft-plan.md](../../../references/draft-plan.md) の形) の後に、次の節をこの順に書きます。節「参照」から最後までが、そのままリリース Issue の本文になります。

| 節 | 書くこと |
| --- | --- |
| 対象 | 項目「リリース Issue」(リリース Issue の URL) |
| 変えたこと | 承認の後に計画を変えるときだけ書く。何を変えたか・理由・決めた人 |
| 参照 | 本文の項目「参照」 |
| 目的 | 本文の項目「目的」 |
| 範囲の判断 | 本文の項目「範囲の判断」 |
| 順序 | 本文の項目「順序」 |
| メモの扱い | 本文の項目「メモの扱い」 |
| リリースの手順 | 本文の項目「リリースの手順」 |
| 完了の条件 | 本文の項目「完了の条件」 |

- 節「元にした Issue」には、リリース Issue の URL と、計画案を作ったときの本文のハッシュ値 (サブコマンド `body show` の出力の `sha256`) を書きます。
- 節「参照」のマイルストーンの URL は、リリース Issue のリリースマイルストーンの URL (サブコマンド `release show` の出力の `milestone.url`) と同じにします。

## 書くことと、やり直し

サブコマンド `release issue-plan` (示す) と `release issue-apply` (実行する) が、計画案を GitHub に書きます。

| 場合 | 書くこと (この順) |
| --- | --- |
| 計画の承認 (題名に `[DRAFT]` がある) | 本文を書く → 記録のコメント `draft-removed` (1 行目は `issue-practice: draft-removed date=<書いた日> draft=<計画案のファイル名>`) を書く → 題名の `[DRAFT]` を外す |
| 承認の後の変更 (題名に `[DRAFT]` が無い) | 本文を書く → 記録のコメント `plan-change` (1 行目は `issue-practice: plan-change draft=<計画案のファイル名>`。本文は節「変えたこと」) を書く |

- 記録のコメント `draft-removed` を書いてから題名の `[DRAFT]` を外します。順序を逆にすると、途中で中断したときに、記録の無いまま `[DRAFT]` が外れた状態 (決めた形の崩れ。計画の R8) が残るためです。
- 承認の後に計画を変えても、`[DRAFT]` は付け直しません (計画の R46)。承認の後の変更は、新しい計画案 (別のファイル) で、節「変えたこと」を書いて行います。承認に使った計画案を直して、もう一度「実行する」で本文を書くことはできません。変更の記録が残らないためです。
- 途中で失敗しても、同じ計画案で「実行する」をやり直せば、済んでいない書き込みだけを行います。
- リリースの実行を始めた後の変更は、スキル `release-run` が、同じサブコマンドで行います。
