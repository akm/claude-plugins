# リリース計画 Issue と、リリース計画の計画案

スキル `release-plan` が作るもの (リリース計画 Issue・リリース Issue・リリースマイルストーン) の名前と本文の形、リリース計画の計画案の書式、計画案を GitHub に書く順とやり直しを決めます。用語は [terms.md](../../../references/terms.md) にあります。リリース計画 Issue の節「リリースの順番」の表の書式と、表から「今のリリース」と「次のリリース」を決める規則は [release-plan-table.md](../../../references/release-plan-table.md)、計画案の先頭の書式と保存先は [draft-plan.md](../../../references/draft-plan.md) にあります。

この文書と、モジュール `issue-practice/scripts/issue_practice/releaseops.py`・`issue-practice/scripts/issue_practice/releaseplan.py` が、ここで決める形の [SSOT](../../../../CONCEPTS.md#ssot) です。テスト (ファイル `issue-practice/tests/test_releaseops.py`) が、下の計画案の節の表・表の見出しの行・名前の形が、モジュールの定数と一致することを確認します。

## 名前

名前には、リリース Issue の番号と主題を入れます。日付は、リリース計画 Issue の題名にだけ入れます (計画の R35・R41)。

| 対象 | 形 | 例 |
| --- | --- | --- |
| リリース計画 Issue の題名 | `📅 リリース計画 YYYYMMDD` | `📅 リリース計画 20261114` |
| リリース Issue の題名 (計画の承認の前) | `[DRAFT] 🔖 リリース R<番号> (主題)` | `[DRAFT] 🔖 リリース R285 (バックアップ一式)` |
| リリース Issue の題名 (計画の承認の後) | `🔖 リリース R<番号> (主題)` | `🔖 リリース R285 (バックアップ一式)` |
| リリースマイルストーン | `R<番号> (主題)` | `R285 (バックアップ一式)` |
| リリースブランチ (リリースに PR が要るとき) | `release/<番号>-<英語の短い名前>` | `release/285-backup` |

- `<番号>` は、リリース Issue の番号です。リリース Issue を作った後に、題名へ番号を書き足し、その後でマイルストーンを作ります。
- `YYYYMMDD` は、リリース計画 Issue を作った日 (ローカル時刻) です。
- リリース対象が複数あるとき (リポジトリにラベル `release-target:<名前>` があるとき) は、リリース計画 Issue の題名の日付の前と、リリース Issue の題名とマイルストーンの名前の番号の後に、リリース対象の名前を入れます (例: `📅 リリース計画 platform 20261114`・`🔖 リリース R285 platform (バックアップ一式)`・`R285 platform (バックアップ一式)`)。リリースブランチの名前には入れません (番号だけで決まるため)。リリース計画 Issue とリリース Issue には、ラベル `release-target:<名前>` を付けます。
- スクリプトは、題名がこの形の Issue を、リリース計画 Issue かリリース Issue として扱います。マイルストーンの無い Issue の見直し (計画の R37) からは、この形の題名の Issue と、ラベル `no-release` の付いた Issue を除きます。

## リリース計画 Issue の本文

本文には、節「リリースの順番」の表 (書式は [release-plan-table.md](../../../references/release-plan-table.md)) だけを書きます。計画を承認したこと・ラベル `current` を付け替えたこと・表を変えたことは、記録のコメントに書きます (計画の R3)。本文の最後の行は、計画案から作ったことを示す `created-from` の行です (形は [record-comments.md](../../../references/record-comments.md))。

```markdown
## リリースの順番

| 順 | リリース Issue | 主題 |
| --- | --- | --- |
| 1 | #285 | バックアップ一式 |
| 2 | #290 | 一覧の絞り込み |

issue-practice: created-from draft=20261114-1530-release-plan-next.md key=plan
```

## リリース Issue を作ったときの本文

スキル `release-plan` は、リリース Issue を次の本文で作ります。計画 (7 つの項目) は、スキル `release-issue-plan` が書きます (形は [release-issue.md](../../release-issue-plan/references/release-issue.md))。本文の最後の `created-from` の行は、`release-issue-plan` で本文を書き換えた後も残します。

```markdown
## 参照

- リリースマイルストーン: https://github.com/<owner>/<repo>/milestone/<番号>

この Issue の計画 (目的・範囲の判断・順序・メモの扱い・リリースの手順・完了の条件) は、スキル release-issue-plan で書く。メモは、この Issue のコメントに 1 件ずつ書く。

issue-practice: created-from draft=<計画案のファイル名> key=<キー>
```

マイルストーンの説明には `リリース Issue: <リリース Issue の URL>` と書きます。リリース Issue 自身には、リリースマイルストーンを設定しません (計画の R42)。

## 計画案の書式

計画案は、先頭 ([draft-plan.md](../../../references/draft-plan.md) の形) の後に、次の 4 つの節をこの順に書きます。

```markdown
# 計画案: 次のリリース

## 元にした Issue

- https://github.com/o/r/issues/30 本文の SHA-256: <64 桁の 16 進数>

## 対象

- 種類: 新しい計画
- リリース対象: なし
- 今の計画: https://github.com/o/r/issues/30

## リリースの順番

| 順 | リリース Issue | 主題 |
| --- | --- | --- |
| 1 | #285 | バックアップ一式 |
| 2 | filter | 一覧の絞り込み |

## Issue の入れ先

| Issue | 入れるリリース |
| --- | --- |
| #301 | filter |
| #302 | 未定 |
| #303 | 入れない |

## 取りやめるリリース

| リリース Issue | 理由 | メモの移し先 |
| --- | --- | --- |
| #288 | 一覧の絞り込みにまとめた | filter |
```

| 節 | 書くこと |
| --- | --- |
| 対象 | 項目「種類」(`新しい計画` か `急ぎのリリースの追加`)・項目「リリース対象」・項目「今の計画」 |
| リリースの順番 | リリースの順番の表。まだ無いリリース Issue はキーで書く |
| Issue の入れ先 | マイルストーンを設定する・外す Issue と、入れるリリースの表。無ければ「なし」 |
| 取りやめるリリース | 今の計画にあって、新しい計画で取りやめるリリース Issue の表。無ければ「なし」 |

### 節「対象」

- **項目「種類」**: `新しい計画` は、新しいリリース計画 Issue を作り、ラベル `current` を付け替えます (計画の R38)。`急ぎのリリースの追加` は、計画に無い急ぎのリリースを、今のリリース計画 Issue の表に足します。新しいリリース計画 Issue は作りません (R40)。
- **項目「リリース対象」**: リリース対象の名前 (ラベル `release-target:<名前>` の `<名前>`)。リリース対象が 1 つなら `なし`。
- **項目「今の計画」**: ラベル `current` の付いたリリース計画 Issue の URL。`新しい計画` では置き換える計画、`急ぎのリリースの追加` では行を足す計画です。最初の計画では `なし` と書きます。URL を書いたときは、同じ Issue を節「元にした Issue」に、計画案を作ったときの本文のハッシュ値と一緒に書きます。`なし` のときは、節「元にした Issue」を `- なし` にします。

### 節「リリースの順番」

[release-plan-table.md](../../../references/release-plan-table.md) の表と同じ形で書きます。違いは、列「リリース Issue」に、まだ無いリリース Issue をキー (英小文字で始まり、英小文字・数字・`-` が続く文字列。`plan` は使えない) で書けることです。キーの行は、「実行する」がリリース Issue とマイルストーンを作り、列「主題」を題名とマイルストーンの名前に使います。

- `急ぎのリリースの追加` では、今の計画の表の行を、順序を変えずにすべて書き、足すリリースをキーの行で書きます。
- `新しい計画` では、今の計画の表の開いているリリース Issue を、この表か節「取りやめるリリース」のどちらかに書きます。

### 節「Issue の入れ先」

表の見出しの行は `| Issue | 入れるリリース |` です。

- 列「Issue」は、開いている Issue の `#<番号>`。リリース計画 Issue とリリース Issue は書けません。
- 列「入れるリリース」は、節「リリースの順番」の表のリリース Issue (`#<番号>` かキー)・`未定` (マイルストーンを外す)・`入れない` (マイルストーンを外し、ラベル `no-release` を付ける) のどれかです。計画を立てるときにマイルストーンの無い Issue を見直して、「リリースに入れない」と回答された Issue は `入れない` にします (計画の R37)。
- 表に書かない Issue のマイルストーンは変えません。

### 節「取りやめるリリース」

表の見出しの行は `| リリース Issue | 理由 | メモの移し先 |` です (計画の R39)。

- 列「リリース Issue」は、今の計画の表にあるリリース Issue の `#<番号>`。節「リリースの順番」の表には書けません。
- 列「理由」は、取りやめた理由です。取りやめたリリース Issue の記録のコメント `plan-change` に書きます。
- 列「メモの移し先」は、メモ (記録ではないコメント) をコピーするリリース Issue (`#<番号>` かキー) か `なし`。
- 取りやめるリリースのマイルストーンに開いた Issue が残っているときは、その Issue を節「Issue の入れ先」に書きます。書いていないと、「示す」が誤りを返します。

## 書く順と、やり直し

`新しい計画` は、次の順に書きます。手順 1〜6 は計画の R38 の手順で、手順 7 は取りやめたリリースの扱い (R39) です。サブコマンド `release plan` (示す) と `release apply` (実行する) の出力の `actions` の `step` は、この番号です (0 はラベルの作成)。

| 手順 | 書くこと |
| --- | --- |
| 1 | 新しいリリース計画 Issue を作り (ラベル `current` は付けない)、記録のコメント `approval` を書く |
| 2 | キーの行のリリース Issue を作り、題名に番号を書き足し、マイルストーンを作り、リリース Issue の本文にマイルストーンの URL を書く。節「Issue の入れ先」のマイルストーンを設定し、新しい計画の本文に表を書く |
| 3 | 新しい計画にラベル `current` を付ける |
| 4 | 今の計画からラベル `current` を外す |
| 5 | 新しい計画に記録のコメント `current-swap` を書く |
| 6 | 今の計画を閉じる (コメントは書かない) |
| 7 | 取りやめたリリース Issue ごとに、メモをメモの移し先にコピーし、記録のコメント `plan-change` を書き、リリース Issue を閉じ (not planned)、マイルストーンを閉じる |

`急ぎのリリースの追加` は、手順 1 で今の計画に記録のコメント `approval` を書き、手順 2 でリリース Issue とマイルストーンを作り、手順 3 で今の計画の本文の表を書き換え、手順 4 で今の計画に記録のコメント `plan-change` を書きます。

「実行する」は、どの手順も GitHub の今の状態を読み、済んでいない書き込みだけを行います。途中で失敗しても、同じ計画案で「実行する」をやり直せば、残りを行います (計画の R7)。作り済みのリリース計画 Issue とリリース Issue は、本文の最後の `created-from` の行で見つけます (計画の KTD5)。途中で中断したときに残る状態と、やり直したときにすることは次のとおりです。

| どこまで完了したか | GitHub に残る状態 | やり直したときにすること |
| --- | --- | --- |
| 1・2 の途中 | 新しい計画にラベル `current` が無い | 作り済みのものを除き、残りを作る |
| 3 まで | ラベル `current` の付いた計画が 2 つある | 4 から続ける |
| 4 まで | 新しい計画に記録のコメント `current-swap` が無い | 5 から続ける |
| 5 まで | ラベル `current` の無い今の計画が開いている | 6 から続ける |
| 6 まで | 取りやめたリリース Issue が開いている | 7 を行う |

「示す」は、書き込む前に、計画案と GitHub の状態が合わないところをすべて見つけて、誤りとして返します (今の計画の本文が計画案を作ったときから変わった・ラベル `current` の付いた計画が今の計画と違う・入れ先の Issue が閉じている・取りやめるリリースのマイルストーンに移し先の無い Issue が残っているなど)。誤りがあれば、「実行する」は何も書き込みません。

## 記録のコメント

1 行目の形は [record-comments.md](../../../references/record-comments.md) にあります。

| 書く Issue | 1 行目 | 本文 |
| --- | --- | --- |
| 新しい計画 (`新しい計画`)・今の計画 (`急ぎのリリースの追加`) | `issue-practice: approval draft=<計画案のファイル名>` | 利用者が計画案を承認したこと |
| 新しい計画 | `issue-practice: current-swap date=<承認した日> old=#<今の計画の番号>` | 承認した日・置き換えた計画・新しく作ったリリース Issue とマイルストーン。最初の計画では `old=` を書かない |
| 今の計画 (`急ぎのリリースの追加`) | `issue-practice: plan-change draft=<計画案のファイル名>` | 表に足したリリース Issue と、決めた人 |
| 取りやめたリリース Issue | `issue-practice: plan-change draft=<計画案のファイル名>` | 新しい計画・理由・メモの移し先・決めた人 |

承認した日は、記録のコメント `approval` を書いた日 (ローカル時刻) です。

メモのコピーは、記録のコメントではない次の形のコメントで、メモの移し先のリリース Issue に書きます。やり直したときは、元のコメントの URL を含むコメントがあれば、コピーしません。

```markdown
取りやめたリリース Issue #288 のメモ (https://github.com/o/r/issues/288#issuecomment-…) を、新しいリリース計画 #310 で、この Issue に移した。

---

<元のコメントの本文>
```
