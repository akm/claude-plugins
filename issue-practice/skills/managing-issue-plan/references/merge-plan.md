# PR マージ計画の書式

管理 Issue の本文に書く PR マージ計画 (どの作業 Issue の PR を・どの順で・どのブランチにマージするかの表と図) の書式を決めます。用語 (管理 Issue・作業 Issue・自己管理 Issue・計画案など) は [terms.md](../../../references/terms.md) にあります。

この文書と、モジュール `issue-practice/scripts/issue_practice/mergeplan.py` が、書式の [SSOT](../../../../CONCEPTS.md#ssot) です。テスト (ファイル `issue-practice/tests/test_mergeplan.py`) が、この文書の項目の名前と表の見出しの行が、モジュールの定数と一致することを確認します。

## ブランチの構成

ブランチの構成は、計画を立てるたびに利用者に質問して決めます (計画の R32・KD8)。

| 構成 | 管理 Issue のブランチ | 作業 Issue の PR のマージ先 | 管理 Issue の PR |
| --- | --- | --- | --- |
| 1 | 作らない | デフォルトのブランチ (`main` など) | 無い |
| 2 | 最初に作る | 管理 Issue のブランチ | 最初に draft で作り、作業 Issue の PR がすべてマージされてから ready にする |
| 3 | 最初に作る | 管理 Issue のブランチ | 作業 Issue の PR がすべてマージされてから作る |

構成 2 の管理 Issue の PR の本文の先頭には、次の注意書きを書きます (R32)。`<管理 Issue の URL>` は、その管理 Issue の URL に置き換えます。

```markdown
> [!NOTE]
> この PR は、作業 Issue の PR をまとめるための PR です。作業 Issue の PR がすべてマージされるまで、draft のままにします。管理 Issue: <管理 Issue の URL>
```

PR の本文には `Closes #<番号>` を書かず、対応する Issue へのリンクだけを書きます (R21。理由は [closing-conditions.md](../../../references/closing-conditions.md) の節「閉じ方」)。

## ブランチの名前

ブランチの名前は、プロジェクトに規約があればそれに従い、無ければ `<種類>/<Issue の番号>-<英語の短い名前>` にします (R33)。`<種類>` は `feat`・`fix`・`docs` など、コミットの種類と同じ語です。管理 Issue のブランチも、作業 Issue のブランチも、同じ規則で名前を付けます。

作業セッションのブランチの名前と作る元は、管理セッションが作業セッションを起動するときに、最初の指示で渡します ([start-instruction.md](../../../references/start-instruction.md))。作る元は、表の列「マージ先」のブランチです。

## 管理 Issue の本文の PR マージ計画

管理 Issue の本文の節「PR マージ計画」の中を、HTML のコメントのマーク `<!-- issue-practice:merge-plan -->` と `<!-- /issue-practice:merge-plan -->` で囲みます (計画の KTD8)。マークの中は、次の順に書きます。

1. 設定の箇条書き
2. 表
3. 図 (mermaid の gitGraph)

```markdown
<!-- issue-practice:merge-plan -->

- ブランチの構成: 1 (作業 Issue の PR を main にマージする)
- PR をマージする人: 利用者

| 順 | 作業 Issue | ブランチ | マージ先 | 先にマージが要る作業 Issue | PR |
| --- | --- | --- | --- | --- | --- |
| 1 | #12 一覧の絞り込み | `feat/12-filter` | main | なし | https://github.com/<owner>/<repo>/pull/15 |
| 2 | #13 一覧の並べ替え | `feat/13-sort` | main | #12 | |

(図は省略。書き方は下の節「図」)

<!-- /issue-practice:merge-plan -->
```

### 設定の箇条書き

設定は、`- <項目>: <値>` の形の箇条書きで書きます。

| 項目 | 値 |
| --- | --- |
| ブランチの構成 | `1`・`2`・`3` のどれか。後ろに空白と括弧で説明を書いてもよい |
| PR をマージする人 | `利用者` か `管理セッション` |
| 管理 Issue のブランチ | 構成 2・3 では、管理 Issue のブランチの名前 (バッククォートで囲んでもよい)。構成 1 では `なし` と書くか、項目を書かない |
| 管理 Issue のブランチのマージ先 | 構成 2・3 では、管理 Issue の PR のマージ先のブランチの名前。構成 1 では `なし` と書くか、項目を書かない |
| 管理 Issue の PR | 構成 2・3 では、管理 Issue の PR の URL。作るまでは `なし`。構成 1 では `なし` と書くか、項目を書かない |

上の表に無い項目 (計画の文書へのリンクなど) も書けます。検査のスクリプトは読まずに、そのまま残します。

### 表

表の見出しの行は、次のとおりに書きます。

```markdown
| 順 | 作業 Issue | ブランチ | マージ先 | 先にマージが要る作業 Issue | PR |
```

| 列 | 書き方 |
| --- | --- |
| 順 | 1 から始まる連番。PR をマージする順 |
| 作業 Issue | `#<番号>` と、空白の後に短い説明 (書かなくてもよい) |
| ブランチ | 作業 Issue のブランチの名前。バッククォートで囲んでもよい |
| マージ先 | 作業 Issue の PR のマージ先のブランチの名前。構成 1 ではどの行も同じブランチ (デフォルトのブランチ)、構成 2・3 ではどの行も管理 Issue のブランチ |
| 先にマージが要る作業 Issue | この行より前の行の作業 Issue を `#<番号>` で、`, ` で区切って並べる。無ければ `なし` |
| PR | 作業 Issue の PR の URL (`#<番号>` でもよい)。作るまでは空 |

- 表の行は、作業 Issue 1 つにつき 1 行です (作業 Issue と PR は 1 対 1。R31)。同じ作業 Issue・同じブランチを 2 回書けません。
- マージしたかどうかは、表に書きません (R34)。検査のスクリプトが GitHub で確認します。
- PR がマージされずに閉じられて作り直されたら、列「PR」の URL を書き換えます (R34)。

### 自己管理 Issue

自己管理 Issue (PR 1 つで済む Issue) の本文にも、節「PR マージ計画」をマークで囲んで書きます。ブランチの構成は 1 にし、表の行は 1 つだけで、列「作業 Issue」にはその Issue 自身を書きます。作業 Issue は作りません (R26)。

### 図

図は、表から検査のスクリプトが作ります (計画の KTD8)。手で書かず、表を書き換えたら作り直します。サブコマンド `merge-plan show` は、本文の図が表から作った図と同じかを確認します。

図の作り方:

- 最初に、デフォルトのブランチ (構成 1 では列「マージ先」のブランチ、構成 2・3 では「管理 Issue のブランチのマージ先」) にコミットを 1 つ置きます。コミットの ID は、ブランチの名前です。
- 構成 2・3 では、そこから管理 Issue のブランチを作ります。構成 2 では、管理 Issue のブランチに `draft PR` のコミットを 1 つ置きます (draft の PR を作るため)。
- 作業 Issue のブランチは、先にマージが要る作業 Issue がすべてマージされた時点で、マージ先のブランチから作ります。コミットの ID は、作業 Issue の番号です。先にマージが要る作業 Issue が無い行のブランチは、最初に作ります。
- 作業 Issue のブランチは、表の順にマージ先のブランチにマージします。
- 構成 2・3 では、最後に管理 Issue のブランチをデフォルトのブランチにマージします。
