# クローズ条件の書き方

Issue を閉じてよい条件は、Issue の本文の節「クローズ条件」に書きます。この文書は、節の形・書く時期・チェックの入れ方・閉じ方を決めます。用語 (管理 Issue・作業 Issue など) は [terms.md](terms.md) にあります。

この文書と、モジュール `issue-practice/scripts/issue_practice/checkboxes.py` が、チェックボックスの書式の [SSOT](../../CONCEPTS.md#ssot) です。

## 節の形

節「クローズ条件」の下を、「期待する状態」と「確認するポイント」の 2 つに分け、どちらも GitHub のタスクリスト (チェックボックス) で書きます (計画の R16)。

- **期待する状態**: 作業の結果として成り立っている状態を書きます。「〜を書く」「〜を上げる」のような作業の形では書きません。項目は、次のどれかです。
  - 作成するものの名前と、それがある状態
  - 追加・変更する機能の名前と、その振る舞い
  - 削除する機能の名前と、それが無い状態
  - リファクタリングの結果の状態
- **確認するポイント**: 項目ごとに、確認の方法と記録先を、項目の下の箇条書きで添えます。確認の方法は、自動テスト (何を確認するテストか) か、手で確認するかです。手で確認するときは、誰が・どこで・どの手順で確認するかを書きます。

例:

```markdown
## クローズ条件

期待する状態:

- [ ] スキル wording-guard の文書 (ファイル `wording-guard/skills/wording-guard/SKILL.md`) に、手順 X がある
- [ ] コマンド `wording_lint.py check` が、用語ファイルの避ける語を検出する
- [ ] オプション `--legacy` が無い
- [ ] 用語ファイルの読み込みが、モジュール `terms` 1 つにまとまっている
- [ ] プラグイン wording-guard のバージョンが、この変更を含む版に上がっている

確認するポイント:

- [ ] 用語ファイルの避ける語を検出する
    - 確認の方法: 自動テスト (`wording-guard/tests/test_terms.py` で、検出する例と検出しない例を確認する)
    - 記録先: PR の CI の結果
- [ ] スキルを対話で実行すると、言い換えの候補が示される
    - 確認の方法: 手で確認する (利用者が、Claude のデスクトップアプリで、手順 Y で実行する)
    - 記録先: この Issue のコメント
```

「期待する状態」と「確認するポイント」は、`期待する状態:` の行で書いても、`### 期待する状態` の見出しで書いてもかまいません。検査のスクリプトは、どちらも同じに読みます。

## 節の場所

検査のスクリプトは、本文の中のクローズ条件の範囲を、次の規則で決めます。

- **管理 Issue**: 節「クローズ条件」の中を、HTML のコメントのマーク `<!-- issue-practice:closing-conditions -->` と `<!-- /issue-practice:closing-conditions -->` で囲みます。管理 Issue の本文には PR マージ計画もあり、マーク `<!-- issue-practice:merge-plan -->` と `<!-- /issue-practice:merge-plan -->` で囲みます (計画の KTD8)。スクリプトは、マークで囲んだ範囲だけを読み書きします。
- **作業 Issue と自己管理 Issue**: マークを書かず、見出し `## クローズ条件` の節 (次のレベル 2 以上の見出しの手前まで) を範囲にします。

本文にマーク `closing-conditions` が 1 つでもあれば、スクリプトはマークで囲んだ範囲を使い、マークが閉じていないなどの誤りは誤りとして返します。マークが無ければ、見出しの節を使います。範囲の名前は、上の 2 つ (`closing-conditions`・`merge-plan`) だけです。

マークと見出しは、その行にマークや見出しだけがある行として書きます。コードブロックの中に書いたものは数えません。

## 書く時期

- Issue を作るときに、分かる範囲で書きます。決まっていない部分は、決まっていないと書きます (R17)。
- 着手する前に、管理セッションが条件を補い、利用者の承認を得てから作業を始めます。作業 Issue なら、作業セッションを起動する前に行います。承認したことは、記録のコメント (形は [record-comments.md](record-comments.md)) に書きます。作業を始めた後に条件を書くと、作ったものに合わせて書いてしまい、確認すべき点が抜けるためです。

## 管理 Issue の条件

- 管理 Issue に、節「すべての作業 Issue に共通するクローズ条件」を書きます。管理セッションは、作業 Issue を作るときにその項目を作業 Issue にコピーし、固有の条件と並べます。作業 Issue の見出しには、コピー元の管理 Issue へのリンクを書きます (R19)。チェックボックスは、それが書かれた Issue の中でしか入れられないためです。
- 共通の条件を変えたら、開いている作業 Issue にも反映します。
- どの管理 Issue にも、次の 2 つを管理 Issue 自身のクローズ条件にします (R20)。
  1. 作業 Issue がすべて閉じている
  2. ブランチの構成が 2 か 3 なら、管理 Issue の PR がマージされた

### 見出し

管理 Issue のマーク `closing-conditions` の中と、作業 Issue の節「クローズ条件」の中は、次のレベル 3 の見出しで分けます。検査のスクリプトは、この見出しで、管理 Issue 自身の項目と共通の項目を分けます。

| Issue | 見出し | 中身 |
| --- | --- | --- |
| 管理 Issue | `### 管理 Issue (#<番号>) 自身のクローズ条件` | 管理 Issue 自身の条件。上の 2 つを含める |
| 管理 Issue | `### すべての作業 Issue に共通するクローズ条件` | 作業 Issue にコピーする条件。管理 Issue の中ではチェックを入れず、管理 Issue を閉じる前の検査でも数えない |
| 作業 Issue | `### 共通 (#<管理 Issue の番号> の「すべての作業 Issue に共通するクローズ条件」からコピー)` | 管理 Issue の共通の条件のコピー。管理 Issue が別のリポジトリにあるときは、`#<番号>` の代わりに `<owner>/<repo>#<番号>` と書く |
| 作業 Issue | `### この作業 Issue に固有の条件` | 作業 Issue に固有の条件 |

例 (作業 Issue):

```markdown
## クローズ条件

### 共通 (#239 の「すべての作業 Issue に共通するクローズ条件」からコピー)

期待する状態:

- [ ] 単位の機能を確認する自動テストがあり、CI で成功する

### この作業 Issue に固有の条件

期待する状態:

- [ ] PR マージ計画の図を、表からスクリプトが作る
```

コピーが古いかは、項目の文 (末尾の根拠のリンクを除いたもの) と、「期待する状態」か「確認するポイント」かを、上から順に比べて判定します。項目の下の箇条書き (確認の方法と記録先) は比べません。記録先は、作業 Issue に合わせて書き換えてよいためです。サブコマンド `checkboxes common` が、開いている作業 Issue のうちコピーが古いものを一覧にします。

## チェックの入れ方

- チェックを入れるときは、その項目の末尾に、根拠へのリンクを `(根拠: <URL>)` の形で足します (R18・KTD9)。根拠は、テストを実行した PR・確認を記録したコメントなどです。
- 項目を別の Issue に切り出したときは、その Issue へのリンクを `(切り出し: <URL>)` の形で足して、チェックを入れます (R15)。この Issue のクローズ条件としては、満たしたことを表します。
- チェックを入れるのは、確認したセッション (作業セッションか管理セッション) か、利用者です。
- 本文を書き換える前に本文を再度読み込み、読んだときから変わっていないことを確認します (照合の方法は [draft-plan.md](draft-plan.md) の節「本文の照合」)。

例:

```markdown
- [x] コマンド `wording_lint.py check` が、用語ファイルの避ける語を検出する (根拠: https://github.com/<owner>/<repo>/pull/12)
- [x] スキルを対話で実行すると、言い換えの候補が示される (切り出し: https://github.com/<owner>/<repo>/issues/34)
```

検査のスクリプトのサブコマンド `checkboxes list` は、項目を次の 4 つに分けます。

| 状態 | 項目の形 | 満たすか |
| --- | --- | --- |
| `unchecked` | チェックが入っていない | 満たさない |
| `checked` | チェックが入っていて、末尾に `(根拠: <URL>)` がある | 満たす |
| `checked_without_evidence` | チェックが入っているのに、末尾に根拠のリンクが無い | 満たさない |
| `carved_out` | チェックが入っていて、末尾に `(切り出し: <URL>)` がある | 満たす |

URL は `https://` で始まるものだけを根拠のリンクとして読みます。

## 閉じ方

- PR の本文には `Closes #<番号>` を書かず、対応する Issue へのリンクだけを書きます (R21)。`Closes` はデフォルトのブランチへのマージでしか Issue を閉じないので、ブランチの構成 2 と 3 では作業 Issue が閉じません。また、マージの後に確認するポイントが残っていても、閉じてしまいます。
- 作業 Issue は、PR がマージされていることと、すべてのチェックと根拠のリンクを、管理セッションが確認してから閉じます。チェックが入っていない項目が残っているうちは閉じません。作業 Issue を閉じるときは、利用者の承認を得ません (R22)。チェックを入れるセッションと閉じるセッションを別にして、確認の漏れに気づけるようにするためです。
- 管理 Issue と自己管理 Issue は、確認の結果を利用者に示し、承認を得てから閉じます (R23)。
- Issue を閉じたら、閉じた Issue を依存先とする Issue (GitHub の blocking の一覧にある、開いている Issue) に、依存先が片付いたことを記録のコメント `dependency-resolved` で書き、その Issue の節「依存先」から閉じた Issue の項目を消します。項目が無くなったら、節ごと消します (R50)。消す項目は、閉じた Issue の URL か参照 (`#<番号>`・`<owner>/<repo>#<番号>`) を含む箇条書きの項目と、その下の字下げした行です。サブコマンド `dependents plan` が行う書き込みを示し、`dependents resolve` が書き込みます。

### 閉じる前の検査

サブコマンド `close check` が、閉じる前に次のことを検査します。どれか 1 つでも満たさなければ、終了コード 3 と、満たさない項目の一覧を返します (計画の KTD10)。`gh` が失敗して検査できなかったときは、終了コード 4 を返します。

| 種類 (`--role`) | 検査すること |
| --- | --- |
| 作業 Issue (`working`) | 節「クローズ条件」のどの項目も、チェックと根拠のリンクがあるか、切り出し済み。管理 Issue の PR マージ計画の表のこの作業 Issue の行に PR があり、その PR が列「マージ先」のブランチにマージされている。共通の条件のコピーが、管理 Issue の今の共通の条件と同じ。マイルストーンが管理 Issue と同じ (R49) |
| 管理 Issue (`managing`) | マーク `closing-conditions` の中の、節「すべての作業 Issue に共通するクローズ条件」を除いたどの項目も、チェックと根拠のリンクがあるか、切り出し済み。PR マージ計画の表のどの作業 Issue も閉じている。ブランチの構成 2・3 では、管理 Issue の PR が「管理 Issue のブランチのマージ先」にマージされている (R20) |
| 自己管理 Issue (`self-managing`) | 節「クローズ条件」のどの項目も、チェックと根拠のリンクがあるか、切り出し済み。PR マージ計画の表の 1 つの行がこの Issue 自身で、その PR が列「マージ先」のブランチにマージされている |

検査の結果の JSON には、根拠の URL (チェックの根拠と PR) と、閉じる Issue を依存先とする開いた Issue の一覧も入れます。スキルは、根拠の URL を閉じるときの記録のコメント `close-check` に書きます。

## 作業の途中で条件を変えるとき

- 作業セッションが変えたいと気づいたら、管理セッションに報告します。管理セッションも変更の内容を確認します (R24)。
- 管理セッションは、必要なら、その変更を他の作業 Issue に反映するか、新しい作業 Issue を作るかを、利用者に質問します。
- 利用者の承認を得てから、管理セッションが本文を書き換え、何を変えたか・理由・決めた人を記録のコメントに書きます。
- 外した項目は本文から消します。外したことと理由は、記録のコメントに残ります。
