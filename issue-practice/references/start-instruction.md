# 最初の指示の形

最初の指示 (用語は [terms.md](terms.md)) は、管理セッションが作業セッションを起動するときに渡す文です。受け持つ作業 Issue を、作業セッションに渡す手段です (計画の R27・KTD6)。自己管理 Issue では作業セッションを起動しないので、最初の指示はありません。

## 書くこと

最初の指示には、次のことを書きます。

| 項目 | 書き方 |
| --- | --- |
| 作業 Issue | URL と題名 |
| 管理 Issue | URL |
| 報告先の管理セッション | 管理セッションの名前と ID |
| ブランチ | ブランチの名前と、作る元 (`origin/main` など)。名前は、プロジェクトに規約があればそれに従い、無ければ `<種類>/<Issue の番号>-<英語の短い名前>` |
| PR のマージ先 | ブランチの名前 (PR マージ計画の表の列「マージ先」) |
| PR をマージする人 | 利用者か管理セッション (管理 Issue の計画に書いたもの) |
| 使うスキル | スキル `issue-practice:working-issue` を使うこと |

セッションの名前は `<リポジトリ名>#<番号> 作業: <短い説明>` にします (管理セッションは「作業」を「管理」にする。R28)。セッション間のメッセージは、この名前に宛てます。

## テンプレート

```text
あなたは作業 Issue <作業 Issue の URL> の作業セッションです。スキル issue-practice:working-issue を使って進めてください。

- 作業 Issue: <作業 Issue の URL> (<題名>)
- 管理 Issue: <管理 Issue の URL>
- 報告先の管理セッション: <管理セッションの名前> (ID: <管理セッションの ID>)
- ブランチ: <ブランチの名前> を <作る元> から作る
- PR のマージ先: <マージ先のブランチ>
- PR をマージする人: <利用者 か 管理セッション>

報告 (PR を作った・チェックを入れた・分けたい・条件を変えたい・切り出したい・中断する) は、作業 Issue に記録のコメントとして書き、そのコメントの URL を報告先の管理セッションにメッセージで知らせてください。
```

## 起動の後の記録

管理セッションは、作業セッションを起動した直後に、作業 Issue に記録のコメント `session` を書きます (形は [record-comments.md](record-comments.md))。1 行目には役割 (`role=working`)・セッションの ID・ブランチを書き、本文に作業セッションの名前と報告先の管理セッションを書きます。

```text
issue-practice: session role=working session=<作業セッションの ID> branch=<ブランチ>

この作業 Issue の作業セッションを起動した。

- 作業セッションの名前: <作業セッションの名前>
- 報告先の管理セッション: <管理セッションの名前> (<管理セッションの ID>)
```

管理セッションも、受け持つ管理 Issue に記録のコメント `session` を書きます (R28)。自己管理 Issue を進めるセッションは、`role=self-managing` で自己管理 Issue に書きます。

```text
issue-practice: session role=managing session=<管理セッションの ID>

この管理 Issue の管理セッションを受け持った。

- 管理セッションの名前: <管理セッションの名前>
```

本文の 1 行目の箇条書きの `- 作業セッションの名前: ` と `- 管理セッションの名前: ` は、検査のスクリプトがセッションの名前として読む行です。この形のまま書きます。自己管理 Issue を進めるセッションは、`- 管理セッションの名前: ` の行で書きます。

作業セッションの会話が要約されて最初の指示が失われたときや、最初の指示が見当たらないときは、作業セッションはこの記録のコメントを再度読み込みます。検査のスクリプトのサブコマンド `records list --issue <作業 Issue> --kind session` で読めます。

## セッションの交代

セッションが替わったら、新しいセッションは、受け持つ Issue に記録のコメント `session` を書き、1 行目の `previous=` に前のセッションの ID を、本文に前のセッションの名前と替えた理由を書き足します (R29)。

```text
issue-practice: session role=managing session=<新しい ID> previous=<前の ID>

この管理 Issue の管理セッションを交代した。

- 管理セッションの名前: <名前>
- 前の管理セッション: <前の名前> (<前の ID>)
- 替えた理由: <理由>
```

セッション間のメッセージは、セッションの名前に宛てます (計画の KTD17)。名前は Issue の番号から決まるので、交代すると古いセッションと新しいセッションが同じ名前になり、メッセージが古いセッションに届くことがあります。そのため、次の順に進めます。

1. 古いセッションをアーカイブする (アーカイブしたセッションは、メッセージの宛先の一覧から消える)。アーカイブできないときは、利用者に質問する
2. 新しいセッションに、規則どおりの名前を付ける
3. 記録のコメント `session` (`previous=` 付き) を書く
4. 管理セッションが替わったときは、検査のスクリプトのサブコマンド `sessions active` で動いている作業セッションを集め、それぞれに、新しい管理セッションの名前と ID をメッセージで送る

作業 Issue を閉じずに作業セッションを終えるときは、理由を書いた記録のコメント `abandon` を作業 Issue に書きます。`sessions active` は、`abandon` の記録がある作業セッションと、閉じた作業 Issue を、動いている作業セッションから除きます。

## 報告

作業セッションは、報告を作業 Issue の記録のコメント `report` に書き、セッション間のメッセージでは、そのコメントの URL を知らせます (R30・KTD16)。管理セッションが交代しても、報告が Issue に残るためです。同じ本文のメッセージは受け手に捨てられることがありますが、URL が毎回違うので、メッセージの本文も毎回変わります。
