# 6 つのシナリオ

プラグイン issue-practice のスキルを、架空のプロジェクトで最初から順に使う例です。スキルを呼び出すセッションと GitHub に書くものの全体は [workflow.md](workflow.md) に、用語は [terms.md](terms.md) にあります。

架空のプロジェクトは、家計簿の Web アプリ kakeibo です。デフォルトのブランチは `main` で、`tmp/` は `.gitignore` で git に無視されています (計画案のファイルを git に入れないため)。リリースの手順は、プロジェクトの文書 `RELEASE.md` にあります (リリースの PR で `CHANGELOG.md` を更新してマージし、タグを付けて、告知する)。

このシナリオは、確認用のリポジトリ [akm/issue-practice-sandbox2](https://github.com/akm/issue-practice-sandbox2) で、この順に実際に実行しました ([#270](https://github.com/akm/claude-plugins/issues/270))。Issue と PR の番号は、そのときの番号です。

| シナリオ | 使うスキルの順 |
| --- | --- |
| 1. Issue が 1 つも無い状態で、最初のリリース計画を立てる | `new-issue` → `release-plan` |
| 2. 立てたリリース計画に基づいて、実装を進める | `release-issue-plan` → `managing-issue-plan` → `managing-issue-run` → `working-issue` → `managing-issue-close`。自己管理 Issue は `managing-issue-plan` → `working-issue` → `managing-issue-close` |
| 3. 設計を見直すバグが分かり、リリース計画を見直す | `working-issue` → `managing-issue-run` (`new-issue` を使う) → `release-plan` → `release-issue-plan` (実行を始めた後なら `release-run`) |
| 4. 最初のリリースを実施する | `managing-issue-close` → `release-run` とプロジェクトのリリースの手順 → `release-close` |
| 5. 要望の Issue が溜まってきたので、リリース計画に反映する | `new-issue` か GitHub での直接の作成 → `release-plan` |
| 6. 2 回目のリリースを実施する | `release-issue-plan` → シナリオ 2 と同じ → シナリオ 4 と同じ |

各シナリオの「依頼の例」は、利用者がセッションに書く文の例です。スキルは、書き込む前に計画案のファイルか会話で書き込みを示し、利用者の承認を得ます。下の手順では、承認を得る段階を省かずに書きます。

## 1. Issue が 1 つも無い状態で、最初のリリース計画を立てる

状況: リポジトリには、コードと文書だけがあり、Issue もマイルストーンもありません。利用者は、最初のリリースで「支出の記録」と「月ごとの集計」を出したいと考えています。

1. **要望の Issue を作る** (スキル `new-issue`。依頼の例: 「この 3 つの要望を Issue にして」)
   - 何件かを作るので、計画案のファイル (`tmp/issue-practice/<日時>-new-issue-<対象>.md`) に、作る Issue の題名・本文・マイルストーン・ラベルを書きます。
   - リリース計画 Issue がまだ無いので、入れるリリースは未定だけを選べます。マイルストーンは設定しません。
   - 利用者が計画案を読んで承認すると、Issue を作り、Issue ごとに記録のコメント `approval` を書きます。#1「支出を記録したい」・#2「月ごとに集計したい」・#3「CSV に書き出したい」ができます。
2. **最初のリリース計画を立てる** (スキル `release-plan`。依頼の例: 「リリースの計画を立てて」)
   - 検査のスクリプトのサブコマンド `release review` で、マイルストーンの無い Issue (#1〜#3) を 1 件ずつ示し、どのリリースに入れるかを利用者に質問します。#1・#2 は最初のリリース、#3 は 2 回目のリリースに入れると決めます。
   - 計画案 (種類 `新しい計画`、項目「今の計画」は `なし`) に、リリースの順番 (まだ無いリリース Issue はキーで書く) と Issue の入れ先を書きます。
   - 承認を得ると、次のものを書きます。ラベル `current` がリポジトリに無ければ、作ってよいかの承認も得て作ります。
     - リリース計画 Issue #4「📅 リリース計画 20261115」と、記録のコメント `approval`
     - リリース Issue #5「[DRAFT] 🔖 リリース R5 (支出の記録と集計)」と #6「[DRAFT] 🔖 リリース R6 (書き出し)」
     - マイルストーン「R5 (支出の記録と集計)」と「R6 (書き出し)」。#1・#2 に R5 を、#3 に R6 を設定する
     - #4 にラベル `current` を付け、記録のコメント `current-swap` を書く (古い計画が無いので、外す計画と閉じる計画は無い)

完了した後の状態: ラベル `current` の付いたリリース計画 #4 の表が、R5 → R6 の順を持ちます。どのリリース Issue も題名に `[DRAFT]` があるので、「今のリリース」はまだ無く、「次のリリース」が R5 です。R5 の計画を承認すると (シナリオ 2 の手順 1)、R5 が「今のリリース」になります。

## 2. 立てたリリース計画に基づいて、実装を進める

状況: シナリオ 1 の後です。#1「支出を記録したい」は、データの保存・入力の画面・一覧の画面の 3 つの PR に分けたい大きさです。#2「月ごとに集計したい」は PR 1 つで済みます。

1. **リリース Issue の計画を承認する** (スキル `release-issue-plan`。依頼の例: 「R5 の計画を立てて」)
   - リリース Issue #5 のメモ (利用者がコメントに書いたもの) を 1 件ずつ示し、計画に取り込むか・Issue に切り出すか・次のリリースに回すかを質問します。
   - リリースの手順の文書の場所を質問し、手順ごとに行うか省くかと理由を、利用者と決めます。手順の文書へのリンクは、コミットを指定した URL で書きます。
   - 計画案に、本文の 7 つの項目 (参照・目的・範囲の判断・順序・メモの扱い・リリースの手順・完了の条件) を書きます。承認を得ると、#5 の本文に計画を書き、記録のコメント `draft-removed` を書いて、題名の `[DRAFT]` を外します。
2. **大きい Issue を作業 Issue に分ける** (スキル `managing-issue-plan`。依頼の例: 「#1 を作業 Issue に分けて計画して」。このセッションが #1 の管理セッションになる)
   - ブランチの構成 (1・2・3) と、PR をマージする人 (利用者か管理セッション) を質問します。ここでは、構成 1 (作業 Issue の PR を `main` にマージする) と、利用者がマージすることを選びます。
   - 計画案に、#1 自身のクローズ条件・すべての作業 Issue に共通するクローズ条件・PR マージ計画の表・作る作業 Issue を書きます。表では、まだ無い作業 Issue をキーで、ブランチの番号を `<番号>` で書きます。
   - 承認を得ると、作業 Issue #7「支出のデータを保存する形を決めたい」・#8「支出を入力する画面がほしい」・#9「記録した支出を一覧で見たい」を #1 の sub-issue として作り (マイルストーンは #1 と同じ R5)、#1 の本文にクローズ条件と PR マージ計画 (表と、表から作った図) を書いて、#1 と作業 Issue に記録のコメント `approval` を書きます。表では、#8 と #9 の「先にマージが要る作業 Issue」を #7 にしました。
3. **作業セッションを起動する** (スキル `managing-issue-run`。依頼の例: 「#1 の作業セッションを起動して」)
   - 管理セッションは、Claude Code のデスクトップアプリのセッションです。自分の名前を `<リポジトリ名>#1 管理: 支出の記録` にし、#1 に記録のコメント `session` (`role=managing`) を書きます。
   - 作業セッションの無い作業 Issue のうち、表の「先にマージが要る作業 Issue」がすべて閉じているものを候補として示し、どれを起動するかを質問します。最初は #7 だけが候補です。#8 と #9 は、#7 が閉じてから候補になります。
   - 最初の指示 (作業 Issue・管理 Issue・報告先の管理セッション・ブランチ・PR のマージ先・PR をマージする人) を渡して作業セッション `<リポジトリ名>#7 作業: データの保存` を起動し、#7 に記録のコメント `session` (`role=working`) を書きます。
4. **作業 Issue を進める** (スキル `working-issue`。作業セッションが、最初の指示から呼び出す)
   - ブランチ `feat/7-storage` を作って作業し、PR #10 を作ります。PR の本文には #7 へのリンクを書き、`Closes #7` は書きません。
   - #7 に記録のコメント `report` (`type=pr`) を書き、そのコメントの URL を管理セッションにメッセージで知らせます。管理セッションは、記録のコメントを読み、#1 の表の列「PR」に PR の URL を書きます (サブコマンド `merge-plan set-pr`)。
   - クローズ条件の項目ごとに、根拠の URL (CI の実行・確認を記録したコメントなど) を添えてチェックを入れ、`report` (`type=check`) で知らせます。
5. **確認して閉じる** (スキル `managing-issue-close`。依頼の例: 「#7 の PR をマージした」)
   - 利用者が PR をマージしたことを伝えると、管理セッションは検査のスクリプト (サブコマンド `close check`) で、PR のマージ・チェックと根拠のリンク・共通の条件のコピーを確認し、利用者の承認を得ずに #7 を閉じて、記録のコメント `close-check` を書きます。
   - #8 (PR #14)・#9 (PR #15) も、手順 3〜5 で進めます。#8 の途中のことは、シナリオ 3 にあります。
   - 作業 Issue がすべて閉じたら、#1 自身の条件にチェックを入れ、確認の結果を利用者に示して、承認を得てから #1 を閉じます。
6. **PR 1 つで済む Issue を進める** (#2「月ごとに集計したい」)
   - スキル `managing-issue-plan` で、#2 を自己管理 Issue として計画します (ブランチの構成は 1)。作業 Issue は作らず、#2 の本文に、クローズ条件と 1 行だけの PR マージ計画を書きます。
   - 同じセッションで、スキル `working-issue` を使って進めます。最初の指示は無く、#2 に記録のコメント `session` (`role=self-managing`) を書きます。報告は送らず、表の列「PR」もこのセッションが書きます (PR #16)。
   - PR がマージされたら、スキル `managing-issue-close` で確認し、利用者の承認を得てから #2 を閉じます。

## 3. 設計を見直すバグが分かり、リリース計画を見直す

状況: シナリオ 2 の途中です。作業 Issue #8 (入力の画面) の作業セッションが、税込の金額を入力すると 1 円未満の端数が出ることに気づきました。#7 で決めたデータの形は金額を整数の円で持つので、直すにはデータの形 (金額の持ち方と丸め方) を見直す必要があり、#8 の PR では扱えません。

1. **切り出したいと報告する** (スキル `working-issue`。作業セッション)
   - #8 に記録のコメント `report` (`type=carve-out`) を書き、何を後で行いたいか・理由・判断してほしいことを本文に書いて、管理セッションに知らせます。判断があるまで、その作業を進めません。
2. **切り出す** (スキル `managing-issue-run`。管理セッションが、報告のメッセージを受けて呼び出す)
   - 報告の記録のコメントを読み、切り出すか・#1 の sub-issue にするか (#1 のゴールに必要か)・入れるリリースを、利用者に質問します。ここでは、R5 では金額を整数の円だけ受け付けることにして、丸め方の見直しは #1 のゴールに含めず (sub-issue にしない)、R5 と R6 の間に足すリリースで行うと決めます。
   - 利用者の回答を渡して、スキル `new-issue` で切り出しの Issue #11「税込の金額の端数で、集計の合計が実際の支払いと合わない」を作ります。入れるリリースは、サブコマンド `release current --carve-out` が示す今のリリース・次のリリース・未定から選びます。足すリリースはまだ無いので、いったん未定 (マイルストーン無し) にします。
   - 作業セッションは、整数の円だけを受け付けることを #8 のクローズ条件に足したいと、`report` (`type=condition-change`) で知らせます。管理セッションは、利用者の承認を得てから #8 の本文の固有の条件を書き換え (書く直前に、本文が読んだときから変わっていないことを確認する)、記録のコメント `plan-change` に何を変えたか・理由・決めた人を書きます。
   - 依存関係が変わる (ある作業 Issue が、切り出した Issue を依存先とする) ときは、スキル `managing-issue-plan` で PR マージ計画も書き換えます。ここでは #8 は #11 を依存先としないので、書き換えません。
3. **リリース計画を見直す** (スキル `release-plan`。依頼の例: 「#11 を入れたリリースを R5 と R6 の間に足して」)
   - サブコマンド `release review` がマイルストーンの無い #11 を示します。計画案 (種類 `新しい計画`、項目「今の計画」は #4) に、新しいリリース (キーで書く) を R5 と R6 の間に入れた順番と、#11 の入れ先を書きます。
   - 承認を得ると、新しいリリース計画 Issue #12 と、リリース Issue #13・マイルストーン「R13 (金額の丸め)」を作り、#11 に設定します。ラベル `current` を #4 から #12 に付け替えて、記録のコメント `current-swap` を書き、#4 を閉じます。
   - 計画に無い急ぎのリリースを足すだけで、順番を変えないときは、計画案の種類を `急ぎのリリースの追加` にします。このときは新しいリリース計画 Issue を作らず、今の計画の表を書き換えます。
4. **承認済みのリリース Issue の計画を変える**
   - R5 の範囲の判断が変わった (丸め方は R13 で扱い、R5 では整数の円だけを受け付ける) ので、R5 の計画を変えます。実行を始める前なので、スキル `release-issue-plan` で、新しい計画案に節「変えたこと」(何を変えたか・理由・決めた人) を書き、承認を得て本文を書き換え、記録のコメント `plan-change` を書きます。題名に `[DRAFT]` は付け直しません。
   - 実行を始めた後 (記録のコメント `release-start` がある) なら、同じことをスキル `release-run` で行います (シナリオ 4 の手順 3)。

## 4. 最初のリリースを実施する

状況: R5 に含める Issue (#1・#2 と作業 Issue #7〜#9) がすべて閉じ、リリースの手順を行える状態です。

1. **残りの Issue を閉じる** (スキル `managing-issue-close`)
   - 残りの作業 Issue と管理 Issue を、シナリオ 2 の手順 5 で閉じます。
2. **リリースの実行を始める** (スキル `release-run`。依頼の例: 「R5 のリリースを始めて」)
   - 実行を始めてよいかを利用者に確認してから、#5 に記録のコメント `release-start` を書きます。このコメントがあるリリース Issue を、実行中とします。
   - 計画でリリースの PR が要ると決めたので、ブランチ `release/5-first-release` で PR #17 を作ります。PR の本文に #5 の URL を書き (`Closes` は書かない)、#5 の本文の項目「参照」に PR の URL を足します。
3. **プロジェクトのリリースの手順を行う** (人間か、プロジェクトのほかのスキル)
   - PR のマージ・タグ・告知などは、プロジェクトの手順の文書に従います。スキル `release-run` は、手順を 1 つ行うたびに、何を行ったか・結果・根拠の URL を、リリースの PR (PR が無ければ #5) のコメントに書きます。
   - 実行の中で計画を変える (ここでは、完了の条件に「タグ r5 が、リリースの PR のマージのコミットに付いている」を足す) ときは、スキル `release-run` で、新しい計画案に節「変えたこと」を書き、承認を得て本文を書き換え、記録のコメント `plan-change` を書きます。
   - 実行の中で見つかった問題 (ここでは、CHANGELOG の節の書き方が決まっていない) を R5 では直さないと利用者が決めたら、スキル `new-issue` で切り出します (#18)。実行中の R5 は、入れるリリースに選べません。切り出した Issue の URL を、実行の記録に書きます。
4. **閉じる** (スキル `release-close`。依頼の例: 「R5 を閉じて」)
   - サブコマンド `release close-plan` で、計画の承認・実行の開始・マイルストーンの Issue がすべて閉じていること・PR のマージ・項目「完了の条件」のチェックを確認します。チェックの無い項目は、確認した結果を #5 のコメントに書き、そのコメントを根拠にチェックを入れます。閉じていない Issue があれば、次のリリースのマイルストーンに移すか外すかを利用者に質問します。
   - スクリプトが判定できない 2 つ (行うと決めた手順を最後まで行ったか・直さない問題を切り出したか) を、実行の記録の URL と一緒に利用者に確認します。
   - 承認を得ると、記録のコメント `close-check` を書き、#5 とマイルストーン R5 を閉じます。#5 を依存先とする Issue があれば、記録のコメント `dependency-resolved` を書きます。

完了した後の状態: リリース計画 #12 の表の次の行の R13 は、題名に `[DRAFT]` があるので、「今のリリース」は無く、「次のリリース」が R13 です。

## 5. 要望の Issue が溜まってきたので、リリース計画に反映する

状況: R5 の後、要望の Issue が増えました。スキル `new-issue` で作ったもの (入れるリリースを選んだもの) と、利用者が GitHub の画面で直接作ったもの (マイルストーンが無いもの) があります。また、モバイルアプリを同じリポジトリで作り始め、Web アプリとは別にリリースすることにしました。

1. **要望を Issue にする** (スキル `new-issue`、または GitHub での直接の作成)
   - GitHub の画面で、#19「費目を利用者が足したい」と #20「モバイルアプリで支出を記録したい」を直接作ります。マイルストーンはありません。
   - スキル `new-issue` で、#21「費目ごとに予算を設定したい」を作ります。入れるリリースは、今のリリース (無い)・次のリリース (R13)・未定から、R13 を選びます。予算との差を出すには丸め方 (#11) が決まっている必要があるので、計画案の項目「依存先の Issue」に #11 を書き、GitHub の blocked by と本文の節「依存先」に設定します。
2. **リリース計画に反映する** (スキル `release-plan`。依頼の例: 「溜まった要望をリリース計画に反映して」)
   - サブコマンド `release review` が、マイルストーンの無い開いた Issue (#18・#19・#20) を示します (リリース計画 Issue・リリース Issue と、ラベル `no-release` の付いた Issue は除きます)。1 件ずつ、どのリリースに入れるか・未定のままにするか・どのリリースにも入れないか (ラベル `no-release` を付ける) を質問します。#20 は、別のリリース対象 (手順 3) なので、未定のままにします。
   - ここでは、R6 (書き出し) を取りやめ、書き出しと予算を合わせた新しいリリースを R13 の後に足すと決めます。計画案の節「取りやめるリリース」に、R6 の理由とメモの移し先 (新しいリリース) を書きます。取りやめる R6 のマイルストーンに残っている #3 は、節「Issue の入れ先」で新しいリリースに移します。#21 も R13 から新しいリリースに移し、#18 を R13 に、#19 を新しいリリースに入れます。
   - 承認を得ると、新しいリリース計画 Issue #22 とリリース Issue #23「[DRAFT] 🔖 リリース R23 (書き出しと予算)」を作り、ラベル `current` を付け替えます (シナリオ 3 の手順 3 と同じ)。取りやめた #6 は、メモを #23 にコピーし、記録のコメント `plan-change` を書いてから、not planned で閉じ、マイルストーン R6 も閉じます。
