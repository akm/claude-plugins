# 6 つのシナリオ

プラグイン issue-practice のスキルを、架空のプロジェクトで最初から順に使う例です。スキルを呼び出すセッションと GitHub に書くものの全体は [workflow.md](workflow.md) に、用語は [terms.md](terms.md) にあります。

架空のプロジェクトは、家計簿の Web アプリのリポジトリ `example/kakeibo` です。デフォルトのブランチは `main` で、`tmp/` は `.gitignore` で git に無視されています (計画案のファイルを git に入れないため)。シナリオの Issue の番号は例です。

| シナリオ | 使うスキルの順 |
| --- | --- |
| 1. Issue が 1 つも無い状態で、最初のリリース計画を立てる | `new-issue` → `release-plan` |
| 2. 立てたリリース計画に基づいて、実装を進める | `release-issue-plan` → `managing-issue-plan` → `managing-issue-run` → `working-issue` → `managing-issue-close`。自己管理 Issue は `managing-issue-plan` → `working-issue` → `managing-issue-close` |
| 3. 設計を見直すバグが分かり、リリース計画を見直す | `working-issue` → `managing-issue-run` (`new-issue` を使う) → `release-plan` → `release-run` |
| 4. 最初のリリースを実施する | `managing-issue-close` → プロジェクトのリリースの手順 → `release-run` → `release-close` |
| 5. 要望の Issue が溜まってきたので、リリース計画に反映する | `new-issue` か GitHub での直接の作成 → `release-plan` |
| 6. 2 回目のリリースを実施する | `release-issue-plan` → シナリオ 2 と同じ → シナリオ 4 と同じ |

各シナリオの「依頼の例」は、利用者がセッションに書く文の例です。スキルは、書き込む前に計画案のファイルか会話で書き込みを示し、利用者の承認を得ます。下の手順では、承認を得る段階を省かずに書きます。

## 1. Issue が 1 つも無い状態で、最初のリリース計画を立てる

状況: リポジトリには、コードだけがあり、Issue もマイルストーンもありません。利用者は、最初のリリースで「支出の記録」と「月ごとの集計」を出したいと考えています。

1. **要望の Issue を作る** (スキル `new-issue`。依頼の例: 「この 3 つの要望を Issue にして」)
   - 何件かを作るので、計画案のファイル (`tmp/issue-practice/<日時>-new-issue-<対象>.md`) に、作る Issue の題名・本文・マイルストーン・ラベルを書きます。
   - リリース計画 Issue がまだ無いので、入れるリリースは未定だけを選べます。マイルストーンは設定しません。
   - 利用者が計画案を読んで承認すると、Issue を作り、Issue ごとに記録のコメント `approval` を書きます。例: #1「支出を記録したい」・#2「月ごとに集計したい」・#3「CSV に書き出したい」。
2. **最初のリリース計画を立てる** (スキル `release-plan`。依頼の例: 「リリースの計画を立てて」)
   - 検査のスクリプトのサブコマンド `release review` で、マイルストーンの無い Issue (#1〜#3) を 1 件ずつ示し、どのリリースに入れるかを利用者に質問します。#1・#2 は最初のリリース、#3 は 2 回目のリリースに入れると決めます。
   - 計画案 (種類 `新しい計画`) に、リリースの順番 (まだ無いリリース Issue はキーで書く) と Issue の入れ先を書きます。
   - 承認を得ると、次のものを書きます。
     - リリース計画 Issue #4「📅 リリース計画 <日付>」と、記録のコメント `approval`
     - リリース Issue #5「[DRAFT] 🔖 リリース R5 (支出の記録と集計)」と #6「[DRAFT] 🔖 リリース R6 (書き出し)」
     - マイルストーン「R5 (支出の記録と集計)」と「R6 (書き出し)」。#1・#2 に R5 を、#3 に R6 を設定する
     - #4 にラベル `current` を付ける (ラベルが無ければ、承認を得て作る)。古い計画が無いので、付け替えと `current-swap` の記録は無い

完了した後の状態: ラベル `current` の付いたリリース計画 #4 の表が、R5 → R6 の順を持ちます。今のリリースは R5 です。

## 2. 立てたリリース計画に基づいて、実装を進める

状況: シナリオ 1 の後です。#1「支出を記録したい」は、データの保存・入力の画面・一覧の画面の 3 つの PR に分けたい大きさです。#2「月ごとに集計したい」は PR 1 つで済みます。

1. **リリース Issue の計画を承認する** (スキル `release-issue-plan`。依頼の例: 「R5 の計画を立てて」)
   - リリース Issue #5 のメモ (利用者がコメントに書いたもの) を 1 件ずつ示し、計画に取り込むか・Issue に切り出すか・次のリリースに回すかを質問します。
   - リリースの手順の文書の場所を質問し、手順ごとに行うか省くかと理由を、利用者と決めます。
   - 計画案に、本文の 7 つの項目 (参照・目的・範囲の判断・順序・メモの扱い・リリースの手順・完了の条件) を書きます。承認を得ると、#5 の本文に計画を書き、題名の `[DRAFT]` を外して、記録のコメント `draft-removed` を書きます。
2. **大きい Issue を作業 Issue に分ける** (スキル `managing-issue-plan`。依頼の例: 「#1 を作業 Issue に分けて計画して」。このセッションが #1 の管理セッションになる)
   - ブランチの構成 (1・2・3) と、PR をマージする人 (利用者か管理セッション) を質問します。例では、構成 1 (作業 Issue の PR を `main` にマージする) と、利用者がマージすることを選びます。
   - 計画案に、#1 自身のクローズ条件・すべての作業 Issue に共通するクローズ条件・PR マージ計画の表・作る作業 Issue (#7・#8・#9 になるもの) を書きます。
   - 承認を得ると、作業 Issue を #1 の sub-issue として作り (マイルストーンは #1 と同じ R5)、#1 の本文にクローズ条件と PR マージ計画を書いて、#1 と作業 Issue に記録のコメント `approval` を書きます。
3. **作業セッションを起動する** (スキル `managing-issue-run`。依頼の例: 「#7 の作業セッションを起動して」)
   - 管理セッションは、Claude Code のデスクトップアプリのセッションです。自分の名前を `kakeibo#1 管理: 支出の記録` にし、#1 に記録のコメント `session` (`role=managing`) を書きます。
   - 表の作業 Issue のうち、起動できるものを示し、どれを起動するかを質問します。
   - 最初の指示 (作業 Issue・管理 Issue・報告先の管理セッション・ブランチ・PR のマージ先・PR をマージする人) を渡して作業セッション `kakeibo#7 作業: データの保存` を起動し、#7 に記録のコメント `session` (`role=working`) を書きます。
4. **作業 Issue を進める** (スキル `working-issue`。作業セッションが、最初の指示から呼び出す)
   - ブランチを作って作業し、PR を作ります。PR の本文には #7 へのリンクを書き、`Closes #7` は書きません。
   - #7 に記録のコメント `report` (`type=pr`) を書き、そのコメントの URL を管理セッションにメッセージで知らせます。管理セッションは、#1 の表の列「PR」に PR の URL を書きます。
   - クローズ条件の項目ごとに、根拠の URL (CI の実行・確認を記録したコメントなど) を添えてチェックを入れ、`report` (`type=check`) で知らせます。
5. **確認して閉じる** (スキル `managing-issue-close`。依頼の例: 「#7 の PR をマージした」)
   - 利用者が PR をマージしたことを伝えると、管理セッションは検査のスクリプト (サブコマンド `close check`) で、PR のマージ・チェックと根拠のリンク・共通の条件のコピーを確認し、利用者の承認を得ずに #7 を閉じて、記録のコメント `close-check` を書きます。
   - #8・#9 も、手順 3〜5 で進めます。作業 Issue がすべて閉じたら、#1 自身の条件にチェックを入れ、確認の結果を利用者に示して、承認を得てから #1 を閉じます。
6. **PR 1 つで済む Issue を進める** (#2「月ごとに集計したい」)
   - スキル `managing-issue-plan` で、#2 を自己管理 Issue として計画します (ブランチの構成は 1)。作業 Issue は作りません。
   - 同じセッションで、スキル `working-issue` を使って進めます。最初の指示は無く、#2 に記録のコメント `session` (`role=self-managing`) を書きます。報告は送らず、表の列「PR」もこのセッションが書きます。
   - PR がマージされたら、スキル `managing-issue-close` で確認し、利用者の承認を得てから #2 を閉じます。

## 3. 設計を見直すバグが分かり、リリース計画を見直す

状況: シナリオ 2 の途中です。作業 Issue #8 (入力の画面) の作業セッションが、データの保存の形では金額の丸めが正しくないことに気づきました。直すにはデータの保存の設計を見直す必要があり、#8 の PR では扱えません。

1. **切り出したいと報告する** (スキル `working-issue`。作業セッション)
   - #8 に記録のコメント `report` (`type=carve-out`) を書き、何を後で行いたいか・理由・判断してほしいことを本文に書いて、管理セッションに知らせます。判断があるまで、その作業を進めずに待機します。
2. **切り出す** (スキル `managing-issue-run`。管理セッションが、報告のメッセージを受けて呼び出す)
   - 報告の記録のコメントを読み、切り出すか・#1 の sub-issue にするか (#1 のゴールに必要か)・入れるリリースを、利用者に質問します。
   - 利用者の回答を渡して、スキル `new-issue` で切り出しの Issue #10「金額の丸めの設計を見直したい」を作ります。入れるリリースは、サブコマンド `release current --carve-out` が示す今のリリース・次のリリース・未定から選びます。例では、R5 では直さず、新しいリリースを足して入れると決めたので、いったん未定 (マイルストーン無し) にします。
   - 依存関係が変わるので、スキル `managing-issue-plan` で #1 の計画を変え (#8 は #10 が閉じてから進める)、#1 に記録のコメント `plan-change` を書きます。
3. **リリース計画を見直す** (スキル `release-plan`。依頼の例: 「#10 を入れたリリースを R5 と R6 の間に足して」)
   - サブコマンド `release review` がマイルストーンの無い #10 を示します。計画案に、新しいリリース (キーで書く) を R5 と R6 の間に入れた順番と、#10 の入れ先を書きます。
   - 承認を得ると、新しいリリース計画 Issue #11 と、リリース Issue #12・マイルストーン「R12 (金額の丸め)」を作り、#10 に設定します。ラベル `current` を #4 から #11 に付け替えて、記録のコメント `current-swap` を書き、#4 を閉じます。
   - 計画に無い急ぎのリリースを足すだけで、順番を変えないときは、計画案の種類を `急ぎのリリースの追加` にします。このときは新しいリリース計画 Issue を作らず、#4 の表を書き換えます。
4. **承認済みのリリース Issue の計画を変える**
   - R5 の範囲が変わった (#8 が R12 の後になる) ので、R5 の計画を変えます。実行を始める前なら、スキル `release-issue-plan` で、新しい計画案に節「変えたこと」(何を変えたか・理由・決めた人) を書き、承認を得て本文を書き換え、記録のコメント `plan-change` を書きます。題名に `[DRAFT]` は付け直しません。
   - 実行を始めた後 (記録のコメント `release-start` がある) なら、同じことをスキル `release-run` で行います。

## 4. 最初のリリースを実施する

状況: R5 に含める Issue の作業が完了し、リリースの手順を行える状態です。

1. **残りの Issue を閉じる** (スキル `managing-issue-close`)
   - 残りの作業 Issue と管理 Issue を、シナリオ 2 の手順 5 で閉じます。
2. **リリースの実行を始める** (スキル `release-run`。依頼の例: 「R5 のリリースを始めて」)
   - 実行を始めてよいかを利用者に確認してから、#5 に記録のコメント `release-start` を書きます。このコメントがあるリリース Issue を、実行中とします。
   - リリースに PR が要るなら、ブランチ `release/5-<英語の短い名前>` で PR を作ります。PR の本文に #5 の URL を書き (`Closes` は書かない)、#5 の本文の項目「参照」に PR の URL を足します。
3. **プロジェクトのリリースの手順を行う** (人間か、プロジェクトのほかのスキル)
   - タグ・デプロイ・告知などは、プロジェクトの手順の文書に従います。スキル `release-run` は、手順を 1 つ行うたびに、何を行ったか・結果・根拠の URL を、リリースの PR (PR が無ければ #5) のコメントに書きます。
   - 実行の中で見つかった問題を R5 では直さないと利用者が決めたら、スキル `new-issue` で切り出します。実行中の R5 は、入れるリリースに選べません。
4. **閉じる** (スキル `release-close`。依頼の例: 「R5 を閉じて」)
   - サブコマンド `release close-plan` で、計画の承認・実行の開始・マイルストーンの Issue がすべて閉じていること・PR のマージ・項目「完了の条件」のチェックを確認します。閉じていない Issue は、次のリリースのマイルストーンに移すか外すかを利用者に質問します。
   - スクリプトが判定できない 2 つ (行うと決めた手順を最後まで行ったか・直さない問題を切り出したか) を、利用者に確認します。
   - 承認を得ると、記録のコメント `close-check` を書き、#5 とマイルストーン R5 を閉じます。#5 を依存先とする Issue があれば、記録のコメント `dependency-resolved` を書きます。

完了した後の状態: 今のリリースは、ラベル `current` の付いたリリース計画 #11 の表の次の行 (R12) です。

## 5. 要望の Issue が溜まってきたので、リリース計画に反映する

状況: R5 の後、要望の Issue が増えました。スキル `new-issue` で作ったもの (入れるリリースを選んだもの) と、利用者が GitHub の画面で直接作ったもの (マイルストーンが無いもの) があります。

1. **要望を Issue にする** (スキル `new-issue`、または GitHub での直接の作成)
   - スキル `new-issue` で作るときは、入れるリリースを、今のリリース・次のリリース・未定から選びます。未定ならマイルストーンを設定しません。
2. **リリース計画に反映する** (スキル `release-plan`。依頼の例: 「溜まった要望をリリース計画に反映して」)
   - サブコマンド `release review` が、マイルストーンの無い開いた Issue を示します (リリース計画 Issue・リリース Issue と、ラベル `no-release` の付いた Issue は除きます)。1 件ずつ、どのリリースに入れるか・未定のままにするか・どのリリースにも入れないか (ラベル `no-release` を付ける) を質問します。
   - 新しいリリースが要るなら、計画案に足して、新しいリリース計画 Issue とリリース Issue を作り、ラベル `current` を付け替えます (シナリオ 3 の手順 3 と同じ)。今の計画の開いているリリースを取りやめるときは、計画案の節「取りやめるリリース」に理由とメモの移し先を書きます。取りやめたリリース Issue は、メモを移し先にコピーしてから、not planned で閉じます。
3. **2 つ目のリリース対象を足す** (要望の中に、別のリリース対象のものがあるときだけ。スキル `release-plan`)
   - 例: モバイルアプリを同じリポジトリで作り始め、Web アプリとは別にリリースすることにした。
   - 足すリリース対象の名前 (例: `mobile`) と、既にあるリリース対象に付ける名前 (例: `web`) を、利用者に質問します。
   - 種類 `リリース対象の追加` の計画案で承認を得ると、ラベル `release-target:web` を作り、開いているリリース計画 Issue とリリース Issue に付けて、題名とマイルストーンの名前に `web` を入れます (例: `📅 リリース計画 web <日付>`・`🔖 リリース R12 web (金額の丸め)`)。閉じた Issue のうち表に無いものは、題名を変えません。
   - その後で、`mobile` の最初のリリース計画を、種類 `新しい計画` で立てます (ラベル `release-target:mobile` を付ける)。
   - これ以降、検査のスクリプトのサブコマンド (`release current`・`release review` など) は、リリース対象の指定 (`--target`) を求めます。スキルは、どのリリース対象かを利用者に質問します。

## 6. 2 回目のリリースを実施する

状況: シナリオ 5 の後です。今のリリースは R12 です (リリース対象を足したなら、`web` の R12)。

1. **リリース Issue の計画を見直して承認する** (スキル `release-issue-plan`。依頼の例: 「R12 の計画を立てて」)
   - R12 は、シナリオ 3 で作ったときから時間が経っています。メモを 1 件ずつ見直し、マイルストーンの無い Issue をこのリリースに入れるか、依存先 (本文の節「依存先」) に閉じた Issue が残っていないかを確認します。閉じた依存先が残っていれば、記録のコメント `dependency-resolved` を書くかを質問します。
   - リリースの手順の文書の場所は、前の計画の値を使わずに、もう一度質問します。
   - 承認を得ると、#12 の本文に計画を書き、`[DRAFT]` を外します。
2. **実装を進める**: シナリオ 2 の手順 2〜6 と同じです。シナリオ 3 で #10 を依存先にした #8 は、#10 が閉じたときに `dependency-resolved` の記録が書かれ、着手するかを利用者に質問されます。
3. **リリースを実施する**: シナリオ 4 と同じです。
