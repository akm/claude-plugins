# 計画案の書式と保存先

計画案 (用語は [terms.md](terms.md)) は、Issue を作る・書き換える前に会話で調整する Markdown のファイルです。計画のスキルは、計画案を作り、利用者と調整し、承認を得てから GitHub に書き込みます。この文書は、すべてのスキルに共通する部分 (保存先・ファイル名・先頭の書式・本文の照合) を決めます。計画案の中身の書式は、それぞれのスキルの文書が決めます。作る Issue の一覧 (節「作る Issue」) は、Issue を作るスキルに共通なので、[issue-bodies.md](issue-bodies.md) が決めます。

この文書と、モジュール `issue-practice/scripts/issue_practice/draft.py` が、計画案の書式の [SSOT](../../CONCEPTS.md#ssot) です。

## 保存先

計画案は、リポジトリのルートのディレクトリ `tmp/issue-practice/` の下に書きます。

- **そのディレクトリが git に無視されていないときは、計画案を書かずに中断し、`tmp/` を `.gitignore` に足すよう利用者に案内します。** スキルは `.gitignore` を変えません。計画案には、承認の前の案や、利用者との調整の途中の文が入るので、コミットしないようにするためです。
- 無視されているかは、検査のスクリプトのサブコマンド `draft dir-check` か `draft path` で確認します。どちらも、リポジトリのルートの絶対パス (コマンド `git rev-parse --show-toplevel` の出力) を引数 `--root` で受け取り、`git check-ignore` で判定します。パスの基準をカレントディレクトリにしないのは、サブディレクトリから実行したときに、別のパスを判定してしまうためです。
- `git check-ignore` は、まだ無いパスでも判定できます。ディレクトリを作る前に確認します。

## ファイル名

ファイル名は `<YYYYMMDD>-<hhmm>-<スキル名>-<対象>.md` にします。

| 成分 | 書き方 |
| --- | --- |
| `<YYYYMMDD>-<hhmm>` | 計画案を作った日時 (ローカル時刻) |
| `<スキル名>` | 計画案を作ったスキルの名前 (`managing-issue-plan` など)。プラグイン issue-practice のスキルの名前のどれか |
| `<対象>` | 計画の対象。管理 Issue の番号 (`239`) か、英小文字・数字・ハイフンの短い名前 (`next-release`) |

**既にあるファイルは上書きしません。** 同じ名前のファイルがあれば、サブコマンド `draft path` は名前を返さずに理由を返すので、時刻か対象を変えて作り直します。前の計画案を、承認した記録 (記録のコメントの `draft=`) から辿れるようにするためです。

## 先頭の書式

計画案の先頭は、次の形で書きます。サブコマンド `draft parse` がこの部分を読み、形が違えば行番号を付けた誤りを返します。誤りがあるときは、スクリプトは計画案から何も書き込みません。

```markdown
# 計画案: <題>

<この計画案の説明。書かなくてもよい>

## 元にした Issue

- https://github.com/<owner>/<repo>/issues/<番号> 本文の SHA-256: <64 桁の 16 進数>

## <スキルごとの節>
```

- 1 行目は `# 計画案: ` と題。
- 節「元にした Issue」は、最初のレベル 2 の見出しにします。項目は、計画案を作るときに読んだ Issue (か PR) の 1 つにつき 1 行で、URL と、そのときの本文のハッシュ値を書きます。ハッシュ値は、サブコマンド `body show` の出力の `sha256` をそのまま書きます。
- 本文を書き換える Issue が無い計画 (Issue を新しく作るだけの計画など) では、項目を `- なし` の 1 行だけにします。
- 節「元にした Issue」の後の節は、スキルごとの文書が決めます。

## 本文の照合

計画のスキルは、Issue の本文を書く直前に本文を再度読み込み、計画案を作ったときの本文と比べます (計画の R6・KTD7)。

- 比べるのは、本文のハッシュ値だけです。Issue の `updatedAt` (更新日時) は比べません。`updatedAt` はコメントが付くだけでも変わるので、比べると、記録のコメントを書いた直後の書き込みが、本文は変わっていないのに中断してしまうためです。
- サブコマンド `draft compare` が、節「元にした Issue」のすべての Issue の本文を再度読み込んで比べます。1 つでも違えば、スキルは書かずに中断し、違いを示して利用者に質問します。
- チェックボックスは作業セッションと管理セッションの両方が書くので、チェックを入れるときも同じ照合をします。

## 承認の記録

利用者が計画案を承認したら、スキルは記録のコメント `approval` を書き、`draft=` に計画案のファイル名を書きます (形は [record-comments.md](record-comments.md))。承認は、その操作をするセッションが会話で利用者から直接得ます。
