# 要望・バグ・切り出しの Issue の本文

スキルが作る要望・バグ・切り出しの Issue の本文の形と、何件かをまとめて作るときの計画案の節「作る Issue」の形を決めます。用語 (管理 Issue・計画案など) は [terms.md](terms.md) にあります。

この文書と、モジュール `issue-practice/scripts/issue_practice/issues.py` が、節「作る Issue」の書式とスキルが作るラベルの [SSOT](../../CONCEPTS.md#ssot) です。テスト (ファイル `issue-practice/tests/test_issues.py`) が、この文書の項目の名前とラベルの表が、モジュールの定数と一致することを確認します。

## 要望とバグの Issue

要望とバグの Issue は、問題か要望・関連するリンク・分かる範囲のクローズ条件で書きます (計画の R10)。**解決策は書きません。** 解決策だけを書くと、動機になった問題や検討したことが失われ、後から別の解決策と比べられなくなるためです。

```markdown
## 問題

<何が起きているか・何に困っているか。バグなら、再現の手順・期待する振る舞い・実際の振る舞い>

## 関連するリンク

- <関連する Issue・PR・コメント・文書・ソースコードの URL と、何に関連するか>

## クローズ条件

期待する状態:

- [ ] <成り立っている状態>

確認するポイント:

- [ ] <確認すること>
    - 確認の方法: <自動テストか、手で確認するか>
    - 記録先: <PR の CI の結果・この Issue のコメントなど>
```

- 要望の Issue は、節「問題」の代わりに節「要望」を書きます。
- 関連するリンクが無ければ、節「関連するリンク」に `- なし` と書きます。
- クローズ条件は、Issue を作るときに分かる範囲で書きます。決まっていない部分は、決まっていないと書きます。着手する前に管理セッションが補います (計画の R17)。書き方は [closing-conditions.md](closing-conditions.md) にあります。

## 切り出しの Issue

作業の途中で見つけた、後で行う作業を別の Issue にすることを「切り出し」と呼びます。切り出しの Issue は、次の 5 つの節で書きます (計画の R12)。

```markdown
## 問題

<何が起きているか・何に困っているか>

## 見つけた経緯

<どの Issue・PR のどの作業で見つけたか。元の Issue と、見つけた PR やコメントへのリンク>

## 切り出した理由と決めた人

<元の作業で直さずに切り出した理由と、切り出すと決めた人の名前>

## 依存先

- <依存先へのリンクと、何を待つか>

## クローズ条件

期待する状態:

- [ ] <成り立っている状態>

確認するポイント:

- [ ] <確認すること>
    - 確認の方法: <自動テストか、手で確認するか>
    - 記録先: <記録する場所>
```

- 要望を切り出すときは、節「問題」の代わりに節「要望」を書きます。
- 依存先が無ければ、節「依存先」を書きません。

### 依存先の書き方

依存先の種類によって、書き方が違います (計画の R14)。

| 依存先 | 節「依存先」に書くこと | GitHub の依存関係 (blocked by) |
| --- | --- | --- |
| Issue | Issue へのリンク | 設定する。計画案の項目「依存先の Issue」に書く |
| PR | PR へのリンク | 設定しない (GitHub の blocked by は Issue どうしの関係のため) |
| 人の判断 | 判断を依頼したコメントなどへのリンクと、判断する人の名前 | 設定しない |

### 元の Issue の更新

切り出した作業が、元の Issue のクローズ条件の項目に当たるときは、その項目の末尾に `(切り出し: <切り出した Issue の URL>)` を足して、チェックを入れます (計画の R15)。書き方と、本文を書き換える前の照合は [closing-conditions.md](closing-conditions.md) の節「チェックの入れ方」にあります。

## 本文の末尾の行

計画案から作る Issue には、本文の最後の行に `issue-practice: created-from draft=<計画案のファイル名> key=<計画案の中のキー>` を書きます (形は [record-comments.md](record-comments.md) の節「作る Issue の本文の末尾の行」)。この行は、検査のスクリプトのサブコマンド `issues create` が足します。計画案の本文には書きません。

## 計画案の節「作る Issue」

スキルは、Issue を作る前に計画案 (先頭の書式は [draft-plan.md](draft-plan.md)) を書き、節「作る Issue」に作る Issue を並べます。検査のスクリプトのサブコマンド `issues plan` (示す) と `issues create` (実行する) が、この節を読みます。

````markdown
## 作る Issue

### a: 一覧の絞り込みで、閉じた Issue が残る

- 親 Issue: #239
- 依存先の Issue: #12, #15
- マイルストーン: R285 (バックアップ一式)
- ラベル: bug

~~~markdown
## 問題

...
~~~
````

- 節「作る Issue」は、節「元にした Issue」の後に、見出し `## 作る Issue` で 1 つだけ書きます。
- 作る Issue 1 件ごとに、見出し `### <キー>: <題名>` を書きます。キーは、計画案の中で Issue を区別する名前で、英数字で始まり、英数字・`.`・`_`・`-` が続く文字列です。同じキーを 2 回書きません。上から順に作ります。
- 見出しの次に、4 つの項目を下の表の順にすべて書きます。値が無い項目は `なし` と書きます。
- 項目の次に、本文を `~~~markdown` の行と `~~~` の行で囲んで書きます。本文の中には、`~~~` で始まる行を書けません (本文のコードブロックは ```` ``` ```` で書きます)。

| 項目 | 値 |
| --- | --- |
| 親 Issue | sub-issue にするときの親 Issue の参照 (`#番号`・`owner/repo#番号`・URL)。1 つだけ |
| 依存先の Issue | blocked by に設定する Issue の参照を `, ` で区切って並べる。PR と人の判断は書かない (本文の節「依存先」だけに書く) |
| マイルストーン | 設定するリリースマイルストーンの名前。入れるリリースが未定なら `なし` |
| ラベル | 付けるラベルの名前を `, ` で区切って並べる |

形が違う節 (見出しの形・項目が足りない・本文の囲みが閉じていない・同じキーが 2 回ある) があると、サブコマンドは何も作らずに、行番号を付けた誤りを返します。

## 「示す」と「実行する」

何件かをまとめて作る書き込みは、検査のスクリプトの 2 つのサブコマンドに分けます (計画の KTD3)。

- **`issues plan` (示す)**: 計画案と GitHub の今の状態から、行う書き込みの一覧を JSON で出します。GitHub には書き込みません。スキルは、この一覧を利用者に見せて承認を得ます。
- **`issues create` (実行する)**: 一覧の書き込みを行います。

書き込みが途中で失敗したときは、同じ計画案で `issues create` をやり直せます (計画の R7・KTD5)。やり直しでは、本文の末尾に同じ `created-from` の行を持つ開いた Issue を作り済みとして扱い、作りません。作り済みの Issue についても、マイルストーン・ラベル・親 Issue・blocked by を GitHub の今の状態と比べ、足りないものだけを設定します。今の状態が計画案と違う (別のマイルストーンや別の親 Issue が設定されている) ときは、上書きせずに誤りとして返します。`gh` は、既に別の親 Issue がある Issue に親を設定すると、エラーにせずに親を置き換えるためです (確認用のリポジトリで確認した振る舞い。ファイル `issue-practice/tests/fixtures/gh/README.md`)。

`issues plan` は、次のときに誤りを返します。

- 親 Issue と依存先の Issue が無い・閉じている・PR である。
- マイルストーンが無いか閉じている。
- ラベルがリポジトリに無い (下の表のラベルを除く)。
- マイルストーンとラベル `no-release` の両方がある。

## スキルが作るラベル

リポジトリに無いときにスキルが作るラベルは、次の 3 種類だけです (計画の R9)。`issues plan` は、計画案の項目「ラベル」にあってリポジトリに無いものを、作るラベルとして名前・色・説明と一緒に返します。スキルは、それを利用者に示して承認を得てから `issues create` を実行します。ほかのラベルは作らず、リポジトリに無ければ誤りにします。

| ラベル | 色 | 説明 |
| --- | --- | --- |
| `current` | `0e8a16` | 有効なリリース計画 Issue (issue-practice) |
| `release-target:<名前>` | `1d76db` | リリース対象 <名前> のリリース計画 Issue とリリース Issue (issue-practice) |
| `no-release` | `cfd3d7` | どのリリースにも入れない Issue (issue-practice) |
