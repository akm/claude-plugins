# 記録のコメントの形

記録のコメント (用語は [terms.md](terms.md)) は、スキルが Issue に書くコメントのうち、1 行目を決まった形にしたものです。Issue の本文には決めたことだけを書き、経緯 (承認・変更・報告・確認の結果) は記録のコメントに書きます (計画の R3)。1 行目で種類が分かるので、検査のスクリプトが確実に読め、人もコメントの一覧で種類を判別できます。

この文書と、モジュール `issue-practice/scripts/issue_practice/records.py` が、形の [SSOT](../../CONCEPTS.md#ssot) です。テスト (ファイル `issue-practice/tests/test_docs.py`) が、下の表の種類とキーが、モジュールの定数と一致することを確認します。

## 1 行目の形

```text
issue-practice: <種類> <キー>=<値> <キー>=<値> ...
```

- 先頭は `issue-practice:` で、空白を 1 つ挟んで種類を書きます。キーと値の組は、空白で区切って続けます。
- 値には空白を入れられません。空の値も書けません。人が読む説明 (セッションの名前・理由など) は、1 行目ではなく本文に書きます。
- 同じキーを 2 回書けません。種類ごとに決まったキー (下の表) だけを書けます。必須のキーが無い・知らないキーがある・知らない種類の 1 行目は、誤りとして扱います。
- 1 行目の後に空行を 1 つ挟み、人が読む本文を続けます。本文の書き方は、それぞれのスキルの文書が決めます。
- 1 行目は手で書かず、検査のスクリプトのサブコマンド `records format` で作ります。キーは下の表の順に並びます。

例:

```text
issue-practice: session role=working session=local_89aab7c6-87c8-432f-97dc-4de4f3bc345d branch=feat/266-issue-practice-base

この作業 Issue の作業セッションを起動した。

- 作業セッションの名前: claude-plugins#266 作業: issue-practice の共通部分
- 報告先の管理セッション: claude-plugins#239 管理: Issue の使い方のスキル (local_7eefe131-5f84-4c43-b029-e14eb2449d29)
```

## 記録として読むコメント

サブコマンド `records list` は、Issue のコメントを投稿の順に読み、次のものを記録として返します。

- **投稿者が、`gh` の認証のログイン (`gh api user` の `login`) と同じコメントだけを読みます。** 投稿者が違うコメントは、1 行目が記録の形でも記録として読みません。公開のリポジトリでは第三者もコメントを書けるので、1 行目の形だけで受け入れると、第三者のコメントで承認や報告を装えてしまうためです。このプラグインは 1 つの GitHub アカウントで使う前提なので、ログインで絞っても、スキルが書いた記録は除かれません。ログインは大文字と小文字を区別せずに比べます。
- 1 行目が `issue-practice:` で始まらないコメントは、記録ではないので読みません。
- 1 行目が `issue-practice:` で始まるのに形が違うコメントは、誤りの一覧 (`invalid`) に入れ、終了コード 3 を返します。スキルは中断し、見つけたことを示して利用者に質問します (計画の R8)。

## 種類

表は、種類と、1 行目に書くキーの一覧です。「なし」はキーが無いことを表します。

| 種類 | 必須のキー | 任意のキー | 書くとき |
| --- | --- | --- | --- |
| `session` | `role`・`session` | `branch`・`previous` | セッションを起動した・受け持った・交代した (計画の R27〜R29)。セッションの名前は本文に書く |
| `approval` | `draft` | なし | 利用者が計画案を承認した (R2) |
| `plan-change` | なし | `draft` | 計画・クローズ条件・PR マージ計画を変えた (R24・R34・R46)。何を変えたか・理由・決めた人は本文に書く |
| `report` | `type` | `pr` | 作業セッションが報告する (R30)。報告の中身は本文に書く |
| `draft-removed` | `date` | `draft` | リリース Issue の計画を承認して、題名の `[DRAFT]` を外した (R44) |
| `current-swap` | `date` | `old` | ラベル `current` を新しいリリース計画 Issue に付け替えた (R38)。新しく作ったリリース Issue とマイルストーンは本文に書く |
| `release-start` | なし | なし | リリースの実行を始めた (R46) |
| `dependency-resolved` | `issue` | なし | 依存先の Issue が閉じた (R50) |
| `close-check` | `result` | なし | 閉じる前の確認の結果 (R22・R23・R48)。確認した項目と根拠の URL は本文に書く |
| `abandon` | `session` | なし | 作業 Issue を閉じずに作業セッションを終えた (R29)。理由は本文に書く |

## キー

| キー | 値 |
| --- | --- |
| `role` | セッションの役割。`managing` (管理セッション)・`working` (作業セッション)・`self-managing` (自己管理 Issue を進めるセッション) のどれか |
| `session` | セッションの ID (英数字で始まり、英数字・`_`・`.`・`-` が続く文字列) |
| `previous` | 交代する前のセッションの ID (`session` と同じ形) |
| `branch` | ブランチの名前 (英数字で始まり、英数字・`.`・`_`・`/`・`-` が続く文字列。`..` を含まない) |
| `draft` | 計画案のファイル名 (形は [draft-plan.md](draft-plan.md) の節「ファイル名」) |
| `type` | 報告の種類。`pr` (PR を作った)・`check` (チェックを入れた)・`split` (分けたい)・`condition-change` (条件を変えたい)・`carve-out` (切り出したい)・`suspend` (中断する) のどれか |
| `pr` | PR の URL (`https://github.com/<owner>/<repo>/pull/<番号>`) |
| `date` | 利用者が承認した日 (`YYYY-MM-DD`) |
| `old` | 置き換えた古いリリース計画 Issue の参照 (`#番号` か `owner/repo#番号`) |
| `issue` | Issue の参照 (`#番号` か `owner/repo#番号`) |
| `result` | 確認の結果。`pass` (満たす)・`fail` (満たさない) のどちらか |
| `key` | 計画案の中の、Issue を表すキー (英数字で始まり、英数字・`.`・`_`・`-` が続く文字列。下の節の行だけで使う) |

## 作る Issue の本文の末尾の行

スキルが計画案から Issue を作るときは、Issue の本文の最後の行に、次の行を書きます (計画の KTD5)。記録のコメントと同じ形ですが、コメントではなく Issue の本文に書くもので、種類 `created-from` はこの行だけで使います。コメントの 1 行目に書いたものは、誤りとして扱います。

```text
issue-practice: created-from draft=<計画案のファイル名> key=<計画案の中のキー>
```

| 種類 | 必須のキー | 任意のキー | 書くとき |
| --- | --- | --- | --- |
| `created-from` | `draft`・`key` | なし | 計画案から Issue を作った。書き込みが途中で失敗してやり直すときに、同じ行を持つ開いた Issue を作り済みとして扱い、二重に作らないため |
