  # Claude Code 2.1.273 の公式文書の調査結果 (サンドボックス・権限・auto モード・`-p`)
  
  ## 最初に: ネットワークの制限が効かなかった原因は、利用者設定の 1 行の可能性が高い
  
  ファイル `~/.claude/settings.json` の `permissions.allow` に、許可の規則 `"WebFetch(domain:*)"` があります (200 行目。読んだだけで変更はしていません)。
  
  - 文書によると、`WebFetch(domain:...)` の許可の規則はサンドボックスのネットワークの許可一覧にそのまま加わります。
  - ドメインを `*` だけにした書き方もサンドボックスは解釈します (v2.1.186 以降)。
  - このため、許可一覧が「すべてのホスト」になります。設定キー `strictAllowlist` は許可一覧の外を拒否するだけなので、この状態では何も拒否しません。
  - 根拠の文書: https://code.claude.com/docs/en/sandboxing#network-isolation (「Claude Code also pre-allows domains from `WebFetch(domain:...)` allow rules」の段落と、ワイルドカードの段落)。
  - 観測との因果は**推測**です。確かめるには、利用者設定を読み込まない起動方法 (後述のフラグ `--setting-sources` またはフラグ `--restricted`) で、同じ curl を再実行します。
  
  `strictAllowlist` を付けていない場合は、もう 1 つ原因があります。auto モードでサンドボックスが有効なとき (v2.1.271 以降)、Claude はコマンドごとに接続先のホストを書き添えます。判定用のモデル (以下「判定器」) がそれを許可すると、そのコマンドの間だけ外に出られます。判定器は「読み取りだけの HTTP 要求」を初期状態で許可します。
  
  ## 調べ方と文書の版
  
  - WebFetch は使えました。ただし、要約されて返るページがあったため、同じ公式ページの Markdown 版 (URL の末尾に `.md`) を curl で取得し、原文で読みました。ファイルは作っていません。
  - `claude --help` は実行しました (版は 2.1.273)。`claude -p` とその他のサブコマンドは実行していません。
  - 公式文書は最新版 (変更履歴の先頭が v2.1.283、2026-09-25) の内容で、2.1.273 時点の文書ではありません。版の条件が付いた記述は、変更履歴 https://code.claude.com/docs/en/changelog と照らしました (末尾の「2.1.273 と現行文書の差」)。

  ## 1. サンドボックスのネットワークの制限
  
  主な URL:
  - https://code.claude.com/docs/en/sandboxing#network-isolation
  - https://code.claude.com/docs/en/settings-reference#sandbox-network (各キーの節)
  
  **仕組み**
  - Bash・PowerShell・Monitor のコマンドの通信は、サンドボックスの外で動くプロキシを通ります。
  - プロキシは要求されたホスト名で許可するかどうかを決めます。初期状態では TLS の中身を検査しません。
  - 初期状態で許可されているドメインはありません。
  
  **設定キーと、読み込まれる場所**
  
  | 設定キー | 読み込まれる場所・要点 |
  |---|---|
  | `sandbox.network.allowedDomains` | どの設定ファイルでも有効。全スコープで結合し、重複を除く。プロジェクトの設定からも追加できる |
  | `sandbox.network.deniedDomains` | どの設定ファイルでも有効。許可より優先する。`allowManagedDomainsOnly` があっても全スコープから結合する |
  | `sandbox.network.strictAllowlist` | 利用者設定・管理設定 (組織が配布する設定)・`--settings` から読まれる。リポジトリの `.claude/settings*.json` では効かない。v2.1.219 以降。有効にした設定元が 1 つでもあれば有効のまま。サンドボックス内のコマンドだけが対象で、WebFetch ツールには効かない |
  | `sandbox.network.allowManagedDomainsOnly` | 管理設定だけ。`--settings` の値は使われない (SDK の文書では「SDK の options で指定しても効果なし」) |
  | `httpProxyPort` / `socksProxyPort` | 独自のプロキシを使うための設定。どの設定ファイルでも有効 |
  | `tlsTerminate` | 利用者設定・管理設定・`--settings` から読まれる |
  
  **`--settings` で渡したときに効くか**
  - https://code.claude.com/docs/en/settings#change-a-setting-for-one-session によると、`--settings` は「利用者設定に書けるキーはすべて設定できる」一方、管理設定専用のキーは設定できません。
  - したがって `strictAllowlist` は効き、`allowManagedDomainsOnly` は効きません。
  
  **許可一覧の外のホストへの接続 (`strictAllowlist` が false のとき)**
  
  モードごとの扱いは https://code.claude.com/docs/en/settings-reference#sandbox-network-strictallowlist にあります。
  
  - auto: コマンドごとに添えたホストを判定器が審査する。ホストはそのコマンドの間だけ開く。`strictAllowlist` と `allowManagedDomainsOnly` のどちらかがあれば、この方法は使えない。
  - dontAsk: 拒否する。
  - bypassPermissions: 許可する。
  - それ以外: 利用者に確認する。
  
  **`-p` での振る舞い**
  - 確認を出す先がありません。https://code.claude.com/docs/en/headless#turn-off-permission-prompts-in-unattended-runs によると、確認を出す先のない `-p` では、確認になるはずの要求はいずれにしても拒否されます。
  - フラグ `--permission-prompts none` (v2.1.259 以降) を付けると、「再試行しないように」と Claude にも伝わります。
  
  **WebFetch の許可の規則との関係**
  - `WebFetch(domain:...)` の許可の規則は許可一覧に、拒否の規則は拒否一覧に加わります。
  - 確認で「Yes, and don't ask again」を選ぶと、ファイル `.claude/settings.local.json` に `WebFetch(domain:...)` として保存されます。
  - サンドボックスが解釈するワイルドカードは、先頭の `*.` と `*` だけの 2 種類です。それ以外の位置の `*` はサンドボックスでは効果がありません。
  - 逆方向の関係はありません。`allowedDomains` は WebFetch ツールを制限しません (https://code.claude.com/docs/en/agent-sdk/typescript の `SandboxNetworkConfig`)。
  
  ## 2. サンドボックスの各設定の記載
  
  **`sandbox.allowUnsandboxedCommands` は文書にあります。**
  - https://code.claude.com/docs/en/settings-reference#sandbox-allowunsandboxedcommands
  - https://code.claude.com/docs/en/sandboxing#the-unsandboxed-retry-escape-hatch
  - どの設定ファイルでも有効で、デフォルト値は `true` です。
  - `false` にすると、Bash ツールの引数 `dangerouslyDisableSandbox` を無視します。すべてのコマンドは、サンドボックスの中で動くか、`excludedCommands` に載っているかのどちらかになります。
  - `/sandbox` のタブ Overrides では「Strict sandbox mode」と表示されます。
  - 利用者がプロンプトの `!` から入力したコマンドは、サンドボックスの外で動きます。
  
  **`dangerouslyDisableSandbox`**
  - 違反の後に、Claude がサンドボックスの外で再試行するための引数です。
  - 再試行は通常の権限の流れを通ります。auto モードでは判定器が審査します。
  - 毎回確認させたい場合は、確認の規則 `Bash(dangerouslyDisableSandbox:true)` を足します。
  
  **`sandbox.excludedCommands`** (https://code.claude.com/docs/en/settings-reference#sandbox-excludedcommands)
  - 書式は `Bash(...)` の括弧の中と同じです。
  - 1 回の呼び出しに含まれる全部のコマンドに当てはまった場合だけ、サンドボックスの外に出ます。
  - 当てはまってもサンドボックスの中に残る形があります: `sudo`・`eval`・`xargs` で始まるもの、`cd`、サブシェル、リダイレクト、変数から得たコマンド名。
  - 除外したコマンドも、通常の権限の流れを通ります。
  - 全スコープで結合します。管理設定だけに限る方法はありません。
  
  **`sandbox.filesystem.*`** (https://code.claude.com/docs/en/settings-reference#sandbox-filesystem)
  - パスの書き方:
  
    | 書き方 | 意味 |
    |---|---|
    | `/` で始まる | 絶対パス |
    | `~/` で始まる | ホームディレクトリから |
    | `./` で始まる、または接頭辞なし | プロジェクトの設定ならプロジェクトのルートから、利用者設定なら `~/.claude` から |
  
  - `--settings` で渡した相対パスの基準は、文書に記載がありません。
  - 4 つの一覧はすべて全スコープで結合します。
  - 権限の規則も一覧に加わります: `Edit` の許可 → `allowWrite`、`Edit` の拒否 → `denyWrite`、`Read` の拒否 → `denyRead`。
  - 末尾の `/` と `/**` は取り除かれます。書き込みの一覧のワイルドカードは macOS では効きます。
  - `denyWrite` は、書き込める範囲の中にあるパスも止めます。
  - 読み取りは、狭い方の規則が優先します。書き込みで、`denyWrite` の中に `allowWrite` を置いた場合の優先順位は記載がありません。
  - 保護されたパス (`.claude` の設定、`.git/hooks` など) は、`allowWrite` を書いても書き込めるようになりません。
  
  **`sandbox.failIfUnavailable`**
  - CLI ではデフォルト値が `false` です。サンドボックスを起動できないと、警告を出してサンドボックスなしで実行します。
  - SDK ではデフォルト値が `true` です。
  
  ## 3. 設定の優先順位と合成
  
  主な URL:
  - https://code.claude.com/docs/en/settings#settings-precedence
  - https://code.claude.com/docs/en/permissions#what-runs-before-you-trust-a-folder
  
  **優先順位と合成**
  - 優先順位は、高い順に 管理設定 > コマンドライン (`--settings`) > `.claude/settings.local.json` > `.claude/settings.json` > `~/.claude/settings.json` です。
  - `--settings` はファイルの設定と合成されます。書いたキーだけが上書きされ、書かなかったキーは下位の値が残ります。
  - 配列は置き換えずに結合します。`permissions.allow` も結合されます。
  - 真偽値のキーは、それを書いた最上位のスコープの値が使われます。
  - どこかのスコープの拒否は、他のスコープの許可より優先します。
  
  **使い捨ての作業ツリーにある `.claude/settings.json` も読まれます。**
  - 読む場所は、主作業ディレクトリです。
  - `-p` では、信頼の確認 (フォルダを信頼するかの確認画面) が出ません。その結果、項目ごとに次のように扱われます。
  
    | 作業ツリーの設定の項目 | `-p` での扱い |
    |---|---|
    | `permissions.allow`・`additionalDirectories` | 使われない。標準エラー出力に警告が出る |
    | 拒否・確認の規則 | 使われる |
    | フック・`env`・`apiKeyHelper` | 使われる |
    | `.mcp.json` のサーバー | 確認なしで接続される |
    | `autoMode` | 読まれない |
    | `defaultMode` の `auto` / `bypassPermissions` | 効かない |
    | `disableAutoMode` | 効く。**リポジトリ側で auto モードを止められる** |
    | サンドボックスの配列 (`allowWrite`・`allowedDomains`・`excludedCommands`) | 結合される。**リポジトリ側からサンドボックスの範囲を広げられる** |
    | `strictAllowlist`・`filesystem.disabled`・`tlsTerminate`・`allowAppleEvents`・`mask` | 無視される |
  
  **`.claude/settings.local.json` の置き場所**
  - `git worktree` で作った作業ツリーでは、主のチェックアウトのルートにあるものが使われます (https://code.claude.com/docs/en/settings#where-claude-code-keeps-the-local-file-in-a-git-repository)。
  
  **読み込む設定を限る方法**
  - フラグ `--setting-sources user,project,local`: 除いた設定元の `sandbox.filesystem`・`Edit` の規則・`Read` の拒否は、サンドボックスの構成に使われません (v2.1.246 以降)。
    - 利用者設定の `sandbox.credentials` の拒否は、除いても適用されます。
    - 文書は、他人のリポジトリでは `--setting-sources user` を勧めています。
    - SDK の文書では、`project` は CLAUDE.md とスキルの読み込みも決めます。CLI でも同じかは**推測**です。
    - 空の値を渡したときの振る舞いは、CLI の文書にありません。
  - フラグ `--restricted` (v2.1.248 以降。2.1.273 の `--help` にあります):
    - 読むのは管理設定と `--settings` だけです。
    - Bash などコマンドを実行するツールと WebFetch を外します。使うには、フラグ `--tools` で名前を指定し直します。
    - ファイル操作のツールを作業ディレクトリの中に限ります。
  - フラグ `--bare`: フックと `.mcp.json` などを読みません。ただし、プロジェクトの `env` は適用されます。また OAuth のログインを使わないため、環境変数 `ANTHROPIC_API_KEY` が要ります。
  
  ## 4. auto モード
  
  主な URL: https://code.claude.com/docs/en/permission-modes#eliminate-prompts-with-auto-mode
  
  **使える条件 (現行の文書)**
  - プラン: すべてのプラン。Team と Enterprise では、組織の管理者が止められます。
  - モデル: Anthropic API では Opus 4.6 以降・Sonnet 4.6 以降・Fable。Bedrock・Vertex・Foundry では Sonnet 5・Opus 4.7 以降・Fable。
  
  **使えないとき**
  - Manual (設定値は `default`) で開始します。
  - 設定ファイルの `disableAutoMode`・対応していないモデル・サーバー側での停止が理由になります。サーバー側で止められたセッションは、終わるまで auto に戻りません。
  - `-p` で利用者に通知が出るかは、文書に記載がありません。
  
  **stream-json の `init` の行**
  - `permissionMode` の型は `"default" | "acceptEdits" | "bypassPermissions" | "plan" | "dontAsk" | "auto"` です (https://code.claude.com/docs/en/agent-sdk/typescript の `SDKSystemMessage`)。
  - 戻った後の実際のモードを示すかは、明記されていません (**推測**: 実際のモードを示す)。
  - 実行中のモードは、フックの入力の項目 `permission_mode` でも確かめられます (https://code.claude.com/docs/en/hooks)。
  
  **`-p` で判定器が拒否したとき**
  - Claude は理由を受け取り、別の方法を試します。
  - 連続 3 回か累計 20 回ブロックされても、確認を出す先のない `-p` では、その操作を実行せずに作業を続けます。実行全体は止まりません (https://code.claude.com/docs/en/permission-modes#when-auto-mode-falls-back)。
  
  **`permission_denials` に入るか**
  - 拒否は、stream-json の行 `permission_denied` と、結果の行の `permission_denials` に出ます (https://code.claude.com/docs/en/headless)。
  - 行 `permission_denied` の項目 `decision_reason_type` の値には `"classifier"` があります。また、`permission_denials` が正式な記録だと書かれています。したがって、判定器の拒否も入ると読めます。
  - 例外: `PreToolUse` フックの経路で決まった拒否は、`permission_denied` の行に出ません。
  
  **サンドボックスが止めた書き込み**
  - 権限の仕組みの外で扱われます。違反の内容は、Bash ツールの結果の本文に書かれます (v2.1.224 以降。終了コード 0 の場合は v2.1.243 で修正)。
  - `permission_denials` に数えられないという観測は、文書と矛盾しません。
  
  ## 5. サンドボックスが有効になったかを確かめる方法
  
  - 対話の画面から:
    - `/sandbox` のタブ Config で、解決済みの設定を見られます。
    - `/status` の「Setting sources」の行で、読み込んだファイルを見られます。
    - `claude doctor` は拒否された設定項目を示します (今回は実行していません)。
  - `-p` で文書に書かれている唯一の確実な方法は、`"failIfUnavailable": true` を `--settings` に足すことです。サンドボックスを起動できなければ、起動時にエラーで終了します。
  - デバッグログ:
    - `--debug`・`--debug-file <path>`・`DEBUG=1` で出せます。デフォルトの出力先は `~/.claude/debug/<session-id>.txt` です。
    - サンドボックスについて何が記録されるかは、文書にありません。
  - 間接的な手がかり (**推測**を含む):
    - サンドボックス内のコマンドには、環境変数 `$TMPDIR` として利用者ごとの一時ディレクトリが渡されます。サンドボックス外では値が違います。
    - 許可されていない場所に書き込む確認用のコマンドを実行させ、ツールの結果に違反の内容が出るかを見る方法もあります。
  - サンドボックス内で有効かを示す環境変数は、文書にありません。
  
  ## 6. 拒否の規則の書式
  
  主な URL: https://code.claude.com/docs/en/permissions#read-and-edit
  
  **`Edit(~/**)` の拒否**
  - 「Edit の規則は、ファイルを編集するすべての組み込みツールに適用される」とあるため、ホームの下への Write ツールも止まります。
  - Bash で使われる `sed`・`tee` とリダイレクトの書き込み先にも適用されます。
  - パスを付けた `Write(...)` の規則は照合に使われず、起動時に警告が出ます (v2.1.210 以降)。利用者設定にある `Write(~/projects/**)` の許可は、効いていません。
  - **推測**: `Edit` の拒否はサンドボックスの `denyWrite` に加わるため、`Edit(~/**)` によってホーム全体が `denyWrite` に入ります。その結果、ホームの下にある作業ツリーと `~/Library/Caches/go-build` への Bash の書き込みも止まる可能性があります。書き込みで拒否と許可が重なったときの優先順位は、文書にありません。
  
  **`Read` の拒否**
  - 書き方の例: `Read(./.env)`・`Read(~/.ssh/**)`・`Read(//abs/path/**)`。書式は gitignore と同じです。
  - `/path` のように `/` 1 つで始まる書き方は、規則を書いた設定元を基準にします。コマンドラインのフラグなら主作業ディレクトリ、利用者設定なら `~/.claude` です。
  - `Read` の拒否は、同じパスへの Edit・Write も止めます。サンドボックスの `denyRead` にも加わります。
  
  **Bash**
  - 現在の書き方は `Bash(git push *)` です。`Bash(git push:*)` も同じ意味になりますが、`:*` は末尾に置いたときだけ有効です。
  - 拒否は、複合コマンドのどの部分に当てはまっても効きます。
  - `git -C . push` や `/usr/bin/curl` の形には当てはまりません (https://code.claude.com/docs/en/permissions#bash-rule-limits)。
  
  **`--disallowedTools`**
  - ツール名だけを書くと、そのツール自体を外します。
  - 括弧で範囲を付けると、ツールは残り、当てはまった呼び出しだけを拒否します。
  
  **調べる途中で見つけたこと**
  - 利用者設定の拒否の規則 `Edit(/etc/**)` などは、文書の規則では `~/.claude/etc/**` を指します。システムの `/etc` を止めるには `//etc/**` と書く必要があります。
