    - 監視の処理は、回が終わるまで周期ごとに通知を送り続ける

  ### 5. 起動時の掃除を起動時の確認の順番のどこに置くかが決まっておらず、`--end` や `unavailable` の後に片付けられない (KTD10・R6・U3・U4)
  
  **根拠**
  - 0.13.0 は、確認の 2 番以降で通らないと `worker.yaml` を `unavailable` として書き直します (ワーカー 195〜199 行目)。書き直した内容には新しいキーが無いので、前のワーカーが残した `reviewer_pgid` と `workspace` が消えます。
  - `end` の確認 (241 行目) も、この 2 番以降にあります。
  - U3 は「R18 と KTD10 の掃除を、順番に足す」(計画 577 行目) としか書いていません。
  
  **起きること**
  - 掃除が `end` の確認より後にあると、ワーカーが `kill -9` で消えた後に人間が `--end` を打った周回では、残ったレビュアの実行と作業場所が片付きません。ワーカーは起動するたびに `end` で止まります。

  - 掃除には数秒以上かかり、その間 `worker.yaml` は前のワーカーのままです。そのため、2 つのワーカーが確認 1 を同時に通りうる時間が、0.13.0 より長くなります (推測: 人間が 2 つの端末で起動した場合だけ)。

  - KTD10 に「掃除は確認 1 の直後、`worker.yaml` を書くどの処理よりも前に行う」と書く。
  - `unavailable` で書き直すときも、掃除が済んでいなければ前のキーを引き継ぐ。
  - SKILL.md 72 行目を U6 の対象に加え、「残ったレビュアの実行があれば、一度起動すると片付けてから止まる」と書き換える。
  
  ### 6. 作業場所のパスが周回 id だけで決まり、別のリポジトリや別の `TMPDIR` と区別できない (KTD1・KTD10・R18)
  
  **根拠**
  - 作業場所は `<TMPDIR の実体>/review-loop-<周回 id>/` です (計画 323 行目)。
  - 周回 id は日時 (分単位) とブランチ名だけでできています (round.md 23 行目)。別のクローンで同じブランチの周回を同じ分に始めると、パスが重なります。
  - KTD10 の最後 (計画 381 行目) は、`worker.yaml` の `workspace` ではなく、いまの環境から計算したパスを消すように読めます。
  
  **起きること**
  - 他の周回の作業場所を消してしまう。
  - 端末が違って `TMPDIR` が違うと、前の作業場所を消せない。
  - `TMPDIR` が無いときに使う `/tmp` は、他のユーザーも書ける場所で、名前も予測できます (推測: macOS では通常ユーザーごとの `TMPDIR` があるので起きにくい)。
  - `--end` の後も、親ディレクトリが空のまま残ります。
  
  **直し方**
  - KTD1 の名前に、置き場の実体パスから決まる短いハッシュを足す。周回の間は固定なので、`~/.claude/projects/` の項目は増えない。
  - 作業場所を作るときに、自分が所有するディレクトリで、シンボリックリンクでないことを確かめる。
  - KTD10 では、`worker.yaml` の `workspace` の名前の形を確かめてから消す。
  - `TMPDIR` が無ければ `/tmp` を使わず、R18 で `unavailable` にする。
  - `end` を見て終わるときに、親ディレクトリも消す。
  
  ### 7. ワーカーの版を「新しいキーが無いこと」で判定しており、起動しなかった回や、権限モードの 2 種類の食い違いを区別できない (KTD14・KTD15・R14・U6)
  
  **起動しなかった回の印**

  **権限モードの食い違いは 2 種類ある** (R14 の「権限モードの不一致」、計画 103 行目)

  **直し方**

  - 版は、印と `worker.yaml` にプラグインの版を明示するキーを足して判定する。
  - R14・U6・stops.md の RA1 で、(i) と (ii) の直し方を分ける。
  
  ### 8. 再開のときに `sandbox_allow_write` を変えられず、F2 の直し方が案内のコマンドに入らない (F2・R17・KTD14・AE14)
  
  **根拠**

  **直し方**
