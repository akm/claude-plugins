#### 1. 経路ごとに規則を書くと収束しない (within `require-explicit-basis-for-relative-paths.md`)
- **File**: `docs/solutions/tooling-decisions/require-explicit-basis-for-relative-paths.md`
- **Module**: review-triage (triagecheck)
- **Problem Type**: `tooling_decision`
- **Relevance**: This is the exact historical episode the plan's own Problem Frame cites as motivating evidence (the 17-round `fix-triagecheck-explicit-path-must-exist.yaml` record). It is a first-party, in-repo instance of precisely the pattern the plan is trying to mechanize (捉え直し after 2 consecutive same-type findings).
- **Key Insight**: The recurring-finding table there was 規則 × 経路 (rule × code path) × フラグ. Convergence happened only when the fix unit changed from "one cell of the table" to "the table itself" — collapsing path-specific special cases into one shared resolution point before the branch. Two concrete symptoms to design detection around: (a) findings that are 修正由来 chain across rounds even when the file/line differs, and (b) findings that repeat on the same file/function across rounds. The plan's R2 (dual trigger: primary 修正由来 chain, secondary same-file/function) mirrors this exactly — this episode is strong validation, not new information to add.
- **Severity**: high

#### 2. LLM が組み立てる入力は型で縛る (typed-contract-for-agent-input)
- **File**: `docs/solutions/design-patterns/typed-contract-for-agent-input.md`
- **Module**: pr-teeth (cross-applicable — CONCEPTS.md already generalizes this as エージェント入力)
- **Problem Type**: `design_pattern`
- **Relevance**: The plan adds new record-YAML fields (detection markers, agreed reframing) that `review-triage` and `review-triage-fix` — both LLM-driven — will write structurally, not by hand. This is exactly the "agent-assembled structured data" shape CONCEPTS.md's エージェント入力 entry and this learning cover.
- **Key Insight**: Required keys must be structurally required (fail loudly with expected-shape + actual-keys on absence), not defaulted via `.get()`-style permissive reads — a wrong or missing key must never silently produce a valid-looking but empty/partial record. Unknown keys should be rejected too (typo detection). CONCEPTS.md's own エージェント入力 entry already states the repo's converged position: "形が違えば期待する形を示して停止する。項目単位の不備はその項目だけを飛ばし、受理件数と一緒に報告する" — the new detection/reframing fields in triagecheck's schema check should follow this, not the config-file-style lenient fallback.
- **Severity**: high

#### 3. データ種別ごとに失敗時の態度を変える (fail-soft-by-data-class)
- **File**: `docs/solutions/architecture-patterns/fail-soft-by-data-class.md`
- **Module**: pr-teeth (cross-applicable)
- **Problem Type**: `architecture_pattern`
- **Relevance**: The record YAML is 蓄積データ (accumulated state across rounds), not config — record-schema.md already treats it this way (corruption/malformed schema must stop, not silently produce a valid-looking record). The new detection and reframing keys must be added to `triagecheck`'s schema check as first-class validated fields, not tolerated as optional-and-silently-absent.
- **Key Insight**: The three-way data classification (config / 蓄積データ / エージェント入力 — read → fallback to default+warn / write → refuse and stop / structural validation + per-item skip+report) should extend cleanly to the new fields: reading an old record without the new keys is a legitimate "not yet migrated" case (default empty, not error), but a *malformed* new field (e.g., a `検知` block with the wrong shape) should be treated as agent-input-class failure, not silently ignored.
- **Severity**: high
