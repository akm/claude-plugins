    6. 本文の書き換えが重なる。sub-issue の本文のチェックボックスは作業セッションと管理セッションの両方が書く。読んでから書くまでの間にもう一方が書くと、上書きされる。書く直前に `updatedAt` を比べる必要がある。

    1. 前の管理セッションに届いたまま読まれていない報告と質問は失われる。報告をメッセージだけで送ると失われるので、sub-issue のコメントに記録し、メッセージではそのコメントの URL を知らせる形を提案する。この形なら、新しい管理セッションは「状況の収集」で報告を取り戻せる。
    2. 会話の中で利用者に尋ね、まだ答えを得ていない質問は失われる。最低限、承認を得たら、操作する前にコメントに記録する順にする。
    3. 途中まで行った操作は、再開したときに検出する必要がある。例: sub-issue を 5 つ作る予定で 3 つ作ったところで止まった、リリース Issue は作ったがマイルストーンはまだ作っていない。作った Issue に再開のときに照合できる値 (例: 本文の 1 行目にある、作った元の記録のコメントの URL) を入れ、照合してから足りない分だけを作る (issue-dispatch の `split-from:` と同じ方法)。
    4. 作業セッションを起動し直したら、新しい作業セッションは、sub-issue のコメント・ブランチ・PR・チェックボックスから状態を組み立て直す。最初の指示には、前の作業セッションの名前と ID も入れる。会話の要約 (compact) の後も、同じ手順で組み立て直せる。

    - スクリプトのテストは、gh の偽物と固定データ (issue-dispatch の U4 と同じ方法) で行う。
    - スキルのテンプレートが書いたコメントを、スクリプトが読めることを確かめるテストを作る。
    - 途中まで行った状態の固定データを用意し、再開しても二重に作らないことを確かめる。
    - 閉じる条件の検査が、会話ではなく GitHub の状態だけで判定することを確かめる。
  - **Scope Boundaries:**
    - Now: 記録の形、読む・検査するスクリプト、手順が複数ある操作の `plan`/`apply`
    - Later: 作業セッションの監視の自動化、issue-dispatch と合わせること
    - Never (人だけが行う): 承認そのもの、利用者が行うと決めた手での確認
