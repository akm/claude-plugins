この claude-plugins だけでなく、Claude Code で開発するアプリケーション、ツール類のドキュメントについて、どのような形が長期的なメンテナンスを行う上で望ましいのかを検討します。

例えば ikinari-order-v2 の セッション「文書の参照の残り (#80〜#83) を直す」で 品切れという用語が glossary に SSOT として登録されていたことをきっかけに「メニューの提供の状態」という状態の一つであり、提供中とともに状態の要素であることが明記されました。レビューを進めるに当たって、どの画面でこれらをどのように使うのかが記載され、SSOT として画面の仕様の話と用語の話の区別が難しくなり、SSOT は仕様に定義して、glossary はSSOT への参照である、という決着になりました。

私はこの形が望ましい形だとは思っていません。SSOTにはその定義が必要であり、それは他の用語と関係しており仕様書の分類方法が明らかでない場合、用語や概念の関係が整理されないまま混乱した状態で定義されてしまうためです。
例えばRFC などの技術文書ではは各ドメインやその中の新しい機能についての定義がありますが、SSOTとなるべき用語はそれを定義する各ドキュメントで定義され、それ以外の用語はそれを定義するドキュメントを参照できるように関連するドキュメントへのリンクが記載されます。

アプリケーションにおいても以下のように分けて

* ユーザーレベルドキュメント( 顧客・ユーザーと共有する用語。設計の用語を使わない )
   * アプリケーションが解決するべき問題を説明するドキュメント
   * アプリケーションが解決するために導入する概念、技術の仕様のドキュメント
      *  概念モデル
      * 画面仕様書
   * 受け入れテストのドキュメント 
* 開発レベルドキュメント( 開発チーム内部で使用する用語 )
   * アプリケーションが解決するための設計のドキュメント
      * スキーマ定義
      * 画面設計書
   * 結合テスト
   * ユニットテスト


ユーザーが API を直接使うのであれば API 定義はユーザーレベルの仕様として定義されるべきですが、そうでなければ設計として扱うべきです。

必ず 概念レベルとスキーマ定義、画面仕様書と画面設計書のような対で定義するべきというつもりはありません。それぞれ必要であれば作るべきものであり、ikinari-order-v2 のようなアプリケーションでは概念モデルや画面仕様書をそのまま顧客と共有する必要性は少ないと思われます。


解決したい問題

* ドキュメントを含むメンテナンス対象は最小限に( Claude 文書を増やしがち )
* Claude は 一つのファイルに追記しがち ( ディレクトリ構造wo考えたい )
* 関連する文書の変更が見落とされがち
* 一つの文書が大きすぎる
* 同じ記述を複数の箇所に書かない。書いた場合にはどちらが正しいのかを必ず決める
* 


問題解決方法案

* ディレクトリ単位での文書構築が良さそう
* ドキュメントが参照するほかのドキュメントは 参照する Issue や PR と同様にリンク可能にする
