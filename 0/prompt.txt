  #### 2. Python のスクリプトの書き方 (gh-notification-dispatch と issue-practice が同じ)
  
  - **版**: Python 3.11 以上・標準ライブラリだけ。README の「前提」と節「テスト」に書く。CI は、テストのディレクトリの親にファイル `.python-version` が無ければ 3.11 で実行する (ファイル `.github/workflows/test.yml`)。3.11 に無い機能は使えない。例: issue-dispatch は `PurePath.full_match` が 3.13 からなので自前の正規表現にした (計画 `docs/plans/2026-10-06-2025-feat-issue-dispatch-plan.md` の KTD9)。`tomllib` は 3.11 にあるので読み込みには使える
  - **入口**: `sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))` の後にパッケージを import する。argparse のサブコマンドで、「グループ → コマンド」の 2 段も使う (`subscriptions add` など)。関数 `_add` が、description と、epilog の「出力 (標準出力の JSON):」「終了コード:」を組み立てる。入口の docstring に「サブコマンドの一覧:」と終了コードを書く。**`<サブコマンド> --help` が、引数・出力の JSON のキー・終了コードの SSOT**。SKILL.md は引数を書かずに `--help` を参照する
  - **出力**: 標準出力に JSON 1 つ (`ensure_ascii=False, indent=2`)。どの出力もキー `errors` (配列) を持つ。外部コマンドが失敗したときは `gh_error` ({args, exit_code, failure, stderr_tail, json_error})。モジュールの関数は `status` (`ok`・それ以外・`gh_failed`) を含む dict を返し、入口の関数 `_emit_status` が終了コードに変える
  - **終了コード**: 0 は続ける。3 は `errors` を示して利用者に判断を求める。4 は外部のコマンドが失敗した。1 と 2 は Python 自身 (捕まえていない例外と引数の誤り) で、スクリプトの不具合として扱う。例外を捕まえて 3 や 4 にはしない。issue-practice の計画の KTD10 と gh-notification-dispatch の計画の KTD11 で同じにした。SKILL.md の冒頭に、この扱いの表を置く
  - **外部コマンドの実行**: 1 つのモジュールの 1 つの関数 (`gh.run`) だけが起動する。返り値は {args, exit_code, stdout, stderr_tail, timed_out, failure, json, json_error}。失敗の種類 (`failure`) は標準エラー出力の文言から分け、再試行しない。標準入力は `DEVNULL`、タイムアウトあり。`OSError` は `missing` か `other` にする。テストは PATH の先頭に偽のコマンドを置いて差し替える
  - **Claude が組み立てる入力**: Claude はツール `Write` でファイルに書き、スクリプトに `--message-file <ファイル>` で渡す。シェルのヒアドキュメントでは書かない (ファイル `gh-notification-dispatch/skills/dispatch/SKILL.md` の節「申し込みのメッセージを受け取ったとき」)。入力の検査は pr-teeth のファイル `pr-teeth/scripts/prteeth/agent_input.py` と、学びの文書 `docs/solutions/design-patterns/typed-contract-for-agent-input.md` の形 (未知のキーはエラー・値の一覧を検査する・導出できる値は受け取らない)
  - **スキルからの呼び出し**: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/gh_notification_dispatch.py" <サブコマンド>` と 1 回書き、以降は `gh_notification_dispatch.py <サブコマンド>` と略すと書く。`${CLAUDE_PLUGIN_ROOT}` は SKILL.md の本文をハーネスが置き換えるもので、シェルの環境変数として読めるとは限らない (`docs/solutions/conventions/plugin-cannot-resolve-its-own-source.md`)。利用者が端末で実行するものには、展開した絶対パスを書く (`review-triage/skills/review-loop/references/guide-template.md`)。プラグインを更新すると古い版のディレクトリは消えうる (`review-triage/skills/review-loop/references/worker.md`)。
  
  #### 3. テストの書き方
  
  - unittest だけを使う。`python3 -m unittest discover -s <plugin>/tests` で実行する。テストのファイルの docstring に、対象のファイルとこのコマンドを書く
  - 基底クラスのファイル `gh-notification-dispatch/tests/fakegh_case.py` では、`setUp` が次を行う。
    - 一時ディレクトリに `bin/gh` という名前で `fake-gh` へのシンボリックリンクを作り、PATH の先頭に足す
    - `FAKE_GH_ARGS` (受けた引数を JSON の 1 行ずつ追記するファイル) と `FAKE_GH_RESPONSES` (応答の指定の JSON) を設定する
    - 記録のディレクトリ (`GH_NOTIFICATION_DISPATCH_HOME`)・`TMPDIR`・セッションの ID・今の時刻 (`GH_NOTIFICATION_DISPATCH_NOW`) をテストごとの値にする。触る環境変数は `_ENV_KEYS` に並べ、`tearDown` で戻す
    - 補助の関数: `cli()` は入口をサブプロセスで実行し (終了コード, JSON, 標準エラー出力) を返す。`home_files()` は書き込みが無かったことを比べるために使う。`recorded()` は受けた引数を返す。`fixture()` は固定データを読む
  - 偽のコマンドのファイル `gh-notification-dispatch/tests/fake-gh` は、`FAKE_GH_MODE` (auth_expired・network・hang・exit など) と、応答の指定 (`prefix`・`contains`・`substring` で照合し、`stdout`・`stderr`・`exit`・`once` を返す。`{"fixture": "<場合>"}` で固定データを返す) で動く。一致しない引数は終了コード 99 で終了する。指定の漏れを、成功した応答と取り違えないため
  - 固定データは実物の出力をコピーしたもの。README に、コマンド・終了コード・取った日・版・切り詰めたかを表で書く
  - 文書とコードが一致することのテスト (ファイル `gh-notification-dispatch/tests/test_docs.py`): references の表の値とモジュールの定数・README のスキルの表とディレクトリ `skills/`・SKILL.md の frontmatter・入口の docstring の一覧と argparse・各 `--help` に「出力 (標準出力の JSON):」「errors」「終了コード:」の 0・3・4 があること・引数の誤りが 2 であること
  - **CI の条件**: ディレクトリ `<plugin>/tests` を、ファイル `.github/test-targets.txt` に `python disk-usage-triage/tests` の 1 行で書く。ワークフローは追跡中の `test_*.py` を見つけてこの一覧と比べ、差があれば失敗にする。そのため、この 1 行は**最初の `test_*.py` を足すコミットで一緒に足す** (gh-notification-dispatch は ce39ccbb で足した)。0 件の実行も失敗になる。CI は ubuntu-latest。
  - **macOS に固有の出力**: リポジトリに `sys.platform` で darwin を分ける例は無く (pr-teeth の入口でブラウザを開く処理だけ)、テストを skip する例も無い。環境の違いは、偽の実行ファイルと、実物から取った固定データで吸収する形が確立している。disk-usage-triage では `du`・`docker`・`asdf` を偽のコマンドにし、macOS で取った出力を固定データにする形が、この既存の形に合う。GNU の du (CI) と BSD の du (macOS) は `-k -d 1` の標準出力の形 (`<KiB>\t<パス>`) は同じだが、エラーの文言が違う。実物の du をテストで実行させないこと
  
  #### 4. 利用者ごとの記録 (ファイル `gh-notification-dispatch/scripts/gh_notification_dispatch/store.py`)
  
  - 定数 `DEFAULT_HOME = ~/.claude/gh-notification-dispatch`。環境変数 `GH_NOTIFICATION_DISPATCH_HOME` があればその場所 (テスト用) で、関数 `home()` が `abspath(expanduser(...))` を返す。今の時刻も環境変数 `*_NOW` で差し替える

  ### 計画に効く発見 (scope の外を含む。決めたことと合わない可能性があるもの)
  
  1. **worktree の削除で、承認のカードが出ないことがある。** ツール `mcp__ccd_host__clean_up_worktrees` の説明 (スキーマを読み込んで確認) に「in auto mode the app may decide a plain cleanup itself」とある。権限モード auto では、`include_uncommitted` と `delete_sessions` を付けない削除を、カードを出さずにアプリが決めうる。決めたこと「アプリの承認のカードで利用者が承認してから削除する」は、auto のセッションでは保証されない。引数は `older_than_days` (30・60・90 のどれか。必須) だけで、worktree を 1 つずつ指定できない。アーカイブしたときに残された worktree は、別のツール `mcp__ccd_host__discard_kept_worktree` (`session_id` を指定。どの権限モードでもカードが出る) の対象。要望 5 の手順と U1 の実測の項目に入れる必要がある
  2. **asdf の参照は、設定したディレクトリの外にもある。** このマシンにはファイル `~/.tool-versions` (グローバルの版。nodejs・golang・ruby・awscli・python・gcloud・terraform・yq) がある。設定したディレクトリ (例: `~/workspace`) の下だけを探すと、グローバルの版が「参照されていない」と判定され、「消してよい」の候補になる。`~/.tool-versions` を必ず参照に含める規則が要る (asdf 0.20.2、`ASDF_DATA_DIR` は未設定)
  3. **スクリプトを実行する `python3` 自身が asdf の版でありうる。** このマシンの `python3` は asdf の shim (`~/.asdf/shims/python3`。3.13.3) で、`/usr/bin/python3` は 3.9.6。asdf の python の版を消すと、このプラグインのスクリプトが実行できなくなりうる。セッションの作業ディレクトリの `.tool-versions` が、入っていない python の版を指していても、shim は失敗する (前例: review-triage の記録に「`.tool-versions` が 1.25.4 を指すが未インストール」)
  4. **macOS の `du` は、読めないディレクトリがあると終了コード 1 になり、それでも標準出力に結果を出す。** 標準エラー出力の形は `du: <パス>: Operation not permitted`。gh.py の形をコピーするとき、終了コードが 0 でないことを失敗とする判定は使えない。部分的な結果と読めなかったパスを分けて返す設計と、macOS で取った固定データが要る
  5. **端末のツールで実行すると、Claude が削除を実行したことになる。** review-loop の前例は `run_in_terminal` で起動するかを質問するが、決めたこと「Claude は削除のコマンドを実行しない」と合わない。シェルスクリプトは、案内 (絶対パスのコマンド) を示すだけにする、と計画に明記する必要がある。スクリプトは `${CLAUDE_PLUGIN_ROOT}` に頼らず、プラグインのファイルを呼ばない自己完結の形にする (プラグインを更新すると古い版のディレクトリが消えるため)

  ## 2. Docker Desktop for Mac
  
  ### 2.1 Docker.raw の `ls` と `du`、ディスクイメージの形式
  
  - Docker.raw は疎なファイル (sparse file。書き込んでいない範囲にディスクのブロックを割り当てないファイル) で、`ls` は上限の大きさ (論理サイズ) を、`du` と `ls -s` は実際に割り当てられた量を示す。FAQ には、多くのツールが上限の大きさを表示すると書かれ、`ls -klsh Docker.raw` の例が載っている。実際の使用量は、Docker Desktop の Settings > Resources > Advanced にも表示される [公式] https://docs.docker.com/desktop/troubleshoot-and-support/faqs/macfaqs/
  - 4.42.0 で、新規インストールとデフォルト値へのリセットのとき、ディスクの上限を物理ディスクの大きさにするよう変わった (4.37.0 では 1 TB)。観察の 494 GB はこの上限と考えられる [公式] https://docs.docker.com/desktop/release-notes/
  - 形式: Docker Desktop の release notes (ファイル `content/manuals/desktop/release-notes.md` の全体) を検索したが、ASIF への言及は無かった。macOS で使うのは raw (Docker.raw) で、qcow2 は HyperKit の時代の形式。ASIF は macOS 26 で入った、VM 向けのディスクイメージの形式 [コミュニティ] https://eclecticlight.co/2025/06/12/macos-tahoe-brings-a-new-disk-image-format/ 。4.100.0 (2026-11-19) に、新規の Docker VMM のインストールで疎な raw 形式のファイル `DockerDesktop.raw` を使うという記述があるが、VHDX を置き換えると書かれているので Windows 向けと読める [公式]
  - VMM (仮想マシンを動かすしくみ) は、4.44 で Apple Virtualization framework が既定になり、QEMU は削除された。Docker VMM は、4.86 以降 Docker が自前で実装したもの (4.35〜4.85 は libkrun) [公式] https://docs.docker.com/desktop/features/vmm/ 。VirtioFS はホストとのファイル共有 (bind mount) の方式で、Docker.raw が縮むかどうかとは別の話。
  
  ### 2.2 消したとき Docker.raw の `du` が減るか・いつ減るか
  
  しくみ: VM の中のファイルシステムでブロックが空く → ゲストが TRIM を出す → Virtualization framework が、ホストのファイルのその範囲の割り当てを解放する。
  
  - Apple の技術者による回答 (2023 年 10 月): Virtualization framework は、ゲストが TRIM・unmap を出せばファイルを疎なまま保ち、設定は要らない [公式] https://developer.apple.com/forums/thread/739477
  - Docker の FAQ の要約 [公式]:
    - prune の後、ホストに領域が戻るまで数分かかることがある。
    - 自動で領域が空くのは image を消したとき。実行中のコンテナの中でファイルを消しても、自動では空かない。
    - いつでも領域を戻せるコマンドとして、`docker run --privileged --pid=host docker/desktop-reclaim-space` がある。
  - 経緯 [Issue] https://github.com/docker/for-mac/issues/371 : 2019 年 (HyperKit の時代)、Docker の開発者が次のように説明していた。fstrim は image を消した後に実行し、ボリュームを消した後には実行しない。raw 形式なら fstrim の結果はすぐに反映される。この Issue は 4.20.0 で閉じられ、release notes には「コンテナの中で消したファイルの領域を、より早く戻せるようにした」とある。どう実現したかは文書に無い。
  - **計画への含意 [推測]:** ボリュームを消しただけでは Docker.raw の `du` が減らない可能性がある。今の版でも減らないかは公式文書で確かめられなかったので、削除の後に TRIM を明示的に実行し、前後の `du` を比べるのが確実。
  - 版に関わる修正 [公式]:
    - Docker VMM で、ディスクの領域を戻すときにディスクが壊れる不具合を 4.44.0 で直した。
    - 共有フォルダのファイルを何度も置き換えると VM のディスク領域が増え続け、再起動するまで戻らない不具合を 4.90.0 で直した。
  
  ### 2.3 減らないときの手段 (上から順に)
  
  1. **公式の TRIM の image を使う。** image の設定を Docker Hub から読むと、エントリポイントは `/usr/bin/nsenter1 /sbin/fstrim /var/lib/docker`、対応するのは amd64 だけ、最終更新は 2019-09-27 だった [ソース]。Apple silicon では Rosetta かエミュレーションで動く。Docker VMM は Rosetta に対応していない [公式 vmm]。FAQ のコマンドには `--rm` が無いので、そのままでは停止したコンテナが 1 つ残る。スクリプトには `--rm` を付ける [推測]。
     - arm64 で同じことをするなら、この image の元になっている `justincormack/nsenter1` (amd64 と arm64 がある) で、`docker run --rm --privileged --pid=host justincormack/nsenter1 /sbin/fstrim /var/lib/docker` を実行する方法がある。公式文書には無い [推測・未検証]。
  2. **Docker Desktop を再起動する** (4.90.0 の不具合の記述から [推測])。
  3. **VM の中の使用量を確かめる** [推測・未検証]: `docker run --rm --privileged --pid=host --entrypoint /usr/bin/nsenter1 docker/desktop-reclaim-space /bin/df -k /var/lib/docker` 。ホストの `du` が VM の中の使用量より大きければ、その差は TRIM で戻せる見込みがある。
  4. **ディスクの上限を下げる (Settings > Resources > Advanced)。** ディスクイメージを作り直すので、すべてのコンテナと image が失われる [公式]。判定表では「残す」にし、利用者が自分で判断するものとして扱う。
  
  ### 2.4 `docker system df` の合計が Docker.raw の `du` より大きくなる理由
  
  | 理由 | 根拠 | 観察への当てはめ |
  |---|---|---|
  | ボリュームの SIZE は見かけのサイズ (ファイルの st_size の合計)。疎なファイルは割り当て済みの量より大きく数える。同じボリュームの中のハードリンクは 1 回だけ数える | [ソース] moby のファイル `daemon/internal/directory/directory_unix.go` は `fileInfo.Size()` を足している。`docker volume prune` が表示する解放量も同じ関数で計算している | 174.5 GB が過大である主な候補 [推測] |
  | build cache のうち image と共有しているレコード (Shared) は、Images と Build Cache の両方に数えられる | [ソース] moby のファイル `daemon/internal/builder-next/builder.go` の Reclaimable は、InUse と Shared を除いて足している | 12.11 GB と 6.032 GB の差 (約 6 GB) は、使用中か共有のレコード。二重に数えられているのは最大でこの分 |
  | image の層の共有 | [ソース] Images の行の SIZE は、層を重複なく数えた値 (`ImageDiskUsage`)。[公式] `-v` の image ごとの SIZE は、SHARED SIZE と UNIQUE SIZE の和 | 行の合計は二重にならない。`-v` の image ごとの SIZE を足すと二重になる |
  | containerd の image store は、圧縮した層と展開した層の両方を保存する | [公式] https://docs.docker.com/engine/storage/containerd/ 。[ソース] 1 つの image の SIZE は content と展開した snapshot の和 | 実際に両方とも使っているので、過大ではない。4.34 以降の新規インストールでは既定で有効 |

  - TRIM されていない空きブロック。
  - コンテナのログ [推測]。
  
  ### 2.5 `docker system df -v` と `--format`
  
  - `--format json` (`-v` なし) は、1 行に 1 つの JSON を出す。キーは Type・TotalCount・Active・Size・Reclaimable で、値は人が読む形の文字列 [公式] https://docs.docker.com/reference/cli/docker/system/df/
  - `-v` は 4 つの表を出す。Images (SIZE・SHARED SIZE・UNIQUE SIZE・CONTAINERS)、Containers、Local Volumes (NAME・LINKS・SIZE)、Build cache (CACHE ID・CACHE TYPE・SIZE・CREATED・LAST USED・USAGE・SHARED)。
    - LINKS は RefCount、つまりそのボリュームを参照しているコンテナの数で、停止中のコンテナも数える。local 以外のドライバのボリュームと、マウントオプション付きのボリュームは N/A になる [ソース]。
  - `-v --format json`: 公式のリファレンスには「`-v` のときは `--format` が効かない」とある。しかし CLI は、2018 年のコミット (docker/cli `a90b99edf` 「system/df: allow -v with --format」) から両方の指定を受け付けており、現在のコードでは `{"Images":[…],"Containers":[…],"Volumes":[…],"BuildCache":[…]}` という 1 つの JSON を出す [ソース・未実行]。対象の版で一度確かめる必要がある。各要素のキーは次のとおり。
    - Volumes: Name・Driver・Scope・Mountpoint・Labels・Links・Size・Group・Availability・Status
    - BuildCache: ID・Parent・CacheType・Description・Size・CreatedAt・CreatedSince・LastUsedAt・LastUsedSince・UsageCount・InUse・Shared
    - Images: ID・Repository・Tag・Digest・CreatedAt・CreatedSince・Size・Containers・SharedSize・UniqueSize
  - 大きさは 10 進の単位の、人が読む形の文字列 (例: `19.52GB`) [ソース: go-units の HumanSize]。バイト単位の値が要るなら、Engine API の `GET /system/df` が返す `UsageData.Size` (バイト単位。取れないときは -1) を使う [ソース]。
  
  ### 2.6 匿名ボリュームの見分け方
  
  - 匿名ボリュームは、名前を指定せずに作られたボリューム (Dockerfile の `VOLUME` や `-v /path` から作られるもの)。Engine は作成時にラベル `com.docker.volume.anonymous` を付ける [ソース] moby のファイル `daemon/volume/service/service.go`。このラベルは公式文書には書かれていない。
  - 23.0.0 で、API 1.42 以上の `docker volume prune` は匿名ボリュームだけを消すように変わった。23.0.2 で、Dockerfile の `VOLUME` から作ったボリュームが prune から漏れる不具合を直した [公式] https://docs.docker.com/engine/release-notes/23.0/ 。したがって、古い Engine で作ったボリュームにはラベルが無いことがある [推測]。また、古い API の版で呼ぶと、従来どおり名前付きのボリュームも消す (moby の PR #44216 の議論) [Issue]。
  - 一覧を出すコマンドは `docker volume ls -q --filter dangling=true --filter label=com.docker.volume.anonymous`。`dangling` は、どのコンテナからも参照されていないものに一致する [公式] https://docs.docker.com/reference/cli/docker/volume/ls/
  - ラベルが無く、名前が 64 桁の 16 進数のボリュームは「確認が要る」にする。消すときは、prune ではなく `docker volume rm <名前…>` で名前を並べると、消す範囲が計画に書いたとおりになる。使用中のボリュームは `docker volume rm` でも消せない [公式]。
  
  ### 2.7 Docker の削除のコマンド
  
  | コマンド | 何を消すか | 使われているものを消さない保証 | 消した後の影響 |
  |---|---|---|---|
  | `docker container prune` | 停止したコンテナすべて (書き込み可能な層を含む) | あり。実行中のコンテナは消さない | コンテナの中で変えたファイルが失われる。そのコンテナの匿名ボリュームは、参照されていない状態になる |
  | `docker volume prune` (API 1.42 以上) | 参照されていない、local ドライバの、匿名のラベルを持つボリューム | あり。停止中を含め、コンテナが参照しているものは消さない。マウントオプション付きのものも対象外 [ソース] | 中のデータは戻せない。データベースの匿名ボリュームなら、そのデータが消える |
  | `docker volume prune -a` | 上に加えて、参照されていない名前付きボリューム | 同上 | compose で down したプロジェクトのデータベースなども消える |
  | `docker volume rm <名前>` | 指定したボリューム | あり。使用中は消せない [公式] | 同上 |
  | `docker image prune` | dangling (タグの無い) image | あり | ほとんど無い |
  | `docker image prune -a` | どのコンテナ (停止中を含む) からも参照されていない image すべて [公式] | あり | 次の run・build・compose up で pull か build をやり直す。オフラインでは取り直せない |

  ## 4. macOS (BSD) の `du` の注意点
  
  - `-d <深さ>`: 指定した深さまでの項目を表示する。`-k`: 1024 バイト単位で表示する。指定しないと 512 バイト単位になる (環境変数 `BLOCKSIZE` があればその単位)。`-h` の出力は数値で並べ替えにくいので、`-k` の出力を `sort -n` で並べる。`-x`: マウントポイントの先を辿らない (`/Volumes` の外部ディスク、ネットワークのボリューム、マウントしたディスクイメージを除ける)。`-A`: 見かけのサイズを表示する。`du -A` と `du` を比べると疎なファイルを見つけられる。`-A` は手元の macOS 27.2 の man にあるが、古い macOS にあるかは確かめていない [公式] `man du`
  - ハードリンクで複数の場所から参照されるファイルは、1 回の `du` の実行で 1 回だけ数える [公式 man]。このため `du -d 1` では、先に辿った子ディレクトリだけにその大きさが入る。その子ディレクトリだけを消しても、ほかのリンクが残っていれば領域は空かない。`-l` を付けると、リンクごとに数える。
  - APFS のクローンは、ファイルごとに全体の大きさで数えられる。ブロックの共有は考慮されないので、`du` は実際より大きく出る。1 つのクローンを消して空くのは、そのクローンだけが持つブロックだけ [コミュニティ] https://eclecticlight.co/2025/05/13/how-to-tell-the-difference-between-copies-clone-files-and-hard-links/ 、https://eclecticlight.co/2022/12/30/free-space-on-an-apfs-volume-is-an-illusion/ 。pnpm と uv は、macOS では既定でクローンを使う (3)。
  - Time Machine のローカルスナップショット: 消したファイルのブロックはスナップショットが持ち続ける。スナップショットは、領域が要るときか 24 時間を過ぎたときに自動で消され、その分は空き容量として数えられる [公式] https://support.apple.com/102154 。削除の後、すぐに空き容量が増えないことがある。確かめるコマンドは `tmutil listlocalsnapshots /`。
  - TCC:
    - デスクトップ・書類・ダウンロード・iCloud Drive・ネットワークのボリューム・リムーバブルボリュームは、アクセスに同意が要る [公式] https://support.apple.com/guide/security/protecting-app-access-to-user-data-secddd1d86a6/web 。フルディスクアクセスは、ほかのアプリのデータを含むすべてのファイルへのアクセスを許可する [公式] https://support.apple.com/guide/mac-help/change-privacy-security-settings-on-mac-mchl211c911f/mac
    - 許可が無いと、`du` は `Operation not permitted` を表示して続きを辿る。表示される合計は、そのディレクトリの分だけ小さくなる。同意を求めるダイアログは、ターミナルや Claude のアプリなど、`du` を起動したアプリに対して出る。
  - `~/Library/Containers` と `~/Library/Group Containers`: macOS 14 以降、ほかのアプリのコンテナにアクセスすると同意を求められる。同意はプロセスが終わるまでしか続かない [公式: Apple の DTS] https://developer.apple.com/forums/thread/742147 。辿る途中で `open()` が止まったまま戻らない事例があり、DTS は当面これらのディレクトリを辿らないよう回答している [公式: Apple の DTS] https://developer.apple.com/forums/thread/740204
  - 時間がかかるディレクトリ: 上の 2 つのディレクトリ、`node_modules` が多いディレクトリ、`~/Library/Developer` (CoreSimulator・DerivedData)、モジュールキャッシュ、`~/.asdf/installs` など、ファイルが多い場所。時間の上限を付けるなら、`timeout` コマンドがあるかを `command -v timeout` で確かめてから使う (手元の macOS 27.2 には `/usr/bin/timeout` があるが、どの版から入ったかは確かめていない)。

  ```mermaid
    A -- ある --> P{"比較していない前回の<br/>スクリプトがあるか (足す案)"}
    A1 --> M
    P -- ある --> C[比較を先に行うか質問]
    P -- 無い --> M[調査: du -d 1・Docker・asdf]
    C --> K
    M --> L[一覧と判定を示す<br/>判定表・記録・Claude の調査]
    L --> D{利用者の操作}
    D -- 下の階層 --> M
    D -- 決めたことを記録 --> R[記録に保存] --> L
    D -- 番号で選ぶ --> X{削除の方法}
    X -- アプリの worktree --> W[clean_up_worktrees を呼ぶ<br/>承認のカード]
    X -- それ以外 --> G[シェルスクリプトを作る]
    X -- 消せない (保護) --> L
    G --> U[利用者が端末で実行]
    U --> K[比較: 測り直す]
    W --> K
  ```
  
  各段の流れを次の 1〜12 に分ける。表記は「入口 / 分岐 / 終わり方」。【】は、下の節「Gaps」の番号。
  
  1. **初回の設定**
     - 入口: 引数も設定も無い状態での起動
     - 分岐: 候補をどう示すか、引数で渡したディレクトリを保存するか、指定したディレクトリが無い・相対パス・重なっている・シンボリックリンク・外部のボリュームである
     - 終わり方: 保存する、または取りやめる
     - 【M2・M3】
  2. **調査 (一覧)**
     - 分岐: 次の場合の扱い
       - TCC (macOS のプライバシーの保護) で読めないディレクトリがある (du の終了コードが 1)
       - `~/Library/Containers` のように辿ると止まる場所がある
       - 時間の上限を越える
       - 直下のファイル (Docker.raw・*.dmg) が `du -d 1` の一覧に出ない
       - Docker Desktop が起動していない
     - 終わり方: 一覧を示す、一部を測れなかったと示す、エラーで止める
     - 【I2・I3】
  3. **下の階層**
     - 分岐: どの項目へ入るか
       - ファイルシステムの階層
       - 仮想の階層 (Docker の種類と compose のプロジェクト、asdf のツールと版)
       - 前の一覧へ戻る
     - 前の一覧の番号は、新しい一覧を示した後も使えるか
     - 【I1・C3】
  4. **判定**
     - 判定の元: 判定表・記録・Claude の調査
     - 分岐: 判定の元どうしが矛盾する場合と、同じものが 2 つの一覧に出る場合 (Docker.raw と Docker の中身、`.claude/worktrees` と worktree のツール)
     - 消すコマンドがディレクトリの外にも作用する場合: brew cleanup が古い版の formula も消す、など
     - 【C2・C6・I5・I7】
  5. **記録**
     - 契機: 利用者が言ったときか、こちらから質問するときか
     - 決めておくこと: キー、子への適用、期限、一覧と削除の手段、壊れていたときの扱い
     - 【C6・I8】
  6. **選択**
     - 分岐: 番号で選ぶ、「消してよい」をまとめて選ぶ、親と子を両方選ぶ、保護しているものを含む親を選ぶ
     - 【I1・C2・C3】
  7. **シェルスクリプトの作成**
     - 決めておくこと: 引用符の扱い、シンボリックリンク、実行時に状態を確かめ直すか、失敗したときの方針、1,143 件の項目を利用者が読み通せる形にすること
     - 【C4】
  8. **利用者の実行**
     - 分岐: 一部だけ実行した、Ctrl-C で止めた、編集してから実行した、2 回実行した、sudo で実行した、ツールが PATH に無い、asdf の shim が版を決められない、アプリが起動中
     - 【C4・C5・I6・I11】
  9. **比較 (同じセッション)**
     - 確かめること: 終わったことをどう知るか
     - 見込みと実際の差の説明: Docker.raw が減らない、スナップショット、クローン、アプリが書き戻すキャッシュ、量の見込みが立たないツールのコマンド
     - 【C5・I5】
  10. **worktree**
      - 分岐
        - Desktop のセッションか (CLI のセッションでは扱えない)
        - auto モードで承認のカードが出ない
        - 1 つずつ選べない
        - アーカイブで残されたもの
        - アプリが作っていない worktree
        - 開いているセッションは対象にならない
      - 【C1・I9】
  11. **2 回目以降の実行**
      - 状態: 実行していない前回のスクリプトがある、記録したパスが無くなった、プラグインの更新で判定表が変わった、2 つのセッションで同時に実行した
      - 【I8】
  12. **別のセッションからの比較**
      - 決めておくこと: どの実行と比べるか、前回の測定をどこに残すか、worktree の結果を残すか
      - そのセッションが CLI で、ツール `mcp__ccd_host__*` を使えない場合と、作業ディレクトリが違い、asdf の python の版が変わる場合
      - 【I10・I11】
  
  ## Gaps
  
  ### Critical (実装を始められないもの、データを失いうるもの)
  
  **C1. 権限モード auto では、承認のカードが出ないことがある**
  - 問題: 要望 5 は「アプリが承認のカードを出し、利用者が承認してから削除」を前提にしている。しかしツールの説明では、auto モードでアプリがカードを出さずに決めることがある。利用者は普段 auto を使っている。
  - 対象が事前に分からない: 何が消えるかはアプリがその場で決めるので、スキルは事前に示せない。
  - 要件の案: 呼ぶ前に、`get_storage_usage` (アイドルで消せるもの) から見込みを示し、チャットで明示の同意を得る。`include_uncommitted` と `delete_sessions` は使わない。
  
  **C2. シェルスクリプトに入れてはいけないもの (保護の一覧) が決まっていない**
  - `du` の一覧で最も大きいのは `~/Library/Containers/com.docker.docker` (116 GB) なので、利用者が選びうる。
  - 次のものを選んだら、`rm` で消すと実害が出る。
    - Docker.raw: Docker の中身がすべて消える
    - `~/Library/Application Support/Claude`: ツールの説明が、アプリのデータのフォルダを消すことを禁じている
    - `~/.claude` の下: 会話の記録・プラグイン・このプラグインの記録
    - 実行中のプラグインと、それを動かしている python の版
    - 今のセッションの作業ディレクトリ
    - `~/Library/Mobile Documents` と `~/Library/CloudStorage`: 消すと、クラウドの同期で他の端末からも消える
    - アプリの worktree と、それを含む親 (リポジトリそのもの、`.claude/worktrees`)
    - 設定したディレクトリそのものと `$HOME`
  - 記録で「消してよい」になっていても、保護を優先する必要がある。
  
  **C3. 選んだ項目と、削除の単位の対応が決まっていない**
  - 項目ごとに「削除の方法」(rm・ツールのコマンド・アプリのツール・消せない) を持たせる必要がある。
  - 例 1: `~/.asdf/installs/nodejs` を選んだら、版ごとの `asdf uninstall` に分け、参照されている版を除く。
  - 例 2: CoreSimulator は `xcrun simctl` で消す。
  - 親と子を両方選んだときに重複を除くこと、仮想の階層 (Docker・asdf) の項目の扱いも決める。
  
  **C4. 生成するシェルスクリプトの安全性**
  - パスの引用符 (`shlex.quote`) の扱い。
  - 末尾にスラッシュを付けない。シンボリックリンクを判定する。`~` を使わず絶対パスで書く。root で実行されたら止める。
  - 作ってから実行するまでに状態が変わることへの備え (作成と実行の時間差で状態が変わる問題で、TOCTOU とも呼ばれる)。
    - Docker は、調べた時点の ID だけを消す。`docker volume prune` のように実行時の状態で選ぶコマンドは使わない
    - ボリュームが使われていないこと・パスが在ることを、実行時に確かめ直す
  - 1 件が失敗したときに止めるか、続けるか。
  - 失敗の原因になりうるもの: 読み取り専用のファイル、端末のアプリにフルディスクアクセスが無いときの `Operation not permitted`。
  - 1,143 件を 1 行ずつ並べると、利用者は確認しきれない。先頭に要約を置き、データの部分を分ける必要がある。
  
  **C5. 実行の結果を残す仕組みが無い**
  - 比較 (流れ 9・12) では、次の状態を区別する必要がある: 実行していない、途中で止めた、項目が失敗した、消したのに空き容量に表れない。
  - 要件の案: スクリプトが、開始と終了の記録と項目ごとの結果を `~/.claude/disk-usage-triage/runs/<ID>/` に書く。Ctrl-C で止めたときも、trap で書く。
  - 端末の表示は、確実な情報源にしない。
  
  **C6. 記録 (利用者が決めたこと) のキーと適用範囲が決まっていない**
  - キーの候補と注意点
    - パス: `~` で書くか実パスにするか、シンボリックリンクを解決するか
    - パターン: 例えば `~/workspace/**/node_modules`
    - Docker: 匿名ボリュームの名前は毎回変わる。名前付きボリュームの名前か、compose のプロジェクト名にする
    - asdf: (ツール, 版)
  - 「残す」を子にも適用するか。判定表の版が変わったときに、記録を優先するか。期限を設けるか。
  - 壊れた記録は、上書きせずに止める (fail-soft-by-data-class の蓄積データの扱い)。
  - テストの期待値を書くには、この点を先に決める必要がある。
  
  **C7. asdf の参照を探すディレクトリが、調べるディレクトリと同じかどうかが曖昧**
  - 調べるディレクトリ (`~/.asdf`・`~/Library/Caches`) には、プロジェクトが無い。そのため、`.tool-versions` を探す範囲を別の設定にしないと、`~/.tool-versions` 以外のすべての版が「消してよい」になる。
  - 調べる範囲に入っていないプロジェクトの版を消すと、そのプロジェクトで、このマーケットプレイスの python の hook (commit-rules-guard など) が失敗する。
  - 参照の取り出しで決めること
    - 1 行に複数の版がある書き方と、`system`・`ref:`・`path:`
    - 環境変数 `ASDF_DATA_DIR`・`ASDF_DEFAULT_TOOL_VERSIONS_FILENAME`・`ASDF_<TOOL>_VERSION`
    - 他の版のファイル (`.nvmrc`・`.python-version` など)。ファイル `~/.asdfrc` の設定で読むようになる
  
  ### Important (使い勝手を大きく左右するもの、実装者ごとに解釈が分かれるもの)
  
  **I1. 選択の方法**
  - AskUserQuestion は選択肢の数に上限がある (1 つの問に 4 つ程度。上限の値は確かめる必要がある)。そのため、30 件の一覧からは選べない。
  - 番号で選ぶ形にするなら、gh-notification-dispatch のように、番号と項目の対応をスナップショットに保存する。
  - 下の階層の一覧を示した後に、前の一覧の番号が使えるかを決める。
  
  **I2. 調査にかかる時間と、測れなかったときの表示**
  - Bash ツールの時間の上限は、既定で 2 分・最大で 10 分。
  - 測れなかったときの表示: TCC で読めないものがあるときは「X 以上」と示す。
  - `~/Library/Containers` を辿らないなら、Docker.raw だけを `stat` で測る。
  - `-x` を付けて、別のボリュームに入らないようにするか。
  - 直下の大きなファイルは、`du -d 1` の一覧に出ない。
  
  **I3. 出力の大きさ**
  - 1 回の出力は約 30 KB まで。詳細はファイルに書き、会話には要約を出す。
  - 一覧は上位の N 件と「その他」にまとめる。
  - Docker のボリュームは、匿名か名前付きか・compose のプロジェクトでまとめる。
  
  **I4. Docker の判定の材料**
  - コンテナが 0 個なので、名前付きボリューム (DB のデータを含みうる) も含めて、すべてが dangling になる。dangling だけでは消してよいと判定できない。
  - compose のラベル (`com.docker.compose.project`) を、今ある worktree やリポジトリの名前と照らす案がある。ボリュームにこのラベルが付くかは、確かめる必要がある。
  - ローカルでビルドした image は、取得し直せない。
  - 次の場合の扱いが要る: Docker Desktop が起動していない、docker の context が Docker Desktop ではない、`docker system df -v` が遅い。
  - 先に worktree を消すと、そのプロジェクトのボリュームは使われなくなる。そのため、worktree と Docker のどちらを先に扱うかで判定が変わる。
  
  **I5. 空いた量の示し方**
  - 次の値を並べて示す必要がある。
    - 見込み (du の合計)
    - 実際の空き容量の差 (statvfs で測る。Finder の「利用可能」とは値が違う)
    - Docker の中の量 (`docker system df`) と、Docker.raw の du
  - 差が出る理由を説明する: TRIM、スナップショット、ハードリンクとクローン、アプリが書き戻すキャッシュ。
  - ツールのコマンドの扱い
    - `brew cleanup`・`pnpm store prune` は、空く量を事前に見込めない
    - 選んだディレクトリの外にも作用する
    - 作用する場所が、端末の環境変数 (`GOCACHE`・`HOMEBREW_CACHE`・`UV_CACHE_DIR`) で変わりうる。スクリプトは実行時に、その場所が調べたパスと同じかを確かめる (例: `go env GOCACHE`)
  - 判定に「元に戻す方法」(入れ直すコマンド、取得し直しにかかる時間) を添えると、利用者が判断しやすい。
  
  **I6. 起動中のアプリのキャッシュ**
  - Chrome・Slack・VS Code が起動中だと、キャッシュを消してもすぐに書き戻され、アプリの動作も乱れうる。
  - 判定表に「終了してから消す」という条件を持たせ、スクリプトが実行時に確かめる (例: `pgrep`)。
  
  **I7. Claude が調べる範囲**
  - どこまで読むか (ファイル名だけか)、Web 検索を使うか (ディレクトリ名にプロジェクト名が含まれうる) を決める。
  - 調べる件数の上限 (大きさの下限) を決める。
  - Claude の判定を、利用者が決めたことと分けて残すか。残すなら、いつ調べ直すかも決める。
  - sub-agent からは AskUserQuestion を使えない。調べる作業を sub-agent に任せるなら、質問はメインのセッションに戻す。
  
  **I8. 2 回目以降の状態**
  - 実行していない前回のスクリプトがあったときの扱い。
  - 記録したパスが無くなったときの扱い。
  - プラグインの更新で判定表が変わり、記録と矛盾したときの示し方。
  - 2 つのセッションが同時に記録を書くときのロック。
  - 記録の一覧を見る手段と、記録を消す手段。
  
  **I9. worktree を 1 つずつ消せない**
  - 利用者が `du` の一覧で特定の worktree を選んでも、`clean_up_worktrees` では消せない。このツールは最後に使った日からの日数でまとめて消す。
  - アーカイブで残された worktree は、`discard_kept_worktree` で 1 つずつ消せる。
  - アプリが作っていない git worktree は、`rm -rf` で消すと `.git/worktrees/` の情報が残る。`git worktree remove` で消す必要がある。
  - `get_storage_usage` の行と `du` のパスを対応づける方法が要る。Claude が結果をスクリプトに渡すので、型で検証する。
  - 開いているセッションは対象にならない。そのため、カードの件数が利用者の予想より少ないことがある。
  - CLI と SSH のセッションでの扱い。
  - 片付けた後は、`refresh: true` を付けて測り直す。
  
  **I10. 別のセッションからの比較**
  - 実行の ID の選び方。
  - 前回の測定を残す場所。
  - worktree の削除の結果を残すか (アプリのツールの結果は、そのセッションにしか無い)。
  - 何日も後に比べると、ほかの作業による増減が入る。
  
  **I11. Python の起動**
  - `python3` は asdf の shim なので、カレントディレクトリの `.tool-versions` で版が決まる。3.11 未満を指定したプロジェクトで起動すると失敗する。そのときは、はっきりしたエラーを出す (CLAUDE.md の方針で、別の手段への切り替えはしない)。
  - 生成したシェルスクリプトは python を使わない。
  - shim 経由のコマンドには、版の指定 (`cd` か環境変数) を付ける。
  - 実行の案内
    - 利用者に頼む実行のコマンドを、そのターンの最後の返答に書く
    - Claude が `run_in_terminal` でスクリプトを実行しないことを、スキルの手順に書く

  ## Questions
  
  重要な順に並べた。「デフォルト」は、利用者が答えなかったときに置く案。
  
  1. **権限モード auto のときの worktree の削除の確認** (C1)
     - 問: 権限モード auto ではアプリが承認のカードを出さないことがある。ツールを呼ぶ前に、チャットで見込み (対象の worktree と量) を示して同意を得る形でよいか。それとも、権限モードを変えるよう案内するか。
     - 影響: 確認しないまま worktree が消えうる。
     - デフォルト: チャットで明示の同意を得てから呼ぶ。`include_uncommitted` と `delete_sessions` は付けない。
  2. **一覧で選んだ worktree の扱い** (I9)
