  # 実装計画のセキュリティレビュー (security-sentinel の観点)
  
  対象: `docs/plans/2026-09-27-1431-feat-review-loop-sandbox-plan.md`。脅威モデルは「auto モードの LLM (レビュアの実行) は判定が許せば任意のコマンドを実行できる」で、それが作業側の作業ツリー・ホームの下・周回の置き場・ワーカー自身の振る舞いに影響できる経路のうち、計画が扱っていないものを重要度順に挙げる。根拠は Claude Code の公式文書 (2026-09-27 確認、現行 2.1.283)・リポジトリのファイル・git の仕様。KTD/R/U/AE の番号で「どこをどう直すべきか」を示す。コードやシェルのコマンドは書かない。
  
  ## 総評
  
  計画は #68 の実測を踏まえてよく作り込まれている。使い捨ての複製・auto+サンドボックス・拒否の規則・ログからの判定という骨格は妥当。決定済み (案 1、Linux 対象外、サンドボックスが止めた確認も RA1、ネットワークは U1 で調べる) を覆す証拠は見つからなかった。以下は決定の中で残る、あるいは計画が触れていない脅威経路と、その対処。**推測** は明記する。

  ## 質問 1: 計画が扱っていない影響経路
  
  ### [重要度 高] 1. auto モードは広い許可規則を落とすので、`--allowedTools` に足す git 読み取り以外の実行系は auto では機能しない可能性が高い (根拠: 文書、確度=高い推測)
  
  公式文書 permission-modes「How the classifier evaluates actions」に、**auto モードに入ると「任意コード実行を許す広い許可規則は落とされる」** とある。落ちるのは `Bash(*)`・ワイルドカードのインタプリタ (`Bash(python*)`)・パッケージマネージャの run コマンド・`Agent` の許可規則・`Monitor` の許可規則。残るのは `Bash(npm test)` のような狭い規則だけ。
  
  - これは計画の前提を 2 か所で崩す:
    - **KTD5・R8「許可の一覧の既定 (読み取りのツール) は変えない」**: 既定の一覧には `Agent` (KTD5 で残す前提) が入っている (`review-loop-worker.sh` 33〜49 行目)。auto モードでは `Agent` の許可規則は落ちるので、レビュアが sub-agent を起動する呼び出しは許可規則では通らず、classifier 判定を通る (通常は許可されるが、許可規則で保証されない)。
    - **利用者設定の `Bash(python3:*)`・`Bash(go:*)` など (実測済み、`~/.claude/settings.json` に多数存在)**: #68 のコメントは「auto モードでは一覧に無い呼び出しも判定が許す」と書くが、その通り道は「許可規則」ではなく「classifier 判定」。KTD5 の依存の記述が「許可の一覧で通す」ように読めると、実装者が誤解する。
  - **対処**: **U1 に検証項目を足す** (KTD5・R8 の前提)。auto モードで `Agent`・インタプリタ系の許可規則が落ちることを確かめ、レビュアの実行が確認 (テスト実行) と sub-agent 起動を「classifier 判定に依存して」行うことを Dependencies/Assumptions に明記する。**worker.md の「レビュアの実行の権限」**に、auto では許可の一覧は「classifier に回す前の即決」の役割しか持たず、実行の可否は classifier が決める、と書く。この違いは、後述の repeated-block (質問 2 の一部) と RA1 の頻度 (#65) の予測に直結する。
  
  ### [重要度 高] 2. 複製の `.git` 経由でワーカーの後始末の git 実行を乗っ取る経路が、計画では「複製の中で git を実行しない」に一点依存していて、その不変条件の破れが検出されない (根拠: git 仕様・plan 85/214/374 行目)
  
  計画は R5・KTD8 手順 5・AE12 で「レビュアの実行の後は複製の中で git を実行しない」ことを不変条件にし、`core.fsmonitor` の実行を防ぐとしている。方向は正しいが、次が抜けている:
  
  - **サンドボックスは複製の `.git/config`・`.git/hooks` への書き込みを止めない**。公式文書 sandboxing「Protected paths」の保護は「作業ディレクトリとその上位」および「作業ディレクトリを bare リポジトリにするファイル (トップレベルの `HEAD`・`objects`・`refs`、および `HEAD` の隣の `config`/`hooks`)」に効くが、**複製は cwd 直下の `.git/` サブディレクトリ**であり、`tree/.git/config`・`tree/.git/hooks/` はこの保護の対象外 (cwd 直下の作業ツリーのファイルとしての `.git/config` 保護は「working directory only」の項に入るが、これは cwd を bare 化する形のトップレベル `config` を指し、`.git/` 内部の hooks/config への Bash 書き込みは実測でも通っている: #68 コメント結果 2 で `git checkout -- <file>` など複製内 git 書き込みが「通る」)。つまり `.git/hooks/` へのフック配置も `.git/config` への `core.fsmonitor` 等の設定も、サンドボックス下の Bash で書ける。拒否の規則 `Edit(複製/.git/**)` は `Write`/`Edit` ツールを止めるが、**Bash 経由の書き込みは止めない** (サンドボックスは Bash に、拒否の規則は Write/Edit に効く、という計画自身の前提)。
  - 危険なのは `fsmonitor` だけではない。git が後で実行する設定は多い: `core.fsmonitor`・`core.hooksPath` (フックの置き場を差し替え)・`diff.*.textconv`・`diff.external`・`filter.*.clean/smudge`・`.git/hooks/post-checkout` 等・`gc`/`maintenance` の自動起動。**ワーカーが後始末で複製の中の git を 1 回でも実行すれば発火する**。
  - 計画の防御 (「複製の中で git を実行しない」) は正しいが、**この不変条件は「実装者が守る約束」であって、破れても検出されない**。U4 の後始末やデバッグで誰かが `git -C 複製 ...` を足すと、静かに任意コマンド実行になる。AE12 のテストは `.git/config` だけを見ており、`core.hooksPath`・`filter`・`textconv`・`post-checkout` を試していない。
  
  - **対処**:
    - **R5・KTD8 に足す**: 複製を消す前の後始末は「`rm -rf` だけで、git を一切使わない」ことを不変条件として worker.md に明記し (U3)、AE12 のテストを `core.hooksPath`・`filter.*.clean`・`.git/hooks/post-checkout` にも広げる (U4 の Test scenarios)。**推測**: 実装が結果の複写に git を使わない設計なら実害は無いが、明文化しないと将来壊れる。
    - もう一段の防御として、複製を消す前に `.git/hooks/`・`.git/config` を「使わない」ことを保証するだけでなく、**複製の作成時に `core.hooksPath=/dev/null` 等でフックを無効化する**案を KTD2 の選択肢に足すことを検討 (推測: 効果は環境依存なので U1 で確認)。
  
  ### [重要度 高] 3. ワーカーが読むログ (`<識別子>.log`) を、複製内の Bash からレビュアが細工して、サンドボックスが止めた件数を 0 に見せられる経路 (根拠: plan KTD6・worker.sh 588 行目)
  
  ワーカーは `claude -p` の標準出力・標準エラーを置き場の `<識別子>.log` にそのまま書き (`review-loop-worker.sh` 588 行目、worker.md 104 行目)、KTD6・KTD7 はこのログを唯一の真実として件数と権限モードを読む。ところが:
  
  - ログは stream-json の 1 行 1 JSON。レビュアの Bash は**自分の標準出力に任意の JSON 行を書ける**。auto モードは「読み取りとサンドボックス内の Bash」を通すので、`echo` 相当でログに偽の `result` 行や偽の `init` 行を注入する呼び出しは、classifier 判定を通れば実行される (推測: 純粋な標準出力への書き出しは exfiltration にも破壊にも当たらず、classifier は通しやすい。確度=中)。
  - 計画は KTD6 で「`is_error` が真の Bash 結果だけ数える」ことで**文書の grep 誤検出**は防ぐが、**能動的なログ注入**は防いでいない。レビュアがサンドボックスに止められた後、`is_error: false` で終わる整形済み JSON をログに吐けば、ワーカーは件数 0・`permissionMode: auto` と読み、RL1 を通過する。これは質問 3 の核心 (レビュアが件数を 0 に見せる) の具体経路。
  - 質問 1 の観点では、これは「ワーカー自身の振る舞い (判定) をレビュアが変えられる」経路。
  
  - **対処**:
    - **KTD6・KTD7 に前提を明記**: ログはレビュアの標準出力を含むので、ワーカーが数える `tool_result`・`init`・`result` は「Claude Code 本体が書いた行」と「レビュアの Bash が書いた行」を区別できない。**推測**: stream-json の各行に本体由来を示す一意なフィールド (例: `session_id`・`uuid` の整合、または本体しか付けないキー) があるかを U1 で確認し、あればそれで濾す。無ければ「ログ注入で件数を 0 に見せられる」ことを worker.md の「このワーカーが検出しないもの」と Risks に明記する。
    - RA1 の設計思想 (「調べられなかった範囲の指摘が欠けた結果を記録に入れない」) からすると、**ログを信頼できないと RA1 の判定自体が信頼できない**。これは受け入れるにしても、Scope Boundaries に明示的に書くべき残存リスク。
  
  ### [重要度 中] 4. 結果ファイルの複写経路: シンボリックリンク・名前・大きさの扱いに穴 (根拠: plan R4・KTD8 手順 4)
  
  計画は R4・KTD8 手順 4 で「結果が通常のファイル (シンボリックリンク・FIFO・ディレクトリでない) であることを `lstat` で確かめ、一時名で書いてから改名」とし、これは良い。ただし:
  
  - **中間ディレクトリのシンボリックリンク**: `lstat` は結果ファイル自身のみを見る。レビュアが複製内の結果ファイルの**親ディレクトリ**をシンボリックリンクにしていた場合、ワーカーが結果を読む段階で複製の外を読む/書く経路になりうる。ただし結果の書き先は「複製の中」で固定 (KTD1 の `tree/` ではなく作業場所直下の `review-<識別子>.yaml`) なので、レビュアが書けるのは複製の中だけ。**推測**: 結果の実際の置き場が作業場所直下 (複製の外) なら、レビュアはそこに直接書けない (拒否の規則が作業場所を許可、複製を cwd)。ここは KTD1 の配置表と R4 の「複製の外に書く」の整合を U1/U4 で確認すべき。計画内で「結果は複製の中」(437 行目 `…/tree/` はレビュアの cwd) と「複製の外の作業場所に書く」(R4) が読みづらい。
  - **巨大な結果ファイル**: サンドボックスは作業場所への書き込みを許すので、レビュアは作業場所を埋め尽くす巨大ファイルや大量ファイルを作れる。ワーカーがそれを置き場へ複写すると置き場 (git 追跡外だがディスクを食う) や、ワーカーの読み取り (`read_key`・`wc -c`) が遅延・失敗する。計画に大きさの上限が無い。
  - **対処**: **R4・KTD8 に足す** — (a) 結果を読む前に、結果ファイルへ至るパスに複製の外へ出るシンボリックリンクが無いことを確かめる (実体パスが作業場所の下にあること)、(b) 結果ファイルの大きさに上限を設け、越えたら `failed`。**Scope Boundaries** に「作業場所を埋めるディスク濫用は防がない」と書くなら、それでも可 (受け入れるリスクとして明示)。
  
  ### [重要度 中] 5. `TMPDIR` の共有と、サンドボックスが `TMPDIR` を書き込み可能にすることの相互作用 (根拠: 文書 sandboxing「Temporary directories」・plan KTD1・Scope Boundaries)
  
  - サンドボックスは既定で cwd と**per-user の temp ディレクトリ (`$TMPDIR`)** を書き込み可能にし、サンドボックス内では `$TMPDIR` を per-user temp に張り替える (文書「Temporary directories」)。計画は KTD1 で作業場所を `<TMPDIR の実体>/review-loop-<周回 id>/` に置き、これを `sandbox.filesystem.allowWrite` に足す。
  - **問題**: サンドボックスは `$TMPDIR` 全体 (=作業場所の親、他の周回の作業場所、他プロセスの一時ファイル) を書き込み可能にする。計画は Scope Boundaries で「サンドボックスは一時ディレクトリの中への書き込みを止めない」「複製と作業場所の外の一時ディレクトリへの書き込みは検出しない」と受け入れている。しかし、**同じ `$TMPDIR` 下に、並行する別の周回の作業場所や、ワーカーが `worker.yaml` を書く経路と関係する一時ファイルがあれば**、レビュアが Bash でそれらを書き換えられる。特に:
    - `write_atomic` (worker.sh 135 行目) は `worker.yaml` などを `$LOOP_DIR` (置き場) の一時名に書くが、置き場はサンドボックスの `allowWrite` に**入れない**設計 (R10 で置き場への書き込みを拒否) なので、そこは守られる。
    - だが `TMPDIR` を Claude Code 本体が使う一時ファイル (セッションの中間ファイル等) があれば、それはレビュアの書き込み可能領域に入りうる。**推測** (確度=中): レビュアのプロセスが本体と同じ `TMPDIR` を共有するなら、本体の一時ファイルを細工して本体の振る舞いに影響する余地がある。
  - **対処**: **KTD1・R18 に足す** — 作業場所を `$TMPDIR` 直下ではなく、その回だけの `mktemp -d` で作った専用サブディレクトリにし、`allowWrite` にはそのサブディレクトリ**だけ**を足す (親の `$TMPDIR` 全体を許可しない設計であることを明記)。ただしサンドボックスの既定が `$TMPDIR` 全体を書き込み可能にする以上、`allowWrite` を絞っても既定の temp 書き込みは残る。**この既定 temp 書き込みを狭める手段があるか (denyWrite で `$TMPDIR` を絞れるか) を U1 で確認**し、できなければ「サンドボックス下では per-user temp 全体が書けるので、そこに置いた他プロセスの一時ファイルは守られない」を Scope Boundaries に明記。
  
  ### [重要度 中] 6. 拒否の規則が実体パス基準でも、複製内から作業側へ到達する別経路 (根拠: plan KTD5・#68 実測)
  
  - KTD5 は作業側リポジトリの実体と置き場の実体への `Edit(//<実体>/**)` で守り、`Edit(~/**)` でホーム全体を守る。#68 実測で、複製 (temp) からホーム下への Bash 書き込みはサンドボックスが止めた。良い。
  - ただし `Edit` 系の拒否は Write/Edit ツールに効き、**Bash 経由でホームの外にあるが作業側でも置き場でもないパス (例 `/opt/homebrew`・`/usr/local`) への書き込みは、サンドボックスが cwd と temp 以外を止める**ので、原則守られる。Risks 表の「`Write`・`Edit` でホームと作業側の外に書くのを auto が許す」は列挙されているが、**Bash 経由の同じ書き込みはサンドボックスが止める**という非対称が Risks に整理されていない。ここは実は防御が効いている側なので、Risks の当該行を「Write/Edit ツール限定」と明確化すると、読み手が過度に危険視しない。
  - **対処**: Risks 表の該当行 (502 行目) を「Bash はサンドボックスが cwd/temp 外を止めるので対象は Write/Edit ツールのみ」と限定。これは危険の追加ではなく、既存記述の精緻化。

  ## 質問 2: KTD10 と KTD11 の安全性
  
  ### [重要度 高] 7. KTD10 (`reviewer_pgid` のプロセスグループを止める) の PID/PGID 再利用リスクは部分的にしか防げていない (根拠: plan KTD10・worker.sh 148〜150 行目)
  
  KTD10 は「`reviewer_pgid` のプロセスが生きていてコマンドが `claude` なら止める」で、PID 再利用を「コマンド名の確認」で防ぐ。妥当だが穴がある:
  
  - **PGID の再利用**: `worker.yaml` に記録するのは PID ではなく PGID (プロセスグループ ID)。ワーカーが `kill -9` された後、その PGID が**別の無関係なプロセスグループに再利用される**可能性がある。KTD10 は「グループの先頭プロセスのコマンドが `claude` か」を確かめるとするが、`group_alive` (worker.sh 148 行目) は `pgid` 一致だけを見る。**先頭プロセスの特定と、その先頭が `claude` かの確認**を、PGID 再利用のもとで正しく行えるか (先頭プロセスが既に死に、別のプロセスが同じ PGID を持つ場合など) は自明でない。
  - **`claude` へのなりすまし**: レビュアの実行は auto モードの LLM で、複製内で任意プロセスを起動できる。**推測** (確度=中): レビュアが自分の子として `claude` という名前のプロセス (例: `claude` という名の何か) を `setsid` で新しいセッション/プロセスグループに起こしておくと、ワーカーの後始末のプロセスグループ TERM/KILL から抜け、かつ起動し直し時のコマンド名確認 (`claude`) を満たして「止める対象」に見せかける、あるいは逆に別 PGID に逃げて生き延びる。KTD8 手順 1・R5 は「レビュアの実行のプロセスグループに残ったプロセスを止める」だが、**`setsid` で新しいプロセスグループに移った子孫は、記録した `reviewer_pgid` に属さないので止まらない**。
  - 計画の Scope Boundaries・「このワーカーが検出しないもの」に、この「プロセスグループから抜けた子孫」の残存が書かれていない。AE の「子孫のプロセスを残したとき残っていない」テスト (660 行目) は、**同じプロセスグループに留まる子孫**しか検証しない (偽の claude が普通に fork する子)。
  - **対処**:
    - **KTD10・R5・R6 に足す**: `setsid`/`newpgid` でプロセスグループから抜けた子孫は記録した PGID に属さず、後始末でも起動し直しでも止まらない、と「このワーカーが検出しないもの」に明記。**推測**: レビュアが auto モードで `setsid` を実行できるか (classifier が通すか) を U1 で 1 例確認。通せば、これは「外に出る操作をさせない」目的 (Goal) の穴。
    - PGID 再利用対策として、コマンド名だけでなく**起動時刻や親子関係の追加確認**を検討、または「PGID 再利用時に無関係プロセスを止めるリスク」を worker.md に明記。
  
  ### [重要度 中] 8. KTD11 (追加引数の許可リスト) は方向は正しいが、`--settings` の合成と `enabledPlugins` に注意点 (根拠: plan KTD11・文書)
  
  - 「禁止リストではなく許可リスト」の判断は正しい (制限を弱めるフラグを列挙しきれない、は妥当)。
  - **`--plugin-dir <ディレクトリ>` の許可**: プラグインディレクトリはスキル・エージェント・フック・MCP 定義を含みうる。ブランチ版プラグインのディレクトリを渡す用途 (通し確認) だが、**そのディレクトリの中身は「観測されたデータ」ではなく人間が渡すパス**なので、指示注入の対象ではない。ただしプラグインが `.claude/hooks` や MCP を持てば、`--strict-mcp-config` (KTD5) が MCP を止めても**フックは動く**可能性。**対処**: `--plugin-dir` で渡すプラグインのフックがレビュアの実行で動くか、動くなら何を実行できるかを worker.md に一言。通し確認は人間が信頼するブランチだけに使う前提を明記。
  - **`enabledPlugins` だけの `--settings` の合成**: KTD11 はワーカー自身の `--settings` (サンドボックス設定) に `enabledPlugins` を合成し、`claude` には `--settings` を 1 つだけ渡す。**リスク**: JSON 合成で、渡された `enabledPlugins` の JSON にサンドボックスや権限のキーが紛れ込むと、ワーカーの安全設定を上書きしうる。R18・AE11 は「`enabledPlugins` 以外のキーを持つ `--settings` を弾く」としているが、**トップレベルが `enabledPlugins` だけであることの検査を、JSON をパースして厳密に行う**必要がある (文字列一致では回避される)。**対処**: R18・KTD11 に「JSON としてパースし、トップレベルキーが `enabledPlugins` ちょうど 1 つであることを確かめる。合成後の最終 JSON でサンドボックス・権限のキーが上書きされていないことを確かめる」を明記。U4 の Test scenarios (654 行目) に、`enabledPlugins` に紛れたサンドボックスキーを弾くケースを足す。
  - **`--settings` の優先順位と配列結合** (文書・plan 265 行目): `--settings` は利用者設定より優先し配列は結合、拒否は許可より優先。これは味方だが、**`sandbox.filesystem.allowWrite` は結合される**ので、利用者設定やプロジェクト設定に `allowWrite` があれば、ワーカーの絞り込みに加算される。R18 は `--sandbox-allow-write` の値を検査するが、**利用者/プロジェクト設定側の `allowWrite` は検査対象外**。**対処**: worker.md の「このワーカーが検出しないもの」に「利用者・プロジェクト設定の `sandbox.filesystem.allowWrite` は結合され、ワーカーは検査しない」を明記 (Deferred の「ブランチの `.claude/settings.json` 検査」と同じ扱い)。

  ## 質問 3: KTD6 (件数の数え方) をレビュアが誤らせる形
  
  ### [重要度 高] 9. 件数を 0 に見せる経路 = 上記 3 (ログ注入) が本命。加えて数え方自体の偽陰性・偽陽性 (根拠: plan KTD6・文書)

    - **ログ注入** (上記 3): 最有力。標準出力に整形 JSON を吐いてワーカーの python の読みを狂わせる。
    - **`dangerouslyDisableSandbox` の抜け道**: 計画は `allowUnsandboxedCommands: false` (KTD5) で塞ぐ。文書で確認: これで escape hatch は無効化され、`dangerouslyDisableSandbox` パラメータは無視される。**ただし** `excludedCommands` に載るコマンドはサンドボックス外で動く (文書)。KTD5 は `excludedCommands` を渡さない設計だが、**利用者・プロジェクト設定の `excludedCommands` は結合される** (配列結合、上記 8)。レビュー対象ブランチの `.claude/settings.json` が `excludedCommands` を持てば、そのコマンドはサンドボックス外で動き、書き込みも止められず件数にも残らない。計画は Deferred で「ブランチの `.claude/settings.json` がサンドボックスを広げる不具合 (2.1.273、v2.1.282 修正)」に触れているが、**`excludedCommands` は不具合ではなく仕様で外に出る**。これは 0 に見せる正規の経路。**対処**: R10・worker.md に「対象ブランチや利用者設定の `excludedCommands` に載るコマンドはサンドボックス外で動き、件数に残らない」を明記。Scope Boundaries の残存リスクに格上げ。

    - **`operation not permitted` 以外の文面**: サンドボックスが止めた書き込みが別の文面 (Linux の `Read-only file system` など。macOS 対象なので当面は関係薄いが) や、言語ランタイムが EPERM を握りつぶして別メッセージにした場合、数えられない。U1 の手順 5 (touch/mkdir/python/git/リダイレクト) は良いが、**アプリが EPERM を別文面に変換する場合**を worker.md の限界に明記。

  - **推測** (確度=中): レビュアが「わざと 0 に見せる」動機は通常のレビューでは無いが、脅威モデルは「auto の LLM は判定が許せば何でもする」なので、プロンプトインジェクション (レビュー対象コードやファイルに仕込まれた指示) でログ注入を誘発される経路は想定に値する。**対処**: 質問 3 の結論として、KTD6 の件数は「レビュアが敵対的なら信頼できない防御的指標であり、誠実なレビュアの取りこぼしを RA1 で拾うためのもの」と worker.md に位置づけを明記。これは #68 実測 (レビュアがインジェクションを疑って実行を断った例) とも整合。

  ### Scope Boundaries で受け入れているが、受け入れるには重いもの
  
  - **「ログからはサンドボックスが効いていたかを確かめられない」(#68 コメントの残存事項)**: 計画はこれを受け入れつつ、KTD6/KTD7 でログを唯一の真実にしている。**サンドボックスが実際に効いていたかを確認できないまま「件数 0 = 安全」と判定するのは、防御としては弱い**。`failIfUnavailable: true` (KTD5) はサンドボックスを起動できないときに実行をエラーにするので、「起動はした」ことは保証される (U1 で受け付けを確認する項目あり)。だが「起動後も効き続けた」ことはログから読めない。**推奨**: `failIfUnavailable: true` が受け付けられることを U1 で確認する項目 (既にある、283 行目) の結果に依存する旨を KTD5 に明記し、これが成り立たなければ Goal Capsule の止まる条件に該当することを確認。**推測**: `failIfUnavailable` が起動時保証を与えるなら、この残存リスクは許容範囲に下がる。
  
  - **「一時ディレクトリの中への書き込みは止まらない」+「サンドボックスは per-user temp 全体を書き込み可能にする」(上記 5)**: 作業場所を `$TMPDIR` 直下に置く設計 (KTD1) と組み合わさると、**同じ `$TMPDIR` を使う本体や並行周回の一時ファイルが、レビュアの書き込み可能領域に入る**。受け入れるにしても、作業場所を専用サブディレクトリに隔離し、本体と `TMPDIR` を共有しない (レビュアの実行に別の `TMPDIR` を与える) 検討を U1 に足すべき。これは「ワーカー自身の振る舞いに影響する経路」を狭める。

  ## 覆さなかった決定
  
  案 1・Linux 対象外・サンドボックスが止めた確認も RA1・ネットワークは U1 で調べる、のいずれについても「働かない証拠」は見つからなかった。ネットワークが閉じられない場合の分岐 B (名前で拒否) は、文書の「domain fronting で allowlist 外に到達しうる」「per-command allowed domains は auto で classifier 判定」という記述と整合しており、B を受け入れる判断自体は妥当。ただし分岐 B では python 等からの接続が残る (計画も明記) ことは、上記の脅威モデル (auto の LLM は判定が許せば何でもする) では「外に出る操作をさせない」目的の明確な穴なので、Scope Boundaries の残存リスクとして重み付けを上げることを推奨する。
