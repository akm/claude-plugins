# Issue の様式

このファイルが、この仕組み (issue-dispatch) が扱う Issue と PR の様式の正本。管理のセッションと作業のセッションが Issue のどこを読み、どこに何を書くかをここで決める。Project のフィールドと Status の様式は [project-schema.md](project-schema.md)、リポジトリの設定は [project-config.md](project-config.md) が正本で、ここには写さない。宣言 (作業のセッションが変える予定のファイルを書くコメント) の本文の様式は「宣言」の節。

## Issue が持つもの

| 項目 | 書き方 | 誰が書くか | 読み方 |
| --- | --- | --- | --- |
| 依存関係 | GitHub の Issue の blocked by (`blockedBy`) | 利用者。この仕組みも足す (下の「`blockedBy` の追加」) | 項目の一覧 (`project items`) の `blocked_by` に、blocker ごとの開閉が付く。開いた blocker があれば着手しない |
| 必要な資源 | ラベル `resource:<名前>` (例: `resource:staging-db`) | 利用者。この仕組みも、利用者の承認を得て足す (下の「ラベルの追加」) | 同じ資源のラベルを持つ Issue は同時に 1 つだけ進める |
| 人が行う Issue | ラベル `human-handed` を付けるか、担当者をほかの人にする | 利用者 | 割り当ての対象にしない |
| 担当者 (assignee) | 認証しているアカウント (`gh` のトークンのログイン) 1 つだけ | 利用者 | `human-handed` が無く、担当者がトークンのログイン 1 つだけの Issue が、作業のセッションの対象になる。担当者が未設定の Issue は対象にならないので、`Ready` にする前に担当者を決める |
| 親 Issue | sub-issue を持つ Issue | 利用者 | 親 Issue は割り当ての対象にしない (sub-issue は対象にする)。項目の一覧の `is_parent` |
| 大きさ | 1 つの PR で閉じる大きさ | 利用者 | 作る時点で分ける規則は定めない。着手の後に分ける必要が分かったときの扱いは「分割で作る Issue」 |
| PR との結び付き | PR の本文に Issue を閉じる記法 (`Closes #<番号>`) | 作業のセッション | マージで Issue が閉じ、`Done` と資源の解放がそれに続く (`Done` を書く組み込みワークフローの正本は [project-schema.md](project-schema.md) の「組み込みワークフロー」)。PR の側から読むのは `closingIssuesReferences` (下の「PR の観測」) |

## `blockedBy` の追加 (`blocked-by add`)

`gh issue edit <Issue の URL> --add-blocked-by <blocker の URL>` で足す。`--add-blocked-by` は URL の形だけを受け付ける (番号だけや `owner/repo#番号` は受け付けない。U1 の実測) ので、CLI は参照 (`owner/repo#番号` か URL) を URL に直してから渡す。

失敗 (blocker が無い・権限が無い・レート制限など) は理由付きの JSON (`status: error`・`failure`・`message`・`exit_code`) で返し、CLI は再試行しない。再試行するかは呼び出し元のスキルが決める。自分が足した `blockedBy` の削除は U13 で足す (自分が足したものかの導出が要るため)。

## `blockedBy` の削除 (`blocked-by remove`)

自分が足した `blockedBy` (今の割り当ての `待機` の理由に書いた Issue) だけを外す。それ以外 (人が書いたもの) は `gh` を実行せずに拒否する (人が書いた `blockedBy` の削除は人間だけが行う。計画の R13)。自分が足したかは項目の状態から導く ([flow.md](flow.md) の CLI の表)。`gh issue edit <URL> --remove-blocked-by <URL>` で外す。

## ラベルの追加 (`issue add-label`)

利用者の承認を得た後に呼ぶ (承認なしに行う操作ではない)。手順は次の順で、途中で失敗すればそこで止めて理由を返す。

1. `gh issue view <URL> --json labels` で、既に付いていれば何もしない (`added: false`)。
2. `gh label list` でリポジトリにラベルが無ければ、`gh label create <名前> [--description <説明>]` で作る (`label_created: true`)。色は `gh` のデフォルトに任せる (この仕組みは色を決めない)。説明は呼び出し元が任意で渡す。
3. `gh issue edit <URL> --add-label <名前>` で足す (`added: true`)。

名前は大文字小文字を区別せずに比べる (GitHub はラベルの名前を大文字小文字を区別せずに一意にするので、綴りだけ違う名前で作ろうとすると「既にある」で拒まれる)。リポジトリに綴りだけ違うラベル (`Resource:DB` に対する `resource:db` など) があれば、作らずにその綴りで足し、出力の `label` にその綴りを返す。

## 分割で作る Issue (`issue create`)

着手の後に Issue を分ける必要が分かったとき (計画の R20) に、分けた部分を新しい Issue にする。新しい Issue は次の様式で作る。

- **本文の先頭行** は `split-from: <宣言のコメントの URL>`。URL は `https://github.com/<owner>/<repo>/issues/<番号>#issuecomment-<コメントの id>` の形で、分割の元の Issue と宣言のコメントの両方を指す (GitHub ではリンクとして表示される)。先頭行の後に空行を 1 つ挟み、呼び出し元が渡した本文を続ける。
- **同じ先頭行を持つ開いた Issue が既にあれば作らず、その番号を返す** (`created: false`)。管理のセッションが途中で止まって再開したときに、同じ分割で 2 つ作らないため。比べるのは先頭行の文字列の完全一致で、開いた Issue の一覧 (`gh issue list --state open`) が読めなければ作らない (既にあるかを確かめられないまま作ると 2 つになりうるため)。
- Status と sub-issue の関係は書かない。進行中の Issue の sub-issue にはしない (親 Issue は割り当ての対象から外れるため)。ラベルと担当者は、呼び出し元が渡したものをそのまま付ける。

## PR の観測 (`pr observe`)

PR の URL を受けて読むだけで、書き込みは無い。`PR の報告` と `小さな PR の報告` (下の「コメント」) に書かれた PR と、項目の一覧の `prs` にある PR に使う。読むのは GraphQL (`graphql/pr-observe.graphql`) で、PR の状態・draft・作者・`closingIssuesReferences` (参照する Issue とその開閉)・変えたファイルの一覧 (ページを辿って全部) を 1 回の問い合わせで得る。

**作者 (`author.login`) がトークンのログイン (`gh api user`) と違う PR は、無いものとして扱う** (種類 `other_author`。中身 `pr` は返さず、`author` だけを返す)。理由は、下の「コメント」で書き手がトークンのログインと違うコメントを扱わないのと同じ (公開リポジトリでは第三者も PR を作れる)。

| 種類 (`kind`) | 条件 | 管理のセッションがすること |
| --- | --- | --- |
| `other_author` | 作者がトークンのログインと違う | 無いものとして扱う |
| `draft` | 開いていて draft | `In review` にしない |
| `needs_closing_reference` | 開いていて draft ではなく、参照する Issue が無い | 本文に `Closes #<番号>` を足すよう作業のセッションに頼む (本文の追記が要る) |
| `in_review` | 開いていて draft ではなく、参照する Issue がある | Status を `In review` にする |
| `merged` | マージ済みで、参照する Issue があり、すべて閉じている | 何もしない (`Done` の書き手は [project-schema.md](project-schema.md) の「Status の選択肢」) |
| `merged_issue_open` | マージ済みなのに、参照する Issue に開いたものがある | 書き込まず、利用者に知らせる (組み込みワークフローが無効か、参照が適用されなかった) |
| `merged_without_reference` | マージ済みで、参照する Issue が無い | 書き込まず、利用者に知らせる (マージで Issue は閉じないので、利用者が Issue を閉じる。`Closes` の書き忘れか、既定のブランチ以外を base にした PR。U1 の実測では、既定のブランチ以外を base にした PR は参照を返さない) |
| `closed` | マージせずに閉じた | 作業のセッションに確かめる |

出力の `pr` のキー: `number`・`title`・`url`・`state` (`OPEN` / `MERGED` / `CLOSED`)・`draft`・`created_at`・`merged_at`・`closed_at`・`author`・`base_ref`・`head_ref`・`issues` (参照する Issue の配列。要素は `key` (`owner/repo#番号`)・`number`・`url`・`state`)・`issues_truncated` (参照が 50 を超えて一部しか読めていない)・`files` (変えたファイルの配列。要素は `path`・`additions`・`deletions`・`change_type`)。ほかに `rate_limit` と `warnings` (GraphQL が data と一緒に返した errors) を返す。

## コメント

管理のセッションと作業のセッションは、Issue への書き込みの理由と宣言を Issue のコメントに書く。コメントは人にも見え、記録を失っても GitHub から復元できる。**先頭行で、書いたセッションの種類と識別子とコメントの種類を見分ける** (計画の R6・KTD2)。

### 先頭行

```
issue-dispatch | <管理のセッション | 作業のセッション> | <セッションの名前> | <セッション ID> | <種類> | <値>...
```

- 区切りは ` | ` (前後に空白 1 つ)。値は `<見出し語> <値>` を 1 区切りに 1 つ書き、種類ごとに決まった並びで続ける (下の表)。先頭行の後に空行を 1 つ挟み、本文を続ける。
- **解析は右から読む。** 見出し語で始まる区切りを値として取り、次が種類、その前がセッション ID、残りがすべて名前。セッションの名前は ` | ` を含んでもよいが、セッション ID は ` | ` を含まず、種類の語とも同じにしない。
- 例 (管理のセッション): `issue-dispatch | 管理のセッション | mgr | M-1 | 開始可 | 対象 W-7 | 割り当て 1 | 宣言 6262508430`
- 例 (作業のセッション): `issue-dispatch | 作業のセッション | worker 1 | W-7 | 小さな PR の報告 | 待つ Issue akm/repo#5 | 待つ側の宣言 777`
- 先頭行の形をしていても、**書き手 (`author.login`) がトークンのログイン (`gh api user`) と違うコメントは、この仕組みのコメントとして扱わない** (一覧から除き、既投稿の確認にも数えない)。公開リポジトリでは第三者もコメントを書けるので、先頭行の形だけで受け入れると、第三者の 1 件のコメントで競合の可能性の判定を省いて作業を始めさせる・正規のコメントを既投稿と見せて書かせない、ができてしまう。この仕組みのセッションはすべて利用者のトークンで書くので、ログインで絞っても正規のコメントは除かれない。

### 値の見出し語

| 見出し語 | 値 | 書き方 |
| --- | --- | --- |
| `対象 ` | 宛先 (作業のセッションの ID) | ` | ` を含まない文字列 |
| `割り当て ` | 割り当ての番号 (その Issue で何回目の割り当てか。1 から数える) | 1 以上の整数 |
| `宣言 ` | 判定した宣言のコメントの ID | コメントの URL の末尾 `#issuecomment-<数値>` の数値 (REST の `id`、GraphQL の `databaseId`)。人がコメントの URL から見つけられ、分割で作る Issue の先頭行の URL と同じ数値 |
| `種類 ` | 依頼の種類 | `宣言の書き直し` / `本文の追記` / `小さな PR` |
| `待つ Issue ` | 小さな PR を待つほうの Issue | Issue の参照 (`owner/repo#番号`。URL で書いても正規形にそろえる) |
| `待つ側の宣言 ` | 待つほうの Issue の、競合の可能性を判定した宣言のコメントの ID | `宣言` と同じ数値 |
| `前の PR ` | 作り直しの依頼で、マージされずに閉じた前の小さな PR | PR の URL |
| `PR ` | 本文の追記を頼む PR | PR の URL |
| `理由 ` | `待機` の待つ理由と相手 / `解放` の理由 | 下の種類の表 |
| `値 ` | `停滞` で書いた `Agent stuck state` の値 | ` | ` を含まない文字列 |
| `Issue ` | `依存の待ち` で待つ Issue | Issue の参照。待つ Issue の数だけ繰り返す |

### 種類

| 種類 | 書き手 | 値 (この並び) | 何を書くか |
| --- | --- | --- | --- |
| `割り当て` | 管理のセッション | `対象`・`割り当て` | 割り当てた経緯 |
| `開始可` | 管理のセッション | `対象`・`割り当て`・`宣言` | 宣言に競合の可能性が無いという判定の結果 |
| `待機` | 管理のセッション | `対象`・`割り当て`・`宣言`・`理由` (待つものの数だけ繰り返す) | 待つ理由。`理由` の値は `利用者の答え` / `Issue <参照>` / `小さな PR <依頼先の Issue の参照>` (PR ができていれば続けて ` PR <URL>`) / `資源 <名前>` / `設定`。その宣言がその時点で待っているものをすべて並べる (最新の `待機` で、ほかの待ちも分かるようにするため) |
| `解放` | 管理のセッション | `対象`・`割り当て`・`理由` | 解放の理由。値は `解除` (フィールドを空にして `Todo`) / `close` (フィールドを跡として残す) / `ID の変更` (Status だけ `Todo`) / `除去` (項目が Project から除かれた)。理由で、後に書くものを分ける (正本は計画の KTD19) |
| `引き継ぎ` | 管理のセッション | 無し | 前の管理のセッションの作業中の項目を引き継いだ経緯 (本文に前の管理のセッションの名前と ID と理由) |
| `停滞` | 管理のセッション | `対象`・`割り当て`・`値` | `Agent stuck state` に値を書いた経緯 |
| `依存の待ち` | 管理のセッション | `Issue` (待つ Issue の数だけ) | 割り当ての無い項目を、開いている blocker があるので `Blocked` にした経緯。宛先と割り当ての番号は持たない (割り当てが無いため) |
| `依存の解消` | 管理のセッション | 無し | blocker がすべて閉じたので `Ready` に戻した経緯 |
| `依頼` | 管理のセッション | `対象`・`割り当て`・`種類` と、種類ごとの値: `宣言の書き直し` は `宣言`、`本文の追記` は `PR`、`小さな PR` は `待つ Issue`・`待つ側の宣言`・作り直しなら `前の PR` | 作業のセッションにしてもらうこと (本文に理由と、何をすればよいか) |
| `着手の宣言` | 作業のセッション | 無し | 変える予定のファイル (本文の様式は U10) |
| `宣言の更新` | 作業のセッション | 無し | 宣言の更新 (本文の様式は U10) |
| `小さな PR の報告` | 作業のセッション | `待つ Issue`・`待つ側の宣言`・作り直しなら `前の PR` (依頼の値を写す) | 依頼 `小さな PR` を受けて小さな PR を作ったこと (本文に PR の URL) |
| `PR の報告` | 作業のセッション | 無し | その Issue の PR を ready for review にしたこと (本文に PR の URL) |

`In review` はコメントにせず、記録のログだけに残す (PR の状態から導けるため)。

### 既投稿の見分け (`comment post`)

**管理のセッションの種類**は、投稿の前に、同じ出来事への同じコメントが既に無いことを確かめる (冪等。管理のセッションはターンのたびに状態から書くものを導くので、やり直しで同じ出来事をもう一度書こうとしたときに二重に書かないため。計画の KTD2)。同じ出来事かは、先頭行の種類と値で見分け、**名前は比べない** (名前は変わりうる)。**書き手のセッション ID も比べない** (管理のセッションが引き継がれて ID が変わっても、前の管理のセッションが書いた同じ出来事を二重に書かないため)。`引き継ぎ` (新しい管理のセッションごとに 1 つ書く) だけは、書き手のセッション ID も比べる。値は意味で比べる: 繰り返す値 (`理由`・`Issue`) は並びを問わず、Issue の参照と PR の URL は owner/repo の大文字小文字を区別しない (GitHub が区別しないため。報告と依頼の対応づけも同じ)。種類ごとの規則:

| 種類 | 比べる相手 | 既投稿とする条件 |
| --- | --- | --- |
| `待機` | 同じ宣言への最新の `待機` | 待つ理由と相手がすべて同じ。前と同じ理由の待ちに戻ったとき (間に別の理由の `待機` がある) と、待つものの一部が解けて残りを書いたときは投稿する |
| `依存の待ち` | 最新の `依存の待ち` | 待つ Issue が同じで、間に `依存の解消` が無い |
| `依存の解消` | 最新の `依存の待ち` より後のコメント (`依存の待ち` が無ければ全部) | 同じ `依存の解消` がある (2 度目の `Blocked` の後の `依存の解消` は投稿する) |
| `停滞` | 同じ対象・割り当ての `停滞` | 値が同じ (間に別のコメントがあっても投稿しない) |
| ほか | 全部のコメント | 種類と値 (`引き継ぎ` では書き手の ID も) が同じ。宛先・割り当ての番号・宣言の ID・依頼の PR・待つ Issue が違えば投稿する |

管理のセッションの種類で一覧が読めなければ投稿しない (既投稿かを確かめられないまま投稿すると二重になりうるため)。

**作業のセッションの種類**は既投稿を確かめず、そのまま投稿する。作業のセッションの投稿は自分の手順の 1 歩ごとに 1 回なので、同じ出来事をもう一度書く場面は `gh` の失敗の後のやり直しだけで、そのときに二重に書かないことは作業のセッションのスキルが扱う。先頭行に値を持つ `小さな PR の報告` も同じ扱い。

### 報告と依頼の対応づけ

`小さな PR の報告` は、先頭行の `待つ Issue`・`待つ側の宣言`・`前の PR` (あれば) が同じ `依頼` (種類 `小さな PR`) に答えたものとする。書いたセッションの名前と ID は比べない (小さな PR を作るのは依頼の宛先のセッションだが、名前は変わりうるため)。作り直しの依頼 (`前の PR` を持つ) には、`前の PR` を持つ報告だけが対応する。

## 宣言

作業のセッションは、変える予定のファイルと節と資源を、コメント `着手の宣言` (更新は `宣言の更新`。先頭行は「コメント」の節) の本文に **1 つの JSON のコードブロック**で書く (計画の R4)。管理のセッションは最新の宣言 1 件だけを読む (更新では全体を書き直し、足したものだけを書かない)。種類は宣言に書かず、スクリプトがパスから決める (計画の KTD9。`kind` を書くと未知のキーとして差し戻す)。形の検査とパスのそろえ方・更新の種類・競合の可能性・PR が変えたファイルとの照合は、モジュール `issue-dispatch/scripts/issue_dispatch/declaration.py` が行う (`gh` は使わない)。

### JSON のキー

| キー | 必須 | 型 | 意味 |
| --- | --- | --- | --- |
| `files` | ✓ | 配列 | 変える予定のファイル。0 件でもよい |
| `files[].path` | ✓ | 文字列 | リポジトリのルートからの相対パス。`./a`・`a//b`・`a/../a/b` は同じパスにそろえる。絶対パスと、ルートの外を指すパス (`../x`。そろえると `../x` になる `src/../../x` も)・ルートそのものは差し戻す。同じパスを 2 度書けない |
| `files[].units` | | 文字列の配列の配列 | そのファイルのうち変える予定の節。節の書き方 (階層ごとの名前の配列。名前は正規化しない) と、書ける種類 (節の表記 `unit_notation` がある種類) の正本は [file-kinds.md](file-kinds.md) の「節で判定する」と「節の表記」で、ここでは言い直さない。省けばファイル全体を変える予定。空の配列は書けない (節を 1 つも変えない宣言は無いので、全体なら省く) |
| `resources` | ✓ | 文字列の配列 | 使う資源の名前 (ラベル `resource:<名前>` の `<名前>`)。空白を含まない。名前は大文字小文字を区別しない (正本は [resources.md](resources.md)) ので、同じ資源を綴りだけ違えて 2 度書けない |
| `split` | ✓ | オブジェクト | 分ける必要 |
| `split.needed` | ✓ | 真偽値 | 分ける必要があるか |
| `split.reason` | ✓ | 文字列 | 理由。`needed` が偽なら空でよい |
| `split.remaining` | `needed` が真なら ✓ | 文字列 | 新しい Issue にする残りの部分の説明。偽なら書かない |
| `split.blocked_by` | `needed` が真なら ✓ | Issue の参照の配列 | 残りの部分が完了を待つ Issue (`owner/repo#番号` か URL。`owner/repo#番号` にそろえる)。大きさのために分けるなら空の配列。偽なら書かない |

上の表に無いキー (`file` の誤字・`kind` など) と、欠けた必須キーは、理由と期待する形を含むエラーで差し戻す (`declaration parse` の `errors`。誤りはできるだけ全部集める)。管理のセッションの導出 ([flow.md](flow.md)) がコメントの宣言を読むときも、同じ関数で形を検査してパスをそろえる (リポジトリの設定を読まないので、種類は付けず、種類に依る検査 (節の表記の無いファイルの `units`) だけを行わない)。

例 (**この例は様式を示すもので、そのまま写さない**):

```json
{
  "files": [
    {"path": "package.json", "units": [["dependencies", "zod"]]},
    {"path": "src/app.ts"}
  ],
  "resources": ["staging-db"],
  "split": {"needed": false, "reason": ""}
}
```

### 更新の種類

宣言の更新を、最後に `開始可` を書いた宣言 (以下「`開始可` の宣言」) と比べて分ける (計画の R20)。**持っている資源**は、`開始可` の宣言の `resources` のうち、その後のどの宣言の更新にも残っているもの (`開始可` の宣言がまだ無ければ空)。差し戻された宣言は比べる相手にしない。

| 種類 | 条件 | 扱い |
| --- | --- | --- |
| `initial` | `開始可` の宣言がまだ無い | 着手の宣言と同じに判定する |
| `full` | ファイルか節が `開始可` の宣言と違う (または資源も含めて何も変わらない) | 競合の可能性を判定する |
| `resources-only` | ファイルと節が同じで、資源だけが持っている資源と違い、足した資源がある | 資源だけを判定する (扱いは [resources.md](resources.md) の契機「宣言の更新」)。ready for review の後も Issue が閉じるまで受け付ける |
| `resources-removed-only` | ファイルと節が同じで、持っている資源から 1 つ以上を外し、足した資源が無い | 判定せず、`開始可` を書かない |

足した資源と外した資源は持っている資源との差で数える: `{A, B}` が `開始可` → `{A}` → `{A, B}` では B を足したと数え、`{X, Y, Z}` → `{X, Y}` → `{X}` の 2 回目に外すのは Y だけ。

### 競合の可能性

2 つの宣言 (判定する宣言と、既に `開始可` になった宣言) の、同じリポジトリの同じパスごとに判定する (計画の R5。種類ごとの規則と節の比べ方の正本は [file-kinds.md](file-kinds.md))。別のリポジトリの同じパスは競合しない (リポジトリ名の大文字小文字は区別しない)。

| 結果 | 意味 |
| --- | --- |
| `conflict` | 競合しうる |
| `none` | 競合しない |
| `needs-user` | 利用者の判定が要る (`unknown-content` を含む組で同じパス。相手の宣言が今の規則で解析できないときも、その相手はこれ) |

相手ごとにパスごとの結果と理由を返し、相手ごとの結果と全体の結論は `conflict` > `needs-user` > `none` の順で決める。相手の宣言 (過去に受理されたもの) が今のリポジトリの設定の規則では解析できないときは、その相手だけを `needs-user` (理由は `problems`) にし、ほかの相手の判定は続ける (相手 1 つのために、そのリポジトリの新しい宣言をどれも判定できなくならないようにする)。判定する宣言そのものの誤りは差し戻す。

### PR が変えたファイルとの照合

`In review` にするとき、PR が変えたファイル (`pr observe` の `files`) を最新の宣言と比べ、宣言に無いファイル (種類が `generated` のものを除く) と、そのファイルを宣言しているほかの `開始可` の宣言を返す (計画の R21)。宣言にあるファイルだけを変えた PR では何も返さない。

## CLI

| サブコマンド | 書き込み | 返すもの |
| --- | --- | --- |
| `issue create --repo <owner/name> --title <題> (--body <本文> \| --body-file <ファイル \| ->) --split-from <宣言のコメントの URL> [--label <名前>]... [--assignee <ログイン>]...` | `gh issue create` (既にあれば無し) | `created`・`number`・`url` |
| `issue add-label --issue <参照> --label <名前> [--description <説明>]` | `gh label create` (無ければ)・`gh issue edit --add-label` (付いていなければ) | `label_created`・`added` |
| `blocked-by add --issue <参照> --blocker <参照>` | `gh issue edit --add-blocked-by` | `issue`・`blocker` (キー) |
| `pr observe --url <PR の URL>` | 無し | `kind`・`pr`・`author`・`rate_limit`・`warnings` |
| `comment list --issue <参照>` | 無し | `comments` (時刻の順。要素は `id`・`database_id`・`url`・`created_at`・`author`・`header` (先頭行の解析結果か null)・`body` (先頭行を除いた本文))・`excluded` (書き手が違うので除いた件数)・`login` |
| `comment post --issue <参照> --role manager\|worker --name <名前> --session-id <ID> --kind <種類> [--to] [--assignment] [--declaration] [--reason <値>]... [--request-kind] [--waiting-issue] [--waiting-declaration] [--previous-pr] [--pr] [--release-reason] [--stuck-state] [--blocker <参照>]... (--body \| --body-file)` | `gh issue comment` (管理のセッションの種類で既投稿なら無し) | `posted`・`database_id`・`url`・`header` (組み立てた先頭行)。値のオプションは見出し語の表の順 |
| `comment parse --line <先頭行>` | 無し | `header` (解析結果か null) |
| `declaration parse --dir <リポジトリのルート> (--body <JSON> \| --body-file <ファイル \| ->)` | 無し | `declaration` (そろえたパスと種類付き。誤りがあれば null)・`count`・`config_status`。リポジトリの設定の規則は `--dir` から読む |
| `declaration conflictability --dir <管理ディレクトリ> --repo <owner/name> (--body \| --body-file)` | 無し | 本文は `{"declaration": <宣言>, "others": [{"id", "repo", "declaration"}]}`。`result` (全体)・`others` (相手ごと・パスごとの結果と理由)・`declaration`・`repo_config` (設定の読み取りの結果)。リポジトリの設定は `repositories` の clone から既定のブランチの内容として読み (正本は [repositories.md](repositories.md))、読めなければ判定せず `errors` (key `repo-config`) で理由と直し方を返す。`others` の宣言が解析できなければ、その相手は `needs-user` (`problems` に理由) |

`<参照>` は `owner/repo#番号` か Issue の URL。どのサブコマンドも JSON を出せれば終了コード 0 で、失敗は `status: error` と `errors` (`key`・`message`・`failure`) で伝える。参照や URL の形が読めないときは `gh` を実行せずに返す。
