# セッションの宛先と識別

このファイルが、この仕組み (issue-dispatch) のセッションの識別 (ID と名前)・管理のセッションの規約の名前・宛先の決め方・作業のセッションの一時ディレクトリの正本。セッションどうしが送る合図 (本文の様式と種類) の取り決めは U17 でこの文書に足す。スキルの手順書は、Claude Code の公式文書に無い振る舞いに頼るところで、下の「実測」の表を参照する。モジュール `issue-dispatch/scripts/issue_dispatch/sessions.py` がここで決めた規則を実装する (`gh` も `ListAgents` も使わず、環境変数は引数で受ける)。

## 自分の識別 (ID と名前)

セッションは ID と名前の両方を持つ (計画の KTD10)。作業のセッションは割り当てを受けるときに両方を申告し、管理のセッションは Project のフィールド `Agent session ID` に ID、`Agent session title` に名前を書く (フィールドの正本は [project-schema.md](project-schema.md))。

- **ID** は環境変数から決める: `CLAUDE_CODE_HOST_SESSION_ID` (Claude Desktop のセッション ID。`local_` で始まる) があればそれ、無ければ `CLAUDE_CODE_SESSION_ID` (会話の記録と同じ UUID。端末の `claude` にはこちらだけがある)。空の値と、空白か `/` を含む値、`.` で始まる値 (`.`・`..` を含む) は無いものとして扱う (ID は一時ディレクトリのパスの 1 区切りにも使うため)。どちらの環境変数も公式文書に無い振る舞いなので、読むのは関数 `own_session_id` の 1 か所にまとめる。`local_` の有無は区別して保持し、`local_<ID>` と `<ID>` は別のセッションとして比べる (関数 `normalize_session_id`・`same_session_id`)。中身の形 (UUID かどうか) には決め打ちしない。
- **名前**は `ListAgents` の 1 行目 (`This session is <名前> [<短い識別子>]`) の名前で、行に付く短い識別子 (`[2c2f42]` の形。プロセスごとの値で、開き直すと変わる) を除いた部分。作業のセッションは名前を変えない (変わっていれば管理のセッションが `renamed` と見る)。名前が `ListAgents` に無いときの引き直しは、Desktop では `list_sessions` (ID → タイトル)、端末のセッションは引き直せないので利用者に尋ねる。

## 管理のセッションの規約の名前

管理のセッションの名前は `issue-dispatch <owner>/<number>/<login>` (`<owner>` と `<number>` は設定の `project`、`<login>` は `gh api user` で得たトークンのログイン)。管理のセッションは「Project と利用者 (そのマシンの `gh` が認証しているアカウント) の組」を担当するので、名前にその組を含める (計画の KD23。チームでは利用者ごとに自分のマシンで管理のセッションを開き、合図と `ListAgents` は同じマシンの中にしか届かないため)。作業のセッションは、リポジトリの設定の `project` と自分のトークンのログインから同じ名前を導いて宛先にする。

- 生成は関数 `manager_name` (owner と番号と login から。同じ入力なら同じ名前)、解析は関数 `parse_manager_name` (名前から owner・番号・login を読む。`ListAgents` の行の短い識別子は呼び出し元が外してから渡す)。owner と login は名前に使える文字 (英数字と `.`・`_`・`-`) だけ、番号は 1 以上の整数。**owner と login は小文字にそろえる** (GitHub はどちらも大文字小文字を区別しないが、名前は Claude Code が文字列として照合する宛先なので、管理ディレクトリとリポジトリの設定に書かれた owner の綴りが違っても、同じ組から同じ名前を導くため。設定の値は変えない)。
- 名前による管理のセッションの排他 (同じ名前のセッションが `ListAgents` にあれば起動しない) の手順は計画の R18 で、スキルの手順書 (U21・U23) に書く。使われている名前に変えても同じ名前がそのまま付く (下の「実測」) ので、排他は名前を変える前の `ListAgents` で確かめる。

## 宛先の決め方

- **宛先は名前にする。** `SendMessage` の `to` に名前をそのまま渡す (空白と `/` を含んでよい。短い識別子は付けない)。返事は、届いた合図の `from` (ソケットのパス `uds:/tmp/cc-socks/<pid>.sock`) を `to` にして送る。
- **Desktop のセッション ID (`local_…`) を宛先にしない。** 計画の実測 (2026-10-06) で、ID 宛ては利用者の最後の入力から 10 通で送信が拒否され、`notify_when_idle` (入力待ちになったら知らせる申し込み) を申し込めなかった。名前宛ては利用者の入力なしに 30 往復届いた。ID 宛てで届いた合図は `from` と `name` だけの別の形で、端末のセッションは Desktop の ID を持たない。
- 同じ名前のセッションが 2 つあるとき、一方から名前だけを宛先にすると自分以外のもう一方に届く (下の「実測」)。同じ名前を持たない第三のセッションから送ったときの届き先は未確認。

## 作業のセッションの一時ディレクトリ

作業のセッションが作業ツリーの外に置くファイル (待機の `wait.pid` (U14)、伝えたプラグインの版の印 (U18)) は `${TMPDIR:-/tmp}/issue-dispatch/<セッション ID>/` に置く (計画の KTD6・R26。作業ツリーに不要なファイルを残さないため)。パスは関数 `session_temp_dir` が作る。`TMPDIR` は絶対パスのときだけ使う (相対パスは作業ツリーの中を指しうるので `/tmp` にする)。
